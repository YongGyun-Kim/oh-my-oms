# 첫 배포 실행 계획과 후속 백로그

## 결정과 적용 범위

2026-10-11 사용자가 [범위안](first-release-scope-proposal.md)에 대해 **“제안 범위로 확정”**으로 답했다. 첫 배포는 고객사 10곳 이내 제한 파일럿이며 하루 주문 1,000건을 계획 기준으로 삼는다. 고객 확보·동시 사용자·실제 용량은 아직 검증되지 않았다. 10곳은 배포 대상 기준이며 별도의 하드코딩된 기업 등록 상한을 뜻하지 않는다.

전체 69개 스토리·227개 수락 기준과 U1~U10의 원본 ID·소유·의존성은 유지한다. 원본 문서의 ‘전체 첫 제품 Must Have’ 및 대량 부하·재해 실증을 첫 배포 전부의 조건으로 읽는 해석은 이번 범위 결정으로 대체한다. 원본 AC의 성공 판정은 변경하지 않는다. 수동 경로만 지원하거나 모바일·자동화를 보류한 스토리는 원래 모든 AC를 충족했다고 표시하지 않는다.

아래 분류는 구현·검증 결과가 아닌 **배포 대상과 구현 순서**다. 첫 배포 핵심의 정상·실패·권한·중복·동시 변경 기준은 유지하고, 일부 범위를 떼어낸 스토리의 나머지는 후속으로 남긴다. 각 Unit 설계 시 해당 원본 AC의 첫 배포 적용 부분과 후속 부분을 명시한다. 새로운 근거 없이 수락 기준을 통과로 바꾸거나 fixture 값을 사업 정책으로 채우지 않는다.

## 기존 스토리와 첫 배포 범위의 연결

‘첫 배포 핵심’은 지원하는 업무를 포함한다. ‘일부 포함’은 같은 스토리 안의 첫 배포 경로만 포함한다. ‘후속’에도 지원 경로의 안전 경계는 남긴다. 주 책임은 [원래 연결표](../inception/units-generation/unit-of-work-story-map.md)의 Unit이며 화면·업무 연계 협력도 그대로다. 각 행의 US에 속한 AC는 [원본 스토리](../inception/user-stories/stories.md)에 보존돼 있다.

## Unit별 첫 배포 작업과 후속 책임

| Unit | 첫 배포 작업 | 후속 책임 |
|---|---|---|
| U1 | 기존 실행 기반·접수·재조회 경로 재사용 | 전체 제품 통합 접점 유지 |
| U2 | 기존 신원·기업·MFA·접근 검증 재사용, 실제 인증/회사망 준비 연결 | 고급 관리 UI, 미검증·OPEN 증거와 독립 리뷰. 현재 미완료 유지 |
| U3 | 상품·기업 조건·다른 사람 계약 승인·주문 전체 직원 수락 | 자동 확정·복잡한 조건·부분 제공·혼합 지급 |
| U4 | 직원 청구·지급·수동 연결·잔액·실제 환불 근거 | 외부 수금·자동 배분·복잡한 연체/보상 계산 |
| U5 | HW 공급·출고·합의 배송/인수·회수 결과 기록 | 예약/확보 정책 자동화·WMS/배송 연동 |
| U6 | SW 기업 발급·기간·승인 정정·수동 갱신·회수 결과 | 자동 갱신·유예/보상 자동 계산·대량 회수 |
| U7 | 전체 후속 요청·직원 판단·진행/이력·최소 알림 | 정책별 자동 처리·고급 조합 조회/통지 |
| U8 | 첫 배포 고객 업무를 실제 API에 연결한 PC 화면 | 고급 조직/분석 화면·모바일 여부 결정 |
| U9 | 첫 배포 직원 등록·판단·승인·결과 기록 PC 화면 | 고급 편의 화면 |
| U10 | 실제 배포 구성·로그·기본 백업·알림·대응 절차 | 대량 부하·재해 복구·무중단·장기간 실증 |

위 표는 기존 주 책임 Unit과 의존성을 바꾸지 않는다. 첫 배포에는 U3~U10의 필요한 부분을 연결하며, 원래 각 Unit 전체를 완료해야만 첫 배포가 가능하다는 해석은 적용하지 않는다. 실행 순서·미완료 Unit의 처리·다음 단계는 AI-DLC의 승인된 경로로 반영해야 한다. 특히 이 문서로 U2를 완료·Skip 처리하거나 U3가 시작했다고 표시하지 않는다.

## 첫 배포 완료 조건과 개발 중 검사

| 영역 | 첫 배포 후보에서 확인할 결과 | 이번 문서의 현재 판정 |
|---|---|---|
| 1. 대상·준비 | 파일럿 기업·권한자·실제 업무 조건과 지원 밖 계약/요청 처리 방식 확인 | 범위 확정, 실제 고객 근거 미확인 |
| 2. 접근·민감 정보 | 실제 인증/MFA·기업 분리·행위 권한·회사망, 계약 동일인 자기 승인 차단, 고객/직원 PC 경로 | 기존 부분 시험 근거와 실제 운영 실증 구별 |
| 3. 핵심 업무 | 상품/계약→주문→직원 전체 수락→청구/지급→HW 또는 SW 실제 결과→조회·후속 요청 연결 | U3~U9의 첫 배포 경로 미완료 |
| 4. 처리 정확성 | 지원 경로의 금액·수량·기간·상태·중복·동시 변경·정정·이력 불변조건. 재시도 시 미확인을 완료로 표시하지 않음 | 새 범위의 종합 검증 대기 |
| 5. 개발 품질·보안 | 변경에 맞는 단위/통합, 작성한 테스트 가능한 제품 코드 전체 라인 커버리지80%, 타입·린트·형식·필수 보안 검사 | 기존 결과 재사용 조건과 새 변경 영향 확인 필요 |
| 6. 배포·저장 | 실제 AWS/CDK 구성·국내 데이터/포함 로그/백업·첫 배포 전후 핵심 동작·기본 백업 설정 | 미배포. 합성 시험만으로 통과 표시 금지 |
| 7. 운영·알림 | 로그·상태·장애/중단 관측·정해둔 개발자 메신저/이메일 수신·기본 대응 절차 | 실제 경로·수신 증거 대기 |
| 8. 규모·가용성 | 10곳/하루1000건 계획에 맞는 지원 경로 확인, 가용성 관측 시작 | 동시 사용자·짧은 검증의 정확 규모/기간 미정. 99.9%는 목표, 검증 용량·달성 실적 아님 |

개발 중에는 바뀐 코드와 영향을 받는 권한·업무·공통 계약을 검사한다. 첫 배포 후보를 고정할 때 지원 흐름을 종합 검증한다. 긴 부하·복구 묶음을 사소한 변경마다 재실행하지 않는다. 필수 검사를 끄거나 커버리지 분모에서 미실행 제품 파일을 빼는 승인이 아니다.

대량100k/50분 부하·기존 시간 하한 FAIL 재실행·재해 복구 실증은 첫 배포 필수 검증에서 분리한다. 과거 실패 원문과 미실증 표시를 유지한다. RTO30분/RPO0은 후속 실증 전 달성 보장으로 제시하지 않는다. 기존 OPEN의 영향·수정·예외는 각각 검토하며 이번 범위 승인을 일괄 위험 수용으로 기록하지 않는다.

짧은 규모 검증의 동시 사용자·요청 구성·정확 기간은 해당 시험 설계 시 근거를 확인한다. 하루1000건을 단순히 초당 평균으로 나누어 집중 부하나 동시 사용자 수를 확정하지 않는다. 새 시험을 지금 실행하지 않는다.

## 다음 구현 준비

1. 각 Unit의 첫 배포 설계에서 위 지원 범위를 적용하고 원본 AC의 적용/후속 부분과 필요한 계약 차이를 연결한다.
2. 직원 처리도 기존 논리 owner의 권한·상태·금액·수량·기간 규칙과 승인 경계를 통과하게 한다. 외부 사실 기록과 OMS가 직접 외부 업무를 실행하는 것을 구별한다.
3. 미지원 자동화·혼합 지급·조건의 서버 처리와 PC 안내를 명시하고 실제 파일럿 계약을 확인한다.
4. 현재 U2의 미완료·독립 리뷰·이전 보류는 그대로 인계한다. 실제 단계 전환은 기존 작업 경로가 결정한다.
