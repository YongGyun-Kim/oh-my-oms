# 첫 배포 범위 조정안

상태: **APPROVED — 2026-10-11 사용자 “제안 범위로 확정”**. 아래 기능·운영 범위를 고객사 10곳 이내 제한 파일럿의 첫 배포 기준으로 확정했다. 전체 제품 계획은 보존한다. 이 승인은 첫 배포 범위에 한정하며 Unit 완료·미해결 문제의 예외 승인·실제 배포 승인이 아니다. 작업 연결과 완료 조건은 [첫 배포 실행 계획](first-release-delivery-plan.md)을 따른다. 실행 순서와 단계 상태는 기존 AI-DLC 기록을 따른다.

## 근거와 결정 경계

- 사용자는 “지금까지 계획한것을 안만드는건 아니지만 첫 버전에서 가져갈 범위를 조절해야한다”고 요청했다.
- 사용자가 이미 후속으로 넘긴 항목: 현재 부하 측정 종료 처리의 시간 하한 실패, 재해 복구 검증, 기존 열린 문제. 현재 FAIL·미실행·OPEN 증거를 보존하며 통과나 문제 해결로 바꾸지 않는다.
- 이번에 착수한 작업은 U2 최종 산출물 정리다. 이 조정안을 이유로 U2 제품 코드·실패 시험·부하·복구를 재실행하지 않는다.
- 기존 전체 계획은 U1~U10, 69개 스토리·227개 수락 기준이다. 고객사 10곳·하루 주문 1,000건은 기존 계획 목표이며 관측된 수요나 검증된 운영 용량이 아니다.
- **사용자 결정:** 첫 배포 목적은 고객사 10곳 이내의 제한 파일럿이다. 목적 선택 후 별도 제시한 기능·운영 범위에 대해 사용자가 “제안 범위로 확정”으로 답했다. `aidlc engine log answer --stage code-generation --unit u2-identity-enterprise-access --details '제안 범위로 확정'`으로 답변을 기록했다. 하루 주문 1,000건은 계획 기준이며 실제 검증된 용량은 아니다.

## 첫 배포에서 제공할 업무 결과

권한 있는 내부 직원이 상품과 합의 조건을 등록하고, 승인된 고객 기업이 HW 또는 SW 주문을 제출한다. 직원이 주문 전체를 확인·수락하고 지급·HW 제공 또는 SW 발급의 실제 근거를 기록한다. 고객과 직원이 진행 상태·남은 조치·이력을 확인할 수 있어야 한다.

직원 확인과 기록을 사용하는 경로에서도 권한·승인·중복·금액·수량·상태 검증은 유지한다. 확인되지 않은 공급·지급·발급 결과를 완료로 표시하지 않는다.

## 확정한 기능 범위

| 영역 | 첫 배포 포함 | 후속 버전 | 기존 요구 연결 |
|---|---|---|---|
| 기업·접근 | 승인된 기업·담당자, 로그인/MFA, 기업 분리, 필요한 고객·직원 역할, 복구·관리자 대응 | 고급 조직·역할 편집 화면과 대량 관리 편의 기능. 이미 구현한 U2의 접근 검증은 유지 | FR1~FR3, FR16 |
| 상품·계약 | 내부 직원 전용 HW/SW 등록, 상품 조회, 고객사 합의 조건, 다른 사람의 계약 승인, 구매 당시 조건 보존 | 복잡한 조건 중첩·자동 제안·자동 변경 처리 | FR4, FR7 |
| 주문 | HW/SW 별도 주문, 같은 타입 다품목, 전체 직원 확인·수락, 기본 일괄 제공, 고객 상태 조회 | 전체 자동 수락과 다양한 부분 제공 정책의 자동 처리 | FR5~FR6 |

| SW | 영구/기간제 발급 결과·기업·수량 연결, 계약 기간과 실제 기간 보존, 승인된 기간 정정 | 사전 합의 자동 갱신, 유예·보상 중첩 요금 자동 계산, 대량 회수 자동화 | FR10~FR12 |
| 갱신·후속 처리 | 수동 갱신 요청과 직원 검토, 주문 전체 변경·취소/반품 요청, 실제 환불·회수 결과 기록 | 정책별 자동 승인·환불·회수 및 고급 예외 처리 자동화 | FR11, FR13 |
| 조회·알림 | 주문 목록·상세·이력·남은 조치, 필요한 화면·최소 안내 알림 | 고급 조합 조회·분석·검색·알림 정책 편집 | FR14 |
| 정확성 | 제공하는 기능의 권한·다른 사람 승인·금액·수량·기간·중복·동시 변경·감사 이력 | 신규 후속 기능의 추가 시나리오를 해당 기능 구현 시 확장 | FR15, NFR1, NFR5 |

대금의 주문 단위 조건, 자동 수락·복잡한 부분 제공·자동 갱신의 후속 이동은 이번 승인으로 확정한 변경이다. 기존 계약이나 첫 고객의 실제 업무가 이를 요구한다면 지원을 약속하기 전에 범위 변경을 검토한다. 숨긴 화면만으로 기능을 제외하지 않고, 첫 배포에서 지원하지 않는 요청·계약 조건의 서버 처리와 사용자 안내를 명시한다.

## 첫 배포에서도 유지할 조건

- B2B, 판매 회사 한 곳, 상품 등록은 권한 있는 내부 직원만 수행한다.
- HW와 SW를 모두 다루되 혼합 주문은 하지 않는다. 일부 품목만 준비됐다고 주문 전체를 확정하지 않는다.
- 한국어·KRW·한국 시간, 고객·직원 PC 1280 이상. 모바일 지원은 후속 결정이다.
- 내부 직원 접근의 회사망/승인된 원격 접속 경계와 MFA를 유지한다. 단말 관리·기기 인증 자체는 OMS 범위로 추가하지 않는다.
- 기업 분리, 권한 없는 조회·변경 거절, 민감 데이터 최소 노출, 계약 등록자와 승인자 분리, 변경 이력 보존을 유지한다.
- 계약 당시 기간과 실제 SW 이용 기간을 구별하고, 승인되지 않은 기간 변경이나 중복 발급·연장을 허용하지 않는다.
- 기존 TypeScript/NestJS·Express/Next.js/TypeORM/PostgreSQL·Transactional Outbox+queue·Cognito·AWS/CDK 방향과 단일 AWS 계정 원칙을 유지한다. 새 인증·클라우드 구조를 이 제안에서 다시 선택하지 않는다.

## 확정한 운영·검증 범위

| 항목 | 첫 배포에서 필요한 범위 | 후속 범위·미달성 표시 |
|---|---|---|
| 업무 검증 | 첫 배포의 주문→직원 판단→지급 근거→HW/SW 제공 결과→조회, 권한·중복·충돌·실패 회귀 | 미구현 후속 업무의 전체 시나리오는 후속 버전에서 검증 |
| 개발 검사 | 변경에 맞는 단위·통합 검사, 기존 전체 제품 코드 커버리지 80%, 타입·린트·형식·필수 보안 검사 유지 | 제품 변경마다 긴 전체 부하·복구 묶음을 반복하는 방식은 첫 배포 기준 확정 때 조정 |
| 운영 준비 | CDK 배포 구성, 실제 인증·회사망 접근, 로그·상태 확인·필수 알림, 기본 백업 설정·대응 절차 | 실제 설정·접근·수신을 합성 시험으로 대체하지 않음 |
| 부하 | 제한 파일럿의 핵심 경로가 동작하는지 확인하는 범위를 먼저 확정 | 100,000주문/50분 확장 시험은 이미 Deferred. 기존 10분 측정의 시간 하한 FAIL도 사용자 결정에 따라 그대로 보류 |
| 복구 | 기록·백업·대응 절차 등 기본 준비를 정의 | 재해 복구 실증과 RTO/RPO 전수 대조는 사용자 결정에 따라 후속. RTO30분·RPO0을 이미 달성했다고 표시하지 않음 |
| 가용성 | 실제 관측을 시작하고 장애·중단을 기록 | 99.9%는 기존 목표이며 30일 달성 실적이 아님. 무중단 배포·10분 복구 등 고도화는 후속 |

대량 부하·재해 실증을 후속으로 넘기는 것과, 첫 고객의 실제 인증·권한·주문 처리·민감 데이터 보호를 생략하는 것은 구별한다. 첫 배포에서 사용하는 경로의 실동작 확인은 필요하다.

## Unit와 후속 계획의 관계

- U1/U2의 기존 구현을 활용한다. U2는 최종 문서와 변경 목록·추적표를 정리하면서 Deferred/OPEN을 남긴다.
- U3~U7은 각 Unit 전체를 한 번에 첫 배포 조건으로 삼기보다, 위 업무 흐름에 필요한 부분과 후속 자동화를 명시적으로 구분한다.
- U8/U9는 첫 배포에서 제공할 고객·직원 화면을 실제 API에 연결한다. 전체 고급 화면 완성을 첫 배포와 동일시하지 않는다.
- U10은 첫 배포의 배포·로그·진단·기본 백업·알림 준비를 먼저 구성하고, 확장·재해·장기간 실증은 후속으로 구분한다.
- 첫 배포에서 일부를 제공하는 것과 원래 Unit 전체 완료를 구별한다. 기존 Unit 의존성·수락 기준·실행 상태를 이 문서만으로 변경하지 않는다.

## 승인 후 반영과 남은 준비

1. 첫 배포 대상과 위 기능·운영 범위는 확정했다.
2. [첫 배포 실행 계획](first-release-delivery-plan.md)에 기존 요구·스토리 ID, 담당 Unit, 첫 배포/후속 범위와 완료 조건을 연결한다.
3. 계약·상태·지급·이행 규칙과 화면에서 달라지는 부분은 해당 Unit 구현 전 설계에 반영한다. 세부 상태·산식·외부 근거는 이번 범위 승인으로 임의 확정하지 않는다.
4. 개발 중에는 변경 영향에 맞는 검사를 수행하고, 첫 배포 후보를 고정할 때 지원 경로의 종합 검증을 수행한다. 이번 문서 승인으로 시험을 새로 실행하지 않는다.
5. 원래 전체 계획·후속 기능은 백로그로 보존한다. 기존 Unit 의존성과 단계 상태를 문서 편집으로 바꾸지 않는다.
