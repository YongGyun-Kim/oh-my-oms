# U2 보안·품질 상세 설계 질문

## 범위와 유지하는 결정

확인한43개 NFR 요구를 IdentityRecovery/EnterpriseAccess의 실제 원본·목적 제한·인계/청구/단회 소비·회수/현재 권한·보호 변경/실패·닫힌 profile/호환·검증 조건으로 연결한다. 기존 TypeScript/NestJS+Express API·standalone worker·Next BFF·TypeORM/PostgreSQL·Outbox/SQS Standard·독립 보호 DB·단일 AWS 계정/CDK·Cognito 첫 제공자와 출시 후 Keycloak 계획, 현재 MFA/세션/직원 사설 접점·7일 초대·기존 품질 목표를 다시 선정하지 않는다.

대화에서 선택한 Guide me 방식으로 아직 정하지 않은 당사자 인계 방식만 확인한다. 이 단계의 설계는 코드/실계정 변경·실제 provider/회사망·배포/운영 달성 사실이 아니다.

## 질문 근거와 이전 보완

- [security-requirements.md](../nfr-requirements/security-requirements.md)의 NFR1.12는 확인 담당자의 결정과 실제 당사자의 재등록 허가를 구별하고, 원래 case/초대/challenge·계정/인증 연결/보안 세대·목적·근거/개정·기한에 결합한 허가의 안전한 인계/단회 청구를 요구한다.
- [tech-stack-decisions.md](../nfr-requirements/tech-stack-decisions.md)의 U2-ND01/02/04, [functional-spec.md](../functional-design/functional-spec.md), [기능 설계 검토](../functional-design/reviews/review-01.md)의 R-01–R-03을 상세 원본/전이·인계와 기존 다중 scope의 손실 없는 분해/검증으로 연결한다. 이전 산출물/검토 상태는 보존한다.
- [계약](../../../inception/contract-design/contract-summary.md)의 C01/G19/G23은 복구 목적만 허용하는 제한 상태·subject/challenge/근거·업무 접근 금지를 정한다. 업무 접수/조회 ID나 확인 결정만으로 당사자에게 권위를 부여할 수 없다.

## Q1. 담당자가 본인 확인을 마친 뒤 MFA 재등록 허가를 당사자에게 어떻게 인계할까요?

사전 수단이 없는 경우 권한 있는 직원이 본인 확인 후 복구하고, 담당자도 접근할 수 없으면 보호된 비공개 절차로 먼저 담당자를 복구한다는 방향은 이미 정했다. 아래는 그 확인 이후 당사자가 재등록 화면에 들어가는 방식이다. 코드/링크만 보유한 것을 처음부터 본인 확인 완료로 인정하는 선택이 아니다. 최초 미인증 요청자와 확인된 당사자를 구별하는 동일한 서버 원본/청구 검증을 두 방식 모두 적용한다.

A. 일회성 인계 코드. 확인 과정에서 검증한 당사자의 진행 문맥/연락 경로에 한정해 코드를 전달하고, 당사자가 자신의 복구 화면에서 입력해 해당 건의 제한 재등록 허가를 청구한다. 수동 본인 확인 절차에 이어 안내하기 쉬운 첫 버전 제안이다. 계정/원래 복구·challenge/확인 근거·세대/목적·기한 결합과 단회 소비를 검증하며 코드를 일반 업무/로그에 원문 보관하지 않는다. (권장)
B. 일회성 재등록 링크. 확인 과정에서 검증한 당사자의 연락 경로로 보호된 제한 링크를 전달하고, 당사자가 해당 복구 건의 화면을 열어 제한 허가를 청구한다. 링크 대상/현재 진행 문맥/원래 확인 근거·세대/목적·기한과 단회 소비를 검증하며 링크의 비밀 값이 URL/로그/리퍼러·일반 통지 이력에 남지 않도록 전달/표시 경계를 별도 보호한다. 실제 전달 경로가 준비돼야 한다.
X. Other (please specify). 다른 인계 방법이나 채널/당사자 확인 조건을 설명한다.

[Answer]: A. 담당자의 본인 확인 이후 일회성 인계 코드 방식으로 해당 복구 건의 제한 MFA 재등록 허가를 전달한다. 확인 과정에서 검증한 당사자의 진행 문맥/연락 경로에 한정해 전달하고, 당사자가 자신의 복구 화면에서 청구·단회 소비한다. 원래 case/challenge·계정/인증 연결/보안 세대·확인 근거/개정·목적·기한을 서버 원본과 대조하고 일반 업무/로그에 원문을 보관하지 않는다. 사전 발급 복구 코드/password+TOTP 일반 로그인 정책과 구별한다. 사용자 원문: "1".

### 공통 인계·수락 경계

- 사전 발급 복구 코드와 이 코드는 다르다. 사전 코드는 기존 password+미사용 코드의 직접 복구에 쓰고 정기 만료 없는 기존 정책을 유지한다. 인계 코드는 담당자의 확인 결정 뒤 특정 건의 재등록에만 쓴다.
- 일반 password+TOTP 로그인에 새 이메일/SMS MFA를 추가하거나 원래 등록 수단/본인 확인을 생략하지 않는다. 새 실제 MFA·옛 수단/코드/세션 무효화·보호 이력/당사자 통지 후에도 현재 업무 권한을 다시 평가한다.
- 원래 요청/case ID·상태 조회/Receipt·이메일 접근만으로 허가를 청구하지 못한다. 실제 검증된 당사자/진행 문맥·현재 목적 대상과 허가를 결합하고, 교체/재사용·만료/회수/다른 사람·다른 건 청구를 거절한다.
- 인계 비밀은 유한 수명/시도 제한·안전한 verifier/단회 소비·회수·현재 원본/보호 기록으로 관리한다. 구체 형식/수명/시도/한도와 보호 전달·실제 지원은 상세 설계에서 근거와 함께 고정하고 구현 전 검증한다. 실제 채널/권위/지원이 없으면 실행 불가로 남긴다.

## 상세 설계의 기술 기본값 제안

아래는 선택한 일회성 코드 방식을 구현할 구체 설계 기본값이며 아직 구현/실증된 값이나 외부 표준 의무값이 아니다. 통합 요약 확인 전에는 확인된 사용자 결정으로 표시하지 않는다.

- 코드는 암호학적 안전 난수12바이트를16문자 base64url로 표시하는96비트 일회성 비밀로 제안한다. 일반 숫자 TOTP나 사전 복구 코드와 구별하며 복사·붙여넣기를 지원한다. 일반 DB/로그에는 원문 대신 목적/대상/세대에 묶인 보호 verifier와 상태만 둔다.
- 코드의 청구 가능 기간은 발급 후5분, 허가별 잘못된 청구는 최대5회로 제안한다. 한도/만료/회수·근거/원본 변경 시 해당 허가를 폐기하고 권한 있는 주체가 현재 근거를 재검증해 별도 허가를 발급한다. 그 실패만으로 계정 전체를 자동 잠그지 않는다.
- 유효한 코드 청구 후의 재등록 문맥은 별도5분 목적 제한 상태로 제안한다. 코드 청구의 단회 결과/원래 확인 근거와 연결하고 현재 계정/연결/보안 세대·case/등록 target/challenge·기한을 계속 검증한다. 이미 만료/회수된 코드의 재사용이나 원래 외부 실행 작업의 기한 연장으로 구현하지 않는다.
- 본인 확인 검토 기간과 원래 각 HTTP/worker/provider 작업 기한, 코드 청구 기간·재등록 문맥의 수명은 서로 구별한다. 새 코드/등록 상태가 옛 불명 수단 변경을 자동 재실행/해결하거나 MFA 완료·업무 권한을 생성하지 않는다.

## 답변의 모호성·충돌 점검

- Q1은 일회성 인계 코드 A를 명시적으로 선택했다. 기존 사전 복구 코드·일반 password+TOTP 로그인·이메일 접근만 복구 금지와 구별하므로 기존 결정을 바꾸지 않는다.
- 인계 코드만 가지고 있는 초기 미인증 요청자를 확인 당사자로 간주하지 않는다. 검증된 당사자/진행 문맥과 원래 확인 결정·목적 대상·현재 세대/기한 결합, 청구/단회 결과가 필요하다.
- 위 유한 기본값은 코드의 구체 수명/시도 및 보호 구현을 위한 설계 제안이다. 초대7일·로그인/MFA challenge5분·업무 세션 유휴/절대 기준·사전 코드 정기 만료 없음과 다른 역할의 수명으로 정의한다. 실제 제공자/전달·암호/키/성능·복구/부정 시험은 구현 전 검증 조건이다.
- 기능 설계의 보류 재개/종료와 기존 다중 scope의 손실 없는 분해는 상세 설계 원본/전이 및 검증으로 연결한다. 이전 산출물/검토 기록을 수정하거나 실제 보완 해소·위험 수용을 추론하지 않는다.
