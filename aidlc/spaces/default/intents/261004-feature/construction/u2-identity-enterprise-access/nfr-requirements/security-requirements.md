# U2 보안·정확성 요구사항

**Unit:** u2-identity-enterprise-access

## 범위와 판정 의미

U2는 IdentityRecovery/EnterpriseAccess의 신원·MFA/복구·동일인, 기업/조직/소속·고객/직원 역할/행위별 범위·초대·관리자 부재/재지정을 확장한다. 같은 API/worker 호스트에서 실행되는 library이며 원본 쓰기/현재 판단은 해당 소유자에 있다. 전체 PC UI는 U8/U9, 통지 전달은 U7, 실제 운영/부하·복구는 호스트/Infra/U10와 통합한다.

아래 NFRx.y는 S3의 NFRx를 상속한 **이 Unit의 요구 정의**다. 같은 ID는 이 Unit 안에서 한 표에만 정의한다. 기존 U1 정책을 바꾸지 않고 U2가 충족할 조건을 연결한다. NFR2/3/6–10/12/13의 호스트·개발/운영 조건은 [tech-stack-decisions.md](tech-stack-decisions.md)에 정의한다. 문서/traceability의 OK는 요구 연결이며 구현/수락 시험·보안/성능/실제 준비 통과가 아니다.

## 제한 권위·인계의 확인 경계

NFR1.12는 C01의 목적 제한/subject·challenge·verificationBasisRefs와 G19/G23을 초대/수동/비상 복구에도 연결하는 필수 조건이다. 담당자의 확인 결정은 당사자의 재등록 세션 자체가 아니다. 초기 미인증 요청 또는 원래 case/receipt를 가진 사람을 확인된 당사자라고 가정하지 않는다.

상세 설계는 확인 결정→검증된 당사자에 대한 안전한 인계→원래 허가의 청구/단회 소비→원래 대상에 묶인 제한 등록 상태→새 MFA·옛 무효화/보호 이력/통지→현재 업무 접근 재평가의 순서를 닫아야 한다. 제한 허가의 발급자/원래 결정과 실제 청구자를 구별하고 계정·활성 연결/보안 세대·목적·원래 target/challenge·확인 근거/개정·기한을 원본에 결합한다. 토큰/발급·전달 기술이나 추가 두 사람 승인·실계정 변경을 여기서 새로 선정하지 않는다.

비밀은 필요한 제한된 표시/검증/보호 전달 경계에서만 처리한다. 일반 통지 사실/E01은 계정 복구 결과/원래 근거 참조이며 허가 원문이나 일반 업무 권한을 전달하지 않는다. 보호 전달의 실제 제공자/주체·국내 경로·수명·원문 비저장과 손실/재청구·회수/중복 경합은 상세 설계/구현 전에 검증한다. 지원 또는 실제 본인/운영 권위가 없으면 적용하지 않는다.

업무 본인 확인 요청의 검토 기간, 원래 HTTP/worker/provider 실행 기한, 제한 허가/challenge의 수명은 서로 다른 기준이다. NFR6.2의 단일 실행 예산을 사람 본인 확인 전체에 전용하지 않고 원래 작업 기한을 새 청구로 늘리지 않는다. 아직 정하지 않은 제한 허가/요청의 구체 수명/재개 조건은 상세 설계에서 실제 목적·현재성/불명 효과와 연결해 명시해야 하며, 값 없는 경로는 실행하지 않는다.

## 추적과 완료 책임

[traceability.json](traceability.json)의 NFR1–NFR14는 두 요구 문서의43개 하위 ID로 연결된다. 각 전체 가용성/운영/부하·UI/외부 실제 전달의 완성은 해당 호스트/협력 Unit과 대조한다. U2의 신원/권한·보안 상태/효과는 그 경로에서 빠질 수 없는 조건이다. 문서 확인·합성 fixture 또는 예전 U1 측정만으로 변경된 U2 제품/실환경의 충족을 주장하지 않는다.
