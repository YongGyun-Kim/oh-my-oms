# U2 기능 설계 질문

## 범위

`u2-identity-enterprise-access`의 IdentityRecovery와 EnterpriseAccess를 완성한다. 기존 기업 승인·최초 관리자 지정·담당자/조직·행위별 권한·MFA·복구·관리자 부재 정책을 유지하고, 기존 기록으로 해소되지 않은 업무 절차만 질문한다. 아직 선택하지 않은 아래 제안은 확정 요구사항이 아니다.

## 이미 확정한 결정과 근거

- 고객사가 자기 기업의 담당자·소속·활성 상태와 고객용 행위를 조합한 역할을 관리한다. 최초 관리자는 내부 직원이 확인·지정하고 이후 고객사 관리자가 다른 관리자를 추가·회수할 수 있다. 마지막 관리자 부재를 경고·기록하되 다른 사용자 권한을 자동 변경하지 않는다. [요구사항 질문 Q33–Q38](../../../inception/requirements-analysis/requirements-analysis-questions.md)
- 행위별 조합·사업장 전체·부서 전체·기업 전체의 범위만 합친다. 타 행위·타 기업·직원 전용 권한으로 확대하지 않는다. 담당자 이동 후에도 주문의 원래 조직과 현재 접근 권한을 대조하고 폐지 조직의 과거 식별자를 보존한다. [U1 기능 설계 질문 Q1–Q2](../../u1-integrated-foundation/functional-design/functional-design-questions.md)
- 고객/직원 모두 비밀번호+TOTP와 필수 사전 복구 코드·보관 확인을 사용한다. 비밀번호+유효한 미사용 코드 또는 권한 있는 직원의 확인된 본인 근거로 재등록 목적의 제한 상태를 만들고 새 MFA 확인·옛 수단/세션 무효화·이력·당사자 통지를 요구한다. 이메일만으로 MFA를 해제하지 않는다. 코드의 정기 만료는 없으며 사용/재발급/회수/무효 인증 연결은 거절한다. [U1 NFR 설계 Q6–Q7](../../u1-integrated-foundation/nfr-design/nfr-design-questions.md), [구현 준비 Q2](../../u1-integrated-foundation/code-generation/implementation-readiness-questions.md)
- 초기 직원 신원은 Cognito 콘솔에서 생성하고 OMS 최초 최소 관리 권한은 보호된 비공개 절차로 별도 준비한다. 실제 기업/사람/위임·복구 확인 근거와 작업자 권위의 확보는 관련 실계정 적용 전 조건이다. 합성 시험은 실제 확인을 대신하지 않는다. [U1 NFR 설계 Q24·Q24-F1](../../u1-integrated-foundation/nfr-design/nfr-design-questions.md)
- 직원 접점은 승인된 사내망의 사설 경로이며 단말 등록/인증서·NAC/MDM은 회사 IT/보안 책임이다. 모든 고객·직원 화면은 첫 버전 PC 1280부터 지원한다. 모바일 지원은 미확정이며 이 설계에서 추가하지 않는다.

## Q1. 초대한 고객 담당자는 언제 기업 소속과 역할을 사용할 수 있나요?

관리자가 초대할 때 대상 기업·연락 경로·부서/사업장·역할을 지정하는 경계는 이미 있다. 초대 메시지 전달과 실제 본인의 수락, MFA 완료, 현재 허용된 소속/역할의 활성화를 구별해야 하므로 최종 활성화 절차를 정한다.

A. 초대받은 사람이 지정 연락 경로의 확인과 자신의 계정 인증·MFA를 마친 뒤 초대를 수락하면 활성화한다. 수락 시 기업 상태·초대 유효성·현재 조직·역할과 초대한 관리자의 현재 관리 권한을 다시 확인한다. 초대만으로 업무 권한을 주지 않으며 조건이 바뀌면 재확인/재초대를 요구한다. 별도 관리자 재승인은 요구하지 않는다. (권장)
B. 위 본인 확인·인증·MFA와 초대 수락 후에도 관리자가 한 번 더 확인해야 활성화한다. 수락 대기와 관리자 승인 대기를 구별하고 최종 확인 시 현재 소속·역할·관리 권한을 다시 검증한다.
X. Other (please specify)

[Answer]: A. 본인이 지정 연락 경로 확인·자신의 계정 인증·MFA를 마치고 초대를 수락하면 활성화한다. 수락 시 기업 상태·초대 유효성·현재 조직·역할과 초대한 관리자의 현재 관리 권한을 재검증한다. 조건이 바뀌면 재확인/재초대를 요구하고 별도 관리자 재승인은 요구하지 않는다. 초대 메시지 전달만으로 업무 권한을 부여하지 않는다. 사용자 원문: "1".

## Q2. 역할 관리자는 자신이 직접 수행할 권한이 없는 업무도 다른 사람에게 부여할 수 있나요?

이미 정한 “관리 권한만으로 주문을 할 수 없다”와 “관리자가 역할을 정의·부여한다” 사이에서, 관리자의 부여 가능 범위를 정한다. 예를 들어 역할 관리 권한만 가진 최초 고객사 관리자가 구매 담당자에게 주문 제출 권한을 줄 수 있어야 하는지의 문제다.

A. 역할 관리 권한이 부여 권한을 뜻하도록 한다. 고객사 관리자는 자신의 역할 관리 범위 안에서 OMS가 허용한 고객용 행위의 역할을 정의·부여할 수 있고, 자신의 직접 업무 권한이 없어도 다른 담당자에게 줄 수 있다. 자기 자신에게도 별도 기록을 남겨 명시적으로 역할을 부여할 수 있다. 내부 직원 역할 관리도 허용된 직원 행위 목록 안에서 같은 원칙을 적용한다. 관리 권한 보유만으로 해당 업무가 자동 허용되지는 않는다. (권장)
B. 자신이 현재 직접 수행할 수 있는 행위와 범위까지만 역할을 만들어 부여할 수 있다. 역할 관리 권한만 있는 관리자는 주문 권한을 새로 부여할 수 없으므로, 최초 권한과 확대 요청은 권한 있는 내부 직원의 별도 부여 절차로 연결해야 한다. 고객/직원 관리 모두 같은 원칙을 적용한다.
X. Other (please specify). 고객/직원별 다른 한계나 자기 자신에게 부여하는 조건이 있다면 설명한다.

[Answer]: A. 역할 관리 권한을 역할 부여 권한으로 적용한다. 고객사 관리자는 자신의 현재 관리 범위 안에서 OMS가 허용한 고객용 행위의 역할을 정의·부여할 수 있으며, 자신의 직접 업무 권한이 없어도 다른 담당자에게 줄 수 있다. 자기 자신에게 부여할 때도 별도 명시적 부여와 이력을 남긴다. 내부 직원 역할 관리도 허용된 직원 행위 목록 안에서 같은 원칙을 적용한다. 관리 권한 자체는 해당 업무의 자동 수행 권한이 아니다. 고객의 직원 전용 권한·타 기업 접근과 관리 범위 밖 권한 확대를 금지하고 계약의 동일인 자기 승인 금지를 유지한다. 사용자 원문: "1".

### Q2 공통 경계와 근거

어떤 선택에서도 고객은 직원 전용 행위·다른 기업의 권한을 만들거나 부여할 수 없다. 현재 관리 범위 밖의 역할 정의/변경/부여·관리 권한 확대는 거절한다. 계약 등록자와 승인자의 동일인 금지는 역할 합산·자기 역할 부여와 관계없이 유지한다. ## Q3. 모든 복구 담당자가 OMS에 접속할 수 없고 사전 복구 코드도 사용할 수 없다면 어떻게 처리할까요?

일반 복구는 권한 있는 직원의 본인 확인과 MFA 재등록으로 진행한다는 결정이 있다. 그 직원들까지 인증 수단을 잃은 경우의 비상 경로는 아직 정하지 않았다. 이것은 고객 공개 화면의 MFA 우회 기능이 아니라 내부 운영 절차의 선택이다.

A. 별도로 보호된 비공개 운영 절차로 내부 복구 담당자의 접근을 먼저 복원한 뒤 일반 복구를 재개한다. 기존 콘솔/초기 권한 준비 경계와 연결하되 비상 작업자의 권위·대상 신원·원래 인증 연결·사유/근거·현재 권한을 확인하고 작업 이력을 보존한다. 새 MFA 검증 전에는 업무 접근을 허용하지 않고 상시 공유 관리자나 영구 MFA 해제를 만들지 않는다. 실제 작업자·자격·확인 수단이 없으면 이 절차는 실행 불가로 남긴다. (권장)
B. 별도의 비상 인증 복원 경로는 만들지 않는다. 사전 수단이나 기존의 정당한 담당자 접근이 회복될 때까지 복구 요청을 보류하고 상태·필요 조치를 안내한다. 이메일만으로 MFA를 해제하거나 자동 관리자 계정을 만들지 않는다.
X. Other (please specify)

[Answer]: A. 별도로 보호된 비공개 운영 절차로 내부 복구 담당자의 접근을 먼저 복원한 뒤 일반 복구를 재개한다. 비상 작업자의 권위·대상 신원·원래 인증 연결·사유/근거·현재 권한을 확인하고 작업 이력을 보존한다. 새 MFA 검증 전에는 업무 접근을 허용하지 않으며 상시 공유 관리자나 영구 MFA 해제를 만들지 않는다. 실제 작업자·자격·확인 수단이 없으면 실행 불가로 남긴다. 기존 콘솔/최초 권한 준비 경계와 연결하며 실제 AWS/IAM·Cognito 작업이나 계정 생성·변경을 이 답변으로 실행하지 않는다. 사용자 원문: "1".

## 답변의 모호성·충돌 점검

- Q1–Q3은 모두 제시한 A를 명시적으로 선택했다. 수락만 확인한 상태와 MFA·현재 기업/조직/초대/관리 권한을 충족한 활성화를 구별하므로 미인증 접근을 허용하지 않는다.
- Q2의 명시적 역할 부여는 관리 권한의 자동 업무 권한화를 뜻하지 않는다. 현재 관리 범위·허용된 고객/직원 행위 목록과 기업 경계, 계약 동일인 자기 승인 금지를 유지하므로 기존 결정과 충돌하지 않는다.
- Q3은 비공개 비상 복원 절차의 설계 방향을 정한 것이다. 실제 작업자 권위·본인 확인 수단·접근 자격·제공자 지원과 실증은 아직 확보된 사실이 아니며 해당 실제 적용 전 조건으로 남긴다. 최초 콘솔 계정 생성만으로 업무 권한/MFA 완료를 인정하지 않는다.
- 초대 수락 및 비상 복구에 필요한 명령·상태·증거 참조를 상세 설계에서 명시하고 기존 닫힌 계약의 필요한 확장/영향을 식별한다. 기존 계약이나 U1의 완료 기록을 임의 변경하지 않는다.
