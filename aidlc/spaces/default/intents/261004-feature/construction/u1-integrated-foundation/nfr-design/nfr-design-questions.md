## Q1. Next UI와 Nest API 사이의 화면 데이터·세션 전달을 어떤 방식으로 구성할까요?

A. Next를 화면용 중계층(BFF)으로 사용하고 필요한 최초 조회는 요청별 서버 렌더링을 적용한다. 화면 요청은 허용된 Nest operation으로만 전달하고 주문/권한 규칙을 Next에 복제하지 않는다. 어떤 최소화면의 조회를 서버/브라우저에서 할지, 추가단계 지연·현재사용자문맥·cache/CSRF·직원망을 구체화한다. 임의 외부주소를 받아 전달하는 범용 proxy로 만들지 않는다. (권장)
B. Next 화면은 브라우저 중심 데이터 조회/입력으로 시작하고 보호된 전송 경로를 통해 Nest API를 호출한다. Next 라우팅/layout을 사용하되 요청별 민감자료 SSR을 필수로 두지 않는다. cookie/origin/CSRF·동적경로/새로고침과 직원망을 같은 수준으로 검증한다. static export 가능 여부는 실제동적경로와 함께 따로 확인한다.

## Q2. 커밋된 작업을 worker에 전달하는 첫 물리 방식은 무엇으로 둘까요?

논리 원자성/반복전달/consumer별효과한번은 확정이다. 어떤 전달 방식도 DB선택·queue ACK만으로 성공접수 RPO0이나 외부부작용 exactly-once를 보장하지 않는다. 실제승인/접수·작업과 소비표지/효과·후속사실의 원자단위, 내구응답조건·불명결과대조·권한/버전·deadline/상한과 별도논리손상복구근거는 추가설계/시험이 필요하다. PostgreSQL row-lock/queue-like 사용은 가능하지만 SKIP LOCKED는 일반조회용 일관성 보장이 아니며 업무순서를 자동 보장하지 않는다. [S3–S4·S7–S8·W2]

A. DB 기반 트랜잭션 작업 큐: 같은 PostgreSQL transaction에 저장한 작업/미전달 기록을 Nest standalone worker가 제한된 batch·명시적처리소유/수명으로 읽고 처리하는 구성부터 검증한다. 반복/중단/경합을 consumer표지·원본버전/멱등성으로 대조하고 미등록/불명 작업을 보존한다. 별도 broker를 초기필수로 추가하지 않는다. 실제poll/batch/lease/lock·자원상한과복구근거를 설계한다. (조건부 권장 비교 이력; 미채택)
B. Transactional Outbox + relay + 별도 지속 queue: PostgreSQL 원자접수/미전달기록에 더해 별도지속queue로 전달한다. 커밋된 원본만relay하고 반복전송·queue/DB사이 종료·재기동·미전달대조와 같은consumer효과보호를 검증한다. 실제queue제품/보관·국내위치·추가운영/비용은 선정근거가 필요하다.
X. Other (please specify)

[Answer]: B. Transactional Outbox + 별도 지속 queue를 사용한다. 사용자 선택 원문: "그럼 2. Transactional Outbox + 별도 queue 로한다". 업무 변경·접수/필요 작업/발행 기록을 같은 PostgreSQL transaction으로 저장하고 커밋된 발행 기록을 relay가 별도 queue로 전달하며 Nest standalone worker가 소비한다. relay 재전송·DB/queue 사이 종료/복구·소비 중복/불명 결과·권한/원본 버전 대조와 이력/키 보존은 필요하다. 실제 queue 제품/종류·국내 위치·보관/timeout/deadline·실행 배치는 아직 선택하지 않았다. SQS 채택, 외부 효과 exactly-once 또는 RPO0 달성으로 확대 해석하지 않는다.

### Q2 용어 확인 — 선택 전 대화 기록

사용자 원문: "2번은 아웃박스 패턴인거지?\n1번은 그냥 트랜잭션?". 이는 두 후보의 의미를 확인하는 질문이며 B 선택으로 기록하지 않는다.

2번은 업무 변경과 발행할 메시지를 같은 DB transaction에 저장한 뒤 relay가 커밋된 메시지를 별도 queue/broker로 전달하는 일반적인 Transactional Outbox 구성이다. DB와 queue를 하나의 transaction으로 묶는 뜻은 아니다. 1번도 업무 변경만 저장하는 일반 transaction을 넘어서 후속 작업을 같은 transaction에 영속 저장하지만 worker가 그 DB 작업 기록을 직접 소비한다. 따라서 이 후보는 DB 기반 트랜잭션 작업 큐라고 부른다. 두 후보는 업무 변경과 후속 작업의 원자 기록이라는 원칙을 공유하며, 선택의 차이는 worker의 소비 경로가 DB 직접인지 relay→queue인지다. DB를 poll하는 것 자체는 구분 기준이 아니며 2번 relay도 polling 방식일 수 있다. [W4–W5]

업무 변경만 commit한 뒤 내구 기록 없이 queue 전송을 시도하면 그 사이 종료 시 업무는 저장됐지만 후속 작업은 누락될 수 있다. 두 후보 모두 그런 단순 전송에 의존하지 않는다. 처리나 전송 후 완료 표시 전 종료로 중복이 발생할 수 있으므로 멱등성·처리 표지·불명 결과 대조가 필요하다. 이 용어 확인은 성공접수 RPO0, 외부 효과 exactly-once나 실제 queue 제품의 선정을 증명하지 않는다. [S4·S7–S8·W4–W5]

### Q2 권장 근거와 재검토 조건 — 선택 전 대화 기록

사용자 원문: "DB 기반 트랜잭션 작업 큐를 권장하는 이유 말해봐". 이는 권장 근거 요청이며 A 선택이나 작업 큐 구현 승인이 아니다. 위 A의 권장은 아래 조건을 검증하기 위한 초기 설계 가설이다.

- **설계 판단:** PostgreSQL과 별도 Nest worker는 이미 선택됐다. DB 직접 소비는 별도 relay→queue 전달 상태, queue 접근 권한/보관/관측 설정과 DB·queue 간 재전송 대조를 초기 전달 경로에서 줄일 수 있다. 접수/작업/업무 결과를 동일한 DB 원본과 연결해 대기 원인·실패 이력·재처리 조건을 확인하는 경로를 단순하게 구성할 수 있다는 판단이다. 별도 queue를 사용하는 B도 업무 원본과 멱등성 보호는 필요하다. 이것은 DB 큐가 항상 더 안전하거나 전체 구현/운영 비용이 더 작다는 사실 확인이 아니다. [S6–S8·W4]
- **확인된 범위와 가정:** 공유된 업무 핵심/단일 쓰기 권위와 API/worker의 별도 실행은 확정됐지만 별도 broker로 독립 소비자에게 배포해야 하는 구체적 요구·실제 수요/작업 생성량은 아직 확인되지 않았다. 정상20req/s·집중100req/s는 HTTP 합성 부하 시험 기준이며 job/s나 DB 큐 용량 증거가 아니다. 기능 범위를 줄이지 않고1인 기술 운영 목표에 맞게 장애 대조/복구 절차를 단순화할 수 있는지는 실제 시험이 필요하다. [S3·S6–S8]
- **비용/실패의 반대 근거:** poll/claim/update와 작업 자료 증가·정리는 업무 DB의 연결/lock/I/O·저장/유지 작업 자원을 사용한다. 업무 DB가 불가하면 DB 작업 claim/상태 변경도 중단된다. 짧은 처리권 확보 transaction, 소유권 만료/재확보와 이전 worker의 늦은 결과 방지, 안전 재시도/불명 결과 대조·실패 작업 보존과 자료 정리 등을 설계/검증해야 한다. 외부 호출 전체에 DB transaction/lock을 유지하지 않으며 row locking만으로 이 보호나 업무 순서가 완성되지 않는다. [S3–S4·S7–S8·W2]
- **관리형 queue 대안:** SQS는 처리 중 visibility timeout, 실패 메시지 격리와 queue 확장 등 전달 기능을 제공하므로 queue 기반 시설의 운영이나 일부 처리권 관리를 직접 구현할 부담을 줄일 수 있다. 단순히 구성 요소가 하나 더 있다는 이유만으로 B가 운영하기 더 어렵다고 판단하지 않는다. 반면 A/B 모두 업무 멱등성·불명 외부 결과 대조가 필요하며 B는 원자 원본에서 queue로 전달/복구하는 경계를 검증해야 한다. 실제 queue 종류/제품·지역·가격·보관 정책은 미선정이다. [W4·W6]
- **선정 전 검증과 권장 변경:** 실제 작업 종류/생성량·동시성/외부 지연을 포함한 정상/집중 부하에서 API 응답 목표, worker 적체/회복과 중단·반복/동시 처리 정확성,30분 복구/성공접수 보존 및 사람 운영 부담을 검증한다. 검증된 PostgreSQL 작업 큐 구성/라이브러리가 동일 transaction과 업무 계약에 맞는지 확인하고 검증되지 않은 자체 범용 queue 개발을 전제하지 않는다. 업무 DB 부하/적체로 목표를 지키지 못하거나 독립 consumer/queue 격리·처리량 확장이 필요하거나 작업 큐 구현/운영 부담이 더 크면 첫 버전부터 B로 권장을 바꾼다. 두 후보 사이 전환도 키/원본·대기/소비 표지·이중 전달/효과·버전/되돌림 검증 없이 쉽게 가능하다고 표시하지 않는다. [S1·S3–S8]

### OMS/WMS 책임 경계 설명 요청

사용자 추가 원문: "그리고 지금 OMS랑 다른 WMS랑 어떻게 책임을 나눴는지 설명해줘 그리고 곧바로 다음 질문". 이는 기존 경계 설명과 Q3 진행 요청이다. WMS 제품 선정·실제 연결 확보나 책임 변경 요청으로 취급하지 않는다.

- OMS는 고객 주문·계약/지급 조건·전체/동의된 부분 제공을 판단하고 HW 공급 가능성/납기 근거·예약/확보/출고/회수 요청과 확인 결과를 주문의 품목·수량에 연결한다. 출고 허용/취소·반품 판단·미확인/충돌 대조와 고객 진행 조회의 책임은 OMS의 해당 업무 소유자에게 있다. [S9·S12]
- OMS 바깥의 WMS/실물 재고·창고 실행 주체는 재고 원본과 실제 입출고·창고 위치·피킹/패킹 등 현장 실행 근거를 제공하는 경계다. OMS는 이 실행/원본 권위를 가져오지 않는다. 실제 재고 원본·예약의 단일 권위/최신성·WMS/공급자/배송/회수 주체·프로토콜/인증·접근은 미확인이다. 예약은 OMS의 주문별 요청/참조·확인 상태와 외부 실제 할당 결과를 구별하며 두 시스템에 독립 예약 원장을 만들어 중복 가용 수량을 주장하지 않는다. [S8–S9·S12]
- C23은 HardwareFulfillment가 소유하는 외부 adapter port이며 실제 승인 작업 요청과 원래 작업 결과 조회를 분리한다. 실행 주체/지원/증거가 없으면 UNCONFIRMED다. 검증된 외부 연결 또는 권한 있는 직원의 근거 입력으로 결과를 연결할 수 있지만 입력만으로 실제 예약/확보/출고가 발생했다고 보장하지 않는다. [S8–S9]
- queue의 요청 수락·OMS의 접수·WMS 출고 요청과 실제 출고는 각각 다른 사실이다. 출고만 확인한 경우 HW 제공 완료가 아니며 기업·상품 합의에 따라 배송 완료 또는 고객 인수 확인으로 OMS가 완료를 판단한다. 운송/배송 증거는 실제 운송 주체와 대조하며 WMS가 운송 전체를 소유한다고 정하지 않는다. SW 발급/기간/갱신/회수는 별도 SoftwareLifecycle 책임이고 WMS로 넘기지 않는다. [S8–S9·S12]
- 이번 outbox/queue 선택은 후속 작업의 전달 방식이다. 모든 이벤트를 외부 WMS에 자동 공개하거나 WMS가 OMS queue를 직접 구독하도록 선정한 것은 아니다. 외부 연결은 업무 소유 adapter에서 목적·대상·수량·권한/근거·원래 작업 식별자와 실제 결과를 대조해야 한다. [S7–S9]

## Q3. 신원·MFA 기반은 어떤 운영 방향으로 검토할까요?

모든사람의 실제MFA·목적제한 등록/복구, 이메일만으로MFA해제금지·재등록무효화/이력/통지·서버세션/현재권한은 확정이다. 신원서비스의 token/로그인성공을 모든경우 OMS의 MFA완료/업무권한으로 동일시하지 않는다. 예를들어 Cognito 공식문서는 최초가입의인증과이후MFA·federation의주체가다를수있음을 설명하므로 실제선정시각경로를별도대조해야한다. 특정인증제품이나실제계정/접근을이미확보했다고표시하지않는다. [S2·S7–S9·W3]

A. AWS관리형신원서비스를 우선 후보로 두고 OMS의IdentityRecovery adapter/제한challenge/세션과MFA·복구·동일인/직원망 정책의 적합성을 검증한다. 구체적제품/방법·국내처리/저장·수단/복구능력·실제접근/비용과예외를 확인한뒤선정한다. 공급자가지원하지않는복구를자동가능으로표시하지않는다. (권장)
B. OMS가검증된인증라이브러리/서비스를자체운영하는방향부터비교한다. credential/MFA수단·challenge/복구·보안업데이트/감사·secret보호·장애대응과1인운영부담을같은요구로검증한다. 암호알고리즘을새로만드는선택이아니다.
C. 이미사용하는신원/SSO서비스를기준으로비교한다. 실제서비스/관리주체·MFA/복구/현재권한근거·직원/고객적용범위를설명한다. 확보사실은확인전가정이다.
X. Other (please specify)

[Answer]: A. AWS 관리형 신원 서비스를 우선 후보로 검증한다. 사용자 원문: "1". OMS의 실제 MFA·목적 제한 등록/복구·이전 수단/세션 무효화·이력/통지·동일인/직원망·현재 권한과 국내 처리/저장 조건을 유지한다. 구체 제품·pool·인증 방식·지역·복구 방법·실제 계정/자격·비용은 이 답변만으로 선정하거나 확보했다고 표시하지 않는다.

## Q4. Cognito를 우선 후보로 검토할 때 고객과 내부 직원의 계정·인증 저장소를 어떻게 구성할까요?

Q3에서 AWS 관리형 우선 검토를 선택했으므로 Amazon Cognito User Pools를 구체 후보로 비교한다. 공식 문서는 서울의 user pool endpoint와 TOTP MFA/관리자 TOTP 초기화 경로를 설명하지만 국내 저장 전체·본인 확인·사전 복구 코드·같은 사람 식별·망 통제의 자동 충족 근거는 아니다. 실제 기능/SDK·정책·메일/로그/복제 경로와 접근 조건을 검증한 뒤 채택한다. [S2·S6–S9·W3·W8–W10]

동일 user pool의 관리형 로그인 cookie는 여러 app client에서 인증에 사용될 수 있으므로 app client만 분리하는 구성과 계정 저장소 자체를 분리하는 구성의 효과가 다르다. 풀 분리도 동일 AWS 계정/리전 quota의 완전한 격리나 직원 사내망 통제의 자동 구현을 뜻하지 않는다. 두 후보 모두 CUSTOMER/STAFF 발급자·client/토큰 목적·세션을 검증하고 업무 권한은 OMS 원본에서 현재 판정하며 고객 토큰/공개 경로가 직원 인증·UI/API를 우회하지 못해야 한다. 직원 인증의 모든 지원 경로와 초기 등록/복구도 승인 망/PC 경계를 검증해야 한다. [S2·S7–S9·W7]

A. 고객 공용 user pool 1개와 직원 전용 user pool 1개를 분리하는 방향으로 검증한다. 계정 등록/복구·MFA 설정과 로그인 경계를 별도로 관리하고 고객 발급 토큰은 직원 경계에서 거절한다. 고객 기업별 주문/조직/행위 권한은 공유 고객 pool 안에서도 OMS가 현재 검증한다. 이 선택은 기업별 pool이나 worker를 사람 계정으로 로그인시키는 선택이 아니다. 두 설정의 배포/복구 부담과 사람 식별 원본 연결을 검증한다. (권장)
B. 공통 user pool 1개와 고객용/직원용 app client를 분리하는 방향으로 검증한다. 계정/MFA 기반을 공유하되 client·CUSTOMER/STAFF 세션·등록/복구·현재 직원 권한/망을 별도로 확인한다. 관리형 로그인 세션 공유와 다른 app client로 로그인하는 경로가 직원 접근을 허용하지 않는지 검증하며 group/이메일/클라이언트 요청만으로 직원 업무 권한을 부여하지 않는다.
X. Other (please specify)

[Answer]: A. Cognito 기준으로 고객 공용 user pool 1개와 직원 전용 user pool 1개를 분리하는 구성을 선택한다. 사용자 원문: "1". 고객/직원 계정 등록·MFA·복구 설정과 발급자/client/세션 경계를 분리하고 고객 pool 안의 기업/조직/행위 권한은 OMS가 현재 검증한다. 직원 승인 망/PC·실제 MFA·동일인 근거·이전 세션/수단 무효화 조건을 유지한다. 기업별 pool이나 고객 토큰의 직원 접근을 승인하지 않는다. 실제 AWS pool 생성/자격·지역/지원/가격·국내 자료 경로와 기능 적합성의 확보/실증은 아직 없다.

## Q5. 고객·직원의 로그인 화면과 Cognito 인증 처리 경로를 어떻게 구성할까요?

Q4의 pool 분리와 별개로 로그인·초기 MFA 등록·복구·재로그인 경로를 정한다. Cognito는 제공 화면을 사용하는 managed login과 자체 화면/API를 사용하는 인증을 지원한다. 서버 인증 API는 IAM 서명/권한으로 보호할 수 있지만 그 자체가 실제 사용자 망 조건이나 OMS 업무 권한을 검증하는 것은 아니다. 이 질문의 자체 화면은 password/MFA 검증을 Cognito에 맡기는 구성이지 자체 credential 저장/암호 검증이나 Lambda custom-auth 알고리즘을 새로 만드는 선택이 아니다. [S2·S7–S9·W11–W13]

두 후보 모두 Next는 화면/BFF이고 신원·목적/challenge·OMS 업무 세션/현재 권한의 최종 소유자는 Nest의 IdentityRecovery/EnterpriseAccess다. 민감 입력/인증 provider token·refresh token·challenge 원본은 로그/캐시/브라우저 저장소에 남기지 않고 C01/G19–G23의 목적 제한·opaque 업무 세션 경계를 구체화한다. callback/client/발급자/토큰 종류·state/nonce/PKCE·origin/CSRF와 초기 등록 token의 목적을 검증하고 실제 MFA 완료 전 업무 세션을 부여하지 않는다. 직원은 최초 요청부터 challenge·등록/복구·갱신·재조회까지 승인 망/PC 근거가 필요하며 Next 서버 IP·공개 고객 인증 경로로 이를 우회하지 못한다. [S2·S7–S8·W3·W8·W12]

### Keycloak 대안 비교 — 선택 전 대화 기록

사용자 원문: "키클락으로 만드는건 어때". 이는 Keycloak 비교 요청이며 Q5 A/B 답변이나 기존 AWS 관리형/Cognito 우선 검토를 변경하는 확정 선택으로 기록하지 않는다. 현재 Q5는 미응답으로 유지하고 아래 Q5-F1에서 우선 후보 변경 여부를 먼저 확인한다.

- **확인된 기능:** Keycloak은 OIDC/OAuth2/SAML, 로그인 흐름/계정·세션 관리와 외부 신원 연동을 제공한다. realm은 사용자·credential·role/group을 관리하는 논리적 인증 경계다. 공식 최신 문서는 TOTP와 복구 코드를 설명하며 recovery-codes는 지원 기능 목록에 포함된다. 복구 코드의 실제 발급/사용 흐름 설정과 선택 버전의 지원을 확인해야 하고 기존 수단 무효화·본인 확인·OMS 목적 제한/감사/알림을 자동 충족한다고 표시하지 않는다. [W14–W16]
- **이 OMS에 대한 설계 판단:** 고객/직원 분리, 모든 사람 MFA와 복구 수단, 직원 로그인·등록/복구의 사내망 제한과 인증 화면/흐름 제어라는 요구에 잘 맞을 수 있다. 선택한다면 고객/직원 realm을 분리하고 공개 고객 경로에서 직원 realm/관리 경로와 직접 backend 우회를 차단하는 구성을 검토한다. realm/hostname 분리만으로 네트워크·관리자·DB/장애 경계가 격리되지는 않는다. 같은 배포/클러스터의 두 realm과 별도 배포의 비용/장애·권한/망 차이는 추가 검증한다. [S2·S7–S9·W14·W17–W18]
- **추가 운영 책임:** AWS에서 직접 운영하는 Keycloak은 AWS 관리형 신원 서비스와 다르다. 인증 server/지원 runtime·생산용 DB·TLS/키·network/proxy/cluster·health/성능/지표·패치/버전·DB migration·백업/복원/재배포와 장애 대응을 우리 운영 범위에 포함한다. 인증 장애는 OMS 핵심 로그인 가용성에 영향을 주므로99.9%·30분복구·정의한 성공접수 보존과1인 기술 운영의 동시 목표를 자동화/장애 시험으로 검증한다. 인원1은 기능 제외 이유가 아니며 실제 달성/비용을 현재 문서만으로 보장하지 않는다. [S2·S4–S6·W19–W21]
- **책임 유지:** Keycloak은 인증·MFA·신원 연동을 맡는 후보이고 Nest의 IdentityRecovery/EnterpriseAccess는 purpose/OMS 업무 세션·현재 기업/소속·행위별 scope·동일인/업무별 승인 정책의 원본을 연결한다. Keycloak role이나 로그인 token만으로 OMS 주문·조직·계약 승인 권한을 부여하지 않는다. Next/Nest의 TypeScript 앱은 OIDC 방식의 연동을 검토할 수 있다. Keycloak 전용 신원 DB 원본/테이블을 OMS 업무 transaction에서 직접 변경하는 구성이나 별도 Java custom provider 개발을 이 비교로 승인하지 않는다. [S2·S6–S9·W14]
- **미확인 조건:** 국내의 server/DB/복제/backup/로그·메일·연동 경로, 선택 release/지원·기능 설정·실제 계정/자격, 계정 생성/동일인·최초 MFA/복구와 즉시 OMS 세션 무효화·성능/복구·비용은 확인 전이다. Cognito 대비 비용 우위나 완성된 운영 구조를 가정하지 않는다. Keycloak 채택 시 Q3/Q4의 provider 관련 현재 결론과 Q5 후보를 새 선택에 맞게 갱신하고 이전 사용자 선택·그 이후 변경 근거를 보존한다. [S2·S6–S9]

X. Other (please specify)

[Answer]: A. 첫 출시는 Cognito로 진행하고 출시 후 Keycloak으로 전환하는 계획을 선택한다. 사용자 원문: "1 코그니토로 먼저 진행하고 출시후 keycloak 으로 간다 때문에 인증 서비스가 변경될 수 있다는 것을 고려한 설계 필요". 현재 고객/직원 Cognito pool 분리와 업무/보안·국내 저장/복구/운영 목표는 유지한다. 인증 제공자 교체를 지원하는 경계·안정 OMS 계정 ID·외부 신원 연결·세션/MFA/복구 정책과 전환/되돌림 검증을 첫 버전 설계 요구로 추가한다. Keycloak 전환은 단순 비교 가능성이 아니라 출시 후 계획이며 전환 날짜·방법·실제 자격/인프라·자격증명 이전 가능성은 아직 미확정이다. 이 답변은 미응답 Q5의 로그인 화면/경로 A 또는 B를 선택한 뜻이 아니다.

### 인증 제공자 변경을 고려한 추가 설계 요구 — 사용자 지정

- **ND-PV01 안정 계정·권한 원본:** 기존 Account.accountId를 OMS 계정의 안정 ID로 유지한다. [S2·S6–S9·W11–W14·사용자 Q5-F1]
- **ND-PV03 세션·MFA·직원망:** 기존 IdentitySession의 opaque OMS 세션과 서버 유휴/절대 만료·현재 권한/무효화 정책을 유지한다. 외부 issuer/subject/token을 검증하고 현재 허용 provider/연결 개정을 대조한 후 실제 MFA 완료·주체/audience·직원망 조건에 맞게 OMS 세션을 부여한다. provider 전환 중 오래된 token/challenge/refresh·복구 요청이 새 계정 연결을 덮어쓰거나 현재 검증을 우회하지 못하게 한다. 전환 후 새 인증/필요 MFA 등록과 이전 세션/수단의 취급을 구체화한다. 기존 MFA 비밀/세션을 자동 복사하거나 이메일 접근만으로 MFA/업무 권한을 복구하지 않는다. 고객/직원 분리 의도는 Keycloak 전환에서도 유지하지만 실제 realm/배포/망 구성은 아직 선정하지 않았다. [S2·S6–S9·사용자 Q5-F1]

### Q5에 적용되는 전환 설계 조건

Q5 A/B 중 어느 첫 로그인 구성을 택해도 provider 교체 경계를 적용한다. A의 고객 managed login은 OIDC redirect/callback을 provider adapter와 연결하고 직원 Cognito API challenge는 목적 제한된 OMS 상태로 감싼다. B의 자체 화면도 Cognito API/claim/결과에 직접 의존하지 않도록 한다. Keycloak에서의 제공 로그인/OIDC 흐름과 최초 Cognito challenge가 동일 API/화면 동작을 갖는다고 가정하지 않는다. provider 고유 로그인/MFA/복구 UI·전송 변화는 adapter와 신원 화면/계약 경계에서 처리하고 주문/계약 등 업무 원본은 보존한다. 사용자는 Q5 B를 선택했고 A는 미채택 비교 이력이다. ## Q6. 첫 버전에서 고객·직원의 기본 로그인 MFA 수단은 무엇으로 둘까요?

[S2·S7–S9·W3·W8]

[S2·S6–S9·W3·W25·ND-PV01–06]

X. Other (please specify)

## Q7. TOTP 기기 분실에 대비한 사전 복구 코드는 어떻게 준비할까요?

사전 복구 코드/등록한 별도 수단을 통한 직접 복구와 그것도 없을 때 권한 있는 내부 담당자의 본인 확인 복구는 이미 요구에 포함돼 있다. Q6의 password+TOTP 기본 로그인에 맞춰 아래는 사전 발급 코드 방식의 두 후보를 비교한다. Other에서 등록한 다른 인증 수단 등 다른 구성을 제안할 수 있으며 여기서 기존 직접 복구 지원·담당자 확인·MFA 재등록/무효화·이력/통지를 제거하지 않는다. [S2·S7–S9·S12]

두 후보 모두 **password의 유효성 + 사전에 발급한 사용하지 않은 복구 코드**를 확인하면 TOTP 재등록 목적의 제한된 복구 상태로 진행하는 설계다. password도 사용할 수 없거나 유효한 사전 수단/코드가 없으면 확인된 담당자 복구로 연결한다. 코드만/이메일 접근만으로 업무 세션을 부여하거나 MFA를 영구 해제하지 않는다. 직원 복구도 승인 망/PC를 확인하고 이전 수단/세션 무효화·새 TOTP 검증·기록/통지·현재 권한을 확인한 뒤 일반 업무 접근을 재개한다. 실제 담당자의 신원 확인 근거·권한/접근 불가 상황은 후속 확인 대상이다. [S2·S7–S9·ND-PV01–06]

C21 adapter는 검증된 원래 계정/provider 연결의 TOTP 제거/재등록을 실행·대조한다. 공식 AdminDeleteSoftwareToken은 IAM 권한이 필요하고 TOTP를 제거한 뒤 MFA-required/no-other-factor 상태에서 다음 로그인에 MFA_SETUP을 요구한다. 실제 지원 pool/지역/SDK·최소 서비스 권한·요청 종료/불명 결과/늦은 재시도와 새 수단의 경합을 검증해야 하며 코드 확인만으로 외부 제거가 완료됐다고 표시하지 않는다. NIST의 saved recovery code 기술 지침은 설계 참고이며 이 OMS에 특정 IAL/AAL·미국 의무/준수 인증을 채택한 뜻이 아니다. 정확한 코드 수/길이·검증 방식/수명·challenge/시도 제한과 별도 증거 필드는 후속 설계에서 확정한다. [S2·S6–S9·W27]

## Q8. Transactional Outbox에 연결할 첫 queue 제품·종류는 무엇으로 둘까요?

현재 G08–G09는 반복 전달, 역순/늦은 결과·원본 버전/정정 대조, consumer 처리 표지·업무 효과 한 번과 외부 불명 결과의 안전 대조를 이미 요구한다. 두 후보 모두 같은 PostgreSQL transaction의 업무/접수/작업·발행 원본에서 커밋된 기록만 전달하고 queue 수락/삭제와 실제 업무/외부 효과 완료를 구별한다. SQS/FIFO의 제품 용어를 DB/외부 시스템까지의 exactly-once 보장으로 해석하지 않는다. queue 만료/DLQ 이동·삭제만으로 성공 접수 원본/미해결 작업을 잃지 않아야 한다. [S4·S7–S8·W28–W30]

### Q8 재고 경합 시나리오 검토 — 선택 전 대화 기록

사용자 원문: "만약 재고가 한정된 것을 고객사 A, B가 동일한 시간에 주문했을때를 생각하면 fifo 가 적절한건 아닌가". 이는 FIFO 적합성/권장 근거의 검토 요청이며 Q8 B 선택이나 재고 배정 우선순위 확정 답변으로 기록하지 않는다.

- **설명용 가정:** 특정 HW 재고가1개·A/B가 각각1개를 원하고 추가 조달은 불가하다고 가정한다. 실제 재고/예약 원본·최신성·WMS/공급자 실행/수단은 미확인이고 기존4개 확보 정책·지급 조건·FULL/동의된 PARTIAL을 변경하지 않는다. OMS 요청 접수·주문 수락과 실제 예약/확보·제공 완료를 구별한다. [S8–S9·S12]
- **FIFO가 돕는 부분:** 같은 재고 원본/자원을 사용하는 두 예약 작업을 동일 message group에 전달하고 worker가 그 group의 batch도 순차 처리하면 먼저 전달된 요청 이후 다음 요청을 처리하도록 구성할 수 있다. A/B를 orderId별 서로 다른 group으로 나누면 FIFO여도 병렬 처리되므로 같은 재고의 경쟁을 자동 직렬화하지 못한다. 예시 stockKey는 실제 재고 원본/창고·pool 경계의 확인 후 정할 group 설계 후보이지 OMS가 재고 원본을 이미 소유했다는 뜻이 아니다. [W29]
- **초과 예약 방지의 권위:** 남은 수량 확인과 예약 반영은 실제 재고 원본에서 원자적으로 처리해야 한다. 가정의1개를 A가 예약하면 가용0인 B의 예약은 성공으로 처리하지 않고 계약/공급 정책에 따른 후속 판단을 한다. 원본이 PostgreSQL이면 조건부 갱신·동일 transaction의 예약 기록/잠금·충돌/실패 대조로 검증할 수 있다. 외부 WMS가 원본이면 검증된 WMS 예약 기능의 원자성/멱등성·다른 판매/직원 경로까지 포함한 수량 보호 근거가 필요하며 OMS DB와 별개 재고 원장을 만들어 각자 같은1개를 예약하는 것으로 대체하지 않는다. 읽기나 요청 수락만 확인한 결과를 실제 예약으로 표시하지 않는다. [S8–S9·S12·W31]
- **배정 순서·다품목의 추가 조건:** FIFO는 같은 group의 queue 도착/발행 순서를 제공하며 고객 클릭 시각·HTTP 도착·DB 접수 commit의 순서를 자동 보장하지 않는다. 먼저 유효하게 접수한 주문 우선인지 지급 충족/기업 합의 우선인지 실제 배정 정책은 아직 선택하지 않았고 relay 발행/복구도 선택한 원본 순서와 연결해야 한다. 같은 타입 다품목 주문의 FULL 제공은 SKU별 순서만으로 전체 예약 원자성이 생기지 않으므로 다중 자원의 일관된 동시성/전체 예약·미확인/부분 결과와 조정/복구를 별도 설계한다. 한 메시지에 여러 SKU group이 동시에 적용된다고 가정하지 않는다. [S7–S9·S12·W29–W31]
- **당시 권장 수정과 후속 선택:** 순서 있는 재고 예약 등 업무가 중요하다는 시나리오를 반영해 FIFO+실제 재고 원본의 원자적 예약을 우선 검토하도록 권장을 보완했다. 현재 G08–G09의 멱등성/버전·consumer 표지·불명 외부 결과 대조는 유지하며 FIFO만으로 중복 예약/과다 출고·외부 효과 한 번이나 전체 fairness를 보장하지 않는다. 이후 사용자는 직전1 Standard/2 FIFO/3 Other 중1을 명시해 Q8 A Standard를 선택했다. 실제 배정 순서는 별도 업무 정책/원본에서 구현·검증해야 한다. [S4·S7–S9·W28–W31·사용자 Q8]

## Q9. 한정 HW 재고의 예약 대상은 어떤 순서로 선정할까요?

Q8의 Standard는 중복/역순 전달을 허용하므로 메시지를 먼저 읽은 worker가 임의로 배정 순서를 정하지 않는다. 실제 재고/예약 원본의 수량 보호와 별개로, 어떤 주문을 우선 후보로 선택할지의 업무 정책을 비교한다. 두 후보 모두 주문/상품/기업 합의·네 확보 정책·지급/보류·현재 유효 근거의 예약 허용 조건을 확인하고 이미 확인된 예약을 나중 도착한 정보로 자동 재배정하지 않는다. 미확인 수량/외부 결과는 예약 성공으로 표시하지 않으며 FULL/동의된 PARTIAL 조건을 유지한다. 이 질문은 모든 주문의 전액 선결제나 미지급 주문의 무조건 예약 금지를 추가하는 선택이 아니다. [S7–S9·S12·W28·W31]

이 순서는 이후 HardwareFulfillment/U5의 세부 Functional/Contract 설계에서 후보 등록·순서 원본/동률·조건 상실/재진입·다품목과 WMS/다른 채널을 포함한 실제 예약 권위에 연결해 검증한다. U1은 원본/작업·멱등·버전/동시 변경 보호의 기반을 제공하며 이 질문 답변만으로 U5의 재고 모델/실거래 기능이 이미 구현됐다고 표시하지 않는다. 실제 정책이 입력된 authority가 순서와 예약을 일관되게 적용할 수 없는 경우 대조/확인 대상으로 유지한다. 클릭 시각/queue 도착/처리·특정 PostgreSQL sequence가 올바른 업무 commit 순서를 자동 증명한다고 가정하지 않는다. [S6–S9·S12·W28–W31]

A. 예약 허용 조건을 충족해 원본 소유자가 후보로 확인·기록한 순서대로 배정한다. 먼저 주문했어도 아직 해당 예약 조건을 충족하지 못한 주문은 후보로 앞자리를 점유하지 않는다. 이후 조건 충족이 확인되면 그 시점의 후보 순서를 적용한다. 이미 확정된 예약은 보존한다. (권장)
B. 현재 예약 허용 조건을 충족한 미예약 주문 중 원래 OMS 주문 접수 순서대로 배정한다. 먼저 접수됐지만 당시 조건 미충족이었던 주문이 나중에 조건을 충족하면, 아직 배정하지 않은 후보 사이에서는 원래 접수 순서를 기준으로 한다. 조건 미충족 주문이 실제 배정을 받거나 다른 주문의 이미 확정된 예약을 자동 취소하는 뜻은 아니다.
X. Other (please specify)

[Answer]: A. 예약 허용 조건을 충족해 원본 소유자가 후보로 확인·기록한 순서대로 배정한다. 사용자 원문: "1". 먼저 주문했어도 예약 조건 미충족이면 앞자리를 점유하지 않으며 이후 확인된 후보 순서를 적용한다. queue 도착/worker 처리 순서를 업무 배정 순서로 사용하지 않는다. 기존4개 확보 정책·지급/보류·FULL/동의된 PARTIAL과 실제 재고 원본의 원자 예약·이미 확정된 예약 보존을 유지한다. 순서 원본/동률·조건 상실/재진입·다품목/WMS·다른 채널의 구체 모델/검증은 HardwareFulfillment/U5 상세 설계에 연결하며 실제 재고/실거래 보호를 완료했다고 표시하지 않는다.

## Q10. 비동기 작업의 queue와 실패 작업 격리는 어떤 단위로 구성할까요?

SQS Standard와 각 업무 소유자의 원본/실행 책임은 선택됐다. 아래는 실제 비동기 consumer의 전달·재시도/적체/실패를 분리할 물리 queue 구성을 비교하는 질문이며 도메인별 microservice를 추가하는 선택이 아니다. consumer별 원본/처리 표지·권한/버전·불명 결과 대조와 실제 예약 순서는 두 후보 모두 동일하게 유지한다. queue/DLQ만 나눈다고 공유 worker process/DB/IAM의 장애·권한까지 자동 격리되지는 않으므로 실제 실행 자원/연결·서비스 자격/동시성/관측과 함께 검증한다. [S2–S8·W28·W30·W32]

한 사실이 대금·HW·통지 등 여러 업무 consumer의 처리를 필요로 하면 해당 consumer별 전달/처리 원본을 구성해야 한다. SQS에서 같은 queue를 여러 worker가 읽는 구성을 각 업무 consumer 모두에게 확실히 전달하는 broadcast로 가정하지 않는다. 선택한 첫 outbox/SQS 구성에서 consumer/handler 등록·전달 대상·반복/누락 대조를 구현하며 추가 SNS 제품이나 모든 컴포넌트의 network service를 자동 채택하지 않는다. [S7–S9·W28·W32]

A. 비동기 업무 consumer/소유자별 SQS Standard queue와 전용 DLQ를 둔다. 실제 등록된 필요한 업무부터 적용하고 업무별 적체·재시도/불명 대조·재처리·한도/경보를 구분한다. 하나의 Nest worker 코드 기반과 등록된 handler 의미를 유지하면서 실행 자원/자격 분리 필요성은 NFR/Infra에서 검증한다. 수신/실패 원본을 연결하고 queue/DLQ 만료·격리를 접수 유실이나 업무 완료로 해석하지 않는다. (권장)
B. 공통 SQS Standard queue와 공통 DLQ를 사용하고 검증된 dispatcher가 업무 handler로 전달한다. consumer별 처리 표지·권한·자원/재시도/대기 상태와 관측은 공통 queue 안에서도 구분하며 한 업무 적체/실패가 다른 업무를 지연시키는 영향을 시험한다. 일부 handler가 미등록/불명일 때 전체 사실을 성공 처리/삭제하지 않는다. 구성 요소를 줄이지만 업무별 독립 운영/한도·실패 진단은 추가 설계가 필요하다.
X. Other (please specify)

[Answer]: A. 비동기 업무 consumer/소유자별 SQS Standard queue와 전용 DLQ를 둔다. 사용자 원문: "1". 실제 등록된 필요한 업무부터 적용하고 consumer별 전달/처리 원본·반복/누락 대조·권한/버전·불명 결과와 업무별 한도/경보를 유지한다. 공통 Nest worker 코드 기반을 사용할 수 있으나 실제 실행 자원/자격·DB 연결·동시성 분리는 후속 NFR/Infra 검증 대상이다. queue 분리를 완전한 장애/권한 격리나 도메인별 microservice/SNS 도입으로 확대하지 않는다. queue/DLQ 만료·격리는 성공 접수의 삭제/유실 또는 업무 완료가 아니다.

## Q11. DLQ에 격리된 실패 작업의 재처리는 어떻게 시작할까요?

이전 Contract Design Q5 A에서 안전한 일시 기술 실패의 제한된 자동 재시도를 이미 선택했다. 그 정책과 실제 결과 불명·충돌/입력/권한 실패의 무조건 재전송 금지는 그대로 유지한다. 이번 질문은 정상 queue에서의 제한된 자동 재시도 이후 DLQ에 격리된 작업을 다시 처리하는 시점의 운영 방식만 정한다. 결과 불명은 원래 작업 결과 조회/대조를 먼저 수행하고 확인되지 않은 변경을 반복하지 않는다. 두 후보 모두 시스템 자동 복구 시도 시작부터 개발자 업무 메신저/이메일 통지, 실패/수동 판단 필요 시 즉시 긴급 통지를 유지하며 개별 기술 retry마다 새 알림을 무제한 발행하지 않는다. [S4–S8·S14·W33]

두 후보 모두 원래 work/consumer/operation/target·업무 키/정규화 입력·원본 개정/현재 권한/기한과 이미 확인된 효과를 재검증한다. 종료/취소·폐기된 동의/권한·영구 실패·미등록 handler/호환 불명은 재실행하지 않는다. 기술 재처리를 신규 주문·계약 동의/승인이나 새로운 재고 배정으로 만들지 않는다. SQS messageID/수신 횟수는 업무 식별자/누적 재시도 예산이 아니며 재전달/재기동/DLQ 이동으로 업무 기한·누적 한도를 초기화하지 않는다. 선택적 안전 재처리에는 업무 원본과 연결된 검증 경로가 필요하다. SQS의 관리형 DLQ redrive 자체는 이동 중 메시지 선별/수정을 지원하지 않고 이동 메시지의 messageID/enqueueTime을 새로 부여하므로 단독 사용을 OMS 안전성 증거로 삼지 않는다. [S4·S7–S8·W34]

A. DLQ 격리 후에는 권한 있는 기술 운영 담당자가 원인/처리 여부와 재개 조건을 확인하고 대상 작업 또는 검증된 대상 묶음을 지정해 재처리를 시작한다. 소유 업무의 현재 조건·권한/멱등 보호는 실행 때도 확인한다. 격리 전의 안전한 제한 자동 재시도는 유지하고 담당자 판단 필요 시 즉시 긴급 알림을 보낸다. 첫 버전의 실패 원인 구분/추적을 명확히 하는 권장안이며 사람 작업/발생 빈도와 1인 운영 목표 적합성은 시험해야 한다. (권장)
B. DLQ 격리 후에도 등록된 업무별로 검증된 자동 재개 조건을 충족한 안전한 일시 실패만 제한된 자동 재처리를 허용한다. 조건·기한/누적 예산·처리 여부가 확인되지 않거나 소진되면 격리 상태를 유지하고 담당자 확인/긴급 알림으로 연결한다. 무조건/주기적 전체 DLQ 재전송은 금지하며 정상 queue 복귀와 재격리의 무한 순환을 막는다. 자동 재처리 시작도 기존 개발자 메신저/이메일 통지와 연결하고 개별 retry별 무제한 통지는 추가하지 않는다. 운영 개입을 줄일 수 있지만 자동 재개 조건·경합·예산/알림 보호의 구현/검증이 더 필요하다.
X. Other (please specify)

[Answer]: A. DLQ에 격리된 실패 작업은 권한 있는 기술 운영 담당자가 원인·원래 처리 결과·안전한 재개 조건을 확인한 뒤 대상 작업 또는 검증된 대상 묶음을 지정해 재처리를 시작한다. 사용자 원문: "1". 격리 전 안전한 일시 기술 실패의 제한 자동 재시도와 시스템 자동 복구 시작부터 개발자 메신저/이메일 통지·실패/수동 판단 필요 시 즉시 긴급 알림은 유지한다. 실제 결과 불명은 원래 결과 조회/대조부터 수행하고 무조건 재전송하지 않는다. 원래 업무 키/operation/consumer/target·입력/원본 개정·현재 권한/기한·누적 한도와 이미 확인된 효과를 실행 때도 검증한다. 기술 재처리는 새 주문·새 동의/승인·재고 배정이 아니며 SQS messageID/수신 횟수 변경으로 원래 키나 한도를 초기화하지 않는다. 수동 대상 지정도 소유 업무의 현재 조건/권한을 면제하지 않는다. 실제 운영 담당자/접근·명령/보고 경로·발생 빈도와 1인 운영 목표의 실증은 후속 설계/시험 대상이다.

## Q12. 직원 화면·인증·API에 들어오는 접속 경로는 어떻게 구성할까요?

### Q14 측정/설계 근거

SQS long polling은 메시지가 사용 가능해지면 응답하는 수신 후보 방식이며 최대 대기 값은 빈 queue 수신의 설정이다. 이를 매번 그 시간만큼 업무를 늦추는 timer 또는 OMS의 첫 시작/완료 SLO 보장으로 해석하지 않는다. 10초/60초 후보는 이 제품의 접수 후 내부 반응성에 대한 설계 제안이며 실제 relay 주기·queue/worker의 실행/자원·측정 시간과 배포 후 성능은 추가 검증 대상이다. 전체 완료 기한·재시도 총 예산·최장 대기/경보의 구체 값은 별도로 정한다. [S1·S3–S8·W40]

## Q15. DB 논리 손상/오삭제에 대비한 독립 보호 복구 기록은 어디에 둘까요?

성공 접수 데이터 유실0·논리 손상/오삭제도 포함한30분 복구는 이미 정했다. 목표를 다시 선택하지 않는다. 정상적으로 접수한 뒤 원본/작업/이력이 잘못 삭제되거나 과거 시점으로 복원되면 이후 성공 접수·정정/효과·현재 권한 관계를 재구성할 근거가 필요하다. 업무 DB와 같은 삭제/수정 범위에만 있는 outbox나 queue를 이 근거의 독립 보호로 가정하지 않는다. DB 물리 복제/backup·PITR 이름만으로 이 목표를 충족했다고 표시하지 않는다. [S4·S6–S8]

두 후보 모두 PostgreSQL을 정상 업무 원본으로 유지하며 DB 자체의 검증된 내구/복구와 보호된 복구 기록을 결합한다. 필요한 업무 원본/Receipt·이력·작업/사실/효과/소비 표지의 일관된 재구성이 가능한 기록을 보존하고 ACK된 변경의 누락0을 대조한다. 단순 요청 입력/HTTP 로그/queue 메시지만으로 전체 복구 가능성을 가정하지 않는다. 보호 저장 완료가 확인되기 전 성공 접수/완료 응답을 하지 않는 경계를 설계한다. 서로 다른 저장소를 하나의 PostgreSQL transaction으로 묶었다고 표시하지 않으며 원자 원본→커밋/보호 저장 불명→같은 키 대조/안전 재개, 순서·의존 관계·복구 epoch/스키마·외부 실제 효과를 검증한다. 보호 완료 전 조회/소비/외부 효과에서 안전하지 않은 확정을 공개하는 경로도 막아야 한다. 외부 저장이 불가하면 접수/완료를 허위 성공으로 응답하지 않고 기존 오류/불명 대조·가용성 집계를 유지한다. [S4·S7–S8]

A. 업무 DB와 분리한 S3의 버전별 삭제/덮어쓰기 보호 복구 기록을 우선 설계한다. 동일 transaction에 연결한 원래 변경의 완전한 복구 자료를 별도 보호 객체로 저장·대조하고 성공 응답에 필요한 보호 확인을 연결한다. 기록의 암호화·국내 저장·별도 쓰기/복구 자격·잠금/보존/참조와 정정·재구성/중복/순서 대조를 설계한다. 추가 업무 DB를 운영하는 대신 관리형 객체 저장의 보호 기능을 이용하는 조건부 권장안이며 실제 잠금 모드/기간·권한과2초 응답/30분 복구·비용은 검증해야 한다. Object Lock만으로 재구성 가능·ACK 유실0/정확성 달성을 보장하지 않는다. (조건부 권장)
B. 업무 DB와 별도로 보호된 독립 DB 복구 원장을 설계한다. 원래 변경/복구 자료를 별도 원장에 지속 저장·대조한 뒤 성공 응답 조건을 충족한다. 원장 전용 append/복구 자격·수정/삭제 방지·내구/backup·독립 실패 범위와 같은 키/순서/참조·정정/외부 효과 재구성을 검증한다. 같은 업무 schema나 단순 복제본을 독립 보호 원장으로 부르지 않는다. 두 번째 DB의 운영·복제/복구/접근·비용·2초 응답/30분 복구를 추가 검증한다. PostgreSQL/S3 사이 또는 두 DB 사이의 분산 transaction을 자동 채택하는 선택은 아니다.
X. Other (please specify)

[Answer]: B. 업무 DB와 별도로 보호된 독립 DB 복구 원장을 사용한다. 사용자 원문: "별도 보호된 DB 복구 원상 사용으로 간다". 문맥의 "원상"은 앞서 제시한 B의 복구 원장을 가리키는 것으로 기록하며 S3 보호 복구 기록 A는 선택하지 않았다. 정상 업무 PostgreSQL 원본과 분리한 복구 원장에 원래 변경/복구 자료를 지속 저장·대조한 뒤 성공 응답의 보호 조건을 충족한다. 원장 전용 append/복구 자격·수정/삭제 방지·내구/backup·독립 실패 범위와 같은 업무 키/입력/순서·의존/원본·이력·작업/효과/consumer 표지·정정/외부 실제 결과의 재구성을 검증한다. 같은 schema/단순 replica를 독립 보호 원장으로 보지 않고 두 DB 사이 전체 원자성이나 분산 transaction을 자동 보장/채택하지 않는다. 불명 커밋/저장·중복/응답 유실은 같은 원래 식별자로 대조하고 보호 확인 전 허위 성공/안전하지 않은 확정·소비를 금지한다. 실제 두 번째 DB 제품/버전/보호 방식·보존/국내 자격/키/backup·2초 p95 응답/30분 복구/성공 접수 누락0과 1인 운영 적합성은 후속 설계/시험으로 확인한다.

### Q15 기술 근거·미확인 경계

S3 Object Lock은 특정 object version의 덮어쓰기/삭제를 보호한다. 새 version/삭제 marker·보존 기간·governance 우회 권한과 compliance의 보호 범위가 다르므로 원래 version/ref·완전성/정정·보존/파기를 검증해야 한다. 임의 보존 연수·미국 규제 준수·법적 의무를 채택하지 않는다. S3의 성공 PUT/읽기 일관성이 업무 DB와의 원자 transaction이나 복구 자료의 올바른 의미/순서를 보장하지 않으며 암호화 키·저장 접근/수명·복구 처리량·논리 손상/ACK 이후 구간과30분 시간 예산을 따로 증명해야 한다. 구체적인 객체/원장 형식·커밋 순서/보호 확인·필드/계약 매핑은 선택 뒤 상세 설계/호환 검증 대상으로 연결한다. [S4·S6–S8·W41·W43]

RDS의 PITR 문서는 transaction log 업로드와 LatestRestorableTime·새 DB 복원/초기화 조건을 설명한다. 이것만으로 특정 성공 응답의 변경이 독립 저장됐거나 잘못된 변경 뒤의 정상 접수까지30분 내 재구성된다는 증거가 되지 않는다. actual RDS/Aurora 상품·버전/backup 배치·잠금/원장·보존/국내 키 경로는 아직 선정/구축하지 않았다. 기존 보안/데이터 수명·운영·정확성 목표와의 동시 적합성을 시험해야 하며 단순 성능 수치를 맞추기 위해 성공 응답 후로 보호 저장을 미루지 않는다. [S4·S6·W42]

### Q15 조건부 권장 근거 — 선택 전 설명

사용자 원문: "조건부 권장인 이유는 무엇이냐". 이는 당시 권장 근거 요청이며 그 질문만으로 Q15 A/B 선택이나 S3 도입 승인을 기록하지 않았다. 당시 Q15 [Answer]는 비워 두었다. 이후 명시한 B의 독립 DB 복구 원장 선택이 현재 답변이며 아래 S3 설명은 미채택 후보의 비교 이력이다.

- **권장 판단/가정:** 업무 DB의 삭제/수정 범위와 분리한 버전 보호 복구 기록을 관리형 객체 저장에 두면 두 번째 업무 DB engine·복제/유지/업그레이드 구성을 추가하지 않는 후보가 된다. 이는 원본 보존 방식의 적합성에 대한 설계 판단이며 S3 방식의 총 구현/운영 부담·비용이 항상 더 작다는 확인이 아니다. 자료 형식·저장 확인/대조·재구성 코드가 복잡해져 관리 부담이 더 커질 수도 있으므로 현재는 우선 검증할 후보라는 의미다. [S4·S6–S8·W41]
- **보존과 재구성의 구별:** Object Lock이 보호하는 것은 지정한 object version이다. 올바른/완전한 원본·이력/정정·Receipt/작업/효과/consumer 표지·현재 권한/키/외부 실제 결과 관계가 복구 자료에 포함되지 않으면 보호된 파일이 있어도 목표 상태를 재구성하지 못한다. 원래 입력만 재실행해 지급/출고/발급 같은 외부 효과가 중복될 수 있는 경로를 만들지 않아야 한다. 잘못된 변경을 보호 저장에 기록하는 것 자체도 그 내용을 올바르게 만들지는 않는다. [S4·S7–S8·W41]
- **저장 사이 실패의 구별:** PostgreSQL 커밋과 S3 저장 확인은 서로 다른 단계다. DB 성공/S3 실패·불명, S3 성공/응답 유실, 중복/동시 기록·순서 공백을 원래 업무 식별자와 기록 내용/보호 version/ref로 대조한다. 전체 원자성/복구 순서를 S3 단일 key 일관성에서 추론하지 않는다. 보호 확인 전 성공 응답/안전하지 않은 공개·소비를 허용하지 않는 경계와 안전한 재개를 구체화해야 한다. 별도 DB 원장 후보도 이 원자 연동/불명 결과와 보호·복구 검증을 면제받지 않는다. [S4·S7–S8·W43]

### Q15 후속 설계 제안 — 선택한 DB 복구 원장의 구체화

아래는 Q15 B의 책임/실패 경계를 구체화할 설계 제안이며 사용자 답변에 없던 원장 DB engine/제품·분산 transaction 또는 실제 달성 사실을 추가로 선택했다고 표시하지 않는다. 최종 설계 전 요약 확인에 포함하고 실제 구현/배치는 근거와 호환/시험을 확인한다.

- 원장 engine은 별도로 보호된 PostgreSQL을 우선 설계 후보로 검토한다. 정상 업무 DB의 변경/키/개정·관계/재구성 도구와 공통 스택을 이용하면서 실제 저장/자격·실패 범위를 분리할 수 있는지 검증한다. 같은 instance/schema/replica를 이름만 독립으로 바꾸지 않는다. actual AWS DB 제품/지원 버전·배치/backup/국내 자료 경로와 자원/비용은 Infra/코드 선행 확인 대상이다.
- 필요한 정상 쓰기 role과 원장 append·제한 대조 reader·복구 reader·관리/수명 role을 구분한다. 기존 원장 entry의 UPDATE/DELETE/TRUNCATE와 schema/owner·grant 우회를 정상 실행 role에 부여하지 않는다. 같은 원래 키/내용의 반복은 대조하고 다른 내용은 덮어쓰지 않으며 정정은 원래 entry를 참조하는 새 기록으로 보존한다. PostgreSQL owner/superuser는 강한 권한을 가질 수 있으므로 INSERT-only라는 표지만으로 관리자/배포 삭제 보호까지 입증하지 않는다. 실제 role membership/권한·독립 저장·backup/DDL/배포·회수/복구 범위를 시험한다. [W44]
- 순차 지속 저장/대조와 보호 완료 확인 후 성공 응답하는 경계를 우선 구체화한다. 한 논리 transaction의 원본/Receipt/이력/필요 작업·복구 자료를 연결하고, 업무 commit·원장 commit 각각의 불명 결과/응답 유실/중복/동시·순서/참조/스키마 공백을 같은 operation/기록 내용으로 대조한다. 보호 전 공개/소비와 늦은 결과의 최신 상태 되돌림을 막고 정상·복구의 현재 권한/기한/원래 키/외부 효과를 보존한다. 두 DB의 자동 전체 원자성/2PC를 가정하지 않으며 원장 기록의 완전성과 ACK된 접수의 재구성 가능한 연속 경계를 코드 전 상세화한다.
- 2초 응답·30분 복구·성공 접수 누락0/8영역 정확성·1인 기술 운영과 보관/파기는 그대로 검증한다. 요청/HTTP 로그만 재실행하는 복구나 snapshot 이후 정상 변경 삭제·옛 grant/외부 효과의 잘못된 재적용으로 목표를 맞춘 것으로 처리하지 않는다. [S1–S8]

## Q20. 복구 원장만 일시 중단됐을 때 서비스는 어디까지 유지할까요?

Q15 B로 업무 DB와 분리한 보호 복구 원장을 선택했다. 성공 접수 유실0 목표에 따라 필요한 복구 자료의 보호 완료를 확인하기 전에는 해당 업무 변경을 성공으로 응답하거나 보호되지 않은 변경을 확정·소비하지 않는다. 이 질문은 업무 DB·신원/현재 권한 검증은 정상이고, 복구 원장에만 일시 연결/저장 장애가 생겼음을 확인한 경우의 사용자 제공 범위를 정한다. 논리 손상·업무 DB/권한 검증 불명은 정상으로 가정하지 않는다. [Q15 B·S2·S4·S7–S8]

B. 고객/직원 업무 전체를 점검 상태로 전환한다. 안전한 조회를 제공할 수 있더라도 업무 화면의 조회·변경을 함께 일시 제한하고 안내 화면을 제공한다. 사용 가능한 범위는 줄어들지만 장애 중 화면 운영 정책을 단순화한다. 독립 운영 감지/알림·복구 경로는 유지한다.
X. Other (please specify)

[Answer]: A. 안전한 조회는 유지하고 복구 보호가 필요한 변경은 일시 제한한다. 사용자 원문: "1". 업무 DB·신원/현재 권한·직원망·자료 정합성이 정상임을 확인한 경우만 허용된 조회를 제공한다. 주문 접수·상품/계약 등 보호 필요한 변경은 보호 완료 전 성공 응답/접수 완료로 표시하지 않으며, 새 외부 효과의 보호/중복 방지를 확인할 수 없는 worker 작업은 대기/대조로 보존한다. 불명 commit/보호 결과는 원래 키/입력·결과로 대조하고 이미 ACK된 자료/작업을 삭제하거나 새 요청으로 바꾸지 않는다. 현재 권한/망/정합성 확인 불가 시 조회도 거절하며 회수/접근 차단의 즉시 효력 요구를 유지한다. 재연결 후 누락/불명·순서/참조·보호 경계/최신 권한을 검증해 재개한다. 일부 조회 제공을 전체 가용성/복구 완료로 집계하지 않고 막힌 핵심 흐름의 중단·Q17 A/Q18 B 알림/RTO·정확성을 별도 기록한다. 실제 장애 구분/차단·재시도/대조/재개 경로의 구현/성공을 가정하지 않는다.

### Q20 공통 실패·보안·복구 조건

두 선택 모두 원장 보호를 건너뛰어 접수 유실0 목표를 낮추거나 HTTP 성공/접수 완료로 표시하지 않는다. commit/보호 확인의 응답이 불명인 원래 요청은 같은 키/입력·원래 결과를 대조하고 무조건 새 요청/재실행으로 바꾸지 않는다. 이미 ACK된 자료/작업은 보존하며 새 외부 효과의 안전한 보호/중복 방지를 확인할 수 없으면 실행을 보류한다. queue/worker의 중단을 작업 원본 삭제나 실제 완료로 처리하지 않는다. [S4·S7–S8·Q2 B·Q10 A·Q11 A·Q15 B]

실패 범위를 검출/격리하고 원장 재연결 뒤 누락/불명·순서/참조·보호 경계를 대조한 후 필요한 처리를 재개한다. 자동 시도 시작·수동 필요/새 실패·복구 결과 통지와 Q17 A·Q18 B를 유지한다. 기능을 일부 제공한 것을 전체 가용성/복구 완료로 집계하지 않고, 실제 막힌 접수 등 핵심 흐름의 중단과 RTO/정확성 검증을 각각 기록한다. 구체적인 circuit breaker/제한 재시도·대조/재개 조건과 실증은 후속 설계에 포함한다. [S4–S6·Q17 A·Q18 B·Q19 C]

### Q21 확장·자원·실패 경계

자동 확장은 하나의 수단이며 DB/외부 병목이나 복구 원장 장애를 replica 수 증가만으로 해결한다고 가정하지 않는다. [S3–S4·S7–S8·Q2 B·Q8 A·Q10 A·Q15 B·Q20 A]

HTTP20req/s를 job20개/s로 전용하지 않고 fanout/예정 작업·relay/consumer별 profile을 고정한다. CPU/연결/lock·DB/외부 부하·retry/lease와 queue 대기를 함께 관측해 API와 worker의 자원 경쟁을 제한한다. [S1·S3–S6·Q14 A]

[W50·S2–S6·Q12 A]

### Q22 분류·복구·파기 경계

## Q23. PostgreSQL 접근 도구는 무엇으로 할까요?

SQL·migration/DB 타입 매핑을 직접 관리할 책임이 있다. SQL 제어를 이유로 제시했던 최초 우선 권장은 아래 사용자 질의/근거 재검토 후 철회했다. (초기 권장 비교 이력; 미채택)

### Q23 SQL 문법·실무 사용 질의와 권장 재검토

[S4·S6–S8·W53–W54·W57]

### Q23 TypeORM과 pg의 역할 구분 — 선택 전 설명

사용자 원문: "TypeORM 과 pg 차이". 이는 역할 비교 요청이며 TypeORM이나 pg 단독 사용의 선택이 아니다. 이 질의 시점에는 미응답이었고 이후 실제 선택은 위 [Answer]에 기록했다.

pg(node-postgres)는 Node.js에서 PostgreSQL에 연결해 SQL/parameters를 보내고 결과를 받는 driver이며 연결 pool/type 처리 등을 제공한다. TypeORM은 그 위에서 entity/repository·관계 매핑/query builder·migration과 transaction 문맥을 제공하는 ORM이다. TypeORM의 일반 postgres driver 구성에는 pg를 설치해 사용하므로 둘은 서로 다른 계층이며 TypeORM을 선택해도 pg를 함께 사용한다. 여기서의 비교 대상은 pg를 직접 사용해 SQL/매핑/수명/transaction 절차를 관리할지, TypeORM을 통해 기본 업무 접근을 구성할지다. [W53–W54·W58–W59]

pg 직접 사용의 transaction은 동일 client에서 BEGIN/COMMIT/ROLLBACK과 관련 query·rollback/release를 관리한다. TypeORM의 transaction은 제공된 EntityManager/QueryRunner 안에서 모든 관련 query를 수행한다. TypeORM 안에서 필요한 SQL은 같은 transaction 문맥으로 실행하고 별도 pg Pool/client를 열어 원자 기록을 분리하지 않는다. SQL 제어와 query/DB 타입 변환·schema/migration·현재 권한/원래 키/Outbox·복구 보호의 책임은 도구 선택에 맞게 명시한다. pg가 언제나 더 빠르거나 TypeORM이 자동으로 정확성을 보장한다는 주장은 하지 않는다. 실제 ORM/driver 버전·연결/driver 범위와 지원 조합은 코드 전 확인한다. [W51·W53·W57–W59·S4·S6–S8]

### Q23 공통 경계·지원 근거

세 후보 모두 실제 transaction 문맥 안에서 모든 관련 쓰기/조회와 권한/expectedRevision·멱등 키/consumer 보호를 수행하도록 설계/시험한다. 개별 save 또는 callback만 감싸고 다른 연결/전역 repository로 기록을 분리하지 않는다. DB transaction 중 외부 지급/출고/메일을 실행하거나 commit 후 내구 Outbox 없이 전송하지 않는다. 별도 보호 원장 DB와의 순차 저장/보호 확인·불명/순서/참조/재구성은 별도 경계이며 동일 library 사용으로2PC나 전체 원자성을 주장하지 않는다. 원장 engine은 Q15 B의 별도 DB 선택과 설계 후보를 따르며 이 질문으로 실제 AWS DB 제품을 선정하지 않는다. 금액/날짜/NULL·stable ID/revision/조직 문맥과 canonical JSON Schema2020-12를 명시 매핑한다. 생성된 DB 타입이나 ORM entity를 전송 schema/runtime validation·현재 업무 권한으로 대신하지 않는다. 실제DB schema/migration/type와 code/consumer·대기 원본/복구 format의 호환을 검증하며 자동 schema 동기화로 운영 원본/이력/키를 삭제하는 전환을 사용하지 않는다. 짧은transaction·pool/statement/lock 대기/누적deadline과 API/worker 합산 연결 상한은 코드/시험 전 고정한다. 문서 조사 시 Prisma 공식 transaction 설명은 ORM8을 다루고 Nest의 Prisma recipe는 ORM7을 다룬다. TypeORM 최신 문서도1.0을 안내한다. 후보 이름 선택을 해당 최신major/예제 API 또는 Nest integration 호환 확인으로 해석하지 않는다. 지원/보안·driver/ORM·runtime/migration의 실제 조합과 exact versions·lockfile은 Code Generation 전 고정하고 격리 시험한다. 이 질문에서는 package를 설치하거나 실제 commit/내구/성능/복구를 시험하지 않았다. [S6·W52–W54]

## Q29. 조회·변경 HTTP 요청의 전체 응답 대기 상한은 얼마로 둘까요?

이미 승인된 정상 부하의 조회p95 1초/변경p95 2초는 유지한다. 이번 질문은 비정상 지연 때 브라우저가 한 요청의 전체 응답을 얼마나 기다릴지 정하는 최대 대기 정책이다. ND-OQ03–04와 FD-OQ1/4/6의 실제 deadline/timeout 값은 아직 미정이다. 아래 수치는 첫 버전 설계 제안이며 기존 승인값이나 AWS가 정한 기준이 아니다. [S1·S4·S6–S8]

A. 조회 최대5초·변경 최대10초를 전체 응답 대기 상한으로 둔다. 정상 목표보다 여유를 두면서 장애 때 긴 대기/동시 자원 점유를 제한한다. (권장)
B. 조회 최대10초·변경 최대20초로 둔다. 지연 응답을 더 기다리는 대신 장애 안내와 자원 회수까지의 대기 부담이 늘어난다.
X. Other (please specify). 원하는 조회/변경 전체 대기 상한을 설명한다.

[Answer]: A. 조회 최대5초·변경 최대10초를 한 HTTP 요청의 전체 응답 대기 상한으로 둔다. 사용자 원문: "1". 정상 부하의 조회p95 1초/변경p95 2초와 주요 화면 최초 표시p95 3초는 유지한다. 브라우저·Next BFF·Nest·DB/독립 보호 원장 및 필요한 동기 호출에 같은 전체 예산의 잔여 기한을 배분하고 단계/재시도마다 다시 시작하지 않는다. 변경 timeout/연결 종료/취소 시도는 미접수·rollback·효과 없음의 증거가 아니므로 원래 ID/멱등 키·정규화 입력과 실제 원본 결과를 대조하며 불명은 접수 확인 필요로 안내한다. 성공 ACK 전 필수 접수/이력/작업·복구 보호와 이후 원본/확인된 효과의 보존을 유지한다. 개별 HTTP 상한을 사람의 MFA 입력/업무 검토·배송/설치/SW 제공 전체 완료나 이미 접수된 비동기 작업의 기한으로 전용하지 않는다. 실제 단계별 연결/대기/취소·시계/지원 제품·늦은 결과/부하/정확성 검증과 목표 달성은 미검증이다.

### Q29 정상 목표·전체 기한·불명 결과와 원본 보호의 경계

브라우저 요청 시작부터 전체 응답까지의 하나의 예산을 Next BFF·Nest·업무 DB/보호 원장과 필요한 동기 호출의 잔여 기한에 배분한다. 각 단계/재시도마다 상한을 새로 시작하지 않는다. 연결/대기·query/lock·provider 호출/응답 전송과 취소/정리의 실제 상한·시계/전달 경로/지연 여유는 지원 제품·실측을 확인해 코드 전에 고정하고, 외부에서 보낸 deadline/header를 믿어 서버 한도를 늘리지 않는다. 최대 대기 상한을 정상p95 목표나 Q16 A의 최초 업무 화면 표시p95 3초를 완화하는 근거로 사용하지 않는다. [S1·S3–S4·S6–S8]

변경 요청의 timeout/연결 종료/취소 시도는 미접수·rollback·외부 효과 없음의 증거가 아니다. 원래 request/operation ID·멱등 키/정규화 입력과 원본 결과를 대조하고 결과가 확인되지 않으면 접수 확인 필요/불명으로 안내한다. 새 ID로 무조건 재제출하거나 이미 진행 중인 효과를 반복하지 않는다. 늦은 결과도 같은 원래 요청·현재 권한/개정에 연결해 확인하며 실제 HTTP 상태/RFC9457 오류·trace와 확인된 실패/불명을 구별한다. [S4·S7–S8·W33]

업무 DB의 접수/이력/필요 작업·발행 원자 기록과 Q15 B의 필요한 독립 복구 보호가 확인되기 전에 성공 ACK/Receipt.ACCEPTED를 보내지 않는다. HTTP 대기 만료 뒤에도 성공 접수한 원본/이력/작업·확인된 효과를 보존하며 같은 ID로 대조/재개한다. 이미 접수된 비동기 작업의 실제 수행 기한/누적 재시도 예산은 WorkItem/ApprovedOperation의 별도 기한으로 설계한다. HTTP10초/20초 만료를 전체 주문 취소나 지급/배송/제공 완료 기한으로 전용하지 않는다. [S4·S7–S8·Q2 B·Q11 A·Q15 B]

사람의 MFA 입력/검토·물리 배송/설치·SW 제공 전체 완료 시간은 개별 HTTP 대기 상한과 구분한다. 실제 제출되는 API 요청에는 검증된 기한/현재 권한을 적용하고 안전한 재조회/같은 원래 명령의 제한 재시도도 기존 총량/기한을 따른다. 실패/timeout을 성공 응답이나 새 타이머로 감추지 않으며 부하·lock/저장 장애·응답 유실·늦은 commit/중복·취소 불가 사례에서 접수 보호/효과/권한과 사용자 안내를 함께 검증한다. 구체 외부 제공자의 기한/대조 기능·실제 연결/운영과 목표 달성은 아직 미검증이다. [S1–S4·S6–S8·W33]

## Q30. 비동기 작업의 안전한 일시 실패는 얼마나 자동 재시도할까요?

기존 Q11 A/Contract Q5는 안전한 일시 기술 실패만 제한 자동 재시도하고, 한도 초과/재개 불가 작업은 원본을 보존해 담당자가 확인하도록 한다. 이번 질문은 짧은 내부 처리/외부 요청 시도의 공통 기본 횟수와 시간 예산을 정한다. 전체 주문·배송·설치/SW 제공 완료 시간이나 Q29의 HTTP 응답 대기 상한을 정하는 질문이 아니다. 수치는 이 OMS의 첫 설계 제안이며 외부 제공자 지원이나 AWS 기본값을 채택/확인한 것이 아니다. [S4–S8·S14·Q11 A·Q29 A·W33·W66]

A. 최초1회 + 추가 최대3회, 첫 실제 시도 시작 후 최대5분을 자동 실행 구간의 한도로 둔다. 개별 시도는 최대30초이고, 재시도 대기에는 각각0–5초/0–20초/0–80초 범위의 무작위 지연을 적용한다. 성공/안전 조건 상실·횟수/시간 상한 도달 시 더 실행하지 않고 실제 결과/원본을 보존해 필요한 대조·격리/담당자 확인으로 연결한다. (권장)
B. 최초1회 + 추가 최대5회, 첫 실제 시도 시작 후 최대15분으로 둔다. 개별 시도는 최대30초이고 대기 범위는0–5초/0–20초/0–80초/0–300초/0–300초이다. 같은 안전 조건/보존과 대조·격리 기준을 유지하며 자동 회복 기회를 더 주는 대신 적체/재시도 부담이 늘어난다.
X. Other (please specify). 원하는 추가 횟수/전체 시간·개별 시도/대기 상한을 설명한다.

[Answer]: A. 비동기 작업의 안전한 일시 실패는 최초1회+추가 최대3회, 첫 실제 시도 시작 후 최대5분을 자동 실행 구간의 한도로 둔다. 사용자 원문: "1". 개별 시도는 최대30초이며 추가 대기는0–5초/0–20초/0–80초 범위로 무작위 분산한다. 원래 업무 기한/현재 권한/원본 개정·실행 허가와 실제 멱등/효과 없음 확인을 우선하며 결과 불명은 같은 원래 ID/키로 대조부터 수행한다. SDK/queue/상위 retry의 중첩·재기동/새 메시지로 시각/횟수 초기화를 금지하고 모든 실제 호출/대기를 잔여 예산과 지속 시도 기록에 연결한다. 한도/안전 조건 상실 뒤에도 원본/접수/이력·확정 효과/미해결 작업을 보존해 대조·격리/담당자 확인으로 연결한다. 수동 재개는 Q11 A의 대상 지정/원인·원래 결과·현재 기한/권한/안전 조건 확인이 필요하다. 전체 배송/설치/SW 제공 완료나 HTTP 상한으로 전용하지 않고 Q17–18의 자동 복구 시작 통지/필요한 수동 병행과30분 복구 예산을 유지한다. 실제 SDK/외부 지원·기한/횟수/부하/복구와 격리·대조/목표 달성은 미검증이다.

### Q30 안전 판정·원래 기한·시도 기록과 격리의 경계

일시 오류라는 이름만으로 재전송하지 않는다. 부작용 없이 실패가 확인됐거나 실제 제공자의 검증된 멱등 지원과 원래 결과 대조로 재시도의 안전함을 확인한 경우에만 실행한다. 외부 지급/예약/배송/발급 등 결과 불명은 먼저 같은 원래 operation/키로 조회·대조한다. 권한 회수/입력 오류·업무 거절/새 동의 필요·버전 충돌·provider 기능 미확인은 기술 retry로 우회하지 않는다. 개별 시도의 timeout/취소 시도 또한 실제 효과 없음의 증거가 아니다. [S2·S4·S7–S8·W33]

기한은 최초 구간 시작/원래 WorkItem·ApprovedOperation 기한과 현재 권한/원본 개정·실행 허가에 연결한다. 기다림/queue 지연·lock/연결/실행/정리와 SDK의 실제 하위 재시도도 같은 잔여 예산·횟수 한도 안에 포함한다. Nest/SDK/queue 각 층에서 독립 retry를 중첩해 호출 수를 곱하지 않는다. 안전한 지연/Retry-After를 지킨 다음 시도가 기한에 맞지 않으면 실행하지 않는다. 업무별 provider 제약/호출 범위가 공통값에 맞지 않으면 handler 등록/해당 코드 전 별도 제한 정책·실제 근거를 검토하며 조용히 기본값을 늘리지 않는다. [S3–S4·S6–S8·W66]

시작/attempt·notBefore/deadline·실제 결과/오류·원래 ID/입력·consumer/현재 허가·누적 호출/재시도와 격리 근거를 원본에 지속 기록한다. 재기동/배포·중복 송달/새 SQS message ID나 visibility 만료로 최초 시각/횟수를 초기화하지 않는다. 동일 작업의 원자 실행 권위/lease·효과/처리 표지 보호를 유지하고, queue 수신 횟수를 실제 업무 실행 횟수와 같다고 가정하지 않는다. DLQ 전송이 불명/실패해도 접수/미해결 작업을 삭제하거나 완료로 바꾸지 않는다. 실제 자동 구간의 종료와 필요한 격리/대조 상태를 지속 보존한다. [S4·S7–S8·Q2 B·Q8 A·Q10 A·Q11 A·Q15 B]

추가 수동 실행은 기존 Q11 A의 원인/원래 결과·현재 권한/기한/안전 조건 확인과 대상 지정 승인이 필요하다. 새 자동 구간/재개 예산을 명시할 때도 원래 업무 ID/입력·전체 시도 이력·확정 효과와 원래 업무 기한을 보존하고 새 주문/승인으로 가장하지 않는다. 시스템 자동 복구 시도 시작 통지와 Q17–18의 발생 시각 기준 감지/긴급/수동 대응/30분 복구 예산은 유지한다.15분 자동 구간을 선택하더라도 필요한 수동 병행 대응을15분까지 미루지 않는다. 개별 기술 retry마다 새 알림을 무제한 생성하지 않는다. [S4–S5·S7–S8·Q11 A·Q17 A·Q18 B]

정상/집중 부하에는 실제 재시도/원본 대조·DB/원장/queue/provider 호출·trace/알림을 포함한다. 실제 SDK/driver/제공자의 지원과 설정·취소/늦은 응답·중복/다중 worker·재기동/초과/격리 실패를 시험하며, 이 기본값 선택만으로 안전한 외부 효과/5분 또는15분 자동 회복·RTO/RPO/비용/1인 운영 달성을 주장하지 않는다. Q14 A의 첫 시작p95 10초와 Q29 A의 조회5초/변경10초 상한·정상 p95는 유지한다. [S1·S3–S8·Q14 A·Q21 A·Q27 A·Q29 A·W66]

## Q31. 외부 연동이 연속 실패하면 신규 호출을 잠시 멈출까요?

Q30 A는 원래 작업 하나의 제한 재시도이고, 이번 질문은 여러 요청/작업이 같은 장애 의존성을 계속 호출하는 것을 제한하는 회로 차단(circuit breaker) 정책이다. 업무 소유자가 등록한 실제 외부 adapter의 제공자/접점·operation 종류별 경계를 대상으로 한다. 실연동이 없는 provider를 연결됐다고 가정하거나 전체 OMS를 하나의 회로로 묶는 질문이 아니다. 다음 수치는 첫 설계 제안이며 공식 문서가 OMS에 지정한 기준이 아니다. [S3–S8·Q10 A·Q21 A·Q30 A·W33·W66–W67]

A. 30초 안에 연속5회 재시도 가능한 기술 실패/timeout이 확인되면 해당 외부 접점의 신규 호출을30초 제한한다. 이후 부작용 없는 검증된 확인 호출1개만 허용해 회복을 확인하고, 성공하면 검증된 동시성 상한 아래 호출을 재개하며 실패하면 다시 제한한다. 확인 수단/현재 권한·실행 근거가 없으면 부작용 명령을 probe로 대신 실행하지 않고 대조/담당자 확인을 유지한다. (권장)
B. 첫 버전에는 자동 회로 차단을 두지 않는다. 기존 deadline·제한 재시도·접점별 동시성/총량 상한·경보와 원본 대조/담당자 확인을 적용하고, 연속 장애에도 그 범위 안에서 개별 호출을 시도한다.
X. Other (please specify). 원하는 차단 조건/대기/회복 확인 정책을 설명한다.

### Q31 차단 범위·현재 권한·실행 허가와 회복 확인의 경계

## 설계 문서에 반영할 구체화 제안

아래는 사용자 답변을 연결한 설계 제안이다. 이전 답변에 없던 구현 세부사항을 이미 사용자가 선택했다거나 구현/검증이 끝났다고 표시하지 않는다. 이 제안과 미확인 항목을 함께 요약 확인한 뒤7개 설계 산출물의 패턴/필드·수명/실패/검증 경계로 상세화한다. [S1–S8]

- **업무 원본과 복구 보호:** 업무 PostgreSQL은 상태/접수의 권위이고 별도 보호 PostgreSQL은 독립 복구 원장의 우선 설계 후보로 둔다. primary transaction에 업무 변경·Receipt·이력·필요 Work/Fact/Outbox와 완전한 복구 후보를 함께 기록하고, commit 후 같은 원래 키/내용으로 독립 원장에 지속 저장·대조한다. 원장은 HTTP 입력 재실행 목록이 아니라 변경 원본/개정·참조/전후 관계/삭제 marker·접수/작업/소비 표지/확정 또는 불명 외부 효과를 재구성하는 자료다. raw password/MFA/복구 코드·provider token 등을 복구 payload로 복제하지 않는다. 둘의 commit을 하나의 자동 분산 transaction/2PC로 부르지 않는다. [Q2 B·Q15 B·Q23 C·S2·S4·S7–S8]
- **순서와 보호 완료 경계:** 복구 epoch별 커밋 순서는 짧은 primary transaction의 잠금된 순번 원본 갱신으로 부여하고 그 transaction의 복구 후보에 저장한다. 단순 timestamp/nextval/queue 도착 순서를 commit 순서로 대체하지 않는다. 순서/참조 의존성이 끊기지 않고 독립 원장에 보호된 연속 경계까지만 성공 ACK·업무 결과 공개/후속 작업 발행·외부 실행의 근거로 허용한다. 보호 전 버전을 노출하지 않도록 원본 버전과 보호된 가시성을 분리한다. 미보호 권한 회수/무효화는 이전 grant 사용으로 허용하지 않고 판정 불가/차단으로 반영한다. 같은 키/내용은 대조하고 다른 내용은 충돌이며 원장 기존 entry 수정으로 정리하지 않는다. 모든 쓰기 경로가 이 원본/가시성 경계를 적용하는지 코드/동시/장애 시험으로 확인한다. 순번/보호 경계의 경합과 앞 기록 장애에 따른 쓰기 중지는 공통 장애 범위/성능 시험에 포함한다. [Q15 B·Q20 A·S1–S4·S7–S8·W44·W69]
