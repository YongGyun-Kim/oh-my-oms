# U4 보안·정확성 상세 설계

## 목적과 범위

[확인한 방향](nfr-design-questions.md)의 Looks correct에 따라 [U4 NFR 요구](../nfr-requirements/security-requirements.md)와 [기술 적용](../nfr-requirements/tech-stack-decisions.md)을 구체화한다. 기존 Nest API/standalone worker·TypeORM/PostgreSQL·별도 보호 DB·Outbox/별도 큐를 재사용하는 library 설계다. 새 금융 서비스·AWS 계정·분산 잠금·파일 업로드·OCR·외부 URL 수집·금융망 실행을 추가하지 않는다.

아래 SD01–SD11은 구현·검증할 설계 의무이며 문서만으로 U4 코드/SQL/복구·금융 원본 검증의 완료를 주장하지 않는다. 실제 진행 상태는 코드 생성 기록과 구분한다. 기능 설계 R-03은 보완된 WF4.7·상태표·VS4.16/17과 추가 검토에서 해소됐으며, 여기서는 그 기준을 같은 트랜잭션·보호 기록 경계에 연결한다. 환불 구현·실행 시험은 아직 미완료다. [S1–S5]

## Authentication and Authorization

### SD01

**현재 신원·행위·대상·원본 개정 확인.** U1/U2의 검증된 세션/MFA·audience·기업 이용/조직 정책과 현재 행위 권한을 사용한다. 기존 직원 유휴15분/고객30분·절대8시간과 origin/CSRF·세션 무효화를 재사용한다. STAFF 진입은 실제 내부망/승인 원격 접점의 신뢰 근거를 요구하며 클라이언트 헤더·URL·화면 폭을 근거로 승격하지 않는다.

명령은 입금, 대상 주문, 모든 청구, 정정 전후 주문, 환불 승인/원래 거래의 기업·조직·소유자/개정을 대조한다. 쓰기 직전 같은 보호 트랜잭션 문맥에서 현재 접근·계약/승인·계획·요청 개정을 다시 검증한다. 현재 호스트의 in-process 원본 포트는 그 트랜잭션에 결합된 읽기를 제공해야 하며, 별도 연결의 오래된 조회 결과를 현재 근거라고 사용하지 않는다. 금융 소유자는 다른 소유자의 원본을 직접 수정하지 않는다.

계약/약정 변경은 U3의 다른 사람 승인과 필요한 동의를 통과한다. 입금 등록 권한으로 약정/제공 전 필수 여부를 수정하지 못한다. 신원·동일인·망/원본 근거가 미확인/조회 실패이면 관련 처리를 보류한다. 실제 신뢰와 기존 U2 위험이 문서로 해소됐다고 표시하지 않는다. 적용: NFR1.1–NFR1.4, NFR5.3, NFR9.2.

### SD02

**허용 원본에서 파생 조회를 구성.** 고객 금융 조회는 해당 행위/기업·조직의 청구·지급 상태/잔액·허용된 이력만 반환한다. 목록 필터·페이지·합계·상세·정정 이력의 조회 조건을 서버에서 구성하며 전체 자료를 받아 UI에서만 숨기지 않는다. 허용 부분의 합계를 기업 전체 합계라고 표시하지 않는다. 일반 고객 응답에 은행 원본·계좌·내부 문서/실제 거래 참조를 포함하지 않는다.

실제 거래 유일성 검사는 기업을 넘어 수행해야 하지만 오류 응답의 대상 권한을 넓히지 않는다. 충돌 시 다른 기업의 존재·식별·금액·계좌·주문을 반환하지 않고 안전한 대조 필요 코드만 제공한다. 권한 있는 내부 대조 경로만 원래 근거를 볼 수 있다. 업무 조회는 기존 ProtectedStore의 현재 epoch/확인된 protected prefix에 결합한다. 단순 primary 최신 행만으로 보호 완료/공식 결과를 구성하지 않는다. 세션/기업별 민감 응답에 공용 캐시를 사용하지 않고 기존 cache-control·보안 헤더를 유지한다. 적용: NFR1.2, NFR1.5, NFR11.2.

## Input and Evidence Protection

### SD03

**두 단계 입력 경계.** U4 HTTP 명령은 일반 JSON64KiB(65,536바이트)를 사용하며 U3 주문 제출/조건 변경 전용1MiB parser로 보내지 않는다. 실제 읽은 본문 크기를 제한하고 Content-Length 주장만 믿지 않는다. 현재 U3 소유자 등록 호스트의 압축 본문 거절 경계를 유지한다. 압축 입력을 지원하는 구성으로 바뀐다면 압축 해제 후 동일 상한을 적용하기 전 허용하지 않는다. parser 중복 적용이나 파일 업로드 전환은 없다. 본문 초과는413, JSON 외 입력은415, 필드/건수 위반은400의 안전한 입력 오류로 전체 거절한다.

런타임의 닫힌 U4 스키마에서 명칭1..100자·필수 설명/정정 사유1..2000자·문서/거래 참조1..256자, Unicode code point 기준으로 검증한다. 선택 필드는 생략 가능성만 명세하고 빈 필수값을 자동 채우지 않는다. 한 배분 명령은 서로 다른 청구1..100건이며 같은 주문이어야 한다. 중복 항목은 자동 합치지 않는다. char 한도·건수·전체 byte 한도를 독립 검사하며 초과를 자동 절삭/분할/부분 반영하지 않는다. 명칭은 계약금/중도금/잔금 enum으로 제한하지 않는다.

금액은 기존 KRW 정수 문자열 형식을 사용하고 BigInt로 계산한다. 소수·음수·잘못된 표현·길이 범위 초과는 거절한다. 기존 Money의 유한 문자열 길이와 합계/차감 결과의 직렬화 범위도 확인하며 허용 범위에 못 담는 합계를 반올림하지 않는다. 금액을 JS Number나 고정 소수 열로 손실 변환하지 않는다. 실제 저장은 기존 Money JSON/정수 문자열 경계에 맞추고 합계는 정확 정수로 비교한다. 적용: NFR5.2, NFR7.1–NFR7.2, NFR12.1.

### SD04

**기존 증빙 보관처 참조와 최소 출력.** OMS에는 원본 문서/거래 참조·확인자·확인 시각·필요 요약과 원래 업무/정정 관계만 저장한다. 참조는 데이터이며 코드·HTML·자동 HTTP 요청으로 실행하지 않는다. 고객 업로드·OCR·원문 파일 다운로드 프록시를 추가하지 않는다. 임의 증빙 주소를 C00의 허용 업무 원본 Ref로 위장하지 않는다. 실제 source profile·원본 접근·신뢰가 확보되지 않으면 REVIEW 자료와 확인된 입금을 구별한다.

원문·전체 계좌·입금자/개인 정보·문서/거래 참조·근거 요약·토큰/세션을 일반 로그/추적/오류/Slack/이메일에 직렬화하지 않는다. 관측용 내부 operation/correlation과 안전한 결과 코드를 별도 투영한다. 실제 기록/보호 원본에는 필요한 최소 정보만 접근 제한·보호된 전송/저장으로 보존한다. 기존 보관처와 OMS의 주/보호 저장·로그·백업·외부 처리 경로의 국내 저장은 실제 근거로 확인한다.

자료별 보존/삭제·적용 의무·원본 보관처 접근을 실데이터 전에 확인한다. 임의 법정 연수를 만들지 않고, 삭제/정정 정책과 거래 중복 보호의 충돌은 확인된 정책으로 해결한다. 원래 거래의 식별 예약/정정 관계를 일반 삭제로 해제하지 않는다. 적용: NFR11.1–NFR11.4, NFR14.1–NFR14.2.

## Transaction and Durable Acceptance Design

### SD05

**업무 식별 예약의 물리 보호.** 요청 키와 실제 거래 식별은 별개다. source profile이 검증한 수취 원본의 안정 namespace와 원래 거래 식별/별칭을 정규 PaymentEvidence에 연결한다. 기업·주문·직원·요청 UUID·채널·profile 버전은 유일성 key에 넣지 않는다. 원본 포맷 확보 전 은행별 정규화/식별 산식을 임의 구현하지 않는다.

아래는 물리 migration에서 구현할 제약/기술 기록의 논리 명세이며 기존 테이블이 이미 이 제약을 갖췄다는 뜻이 아니다. 기술 예약은 별도 사업 엔티티/서비스가 아닌 U4 소유의 보호 가능한 보조 기록이다.

| 보호 대상 | 유일 키/제약 | 변경·복구 의미 |
| --- | --- | --- |
| 실제 입금 식별/별칭 예약 | 검증된 source namespace + canonical identity의 안정 key, NOT NULL + UNIQUE; 하나의 canonical payment에 결합 | 최초/이전 별칭을 보존. 정정/취소 뒤에도 같은 실제 입금 재등록 차단. profile 개정은 구/신 별칭을 같은 변경에서 예약하며 다른 canonical payment에 충돌하면 대조 |
| 입금당 현재 주문 연결 | canonical payment ID를 PK로 하는 단일 현재 binding | 미연결 또는 주문 하나. 연결 변경은 원래/새 주문의 권한·순배분/예약/이행 영향 해소 후 원자 변경. 과거 연결 이력 유지 |
| 현재 지급 의무의 청구 | order ID + 불변 obligationKey의 단일 현재 invoice binding | plan revision·invoice ID를 유일성 차원에 넣어 같은 의무를 복제하지 않음. 재발행은 원래 정정 연결과 옛 청구 비활성/현재 pointer를 같은 변경에서 갱신 |
| 실제 환불 결과 식별 | 검증된 원래 금융 작업/실제 결과의 안정 key, NOT NULL + UNIQUE; 하나의 원래 환불 부분/작업에 결합 | 동일 결과를 다른 RefundCase/요청으로 중복 확정하지 않음. 높은 확인 개정의 정정은 원래 작업을 갱신하며 옛 식별을 해제하지 않음 |

길 수 있는 정규 identity는 기존 canonical encoding/fingerprint 방식의 고정 길이 key와 검증용 정규 원본을 함께 보존하는 방향이다. 같은 key에 서로 다른 정규 원본이면 자동 병합하지 않고 충돌/대조한다. fingerprint 자체를 비밀 암호화나 실제 거래 확인 증거로 보지 않으며 외부 오류/로그에 노출하지 않는다. 실제 profile의 namespace/정규화 호환성은 실거래 전에 확인해야 한다.

유일 제약의 NULL 우회가 없도록 필수 key를 NOT NULL로 둔다. 같은 입금의 새 등록이 원래 canonical payment를 재사용하도록 하고, 단순 새 PaymentEvidence ID 발급으로 binding 제약을 우회하지 못하게 한다. 제약 위반을 자동 다른 key로 재시도하지 않는다. 현재 권한으로 원래 결과/대조를 반환한다. 적용: NFR4.2, NFR5.1, NFR5.5, NFR1.5.

### SD06

**같은 원금과 한도를 소비하는 변경의 직렬화.** U4의 모든 쓰기/정정/사실 반영은 U1 공통 보호 쓰기를 통과한다. U4 보호 쓰기는 READ COMMITTED를 명시하고 먼저 현재 epoch의 공통 commit counter를 잠근 뒤 현재 자료를 읽는 방향으로 구현한다. 공통 helper 확장이 필요하면 다른 Unit의 기존 계약/검사를 유지한다. 동일 트랜잭션 EntityManager/ProtectedTransaction을 끝까지 사용하고 전역 repository/새 연결로 쓰기를 분리하지 않는다.

counter 이후의 고정 잠금 순서는 canonical payment ID 오름차순 → invoice ID 오름차순 → 공통 refund approval root ID 오름차순이다. 없는 식별/binding 행 생성 경합은 SD05의 유일성 제약으로도 보호한다. 모든 소비자가 같은 경계를 따라야 하며, 사전 조회/현재 전역 counter만을 이유로 다른 진입 경로의 검증을 생략하지 않는다. 현재 공통 직렬화는 병목/공유 실패 범위이며 새로운 처리 용량을 보장하지 않는다.

1. 현재 신뢰/대상/expectedRevision·U3의 승인 계획·의무·청구 개정을 재대조한다. 미발행 필수 의무도 제공 전 판단에 남긴다. primary 원본과 확인된 보호 원본/선행 후보의 정합성을 대조하고, 아직 보호 미확인인 선행 변경에 의존하는 새 소비는 보류/원래 결과 대조로 돌린다. counter를 잡은 채 독립 보호 I/O를 기다리거나 보호 전 상태를 새 가용 원금으로 사용하지 않는다.
2. 현재 canonical payment의 P/L/RA/RU/HA/HU와 대상 청구의 순배분을 읽는다. 합계를 계산할 때 페이지1개/최대100개 목록만 읽어 전체 합계로 사용하지 않는다. 보호된 집계 원본/동일 트랜잭션의 완전한 합계와 개정을 사용하며 집계는 원래 배분/환불 원본으로 재구성 가능해야 한다.
3. 배분은 각 청구 잔액과 전체 합계≤U−HU를 동시에 검증한다. 환불 예약은 해당 원금의 잔액과 같은 U7 승인 root의 모든 case·시도/개정에 걸친 확정/예약 소비를 뺀 한도 안에서만 허용한다. 승인 개정 변경을 새 한도 전체로 복제하지 않는다.
4. 관련 binding/배분/예약/확정·원래 정정 관계·집계 개정·이력·후속 사실을 하나의 primary 변경으로 반영한다. 하나라도 실패하면 그 명령 전체를 rollback한다. 다른 청구로 자동 재배분하지 않는다.
5. 정상 확정 상태 P=A+U+RA+RU, A≥HA≥0, U≥HU≥0을 재검증한다. 이미 발생한 외부 초과/상충 사실은 숨기지 않고 DISPUTED/대조 및 관련 추가 소비 보류로 기록한다.

**확정 실패분 재시도와 전체 환불 상태.** 같은 잠금·현재성·EntityManager 경계에서 확정 실패/미실행 부분의 원인 해소·현재 권한/원금/공통 승인 한도·필요 회수 근거를 재확인한다. 해당 부분에만 새 현재 시도를 연결하고 옛 실패 시도·원래 부분/작업 식별은 이력으로 보존한다. 재시도액을 목표액에 더하지 않으며 성공분·불명분을 새 실행 대상으로 삼지 않는다.

같은 primary 원자 변경에서 현재 부분 결과를 집계해 RefundCase 상태·현재 시도/이력·확정액/예약액·원금/공통 승인 소비와 개정을 함께 기록한다. 기존 확정 성공액이 있고 미완료가 남으면 실패분 재예약 뒤에도 PARTIAL이다. 확정 성공액0·불명분 없음·활성 예약 없음인 FAILED의 실패분 재예약만 IN_PROGRESS가 되며, 목표 전액의 실제 성공을 확인해야 COMPLETED다. 상태를 직접 지정해 금액을 바꾸거나 별도 쓰기로 뒤늦게 맞추지 않는다. 하나라도 검증·기록에 실패하면 전체 primary 변경을 되돌리고, commit 이후의 미확정 결과는 SD07의 원래 요청 대조로 확인한다.

WF4.7·VS4.16/17의 상태와 금액을 실제 저장 경로에서 함께 검증한다. P100/L100·공통 한도100의 60성공/40실패→40재예약→40성공은 PARTIAL→PARTIAL→COMPLETED이며 RA/HA/A/공통 가용액은 각각60/0/40/40→60/40/40/0→100/0/0/0이다. 성공0의 FAILED100 재예약은 RA0/HA100/A100/공통 가용0과 IN_PROGRESS를 함께 보존한다. 이 수치는 설계 예시이며 실행 성공 증거가 아니다. 같은 작업의 불명 결과 추가 확인·완료 후 높은 확인 개정의 정정은 기존 별도 경로와 소비 보호를 유지한다.

서로 다른 행의 합계를 PostgreSQL CHECK 하나로 보장한다고 설명하지 않는다. 각 행의 필수값/형식과 물리 유일성, 같은 트랜잭션의 공통 잔액 재검증을 함께 사용한다. 상세 SQL·제약/migration·실제 PostgreSQL 동시 접수 검증은 구현 의무다. 적용: NFR5.1–NFR5.6, NFR4.1, NFR13.1.

### SD07

**primary 원자 기록과 별도 보호 확인.** 현재 [protected-write.ts](../../../../../../../../packages/persistence/src/protected-write.ts)의 전역 counter/epoch fence·요청 내용 fingerprint·원자 원본/요청/복구 후보/버전 기록과 primary commit 뒤 보호 확인을 확장한다. U4 모델/보조 예약도 model catalog·검증/decoder·보호 payload의 등록 대상이어야 한다. 별도 SQL로만 쓴 식별 예약이나 binding을 보호 rows에서 누락하지 않는다.

요청/업무 결과·금융 이력·보조 예약·Outbox 사실은 같은 primary 트랜잭션에 포함한다. 별도 보호 저장과 현재 epoch 확인 뒤에만 성공 응답한다. 두 DB를 하나의 물리 트랜잭션이라고 설명하지 않는다. primary commit 뒤 보호 실패/timeout/응답 유실은 원래 request/후보·보호 prefix/epoch와 결과를 대조한다. 아직 결과를 모른다고 새 현금·배분·환불을 실행하거나 예약을 해제하지 않는다.

Outbox/큐는 중복·역순 전달을 전제로 fact ID/원래 소유자·업무/개정을 대조한다. 낮은 개정은 현재 값을 덮지 않고 원본 조회 실패·버전 공백·충돌은 관련 소비만 보류한다. 대금 ALLOW는 현재 목적/계획/근거 개정과 함께 반환하고 U5/U6 실행 소유자가 실행 직전 다시 확인한다. 자동 외부 자금 이동을 추가하지 않는다. 적용: NFR4.1–NFR4.3, NFR5.3, NFR5.5–NFR5.6, NFR13.3.

## Resource, Recovery and Operational Design

### SD08

**기존 유한 처리 경계와 실패 전파.** 호스트의 프로세스 HTTP25개·GET5초/변경10초·남은 예산에 맞춘 statement 최대2초/lock 최대500ms를 재사용한다. 이는 현행 코드 제한값이며 p95/용량 달성 실적이 아니다. 목록/이력은 서버가 허용한 필터·안정 cursor·공통 페이지1..100 범위를 사용한다. 잔액 검증은 SD06처럼 전체 원본/집계에 기반하며 페이지 상한으로 잘리지 않는다.

budget/abort를 포트·저장·worker 경계까지 전달한다. 제한 초과는 기술 실패/과부하와 이미 지속 접수된 미확정 결과를 구별한다. commit 뒤 timeout을 rollback 증거로 보지 않는다. 신규 동기 금융망 호출·무제한 재시도·캐시된 권한/대금 판단을 추가하지 않는다. 업무 충돌은409/안전한 재확인, 원본/보호 의존 불가는503/원래 결과 대조다. 실제 메시지/응답은 기존 호스트 계약을 유지한다.

DB/보호 DB·counter·API 프로세스는 공유 실패 영역이다. 한 주문의 대조 필요와 공통 쓰기 준비 불가를 구별하고 관련 없는 업무를 이유 없이 중단시키지 않는다. 공유 준비가 실제 무너지면 더 넓은 쓰기 중단이 가능함을 숨기지 않는다. 적용: NFR6.1–NFR6.2, NFR7.1–NFR7.2, NFR9.1.

### SD09

**보호 원본에서 보조 상태 재구성과 현재 관측.** U4 식별/별칭·binding·의무별 현재 청구·금융 집계는 보호 rows의 등록 모델로 저장한다. 파생 인덱스는 해당 보호 원본에서 결정적으로 재생성하며 별도 원본 권위를 갖지 않는다. 쓰기 fence 아래에서 새 epoch의 원본·보조 기록·인덱스/유일 제약·집계/예약/정정 일치를 검증한 뒤 쓰기를 연다. 재구성 실패·중복 충돌·수량/금액 불일치면 준비 상태를 열지 않고 원본과 차이를 보존한다. 거래 식별을 비우고 재시작하는 우회는 없다.

보호/원본 모델 decoder의 schema version·새 U4 계약과 원래 데이터는 구별한다. 기존 PREPAY/POSTPAY 주문을 혼합 약정으로 자동 바꾸거나 불명 필수분을0으로 채우지 않는다. U3 공유 계약·호스트 등록·복구 payload와 migration/rollback 호환을 같이 검증한다. 일반 업무 역할로 이력/거래 별칭을 삭제해 복구 준비를 맞추지 않는다.

관측에는 허용 내부 ID·operation/request/correlation·개정·단계·안전한 코드만 기록한다. 입금/청구·예약의 세부 원문은 권한 있는 업무 대조로 조회한다. 업무 거절·권한 거절·기술 실패·미확정 접수·불변조건 이상을 구별한다. 무결성 이상/보호 불가/미해결 누적은 기존 운영 경로로 전달하고, 자동 복구 경로가 있다면 시도 시작부터 Slack+이메일, 실패/수동 필요는 긴급 알림으로 연결한다. 실제 수신과 발송 수락·사람 확인을 구별한다.

30일99.9%·30분 복구·정의한 장애의 성공 접수 RPO0·계획 점검 기준은 유지한다. 대량100k/50분·재해/야간 복구·무중단·30일/1인 운영 실증은 후속이며 새 실증을 이 단계에서 실행하지 않는다. 기본 백업·알림·국내 저장·지원 업무 정확성 준비는 유지한다. 적용: NFR2.1, NFR3.1, NFR4.3, NFR8.1, NFR10.1–NFR10.2, NFR11.3, NFR13.3.

## Contract, Verification and Handoff

### SD10

**변경 계약과 UI/원본 소유권.** C00/C04/C05의 승인 지급 계획/불변 의무·수동 갱신 회차별 주문, C06의 복수 청구·실제 거래 식별·수동 배분 묶음·판단 목적, C16/C17의 허용 금융 조회/명령과 지속 사실을 함께 버전 관리한다. 기존 닫힌 스키마에 임의 필드를 넣거나 새 계약을 구버전이라고 표시하지 않는다. v1/기존 주문·snapshot·구형 입력의 안전한 거절/명시적 어댑터 의미를 보존한다. 정확한 포트/모델/호스트 등록과 실제 caller의 계약 검사는 구현 계획에 포함한다.

대금 포트는 SALE_ACCEPTANCE와 PROVISION 목적을 명시한다. 수락은 현재 승인 조건/제한을 확인하되 아직 발행하지 않은 청구/입금을 무조건 요구하지 않는다. 제공은 완전한 승인 계획의 제공 전 필수 의무만 대조하며 명시적 빈 집합과 미확인을 구별한다. 후불 금액·과거 갱신 회차 지급으로 현재 제공 조건을 채우지 않는다.

기한 계산은 확인된 U5/U6 완료 원본의 식별/개정을 저장하고 해당 약정의 DueBasis만 적용한다. 실제 완료일 기산이면 완료 시점의 KST 날짜에 N 달력일을 더하고 당일0일·기한일 전체를 허용한다. 완료 정정은 같은 원래 사실의 높은 개정으로 재계산하며 도착일/청구일/조기 설치일을 대체하지 않는다. 다른 약정 기산이나 미확인 사실을 이 산식에 강제로 넣지 않는다. 실제 지연/계약 제한은 직원 확인 경로를 유지한다.

U3는 약정/조건·전체 수락, U4는 청구/입금/배분/환불·대금 판단, U5/U6는 실제 제공/회수/기간, U7은 후속 판단/진행/통지, U8/U9는 한국어 PC1280 이상 화면을 소유한다. 고객 화면은 청구액·실제 입금·순배분·미배분·환불/예약·미확인·기한·남은 조치를 구별하고 상태를 색상만으로 나타내지 않는다. 모바일/미국 영어·실제 외부 자동화는 후속이다. 적용: NFR5.3, NFR5.6, NFR9.1–NFR9.2, NFR12.1–NFR12.2, NFR13.3.

## Assumptions & Open Questions

- 실제 수취/환불 source profile·원래 거래 식별/별칭 정규화·원본 접근 권위와 증빙 보관처·보존/삭제/국내 경로는 미확인이다. 실데이터/실거래 전에 확인하며 합성 UUID/자료로 확정하지 않는다.
- 새 U4 계약·지원 모델/유일 제약·보호 payload/decoder·집계/인덱스 재구성·DB 경합/호스트 통합은 미구현이다. 현재 공통 코드의 존재는 U4 완료 증거가 아니다.
- R-03의 설계는 해소됐지만 해당 환불 재시도 구현·실행 검증은 미완료다. 기존 U2 신뢰/동일인·실제 직원망과 U3 상품 목록 위험은 원래 상태로 인계한다. 복구·용량·운영/국내 저장 달성은 별도 실제 증거가 필요하다.
