# U4 보안·정확성·운영 요구사항

## 목적과 적용 범위

[확인한 답변](nfr-requirements-questions.md)의 Q1 A·Q2 A와 Looks correct에 따라 U4 FinancialSettlement의 비기능 요구를 정의한다. U4는 기존 API·worker 안의 library이며 별도 서비스/배포 단위를 만들지 않는다. 이 문서와 [기술 적용](tech-stack-decisions.md), [추적표](traceability.json)가 이번 필수 산출물이다. 성능·복구·관측은 공통 실행 기반과 운영 소유자의 요구에 연결한다. 문서 작성은 제품 구현·시험 성공·실제 거래 확인·배포 완료가 아니다. [S1–S5]

첫 배포는 직원의 복수 청구·실제 입금 확인·한 주문 안 수동 배분·잔액·실제 환불 결과를 지원한다. 지급 약정의 제공 전/후 혼합, 임의 청구 명칭, 원 단위 금액과 네 중복 방지 장치를 유지한다. 고객 증빙 제출·원문 파일 업로드·OCR·외부 URL 자동 가져오기·금융망 실행·자동 배분/환불은 추가하지 않는다. 참조만 기록해도 실제 원본의 신뢰·접근·국내 저장·보존 확인 의무는 남는다.

추적표의 OK는 요구 정의가 연결됐다는 뜻이다. 실제 구현/검증 성공 판정이 아니다. 기능 설계의 환불 재시도 모순 R-03은 이후 보완된 WF4.7·상태표와 추가 검토에서 해소됐다. 이 문서는 그 설계 상태를 이어받으며, 환불 구현·실행 시험은 별도 미완료로 구분한다. [S1, S6]

| NFR6.1 | 조회 p95≤1초·변경 p95≤2초·유효 요청 기술 오류≤0.1%라는 공통 목표의 측정 의미를 유지한다. | 송신부터 응답 본문 수신, 동기 대기 포함. 변경 응답이 접수인지 완료인지 구분. 첫 실패를 재시도로 지우거나 과부하/잘못된 업무 거절을 성공으로 숨기지 않음. 실제 외부 자금 이동 시간 보장이 아님 | NFR6·공통 계약·첫 배포 계획 |
| NFR6.2 | 호스트의 유한 처리/조회/큐 경계를 재사용하고 데이터 증가로 무제한 조회를 만들지 않는다. | 목록/이력/대조는 현재 권한의 페이지·필터와 공통 상한을 적용. 총 deadline·취소를 전달하고 결과 불명 변경을 무조건 새 실행하지 않음. 요청 크기/건수와 처리 용량을 구별. 구체 시간/풀/실행 파라미터의 적용 근거는 NFR Design에서 기존 호스트와 대조 | C16–C18·G17·실패/시간 계약 |

청구·배분 입력의100건은 제품 입력 정책이며 동시 사용자 수나 성능 보장값이 아니다. 문자 수와 JSON 바이트 수는 별도 검사한다. 각 텍스트가 상한 안이어도 모든 내용이 한 요청64KiB 안에 들어간다고 보장하지 않는다.100건 초과 작업을 직원이 나누면 각각 독립 명령이며, 두 번째 명령은 첫 결과와 현재 잔액/권한을 다시 검증한다.
