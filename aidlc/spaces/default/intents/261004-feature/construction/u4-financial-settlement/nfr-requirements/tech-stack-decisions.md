# U4 기술 적용과 유지보수 요구사항

## 목적과 결정 범위

[확인한 기준](nfr-requirements-questions.md)에 따라 기존 기술을 U4 FinancialSettlement library에 적용한다. 새 기술/제공자/서비스/계정을 선정하지 않는다. 아래 이유는 현재 선택의 적용 판단이며 도구의 최신 지원·성능·보안 적합성을 새로 조사해 보장한 사실이 아니다. dependency/lockfile·호스트 설정·현재 지원과 검사 결과는 실제 구현 준비에서 대조한다.

## Technology Decisions

| 항목 | 기존 선택과 U4 적용 | 이유·검증 경계 |
| --- | --- | --- |
| 언어/계약 | TypeScript·기존 런타임 입력 검증 | 공통 타입/검증 경계를 재사용. 타입 선언만으로 사용자 입력·원 단위 금액·현재 권한이 검증됐다고 가정하지 않음 |
| API | NestJS + Express의 기존 호스트 | 직원 청구/입금/배분/정정·조회 진입을 공통 인증/CSRF/오류/요청 상한에 연결. 별도 금융 HTTP 서비스 추가 없음 |
| worker | Nest standalone의 기존 worker | Outbox 사실과 대금 재대조 처리의 진입/대상·개정·현재 권한 의미를 기존 처리 계약으로 검증. 금융망 자동 실행 서비스로 확대하지 않음 |
| 업무 저장 | TypeORM 위주 + PostgreSQL | 기존 지속 기록을 확장. 실제 거래 유일성·입금당 한 주문·청구/공통 환불 한도의 동시 소비 보호는 DB 제약·트랜잭션으로 검증하며 ORM 선택만으로 보장하지 않음 |
| 접수/전달 | Transactional Outbox + 별도 큐, 기존 보호 DB 저장 확인 | 원본·이력·후속 사실과 접수 결과를 같은 성공 경계에 연결. 큐 중복/역순·응답 유실이 가능함을 전제로 실제 거래 식별·수신 중복 대조 유지 |
| 증빙 | 기존 보관처 참조·확인자/시각·필요 요약 | Q1 A. 새 객체 저장소·업로드/OCR/외부 URL 수집 기능 없음. 실제 보관처 접근/국내 저장/보존 확인은 별도 준비 조건 |
| UI | Next.js App Router + React + TypeScript, 한국어 PC1280 이상 | U8/U9에서 청구/실제 입금/배분/환불·미확인·남은 조치를 구분. 민감 원본의 공용 캐시 금지, 최종 권한·금액 검증은 U4 |
| 인증/접근 | Cognito 첫 제공자·출시 후 Keycloak 전환 경계, OMS 권한은 U2 원본 | 금융 코드가 특정 제공자의 claim/role을 기업/청구 권한으로 직접 채택하지 않음. 제공자 교체가 실제 거래 원본·이력을 변경하지 않음 |
| 인프라/알림 | 단일 AWS 계정·CDK·기존 업무/보호 DB·Slack+이메일 경로 | 새 계정·별도 금융 배포/전용 운영 플랫폼 추가 없음. 기존 환경/역할 분리·민감 전송/저장/국내 경로와 실제 알림은 U1/U10/U7에서 검증 |

## Implementation Obligations

1. U3의 승인 지급 계획/의무·동의·총액과 수동 갱신 회차별 별도 주문을 읽는다. U4는 계획을 임의 변경하거나 원래 주문의 지급을 새 갱신 회차로 복제하지 않는다.
2. 청구 명칭/의무/기한, 실제 거래 source profile·식별/별칭, 입금당 한 주문, 다건 배분 명령, 목적별 자격과 현재 개정의 새 계약을 구체화한다. inception v1 문서를 새 구현 계약과 동일하다고 표시하지 않는다.
3. Q2의 Unicode code point 자수·UTF-8 JSON64KiB·배분1..100건을 서버와 실제 계약 검사에 연결한다. 주문 제출/조건 변경의1MiB를 U4 일반 명령에 적용하지 않는다. 바이트/자수/건수의 한도와 초과, 중복 청구 항목, 원자성 검증을 독립 수행한다.
4. 정확한 정수 금액의 표현 범위/직렬화·DB 저장을 대조한다. 금액을 JS 부동소수 값으로 손실 변환하거나 큰 합계를 자동 반올림하지 않는다. 지원 범위 초과는 거절하며 범위값은 호스트/승인 계약과 상세 설계에서 확정한다.
5. 입금/청구/환불 공통 한도의 동시성 경계와 잠금/개정 대조, 실제 거래 유일 식별/별칭의 물리 보호, 오류/재조회·Outbox/보호 저장을 실제 PostgreSQL 경로에서 검증한다. 정확한 SQL·잠금 순서·시간 제한은 NFR Design의 대상이다.
6. 증빙은 참조 텍스트와 확인 정보다. 실제 은행 원본을 새로운 C00.Ref.entity로 꾸미지 않는다. 허용된 내부 업무 Ref와 원본 문서/거래 식별을 구별하고 일반 로그·알림에는 원문을 내보내지 않는다.
7. 새 레코드·이력·거래 별칭·환불 예약/확정·원래 작업/시도·회차 결합의 migration과 보호 복구 자료 호환을 검증한다. 기존 결과/별칭을 삭제해 새 중복 가용액을 만들지 않는다.
8. 기능 설계 R-03은 보완된 WF4.7·상태표와 [추가 기능 검토](../functional-design/reviews/review-03.md)에서 해소됐다. 실제 재시도 구현·시험은 미완료다. 기존 성공액이 있으면 실패분 재예약에도 PARTIAL을 유지하고 성공액0인 FAILED 재예약만 IN_PROGRESS가 되도록 상태·확정액·예약액·원금·공통 한도·원래 부분/과거 시도를 함께 검증한다. 기술 선택·설계 문서만으로 해당 실행 경로의 통과를 선언하지 않는다.

## 첫 배포 검사와 후속 구분

첫 배포의 지원 업무는 [보안·정확성 요구](security-requirements.md)의 권한·증빙·입력·원금/한도·중복·동시 변경·정정·계약 검증을 갖춘다. test-after/Standard·제품 코드 전체80%·필수 보안 검사와 보고서/실패 차단을 유지한다. 문서의 검사와 실제 제품/DB·PC 통합·운영 증거를 구별한다.

고객사10곳/일 주문1000건·조회1초/변경2초 p95·99.9%/30분/RPO0은 기존 목표다. 대량100k/50분·재해/야간 복구·무중단·30일 가용성·장기간1인 부담 실증은 후속이다. 실제 배포 준비에 필요한 국내 경로·기본 백업·알림·접근·지원 업무 정확성까지 보류한 것은 아니다.

## Assumptions & Open Questions

- 실제 금융 원본의 source profile/안정 식별·보관처·확인 권위와 보존/삭제 정책은 미확인이다. 구현상의 합성 원본은 실제 수취/환불 근거가 아니다.
- 기술 재사용이1인 운영/성능/복구 목표를 달성할 수 있다는 것은 검증할 설계 전제이며 달성 사실이 아니다.
- 새 계약·금액 표현 범위·물리 제약/동시성·복구 호환·실제 신뢰/국내 저장은 후속 상세 설계·구현/실데이터 준비에서 확인한다. 기존 U2/U3 위험은 원래 상태를 유지한다. R-03의 설계 해소와 실제 환불 구현·시험 미완료는 구분한다.
