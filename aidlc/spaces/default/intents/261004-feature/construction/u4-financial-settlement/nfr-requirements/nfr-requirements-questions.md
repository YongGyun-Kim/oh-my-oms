# U4 보안·품질 요구사항 확인

## 범위와 기존 결정

U4 FinancialSettlement는 기존 API·worker에 포함되는 library다. 이번 필수 산출물은 security-requirements.md, tech-stack-decisions.md, traceability.json이다. 별도 금융 서비스·배포 단위나 금융망 실행 기능을 추가하지 않는다. 성능·복구·관측 요구는 공통 실행 기반과 운영 책임에 연결한다.

사용자가 2026-10-14에 “2”를 선택해 기능 설계의 R-03을 미해결로 남기고 NFR 요구사항 진행을 선택했던 기록을 보존한다. 이후 실패분 재시도 상태의 보완을 선택하고 보완 요약을 확인했으며, 현재 기능 설계는 [추가 검토](../functional-design/reviews/review-03.md)에서 R-03 해소를 확인했다. 설계 보완은 관련 환불 구현·시험의 통과 근거가 아니며, 이번 재확인도 다른 위험의 일괄 수용이나 실제 배포 승인이 아니다.

## Q1. 첫 배포의 입금·환불 증빙 보관 방식

직원이 실제 거래를 확인한 근거가 필요하다. 고객의 은행 증빙 제출은 첫 버전의 입금 확정 경로가 아니다. 이번 질문은 내부 직원이 확인한 증빙 원문을 OMS에 새로 업로드하는 기능까지 포함할지에 대한 선택이다.

- A. 기존 보관처의 참조만 등록 (추천): OMS에는 원본 문서/거래 참조, 확인자·확인 시각·필요한 근거 요약을 보존한다. 원문 파일 업로드·OCR·외부 URL 자동 가져오기는 추가하지 않는다. 실제 보관처와 거래 식별의 접근 가능성·국내 저장·보존 정책은 실데이터 사용 전에 확인한다. 참조만으로 실거래가 확인됐다고 간주하지 않는다.
- B. OMS에 원문 파일 업로드도 포함: 파일 크기/종류, 접근·다운로드 통제, 악성 파일 처리, 국내 저장과 삭제/백업 정책을 추가로 설계한다.
- X. Other (please specify)

추천 이유: 실제 입금 확인·중복 방지에 필요한 근거 연결을 유지하면서 파일 보관 시스템 개발을 첫 배포에 추가하지 않을 수 있다. 원본 보관처의 통제 의무가 없어지는 선택은 아니다.

[Answer]: A. 기존 보관처의 참조만 등록

## Q2. U4 텍스트와 한 번의 청구별 배분 입력 상한

현재 기능 설계는 유한 입력 상한을 후속에서 정의하도록 남겼다. 아래 숫자는 기존 결정이나 실측 용량이 아닌 첫 배포 제안이다. 주문 입력100행 제한과 청구별 배분100건 제한은 서로 다른 입력 정책이다.

- A. 다음 상한 적용 (추천): 청구 명칭100자, 직원 설명/정정 사유2000자, 외부 문서·거래 참조256자, 한 번의 수동 배분은 같은 주문의 청구 최대100건. 문자 수는 Unicode code point 기준이며 JSON 요청 전체64KiB 한도도 동시에 적용한다. 하나라도 초과하면 전체 요청을 거절하고 자동 절삭·분할·부분 반영하지 않는다. 주문당 전체 청구 건수를100개로 제한하는 선택은 아니다.
- B. 상한을 직접 지정: 명칭/설명/참조 길이와 한 번의 배분 건수를 정한다. 기존 전체 요청64KiB 한도는 유지한다.
- X. Other (please specify)

추천 이유: 무제한 문자열·일괄 변경을 막고 예측 가능한 실패 응답을 제공한다.100건을 넘는 처리는 직원이 나누어 입력하며 각 명령은 현재 잔액과 같은 입금의 경합을 다시 검증한다. 자수 안에 들어가도 전체64KiB를 넘으면 거절한다.

[Answer]: A. 제안 상한 적용
