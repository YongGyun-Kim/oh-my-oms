# R-03 실패분 재시도 상태 수정 검토안

상태: **기능 설계 보완 검토 완료**. 사용자는 코드 생성 단계의1번과 기능 설계 보완 요약의1번(Looks correct)을 선택했다. 보완본은 [독립 검토](../functional-design/reviews/review-03.md)에서 R-03 Fixed·새 지적 없음으로 확인됐고 기능 설계 Unit 완료도 기록됐다. 환불 구현·실행 시험 완료를 뜻하지 않으며, 현재 후속 비기능 문서의 인계 상태를 대조한다.

## 현재 충돌

[기능 명세](../functional-design/functional-spec.md)의 WF4.7은 성공분과 미완료분이 함께 있으면 RefundCase를 PARTIAL로 집계한다. 그러나 상태표는 실패분 재시도에 PARTIAL/FAILED→IN_PROGRESS를 요구하고, PARTIAL→PARTIAL은 같은 작업의 미확인 결과를 추가 확인하는 경우로 제한한다.

따라서 100원 중60원 성공·40원 확정 실패 후 실패한40원만 새로 예약하면 집계 정의는 PARTIAL, 전이표는 IN_PROGRESS를 요구한다. [최종 기능 검토 R-03](../functional-design/reviews/review-02.md)의 Critical 미해결 사항이며, 기존 계획 승인은 이 모순의 해소를 승인한 것이 아니다.

## 추천 수정

- 이미 확정 성공한 금액이 있는 실패분 재시도는 **PARTIAL→PARTIAL**로 명시한다.
- 성공액이0인 FAILED의 실패분 재시도는 **FAILED→IN_PROGRESS**로 구분한다.
- 같은 작업의 불명 결과 추가 확인과, 확정 실패분의 새 시도 예약은 별도 선행 조건으로 표현한다.
- 성공분·불명분 재실행 금지, 현재 권한/원금/공통 승인 한도 재확인, 실제 회수 조건, 원래 건·부분 연결과 과거 시도 이력 보존은 유지한다.

추천 이유: 전체 환불 건의 상태 집계와 부분 시도의 진행을 구분하면서, 이미 성공한 금액을 상태에서 잃지 않는다. 기존 집계 정의와 금액 보존 규칙을 유지하는 좁은 수정이다.

## 확인할 예시

입금 P100, 누적 배분 L100, 환불 공통 승인 한도100을 가정한다. 배분에서 환불하는 예이므로 RU/HU/U는 모두0이다. 실제 은행 실행을 뜻하지 않으며, 확인된 외부 결과를 직원이 기록하는 경로다.

| 단계                      | 추천 RefundCase 상태 | 확정 환불 RA | 예약 HA | 남은 배분 A | 공통 승인 가용액 |
| ------------------------- | -------------------- | ------------ | ------- | ----------- | ---------------- |
| 60 성공·40 확정 실패      | PARTIAL              | 60           | 0       | 40          | 40               |
| 실패한40만 새 시도로 예약 | PARTIAL              | 60           | 40      | 40          | 0                |
| 그40의 실제 성공 확인     | COMPLETED            | 100          | 0       | 0           | 0                |

모든 단계에서 P100/L100을 보존하며 `P = A + U + RA + RU`, `A >= HA`를 만족한다. 재시도40을 환불 목표100에 다시 더하지 않는다.

## 승인 후 작업

기능 설계의 해당 상태표·설명·시나리오를 일치시키고 필요한 검토를 거친다. 이후 실제 환불 명령과 회귀에서 위 상태/금액/예약/공통 한도 및 성공액0인 FAILED의 재시도를 확인한다. R-03/AC8.6.3을 해소하기 전 Step12/13과 U4 전체 완료를 선언하지 않는다.
