# U4 대금·배분·환불 기능 설계 질문

## 적용할 기존 결정

- 고객사10곳 이내 제한 파일럿의 첫 배포 범위를 유지한다. 개발자1명은 기능 축소의 근거가 아니다.
- 직원 청구·실제 지급 근거 등록, 수동 배분·정정, 미배분 잔액과 실제 환불 결과를 우선한다. 외부 수금 연동·자동 배분·복잡한 연체/보상 자동 계산은 후속이다.
- 한국어·KRW 원 단위 정수·한국 시간·PC1280 이상·FULL 제공을 유지한다. Q4 B의 새 결정에 따라 주문당 PREPAY 또는 POSTPAY 한 조건만 허용하던 첫 배포 제한을 변경하여, 같은 주문에서 계약에 따른 제공 전·후 지급 혼합을 지원한다. 복잡한 부분 제공은 이번 변경에 포함하지 않는다.
- 주문대금은 승인된 주문 조건에 따른 총액이고, 청구는 계약상 지급 약정에 따라 해당 주문의 특정 금액을 지급 요청하는 기록이다. 주문당 복수 청구를 지원한다. 청구 유형을 계약금·중도금·잔금의 세 가지로 고정하지 않는다. 실제 자금 이동·세금계산서 발행·회계 원장 전체를 구현하는 것으로 표현하지 않는다.
- 주문 조건·가격 변경은 U3의 승인된 합의·적용 원본을 따른다. U4 입력만으로 기존 주문 가격·SW 기간을 변경하지 않는다.
- 모든 대상의 현재 권한·기업/조직 범위·MFA·직원망, 근거·정확한 개정, 중복·초과·동시 처리·이력 보존을 유지한다. 미확인 금액·지급·환불을0원이나 완료로 추정하지 않는다.
- U3의 R-02 Critical은 사용자의 명시적 Approve에 따른 미해결 수용 위험이다. U4가 이를 수정·전역 해소한 것으로 표시하지 않는다. U2의 기존 미해결과 실제 운영 원본 미등록도 별도로 유지한다.

## 질문과 사용자 결정

각 질문의 추천은 제시 당시의 안이며, 확정된 기준은 해당 사용자 답변을 따른다. 미답변 추천을 기존 합의로 취급하지 않는다. 기술 스택·AWS 구성은 이번 질문에서 다시 선택하지 않는다.

### Q1. 첫 배포의 주문별 청구 단위

- A. 주문당 유효 청구1개 — 현재 합의된 주문 전체 금액에 연결하고 정정은 원본·개정 이력으로 보존한다. 여러 차례 나눠 입금하는 것은 허용한다. 복수의 동시 유효 청구는 후속이다.
- B. 주문당 복수 유효 청구 — 같은 주문을 여러 청구로 나누고 청구별 금액·기한·배분과 주문 전체 합계를 관리한다.
- X. Other (please specify)

추천: A. 첫 배포의 단일 지급 조건·일괄 제공과 맞으며 분할 청구의 추가 금액·기한 정책을 줄인다. 분할 입금은 지원하므로 나눠 낸 돈을 기록하지 못하는 제약은 아니다.

[Answer]: B 및 사용자 지정 조건 — 주문 하나에 복수 청구를 지원하며 청구를 계약금·중도금·잔금의 고정 유형으로 구분하지 않는다. 위 A 추천은 채택되지 않았다. 계약에 따른 명칭·금액·지급 조건·기한을 표현하며, 이 답변으로 실제 청구·입금·제공이 완료됐다고 판단하지 않는다.

사용자 원문:

> ㅇㅋ 그럼 안정장치로
> 4개 안정장치를 넣고 한 주문에 여러번의 청구를 받을 수 있도록한다
>
> 그리고 청구는 계약금, 중도금 잔금으로 나누지 않는다
> 계약 형태에 따라 해당 세 타입으로 설명할 수 없을 수 있기 때문이다

추가 확인: 사용자는 계약금·중도금·잔금 각각에 지급 기한을 둔 계약도 위 A로 지원할 수 있는지 질문했다. Q1의 답변이나 범위 확대 승인으로 취급하지 않는다. 위 추천안은 여러 차례 입금과 계약상 복수 지급 일정의 차이를 명확히 설명하지 않았다.

이전 보완 제안의 대체: 주문당 청구 하나 아래에 고정된 계약금·중도금·잔금을 두는 제안은 채택하지 않는다. 사용자는 주문당 복수 청구와 계약 형태에 따른 표현을 선택했다. 후속 Q4 B에서 제공 전·후 지급 혼합을, Q5 A에서 같은 주문 안의 여러 청구에 대한 수동 배분을 명시적으로 확인했다. Q3의 완료일+달력일수는 그 기산일로 합의한 후불 기한에 한하며 모든 청구에 일괄 적용하지 않는다.

### Q2. 확인된 입금 한 건의 수동 배분 범위

- A. 같은 고객사의 복수 주문에 수동 배분 — 권한 있는 직원이 청구별 금액을 지정하고 남은 금액은 미배분으로 유지한다. 각 대상의 별도 권한·원본을 확인하며 중복·초과·타 고객사 배분을 거절한다.
- B. 입금 한 건은 한 주문에만 연결 — 다른 주문에 나누지 않고 그 주문의 잔액·미배분을 관리한다.
- X. Other (please specify)

추천: A. 예를 들어 입금15만원을 같은 고객사의 주문10만원과5만원에 명시적으로 연결할 수 있다. 자동 추정 없이 합산 입금과 잔액을 대조하며 같은 금액의 이중 사용을 막는다.

[Answer]: B — 사용자 답변: "2. 2 하나의 주문에만 연결한다"

### Q3. 첫 배포의 후불 기한 계산

- A. 확인된 완료일+합의한 달력일수 — 한국 시간의 실제 제공 완료일에 합의한 N일을 더한다. 완료일은0일이며 N=0이면 당일이다. 기한 당일까지 허용하고 다음 한국 날짜부터 미지급 잔액을 지연 후보로 분류한다. 휴일 이월·영업일 계산은 하지 않고 해당 계약은 별도 확인 대상으로 둔다. 실제 연체 제한 적용은 계약·직원 확인과 별도다.
- B. 직원이 확인한 기한을 등록 — 실제 제공 완료 근거·계약·확정 기한을 연결하되 OMS가 달력 산식을 자동 적용하지 않는다.
- X. Other (please specify)

추천: A. 단순한 합의 일수의 반복 계산 부담을 줄인다. 청구일·조기 설치일로 기산일을 바꾸지 않으며 미확인 완료·미합의 일수·영업일 계약을 임의 계산하지 않는다. 예:12월1일 완료+30일은12월31일 기한이다.

[Answer]: A — 사용자 답변: "3번은 추천안으로 한다"

### Q4. 복수 청구의 제공 전·후 지급 조합

Q1의 복수 청구와 고정 유형 없는 표현은 확정했다. 기존 첫 배포는 주문당 선불 또는 후불 한 조건이었다. 복수 청구를 허용하는 것만으로 제공 전·후 혼합 지급이 승인됐다고 해석하지 않는다.

- A. 첫 버전의 기존 선불/후불 한 조건 유지 — 복수 청구는 허용하되 한 주문에서 제공 전 지급과 제공 후 지급을 섞지 않는다. 선불 주문의 출고·활성화 기준은 기존 합의된 지급 조건을 따른다.
- B. 같은 주문에서 제공 전·후 지급 혼합 허용 — 계약에 제공 전 충족할 지급분을 명시하고 나머지는 제공 후 기한에 지급할 수 있다. U3의 단일 지급 종류·서버 입력/계약 및 U5/U6의 실제 제공 판단에 대한 변경 영향을 설계한다. 청구 명칭으로 제공 허용을 추정하지 않는다.
- X. Other (please specify)

추천: A. 승인한 첫 배포의 혼합 지급 제외 범위를 유지하면서 복수 청구를 추가할 수 있다. 제공 전 일부와 제공 후 나머지를 받는 계약이 첫 버전에 필요하다면 B를 선택해야 하며, 그 계약을 A로 지원한다고 표시하지 않는다.

[Answer]: B — 제공 전·후 지급을 섞는 계약도 첫 버전에 포함한다. 직전 질문 "1번은 B, 즉 제공 전·후 지급을 섞는 계약도 첫 버전에 포함하는 것으로 확정할까요?"에 대한 사용자 답변: "ㅇㅇ". 계약에서 명시한 제공 전 필수 지급분의 충족을 확인한 뒤 출고·활성화를 판단하고, 나머지는 계약의 후속 기한에 관리한다. 지급 충족만으로 다른 권한·공급·FULL 제공 조건을 면제하지 않는다. U3의 단일 지급 종류·서버 입력/계약과 U5/U6의 제공 판단 변경 영향을 U4 상세 설계에 연결해야 하며 아직 관련 코드가 수정·검증된 것은 아니다.

추천 정정의 경위: 사용자는 "1번이 A라면 계약금과 물건을 받고난 다음 원금 지불은 불가능한거 아니냐?"라고 질문했다. A에서는 해당 시나리오를 지원할 수 없어 추천을 B로 정정했다. 당시 질문 자체는 승인으로 간주하지 않았으며, 이후 별도 확정 질문에 대한 "ㅇㅇ"로 Q4 B가 확정됐다. 제공 전 필수 지급분은 계약의 명시적 금액·조건으로 판단하며 고정 청구 유형 이름으로 추정하지 않는다.

### Q5. 같은 주문의 여러 청구에 대한 입금 배분

입금 한 건을 서로 다른 주문에 나누는 것은 Q2에 따라 금지한다. 이번 질문은 같은 주문 내부의 청구 사이에서만 금액을 나눌 수 있는지에 관한 것이다.

- A. 같은 주문 안의 여러 청구에 직원이 수동 배분 — 예를 들어 입금 100만원을 해당 주문의 청구 두 건에 60만원·40만원으로 연결한다. 확인된 입금액과 각 청구의 남은 금액을 초과하지 않으며 미배분 금액을 보존한다. 자동 순서 배분은 하지 않는다.
- B. 입금 한 건은 청구 한 건에만 배분 — 같은 주문의 다른 청구에도 나누지 않고 남은 금액은 미배분으로 관리한다.
- X. Other (please specify)

추천: A. 고객이 같은 주문의 여러 청구액을 합쳐 송금해도 실제 입금 기록을 쪼개거나 중복 등록하지 않고 처리할 수 있다. 주문 간 분할 금지와 네 가지 중복 방지 장치는 그대로 적용한다.

[Answer]: A — 사용자 답변: "2. A". 같은 주문 안의 여러 청구에 확인된 한 입금을 직원이 수동 배분한다. 다른 주문으로 나누거나 자동 순서 배분하는 것으로 확대하지 않는다.

## 이어서 설계할 안전 경계

이 항목은 새로운 질문이 아니라 기존 FR8·FR13·FR15와 공통 계약에서 이어받을 기준이다.

### 사용자가 추가한 입금 중복 방지 장치

사용자는 Q1 답변에서 다음 네 장치의 포함을 명시했다. 구현·검증 완료를 뜻하지 않는다.

1. 실제 입금의 중복 등록 차단: 실제 거래를 식별할 수 있는 원본 참조를 대조한다. 은행 거래 식별번호가 있다면 수취 계좌·출처 등과 함께 유일성 범위를 정한다. 정확한 식별 키는 실제 원본 형식 확인 전 미정이며, 입금자명·금액·증빙 파일 해시만으로 동일 거래 여부를 확정하지 않는다. 식별 근거가 부족한 건은 별개 입금으로 자동 확정하지 않고 직원 대조 대상으로 둔다.
2. 입금 기록당 연결 주문 하나: 이미 주문 A에 연결된 입금을 주문 B에 다시 연결하는 것을 거절한다. Q5 A에 따라 동일 주문의 여러 청구에는 직원이 금액을 지정하여 수동 배분한다. 주문 간 분할이나 자동 순서 배분을 허용하는 것으로 확대하지 않는다.
3. 동시 처리의 DB 보호: 중복 등록과 서로 다른 주문 연결의 검사·기록을 DB 제약과 트랜잭션으로 보호한다. 요청마다 다른 멱등 키를 사용해도 동일 실제 거래 중복을 허용하지 않으며, 동시에 처리한 두 요청이 각각 성공하는 경쟁 조건을 차단한다.
4. 정정 후에도 중복 보호 유지: 원래 입금·거래 식별·주문 연결 및 정정 이력을 보존한다. 정정·취소를 이유로 원본을 삭제하여 같은 거래를 새 입금으로 재등록하지 못하게 한다. 잘못된 연결의 정정은 원래 기록을 참조하며 단순 삭제·신규 등록으로 우회하지 않는다.

- 원래 지급·배분·정정 관계를 보존한다. 상충·미확인 근거에 의존한 추가 이행만 보류하며 실제 완료된 외부 결과를 되돌렸다고 표시하지 않는다.
- 환불 요청·진행 중 한도·실제 결과·부분 실패·잔액을 구별하고 동시 요청·결과 미확인의 중복 처리를 막는다. 실제 회수 필요 여부와 합의 한도는 U7/U5/U6 소유자의 현재 원본으로 확인한다.
- 판매 수락 준비와 실제 지급 충족·출고/발급 허용을 구별한다. 청구·지급 전제 때문에 주문 수락과 순환 의존하지 않도록 각 판단의 목적을 명시한다.
- 고객 대금 조회는 별도 권한을 요구하며 목록·상세·이력·오류·합계에 같은 범위를 적용한다. 고객 주문 조회 권한을 청구·지급 권한으로 확대하지 않는다.
- 실제 은행/환불 주체·신뢰 원본이 확보되지 않은 경로는 미등록·미확인으로 보존한다. 합성 시험을 실제 지급·환불 실행 증거로 바꾸지 않는다.
