# U3 인프라·검사 전달 설계 확인

## 확정 근거와 이번 제안 범위

[첫 배포 실행 계획](../../../release-planning/first-release-delivery-plan.md)과 [U3 상세 설계 확인](../nfr-design/nfr-design-questions.md)의 결정을 재사용한다. 별도 U3 배포·새 AWS 계정/서비스/실제 자원 크기를 선정하지 않는다. library에 적용되는 산출물은 `cicd-pipeline.md`와 `traceability.json`이다. 인프라 일반 지침의 예시 서비스를 제품의 새 선택으로 취급하지 않는다.

새 일반 질문을 만들어 기존 선택을 반복하지 않는다. 아래는 기존 첫 배포 범위를 현재 CI 및 U3 전달 경계에 반영할 구체 제안이며 이 전체 내용을 확인받은 뒤 산출물을 작성한다. 과거 승인을 이번 설계의 사용자 응답으로 소급 기록하지 않는다.

## 확인한 현재 상태

- [현재 workflow](../../../../../../../../.github/workflows/u1-validation.yml)는 PR/main push/manual에서 U1·U2 job과 project 집계를 실행하며 project 단계에 이름부터 `50분 부하·복원`을 포함한 `scripts/u2/ci-full-proof.ts project`를 연결한다. 해당 workflow가 첫 배포 파일럿 모드로 변경됐다고 주장하지 않는다.
- [package.json](../../../../../../../../package.json)에 U1/U2 검사·합성 synth/실행 명령이 있으나 U3 검사 명령은 아직 없다. 새 job/명령/검증 결과는 Code Generation 이후 준비할 대상이다.
- [현재 인프라 profile](../../../../../../../../infra/cdk/src/profile.ts)은 `SYNTHETIC_SYNTH`·합성 계정만 허용한다. 실제 AWS/회사망/이미지·저장 위치 준비 완료나 배포를 뜻하지 않는다. 현재 합성 수치·로그 수명을 실제 고객 용량/법적 보관 기간으로 채택하지 않는다.
- [U3 보안 설계](../nfr-design/security-design.md) SD01–SD10과 [논리 구성](../nfr-design/logical-components.md) L01–L11은 기존 실행/저장/보호/큐와 업무 원본 소유자를 유지한다. C00/C05 v2의 실제 스키마/호스트·호출자/worker·복구 payload 연결은 미구현이다.

## Consolidated Summary Confirmation

- **실행 기반 — 기존 자원 재사용을 추천.** 기존 한 AWS 계정/CDK·API/worker·primary/보호 DB·Outbox/큐·관측 경계에 U3를 연결한다. 이유: U3 library 때문에 별도 운영 자원을 추가할 필요가 없으며 1인 기술 운영 구조를 유지할 수 있다. 실제 AWS 배포/자원 생성은 지금 실행하지 않는다.
- **기본 CI — 파일럿 필수 검사 묶음을 추천.** PR/첫 배포 후보의 기본 집계는 현재 source의 U1/U2 영향 회귀와 U3 단위/통합·C00/C05 v2 계약/100행·1MiB 경계·권한/다른 사람 승인·중복/동시 변경·실패/원래 결과 대조를 포함한다. 전체 직접 작성 테스트 가능 제품 코드 분모의 80% 및 변경에 맞는 필수 보안 검사를 유지한다. 이유: 실제 변경을 확인하면서 이전 장시간 시험을 매번 실행하는 부담을 줄인다. 현재 U3 PC 전면 UI 완료는 U8/U9 전이며 주장하지 않는다.
- **장시간/전체 실증 — 별도 명시 실행 경로로 보존을 추천.** 기존 전체 부하/복원 검증은 수동 선택 가능한 후속 모드로 남기고 기본 파일럿 집계에서는 실행하지 않는다. 이유: 이미 승인한 첫 배포 범위와 현재 CI의 50분 부하/복원 묶음 사이의 차이를 해소한다. 별도 모드/결과 이름·검사 manifest로 구분하고 미실행을 PASS/전체 증거 완료로 바꾸지 않는다. 과거 FAIL·U2 미해결·전체 RPO0/가용성 증거는 보존한다.
- **집계/보고서 — 같은 source·전체 분모·실제 성공 대조를 추천.** U3 검사 job/명령과 기존 공유 집계를 연결하고 각 필수 job의 실패/취소/skip·보고서 누락·source/SHA 불일치 시 통과를 막는다. 같은 source inventory로 커버리지 기여를 합치고 미실행 제품 파일을 분모에서 빼지 않는다. 보고서에는 최소 비민감 결과를 남기며 앱 비밀/고객 원문/원시 trace를 일반 CI artifact로 업로드하지 않는다. 이유: 여러 job의 부분 성공과 전체 제품 준비 상태를 혼동하지 않도록 한다. exact 명령·분모·파일 목록은 코드 계획에서 구체화한다.
- **전환/되돌림 — v2·영속 원본 호환 확인 후 노출을 추천.** C00/C05 v2 schema·API/worker/소비자와 U3 영속 모델·보호/복구 decoder·대기 메시지의 버전을 함께 검증한다. 기존 원본/접수/queue를 삭제하거나 이전 snapshot으로 되돌려 새 접수를 잃는 rollback은 금지한다. 새 기록을 읽지 못하는 이전 image로 무조건 되돌리지 않고 접수를 보류·원래 결과 대조/복구 또는 호환 수정 경로로 연결한다. 이유: image rollback만으로 계약/DB/보호본·메시지 호환이 보장되지 않는다. 원래 v1 명세는 역사적 원본으로 보존하고 무중단 달성을 주장하지 않는다.
- **배포/운영 준비 — 기존 승인 방식과 실제 선행조건 유지를 추천.** 문서·로컬 합성/CI 검증과 실제 배포를 구분한다. 이후 main 병합·필수 검사 후 staging, 운영은 개발자가 실제 핵심 동작/선행조건을 확인해 승인하는 기존 방향을 유지한다. 실제 provider/회사망·국내 원본/로그/백업 경로·기본 백업/알림 수신/대응 준비와 U2 신뢰 미해결은 별도 확인 대상이다. 이유: 파일럿 모드의 검사 성공이 실제 접속/데이터/운영 증거를 대신하지 않는다. 단순 검사는 Luna, 공식 체크포인트 검증은 주 실행자가 맡는다.

위 제안은 파일럿 검사 범위를 설계하는 것이며 기존 full-proof 보고서/공식 검증의 성공 기준을 몰래 낮추거나 현재 CI를 변경한 결과가 아니다. 향후 구현 계획은 영향 파일·기존 보고서 의미/필수 결과·후속 모드의 보존을 포함한다.
