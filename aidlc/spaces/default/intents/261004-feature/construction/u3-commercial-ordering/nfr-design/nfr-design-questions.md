# U3 보안·품질 상세 설계 질문

## 확정한 기준과 재사용 방향

U3의 보안·품질 요구사항과 첫 배포 범위를 유지한다. 필요한 질문은 한 번에 묶고 숫자·줄바꿈·추천안·추천 이유로 제시한다. 기존 기술·MFA/현재 권한·다른 사람 승인·100입력행·원 단위 금액·최초 조건·모든 적용 계약 개정·고객 동의 기준은 다시 선정하지 않는다.

상세 설계는 기존 보호 쓰기/같은 트랜잭션의 현재 근거 재검증·원본 개정 충돌·Outbox/별도 큐·제한된 입력/시간·최소 정보 기록을 U3 소유자에 연결한다. 새로운 AWS 계정/도메인별 서비스·분산 잠금·인증 제공자·자동 확정·대량 부하/재해 실증을 추가하지 않는다. 전역 직렬화의 실제 처리 성능과 실제 외부 신뢰/저장/복구 성과를 확인한 사실로 가정하지 않는다.

## 조사한 현재 코드와 가정

- 현재 API의 JSON 입력 한도는64kb이며 [application.ts](../../../../../../../../apps/api/src/application.ts)의 express.json 설정에서 확인했다.
- [protected-write.ts](../../../../../../../../packages/persistence/src/protected-write.ts)는 같은 primary 트랜잭션에서 commit counter를 잠그고 원본/요청/후보/개정을 보존한 다음 보호 저장/현재 세대를 확인한다. 이를 재사용할 방향이며 U3 코드/100행 경로가 이미 구현된 것은 아니다.
- [u2-repository.ts](../../../../../../../../packages/persistence/src/u2-repository.ts)의 현재 원본/보호 원본 대조·변경 전후 재검증을 참조한다. 기존 U2 검증 미해결을 해결했다고 선언하지 않는다.
- Luna가 문서의 v2 구조를 사용해 합성 JSON UTF-8 크기만 계산했다. 저장소 수정·API/앱 호출·부하 시험은 하지 않았다. 실제 v2 스키마는 아직 구현되지 않았으며 조건 매핑의 하위 필드명은 계산 가정이다.

## Q1 — U3 주문 입력의 요청 본문 한도

100입력행과 조건별 계약 참조를 담는 주문 JSON의 최대 크기를 어떻게 둘 것인가?

**추천안:** U3의 주문 제출·주문 조건 변경 요청만 최대1MiB로 둔다. 다른 접점의 기존64KiB는 유지한다.1MiB는1048576바이트이며 파일 첨부 한도가 아닌 JSON 요청 본문 상한이다.

**추천 이유:** 위 합성100행 표현은 약140–229KB로 현재64KiB를 초과한다.1MiB는 해당 표현에 여유를 주면서 요청 크기를 유한하게 제한하는 첫 배포 제안이다. 최종 v2 스키마의 실제 표현/처리/메모리 적합성은 구현에서 검증한다. 숫자를 실측 처리 용량이나 외부 지침의 의무값으로 제시하지 않는다.

**공통 보호:**100행·타입/필드/조건/원본 검증은 그대로 적용한다. 한도 초과는 요청을 접수하지 않고413으로 안내하며 자동 분할/절삭·파일 업로드로 전환하지 않는다. 클라이언트의 Content-Length 주장만 믿지 않고 실제 parser 한도와 압축 해제 후 크기를 검증한다. U3 전용 parser와 기존 parser를 중복 적용하지 않는다.

- A. U3 주문 입력만1MiB로 한다. 나머지 접점은64KiB 유지. 최종 v2 입력의 크기/경계 검증을 구현에 포함한다. (추천)
- B. 모든 접점의64KiB를 유지한다.100행도 크기 한도 안의 표현만 접수하며 초과는413 안내한다. 정식 v2 표현이100행을 충분히 담는지 구현 전 대조하고 부족하면 입력 표현 또는 한도를 다시 검토한다.
- X. Other (please specify)

## Ambiguity Analysis

Q1의 실제 응답은 A이며 주문 제출·주문 조건 변경 JSON에만 1MiB를 적용한다. 다른 접점은 기존 64KiB를 유지한다. 100입력행 정책과 byte 한도는 독립적으로 검증한다. 소수 금액 자동 반올림, 입력 절삭/분할, 미확인 조건의 0원 처리를 허용하는 응답으로 해석하지 않는다. 기존 보안·정확성 요구와 모순 없음.

합성 입력 크기를 실제 v2 스키마 유효성·CPU/메모리 적합성·처리 용량의 증거로 바꾸지 않는다. 실제 입력 표현과 경계 검증은 Code Generation/Build and Test에 남긴다. 이 구분은 미해결 질문을 임의 확정한 것이 아니라 현재 설계와 후속 검증의 경계다.

## Consolidated Summary Confirmation

다음 전체 기준을 확인한 뒤 U3의 상세 설계 문서 3개를 작성한다. 추천 이유는 기존 요구사항을 U3에 연결하는 판단이며, 새 기술·기능·운영 성과를 확인한 사실로 제시하지 않는다.

- **구조 — 기존 실행 기반 재사용.** ProductCatalog·CommercialAgreement·OrderAcceptance를 같은 API/worker에 들어가는 library로 유지한다. NestJS + Express, Nest standalone, TypeORM/PostgreSQL, 별도 보호 DB, Transactional Outbox + 별도 큐를 재사용한다. 추천 이유: 1명이 기술 운영할 수 있는 구조를 유지하면서 업무 원본의 소유자를 분리할 수 있다. 별도 U3 배포·새 AWS 계정·분산 잠금 서비스를 추가하지 않는다.
- **접근 — 현재 권한과 정확한 승인 근거 검증.** 공통 인증/MFA·현재 기업/조직 권한·TargetScope를 모든 조회/변경과 worker 진입에 연결한다. 직원 접근은 내부망 전제를 유지한다. 계약 승인에는 정확한 개정·근거와 검증된 서로 다른 사람이 필요하며, 미확인/오래된/목적이 다른 근거는 차단한다. 추천 이유: 로그인 성공이나 다른 계정이라는 사실만으로 거래 권한·다른 사람 승인을 보장할 수 없다. U2 미해결 문제와 실제 접속 신뢰 검증은 별도 선행조건으로 남긴다.
- **입력 — 선택한 byte 한도와 기존 업무 한도 동시 적용.** 주문 제출·조건 변경 JSON만 1MiB, 나머지는 64KiB다. 최대 100입력행·지원 타입·원 단위 정수 금액·조건별 모든 계약 개정 매핑과 C00/C05 v2를 검증한다. 과대 입력은 413으로 거절하며 절삭/분할하지 않는다. 실제 parser에서 압축 해제 후 크기까지 제한하고 같은 본문에 parser를 중복 적용하지 않는다. 추천 이유: 합성 100행의 약 140–229KB 표현에 여유를 주되 무제한 입력을 허용하지 않는다. 정식 스키마·경계·처리 적합성은 실제 구현 검증 대상이다.
- **접수/변경 — 원자 기록과 보호 확인 후 성공 응답.** 현재 보호 쓰기 경로에서 주문/조건/요청 식별/결과/이력/Outbox 사실과 개정을 같은 primary 트랜잭션에 기록하고, 별도 보호 저장과 현재 복구 세대를 확인한 뒤 성공으로 응답한다. 두 DB를 하나의 물리적 트랜잭션이라고 설명하지 않는다. 동일 요청·동일 내용은 원래 결과로 연결하고 다른 내용은 충돌로 처리한다. commit 후 응답 유실/보호 실패/시간 초과는 미확정 결과 조회로 연결하며 새 주문을 자동 생성하지 않는다. 추천 이유: 응답 실패를 주문 미생성으로 가정하면 중복 효과가 생길 수 있다.
- **동시 변경/이행 — 현재 원본 재검증과 소유자별 결과 대조.** 트랜잭션 안에서 현재 개정·승인·고객 동의·외부 판단 참조를 재검증하고 expectedRevision 충돌을 보존한다. Outbox/큐 중복 전달을 전제로 수신자의 동일 사실 효과 한 번을 요구한다. 지급 U4, HW U5, SW U6, 후속 U7의 실제 결과 소유권을 유지하며 FULL 주문의 일부 준비를 전체 완료로 승격하지 않는다. 추천 이유: 주문 접수·직원 수락·동의·실제 지급/출고/발급은 서로 다른 사실이다.
- **자원/실패 — 기존 유한 처리 경계와 최소 격리 유지.** 현재 호스트의 25개 동시 HTTP 슬롯, 조회 5초/변경 10초 실행 예산, 트랜잭션 잠금/statement 제한과 유한 목록 처리를 연결한다. 이 값은 기존 코드 경계이며 성능 목표 달성 증거가 아니다. 무제한 동기 재시도·전역 캐시로 권한/현재 개정 우회·업무별 새 microservice를 추가하지 않는다. 추천 이유: 작은 파일럿에서도 입력/대기 제한이 필요하며 추가 운영 복잡도 없이 시작할 수 있다. 현재 전역 쓰기 직렬화의 실제 용량은 미검증이다.
- **정보 보호/관측 — 기존 보호와 최소 기록 연결.** 민감 응답의 캐시 방지, 기존 HTTP 보안/CSRF·출처 확인, 전송/저장 보호, 목적별 접근을 유지하고 일반 로그/오류/알림에는 최소 식별자·개정·결과만 남긴다. 국내 저장 및 실제 보관/삭제 의무는 실제 경로/근거로 확인한다. 자동 복구가 있다면 시도부터 개발자 알림이라는 기존 기준을 U10/U7에 연결한다. 추천 이유: 기록은 진단에 필요하지만 계약/신원 원문이나 비밀을 일반 로그에 복제할 필요는 없다. 새 메신저·임의 법정 기간을 선정하지 않는다.
- **첫 배포/검증 — 파일럿과 후속 실증 구분.** 고객사 10곳 이내·하루 1,000건은 계획이다. 가용성 99.9%/30분 복구와 기존 성능·운영 목표를 보존하되 대량 부하·전체 재해 복구·무중단·장기간 운영 실증은 후속으로 유지한다. 권한/다른 사람 승인/정확한 금액/중복/동시성/원본 조회 실패·C00/C05 v2 계약·80% 커버리지/필수 보안 검사는 해당 코드에 필요하다. 단순 검사는 Luna에 위임한다. 추천 이유: 첫 배포 범위를 줄여도 거래 정확성과 접근 보호는 축소할 수 없다. 실제 인증/내부망/국내 경로/외부 원본 준비와 기존 미해결은 해결했다고 기록하지 않는다.
