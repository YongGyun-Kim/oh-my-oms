# U3 보안·정확성 상세 설계

## 목적과 범위

[확인한 기준](nfr-design-questions.md)의 U3 첫 배포에 적용할 설계다. ProductCatalog·CommercialAgreement·OrderAcceptance는 기존 U1 API/worker 안의 library다. 신규 배포·AWS 계정·인증 제공자·단말 관리 서비스를 추가하지 않는다. 현재 코드에서 확인한 공통 보호 경로를 재사용하도록 설계하며 U3 구현·실제 연동·성능·복구 성공을 주장하지 않는다.

상위 요구사항은 [보안 요구](../nfr-requirements/security-requirements.md)와 [기술 적용](../nfr-requirements/tech-stack-decisions.md)의 33개 파생 ID다. 논리 구성과 공유 실패 범위는 [logical-components.md](logical-components.md), 전체 연결은 [traceability.json](traceability.json)에 있다. 기존 U2 동일인/필수 출처 검증 문제는 별도 선행조건으로 보존한다.

<a id="sd01"></a>
## Authentication and Authorization — SD01

HTTP에서 신원을 얻는 경로와 업무 명령의 권한 판단을 구분한다. Cognito 등 공급자 식별은 기존 IdentityRecovery/EnterpriseAccess가 OMS 계정·현재 세션/MFA·조직 권한에 연결한다. U3는 공급자 role/클라이언트 audience/기업 ID만으로 업무 권한을 부여하지 않는다. 출시 후 Keycloak 방향도 이 원본 소유 경계를 따른다.

| 접점 | 설계 의무 | 실패/노출 경계 |
| --- | --- | --- |
| 상품/공통 조건 등록·개정 | 현재 직원 계정·MFA·직원 audience·허용 내부망 근거·행위 권한 확인 | 고객 접점/외부망/위조 전달 헤더로 등록 불가 |
| 기업 조건/제안/동의/주문 | 현재 기업·조직·행위·대상 권한과 원본 개정 확인 | 입력 기업값을 신뢰하지 않음; 타 기업 내용 비노출 |
| 계약 승인 | 등록자·승인자의 정확한 사람 확인 참조/개정·현재 계정·목적·출처·확인 권위와 승인 대상 개정 대조 | 동일인/UNKNOWN/미확인 출처/확인자 부재는 적용 차단 |
| 조회·목록·이력·원래 요청 결과 | 먼저 현재 대상 접근 권한을 검증하고 허용 범위로 원본/필드를 제한 | 필터 뒤 전체 목록/캐시/이력에서 다른 기업 값 노출 금지 |
| worker/공통 서비스 호출 | 신뢰된 실행 문맥·행위 목적·대상·현재 원본/개정과 명령 전제 검증 | HTTP middleware 통과 여부나 메시지 필드만으로 권한 대체 금지 |

주문의 필수 TargetScope는 enterpriseRef·departmentRef·siteRef·contextPolicyRef·organisationRevision을 접수 때 고정한다. null 하위 조직은 승인된 정책의 명시적 보호 단위 부재만 뜻한다. 조회 실패/누락을 null로 치환하거나 현재 사용자 소속으로 과거 주문 문맥을 재구성하지 않는다. 조직 변경 후 접근은 현재 정책으로 재평가하되 스냅샷의 거래 문맥을 넓히지 않는다.

변경 전과 commit 가능한 전제 확인 시 현재 권한/조직·근거 개정을 다시 대조한다. 일반 직원의 수락·예외 금액 입력은 이 검증을 우회하지 않는다. 인증·현재 조직·동일인 원본을 확인하지 못하면 거절/보류하며 실제 거래 준비 완료로 표시하지 않는다. 구체적 공통 인증 제공자 및 내부망 연결의 실증은 U1/U2/Infra 책임이다. 적용: NFR1.1–NFR1.5, NFR9.2.

<a id="sd02"></a>
## Input Validation — SD02

주문 제출/조건 변경 JSON만 최대 1MiB(1,048,576바이트), 다른 접점은 기존 64KiB다. 라우트·명령은 서버가 정한 허용 목록으로 parser를 선택하며 요청 필드의 operation 주장으로 한도를 높이지 않는다. Express/Nest의 중복 기본 parser를 활성화하지 않고 하나의 parser가 실제 본문 및 압축 해제 후 크기를 제한한다. Content-Length는 단독 판정 근거가 아니다. 경계 초과는 업무 실행 전 413, 잘못된 JSON/타입/추가 필드는 입력 오류로 처리한다. 명령 경로와 parser 예외의 정확한 응답 매핑은 코드/계약 시험에서 검증한다.

최대 100입력행은 byte 한도와 독립적이다. 0/101행·양의 정수가 아닌 수량·소수 단가·HW/SW 혼합·지원 밖 지급/부분 제공을 검증하고 자동 반올림/분할/절삭하지 않는다. 동일 SW 타입의 영구/기간제 혼합은 기존 지원 범위대로 보존한다. 유효 구간의 시점·포함 여부·기간 값은 승인 원본과 C00 값 계약을 따르며 임의 날짜/종료 경계를 추정하지 않는다.

Money는 KRW 원 단위 정수의 정확한 표현 범위에서만 계산한다. 곱셈·합계·추가 비용·할인은 중간값까지 범위를 확인하고 부동소수 오차/넘침을 성공 결과로 반환하지 않는다. 세금 포함 여부와 직원이 확인한 비용/할인·근거를 대조하고 포함 항목을 중복 합산하지 않는다. 미확인은 0원이 아니며 음수 총액 확정/직원 수정만으로 고객 총액 변경을 허용하지 않는다. 정확한 저장/직렬화 표현은 C00 Money와 TypeORM/PostgreSQL 매핑의 구현 검증 대상이다.

필수 TargetScope와 각 입력행 conditionBindings·모든 agreementRevisionRefs, 불변 스냅샷 합집합을 C00/C05 v2에서 보존한다. 닫힌 Ref owner/entity·정확한 revision·허용 값/유효 구간/근거를 역참조하고 임의 값 객체 이름을 Ref.entity로 전송하지 않는다. 승인된 기업 조건 우선은 정상 평가이며 같은 단계의 상충 조건 적용은 차단한다. 검증된 계약 없음과 조회 실패를 빈 목록으로 동일하게 표현하지 않는다.

합성 100행 약 140–229KB는 제안 근거이며 정식 v2 적합성/처리 용량 증거가 아니다. 최대/초과 byte, 압축 입력, 다수 조건, 유효 스키마의 1/100행·무효 0/101행을 구현에서 독립 검증한다. 적용: NFR5.2, NFR5.3, NFR13.3.

## Durable Writes and Idempotency — SD03

기존 [protected-write.ts](../../../../../../../../packages/persistence/src/protected-write.ts)의 보호 쓰기 경로와 [protected-transaction.ts](../../../../../../../../packages/persistence/src/protected-transaction.ts)의 개정 검사를 재사용한다. 아래는 설계 성공 경계이며 U3 영속 모델은 아직 구현하지 않았다.

1. 검증한 principal/audience/기업·대상/operation/request key와 정규화한 입력 지문으로 요청을 식별한다. 중복 결과 조회에서도 현재 접근 권한을 확인한다.
2. primary 트랜잭션의 기존 commit-counter 잠금/복구 세대·writer fence를 확인하고 현재 업무 원본·권한/근거 개정을 대조한다. 같은 키·다른 내용은 충돌이며 같은 키·같은 내용은 원래 후보/결과로 연결한다.
3. 신규 주문 전체 행·최초 조건·모든 적용 개정·TargetScope 또는 승인/조건 변경의 현재 포인터·전후 이력·요청 결과·전달할 Outbox 사실을 하나의 primary commit에 보존한다. 현재 코드의 batch 100개는 모델별 삽입 경계이며 100행 주문 전체를 한 batch에 임의 압축하라는 정책이 아니다. 여러 모델의 쓰기는 같은 트랜잭션 안에서 수행한다.
4. primary commit 뒤 별도 보호 저장 확인과 현재 복구 세대/실행 예산 확인을 마친 결과만 성공으로 응답한다. primary와 보호 DB는 별도 실패 영역이며 하나의 물리적 트랜잭션이라고 설명하지 않는다.

| 실패 시점 | 결과/복구 설계 | 금지하는 해석 |
| --- | --- | --- |
| primary commit 전 입력/권한/개정·기록 실패 | 해당 트랜잭션의 업무 효과 반영 없음, 원래 사유 반환 | 일부 행만 접수/성공 표시 |
| primary commit 후 보호 확인 실패/시간 초과 | 원래 요청은 기록됐을 수 있음. 같은 식별의 원래 후보/결과 대조·재보호 경로로 연결, 성공 접수 미확인 표시 | 실패 응답이 주문 미생성을 보장한다고 가정 |
| 보호 확인 뒤 응답 유실 | 현재 권한 아래 원래 결과 재조회/동일 내용 요청 재전송, 업무 효과 추가 없음 | 새 request key로 자동 주문 생성 |
| 복구 세대/현재 원본 대조 불가 | 현재 결과와 근거를 확인할 때까지 실행 보류 | 오래된 보호본/세대를 현재 원본으로 승격 |
| Outbox 발행/큐 전달 실패 | 원본 사실 유지, 기존 유한 전달 재시도·진단 경로 사용 | 원본 주문을 다시 생성하거나 통지를 이행 완료로 취급 |

초기 구매 조건은 불변으로 남기고 승인된 변경은 별도 개정/적용 이력으로 연결한다. 사용자 성공 접수 목록·원래 입력/결과·보호 후보·현재 개정·전후 이력·전달 사실을 대조할 수 있어야 한다. 전체 장애 범위 RPO0 달성/재해 복구 실증은 이 설계의 성공으로 선언하지 않는다. 적용: NFR4.1, NFR4.2, NFR5.1, NFR5.5.

## Concurrency and Owned Facts — SD04

[u2-repository.ts](../../../../../../../../packages/persistence/src/u2-repository.ts)의 현재 원본/보호 원본 대조·변경 전후 재검증은 재사용할 패턴이다. U3는 expectedRevision뿐 아니라 승인/동의/조건 원본·대상/개정·효력을 commit 가능한 현재 전제와 대조한다. 외부 원본 소유자의 보호된 확정 사실을 읽으며, 그 소유자의 DB를 U3가 직접 변경하지 않는다. 조회 후 원본이 달라졌거나 보호 대조가 불가능하면 충돌/보류로 끝낸다. 수정된 제안에 이전 고객 동의를 이월하지 않는다.

| 전이 | 필요한 현재 전제 | 경쟁/실패 처리 |
| --- | --- | --- |
| 계약 승인/적용 | 정확한 등록 개정·다른 승인자·일치 근거·유효 구간과 비충돌 조건 | 동시 승인/개정 변경은 한 현재 전제만 적용, 기존 유효 조건 유지 |
| 주문 전체 수락 | 현재 REVIEW 주문·전체 판단에 필요한 확인된 근거·조건/금액·권한 | 일부 준비는 전체 HOLD, 원본 조회 실패는 기술 실패와 미확인으로 구분 |
| REVIEW_PRICE_CHANGE | REVIEW 주문, 정확한 제안/고객 동의/newTerms와 명시 null afterSalesDecisionRef | 수락/동의/조건 변경 경쟁은 REVISION_CONFLICT, 최신값 덮어쓰기 없음 |
| ACCEPTED_AFTERSALES_CHANGE | ACCEPTED 주문, 정확한 제안/동의와 확인된 U7 AfterSalesDecisionRecord | 수락 전 경로 혼용/임의 U7 참조 불가; U7이 판단 후 C05 호출, U3 역조정 의존 없음 |
| 큐 사실 수신 | 같은 원본 소유자·fact/operation ID·대상·정확한 개정·현재 전제 | 동일 사실 재전달의 새 효과 없음, 오래된/상충 사실 완료 승격 없음 |

주문 수락은 지급·예약·출고·SW 발급 완료가 아니다. 제한 재고의 A/B 경쟁과 실제 공급은 U5가 소유하며 U3 commit 순서가 재고 FIFO/확보 성공을 보장하지 않는다. 계약 당시 SW 기간/추가 보상 합의와 U6의 실제 활성화/기간 변경 결과를 구분한다. U4/U5/U6/U7 사실 부재를 허용/완료로 추정하지 않는다. 적용: NFR5.4, NFR5.6, NFR9.3, NFR13.3.

## Encryption, Security Headers and Exposure — SD05

기존 호스트의 전송/저장 보호·보안 헤더·cookie/CSRF/출처 검증을 U3 HTTP 연결에도 적용한다. 인증 cookie의 기존 보호를 유지하고 민감 응답/개별 기업 가격·계약·주문을 공유 캐시/CDN에 저장하지 않는다. UI가 최종 권한/금액 판단을 대신하지 않는다. TypeORM의 매개변수/타입 검증을 사용하며 클라이언트 입력을 SQL/조건식/템플릿 실행 문자열로 조립하지 않는다. 자유 텍스트/근거 메타데이터는 정해진 형식/길이로 제한하고 U8/U9에서 텍스트로 안전하게 렌더링한다. 세부 허용 길이는 실제 스키마에서 기존 값 계약과 대조한다.

주문·계약 원본/이력과 근거 참조는 목적별 권한 아래 저장하며, 일반 오류·메신저/이메일·telemetry에 가격/조건 전문·개인 연락/신원 원문·토큰/세션/비밀키를 넣지 않는다. 로컬 합성 데이터와 실제 데이터의 신뢰 수준을 구분한다. 로그는 원문 request body를 남기지 않고 안정된 코드/대상 식별·개정·correlation을 기록한다. 읽기 가능한 운영 진단도 업무 접근과 별도 허용 행위를 확인한다.

AWS 한 계정 안의 기존 CDK 역할·DB/보호 저장 접근 경계를 사용한다. 실제 전송 TLS·주 저장/보호 DB/로그/백업 암호화·비밀 접근 권한의 설정/작동 증거는 Infra/U1/U10에서 확인한다. 일반 업무 역할로 과거 이력이나 보호 복구 원상을 덮어쓰는 경로를 허용하지 않는다. 공급자/계정 이름이나 백업 존재만으로 암호화·분리 보호 달성을 선언하지 않는다. 적용: NFR11.2, NFR14.1, NFR14.2.

<a id="sd06"></a>
## Compliance Controls — SD06

설계용 분류는 공개 범위 상품 설명, 내부 검토 사유, 민감 기업 계약/가격/주문/동의, 제한 개인 연락/신원 근거·인증 비밀로 나눈다. 각 소유자는 처리 목적·허용 조회/정정·근거 참조·실제 저장/외부 처리 경로를 제공한다. 국내 저장 원칙은 원본뿐 아니라 그 내용이 있는 로그/백업/외부 경로까지 확인한다. 미확인 해외 경로를 실데이터 준비 완료로 표시하지 않는다.

정확한 보관/삭제/정정·법적 의무는 실제 업무 및 법적 근거 확인 후 적용한다. 기간/인증 등급을 임의로 생성하지 않는다. 과거 거래 조건의 불변성과 개인 데이터 최소화가 충돌하면 승인된 정책/정정 절차에 연결하고 일반 업무 삭제로 기록을 훼손하지 않는다. 확인 주체는 실제 사업 확인자·해당 원본 소유자·Infra/U10이며 실데이터/실거래 전에 증거가 필요하다. 적용: NFR11.1, NFR11.3.

## Bounded Execution and Failure Isolation — SD07

현재 [application.ts](../../../../../../../../apps/api/src/application.ts)는 공통 admission/budget 뒤 JSON parser를 둔다. [admission.ts](../../../../../../../../apps/api/src/admission.ts)의 25 HTTP 슬롯과 [request-budget.ts](../../../../../../../../apps/api/src/request-budget.ts)의 GET 5초/변경 10초 예산을 U3에도 연결한다. 기존 보호 트랜잭션은 잔여 예산에 맞춘 statement 최대 2초/lock 최대 500ms 제한을 적용한다. 유한 목록/페이지와 중단 신호를 공통 서비스/worker까지 전달하며 무제한 동기 재시도나 전역 캐시로 현재 권한/개정을 우회하지 않는다.

이 수치는 기존 코드의 제한값이다. p95 조회 1초/변경 2초 목표나 동시 사용자 수·하루 주문 용량의 실측이 아니다. HTTP 슬롯은 프로세스별 admission이며 독립 서비스/고객별 자원 격리가 아니다. 현재 primary commit-counter 전역 직렬화 및 공유 DB/보호 DB가 병목·공유 실패 범위가 될 수 있다. timeout/abort는 이미 commit한 업무의 rollback 보장이 아니며 SD03 원래 요청 결과 대조를 따른다.

필요 원본/신원/보호 저장 실패는 관련 명령을 보류하고 다른 검증 가능한 업무의 상태까지 완료/실패로 일괄 추정하지 않는다. 공유 DB/보호 제어 실패처럼 공통 전제를 잃으면 공유 쓰기 준비 상태가 내려갈 수 있으며 library 분리로 이를 없앤다고 주장하지 않는다. 새 microservice/circuit breaker/샤딩/분산 잠금 서비스를 추가하지 않는다. 기존 dispatcher의 유한 재시도/실패 진단을 재사용하고 정확한 v2 전달 처리와 최종 U3 실행 경계는 구현에서 검증한다. 적용: NFR6.1, NFR7.1, NFR9.1.

## Observability and Recovery Evidence — SD08

업무별 operation/request/correlation·허용 대상·현재/적용 개정·행위자 참조·결과 코드/단계·대기/실패 출처를 최소 정보로 기록한다. 정상 권한 거절/업무 검토/기술 실패/접수 미확정/이행 미완료를 분리한다. 업무 거절을 서비스 기술 오류에 섞거나 다른 업무 성공으로 장애를 숨기지 않는다. 불변 이력은 primary 기록과 같이 보존하고 일반 로그를 거래 원본으로 승격하지 않는다.

U10은 U3의 접수/조회/수락 실패와 실제 관측을 연결한다. 유지하는 목표는 계획 중단 포함 30일 가용성 99.9%, 장애 발생부터 감지·판단·복원·검증까지 30분 복구다. 원래 p95/오류율·집중/회복 의미 및 점검 KST 평일 20–22시/회당 10분/30일 합계 20분·24시간 전 안내 기준을 보존한다. 10곳/일 1,000건은 계획이고 대량 100k/50분·전체 재해 복구·무중단·장기 관측 실증은 후속이다.

복구 검증에서는 성공 접수 목록과 요청/주문/스냅샷·모든 개정·결과·전후 이력·전달 사실 및 원본 소유자의 현재 결과를 대조한다. 보호 DB 또는 restore 성공만으로 전체 RPO0를 주장하지 않는다. 복구 시도 자동 경로가 있다면 시작부터 기존 개발자 메신저/이메일 알림 경로에 연결하고 실패/수동 조치 필요는 긴급 통지한다. U3는 새 메신저나 자동 복구를 선정/실행하지 않는다. 발송/실제 수신 증거와 점검/배포 절차는 U10/U7의 책임이다. 적용: NFR2.1, NFR3.1, NFR4.2, NFR8.1, NFR10.1.

## Language and Result Semantics — SD10

U3 계약/결과는 한국어 안내·KRW 원 단위·한국 시간의 정확한 의미를 제공한다. 입력 없음/숨김/미확인/적용 없음/확정 0원을 구분하고 상태/원래 요청 결과/다음 확인 조치를 반환한다. 표시 문자열을 상태나 금액 원본으로 사용하지 않는다. HW/SW와 HARDWARE/SOFTWARE, AGREE와 ACCEPT, 논리 REVIEW/REJECTED와 전송 REVIEW_REQUIRED/DECLINED의 대응은 기능 설계대로 유지한다.

고객·직원 UI는 U8/U9가 PC 1280 이상에서 연결·검증한다. 구매 당시 이용 기간과 U6의 실제 이용 기간을 구분한다. 모바일/미국 영어는 후속이며 화면/언어 확장이 권한·금액·상태 의미를 바꾸지 않도록 공통 계약을 유지한다. 영어/해외 저장/통화 지원 완료를 주장하지 않는다. 적용: NFR12.1, NFR12.2.
