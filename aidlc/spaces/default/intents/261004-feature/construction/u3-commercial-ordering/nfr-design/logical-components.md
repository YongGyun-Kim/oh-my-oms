# U3 논리 구성요소와 실패 경계

## 목적과 설계 원칙

[확인한 기준](nfr-design-questions.md)에 따라 기존 한 AWS 계정/CDK·Nest API/worker·TypeORM/PostgreSQL·보호 DB·Outbox/큐를 사용한다. 아래는 논리적 책임 구분이며 각각의 새 서버/DB/배포를 뜻하지 않는다. 현재 U3 library의 실제 영속 모델/HTTP·worker 연결은 후속 구현 대상이다. [security-design.md](security-design.md)의 SD01–SD10 패턴과 연결한다.

텍스트 흐름: 고객/직원 PC → L01/L02의 현재 신뢰·권한 확인 → L03/L04/L05의 명령/조회 → L06 primary 원자 기록 → L07 보호 확인 → 원래 요청 결과 응답. 같은 primary 사실은 L08로 전달하고 L09는 자기 업무 결과를 소유한다. L10/L11은 허용된 대조·검증을 담당한다. 별도 그림이나 새 서비스 토폴로지를 암시하지 않는다.

## Service Boundaries and Ownership — LC02

U3 내부 C03/C04/C05 호출은 같은 실행 기반의 포트로 연결하고 검증된 문맥/대상/개정을 전달한다. 공유 저장소 접근은 U3 원본 소유자의 repository를 통하며 다른 도메인의 원본 테이블을 수정하지 않는다. L02의 공통 신뢰와 L09의 실제 사실은 해당 원본 조회 계약으로 검증한다. 한 DB 사용은 원본 쓰기 권한 공유를 뜻하지 않는다.

U7 수락 후 변경 경로는 U7의 requestChange → decideAfterSales → readAfterSalesFacts 확인 후 U3 C05를 호출한다. U3가 U7을 역조정하지 않는다. 수락 전 REVIEW_PRICE_CHANGE는 U3의 정확한 동의/제안/current order와 명시 null afterSalesDecisionRef를 사용한다. 두 경로의 전제·버전은 C00/C05 v2로 구현한다. 원래 inception v1을 수정하거나 v2를 v1로 표시하지 않는다.

최초 주문 스냅샷은 모든 행/조건별 실제 계약 개정의 합집합을 보존한다. 합의 변경·SW 조기 활성화/추가 보상 동의가 실제 지급/HW/SW 결과를 대신하지 않는다. 주문을 준비/수락/완료로 표현하는 UI도 각 결과의 원본/미확인 시점을 유지한다. 적용: NFR9.3, NFR13.3.

## Failure Domains and Blast Radius — LC03

| 실패 영역 | 영향을 받는 흐름 | 남기는 결과/다음 조치 |
| --- | --- | --- |
| L01 과대 JSON/잘못된 입력/슬롯 포화 | 해당 요청 또는 같은 API 프로세스의 admission | 413/입력 오류/503, 업무 효과 없음 또는 원래 접수 대조 필요를 실제 단계에 맞게 구분 |
| L02 현재 신뢰/조직/사람 근거 | 해당 접근·등록/승인/명령, 공통 신뢰 장애면 더 넓은 접근 | 미확인 허용 금지, 해당 원본 확인/기존 U2 발견 해소 |
| L03/L04 특정 상품/계약 조건 | 관련 주문/조건 적용 | 기존 유효 조건/구매 스냅샷 보존, 업무 확인 필요와 기술 조회 실패 구분 |
| L06 primary/commit counter/복구 제어 | 공유 저장·변경 및 DB가 필요한 조회 | 공통 쓰기 준비 보류 가능; library 구분이 물리 격리 제공한다고 주장하지 않음 |
| L07 보호 저장/세대 대조 | 안전한 성공 쓰기 응답·현재 보호 원본 확인 | primary commit 가능성 보존, 같은 요청의 후보/결과 대조·재보호; 무조건 재주문 없음 |
| L08 발행/큐/worker 전달 | 후속 사실 전달·관련 업무 진행 | 원본 성공 유지·유한 재시도/실패 진단, 전달 지연을 실이행 완료로 표시하지 않음 |
| L09 외부 소유자의 지급/공급/발급/후속 결과 | 그 판단 근거가 필요한 주문/변경 | 전체 FULL 판단은 HOLD, 실제 결과는 소유자 확인, 무관 업무까지 임의 완료/실패 추정 없음 |
| L10 로그/알림/운영 대조 | 가용성/장애 통지·복구 진단 | 실제 관측/수신 미확인 추적, 일반 로그를 거래 원본/접수 증거로 대체하지 않음 |

공유 primary/보호 DB·실행 호스트·전역 counter는 알려진 공유 자원이며 실제 가용성/용량/복구 실패 전파는 미실증이다. 특정 주문의 검토와 공통 인프라 준비 실패를 구분한다. 첫 배포에서 새로운 물리 격리/DB 분할/자동 장애 전환을 추가하지 않는다.

## Isolation Strategy and Shared Resources — LC04

| 경계 | 기존 적용/설계 | 해석 한계 |
| --- | --- | --- |
| 고객/직원 신뢰 경로 | 기존 audience·망 증거·현재 권한, 모든 library/worker 진입의 재검증 | 고객 필드/전달 헤더/망 허용만으로 권한 확정 없음 |
| 기업/조직·데이터 | 불변 TargetScope + 현재 권한으로 조회/목록/이력 제한, 타 기업 원본 노출 없음 | 단순 화면 숨김/사후 전체 목록 필터는 보호 대체 아님 |
| 입력/메모리 | 주문 제출/조건 변경 parser 1MiB, 나머지 64KiB, 100행·정확 타입/정수·실제 decompressed size | 합성 크기와 final v2/runtime 적합성 구분 |
| HTTP 처리 | 기존 프로세스별 최대 25슬롯과 finish/close 해제, 조회 5초/변경 10초 실행 예산 | admission은 실측 처리 용량/고객별 hard isolation 아님 |
| 지속 변경 | 현재 primary 전역 counter 잠금, statement/lock 제한·잔여 예산·expectedRevision/원본 재검증 | 공유 직렬화 병목 미검증, timeout이 commit rollback 보장 아님 |
| 비동기 전달 | 기존 Outbox/큐·worker 유한 실행/재시도·현재 문맥/개정 및 중복 효과 검증 | 전달 횟수 한 번 보장 대신 동일 사실 업무 효과 한 번 |
| 보관/노출 | 별도 보호 DB, 기존 접근/암호화·민감 응답 캐시 방지·최소 로그/근거 참조 | 한 AWS 계정 안의 실제 보호/국내 경로는 설정/작동 증거 필요 |

공통 풀/실행 예산/결과 페이지를 재사용하며 새 무제한 fan-out·동기 외부 재시도·조건/권한 캐시를 추가하지 않는다. 읽기/목록과 업무의 개정 확인을 결합해 오래된 결과를 현재 판단으로 적용하지 않는다. 정확한 U3 DB 모델·제약·인덱스 및 실제 처리 비용은 코드/인프라 단계에서 현재 패턴과 대조한다. 적용: NFR1.1–1.5, NFR5.1–5.6, NFR6.1, NFR7.1, NFR11.2.

<a id="lc05"></a>
## Maintainability and Single Developer Operation — LC05

1인 기술 운영은 기존 deploy/호스트/저장/큐/관측·검사 경계를 재사용하는 구조 목표다. 새 U3 전용 배포/수동 데이터 동기화/별도 account를 만들지 않는다. 현재 정상일 반복 작업 30분/일·일반 배포 사람 작업 15분·대표 장애 사람 복구 30분 목표와 자동 대기/전체 경과 시간을 구분하고 실제 운영 증거는 U10에서 확인한다.

기술 인력 1명이라는 사실이 사업 등록자/검증된 다른 승인자를 한 사람으로 합쳐도 된다는 뜻은 아니다. 승인자가 없거나 정확한 다른 사람 근거가 없으면 적용 보류다. request/operation ID·대상/개정·미확인/실패 코드로 현재 원본·원래 결과를 추적할 최소 대조 경로를 제공한다. 구체적 반복 업무/운영 성공을 문서만으로 증명하지 않는다. 적용: NFR9.1–NFR9.3.

## First Release and Deferred Evidence — LC06

첫 배포는 한국어·KRW·PC 1280 이상 고객/직원 흐름의 제한 파일럿이다. 고객사 10곳 이내·일 1,000건은 계획이다. L03–L05는 권한/정확한 원본/금액·상태/동의·중복·동시 변경과 v2 계약의 실제 구현 검증을 필요로 한다. 80% 전체 작성 제품 코드 커버리지·필수 보안 검사 경계도 유지한다. 단순 검사는 Luna, 공식 체크포인트는 주 실행자가 맡는다.

| 목표/후속 | 이 설계가 남기는 연결 | 증거 책임/시점 |
| --- | --- | --- |
| 계획 중단 포함 30일 99.9% | SD08 업무별 성공/기술 실패 관측 | U10; 실제 30일 실증 후속 |
| 발생~감지/판단/복원/검증 30분, 전체 성공 접수 RPO0 | SD03 원본/요청/결과/보호 후보·전달 사실 대조 | U1/U10; 전체 재해 복구 실증 후속, 안전한 성공 기록은 첫 배포 필수 |
| 원래 p95/기술 오류·집중/회복 | SD07 유한 실행과 관측 의미 | 품질/U10; 짧은 실제 시험 조건은 해당 시험 설계, 대량 100k/50분 후속 |
| 점검·무중단·실제 복구 알림 | SD08 실패/중단·자동 시도부터 기존 두 알림 경로 | U10/U7; 기본 절차/수신 준비는 첫 배포 전, 무중단/전체 실증 후속 |
| 국내 저장·실제 보관/외부 처리·암호화 | SD05/SD06 데이터 목적·경로/권한·근거 | Infra/U10/사업 확인자; 실데이터 전 |
| 실제 공급자/직원망/다른 사람/외부 원본 | SD01/SD04의 검증 원본 없으면 차단 | U1/U2/U4/U5/U6/U7; 해당 실제 접근/거래 전 |
| 모바일/미국 영어 | SD10 의미 보존, 실제 UI는 U8/U9 | U8/U9; 후속 지원 결정/구현 |

Deferred는 전체 실증/확장 경계를 남기는 말이며 첫 배포 안전한 접수·정확성/권한·기본 배포/알림 준비를 면제하지 않는다. 기존 U2 Major·과거 성능 FAIL/보류·원본 출처의 미확인은 그대로 추적한다. 상세 설계 완료는 원래 Unit 전체/실거래/배포 완료가 아니다.
