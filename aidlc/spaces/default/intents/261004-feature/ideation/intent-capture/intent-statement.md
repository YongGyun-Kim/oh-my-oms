# 신규 OMS 서비스 개발 의도

## Problem Statement

B2B를 타겟으로 하며 하드웨어와 소프트웨어 두 상품 타입을 다루는 Order Management System(OMS)을 새로운 서비스로 개발하려고 한다. 현재 사용자는 OMS 도메인 지식이 부족하며, B2B 내 어떤 고객의 어떤 문제를 해결할지, 어떤 기능을 제공할지, OMS의 시스템 책임 경계를 어디까지 둘지 구체적으로 정의하지 않았다. 따라서 지금 해결할 과제는 근거 있는 도메인 이해와 제품 방향의 수립이다. [Q1] [Q2] [Q9]

일반적인 OMS 기능 목록을 이 제품의 확정 요구사항으로 사용하지 않는다. 조사로 확인할 문제와 기능을 구체적인 고객의 필요에 연결한 뒤 제품 범위를 결정한다. 기술 스택과 아키텍처는 먼저 결정하지 않는다. [Q1] [Q8]

## Target Customer

첫 제품의 타겟은 B2B로 확정했다. B2B 내 세부 고객군과 사용 시나리오는 미정이다. 실제 사용자와 이해관계자, OMS 유형별 사용 시나리오를 조사한 뒤 구체적인 target customer와 use case를 정의한다. 특정 업종, 기업 규모, 판매 채널, 국가 또는 업무 담당자는 아직 확정하지 않았다. [Q1] [Q2] [Q4] [Q5] [Q8] [Q9]

OMS에서 다루는 상품 타입은 하드웨어와 소프트웨어 두 타입이다. 이 상품 구분만으로 상세 주문 처리 방식이나 제공 기능을 확정하지 않으며, 고객의 문제와 인접 시스템의 책임 경계를 조사해 결정한다. [Q1] [Q8] [Q9]

## Success Metrics

현재 단계의 목표는 아래 10개 조사·정의 항목에 대한 근거를 확보하고, 사용자가 첫 제품의 방향과 범위를 판단할 수 있게 하는 것이다. 충분한 근거가 확보되었는지에 대한 최종 판단과 Inception 전환은 사용자의 승인을 따른다. [Q1] [Q3] [Q6]

| 확인 항목 | 확인할 결과 | Source |
|---|---|---|
| 도메인 이해 | 비즈니스 문제, OMS 유형·시나리오, 사용자·이해관계자, 주문 lifecycle에 대한 조사 결과 | [Q1] |
| 제품 비교와 경계 | 상용·오픈소스 OMS의 차이, 인접 시스템과의 책임 구분 | [Q1] |
| 초기 제품 방향 | B2B 내 세부 고객군·use case, 하드웨어·소프트웨어 상품 맥락의 기능 구분, MVP 포함·제외 범위 | [Q1] [Q8] [Q9] |
| 제약과 불확실성 | 주요 기술·운영·보안 제약과 assumption의 명시 | [Q1] |
| 다음 단계 전환 | 조사 근거를 검토한 사용자의 Inception 진입 승인 | [Q3] [Q6] |

제품 출시 후의 정량적 성공 지표와 목표값은 아직 정해지지 않았다. 처리 시간, 오류율, 매출, 사용자 수 등의 수치를 임의로 목표로 삼지 않으며, 조사 후 제품 방향과 함께 정의할 미결정 사항으로 남긴다. [Q3]

## Initiative Trigger

새로운 OMS 서비스를 개발하려는 의도가 출발점이다. B2B 타겟과 하드웨어·소프트웨어 상품 타입을 바탕으로, 아직 미정인 세부 고객군·기능·책임 경계를 Ideation에서 충분히 조사하고 정의한 뒤 요구사항과 아키텍처로 넘어가려 한다. [Q1] [Q9]

사용자는 현재 확정된 기한·예산·대상 국가·필수 연동 등의 조건이 없다고 답했다. 이는 이후 조사에서 기술적·운영적·보안적 제약이 발견되지 않을 것이라는 의미가 아니다. 해당 제약의 발견과 정리는 조사 대상이다. [Q1] [Q4]

## Initial Scope Signal

개발 절차의 workflow-selected scope는 `feature`다. 이 선택 자체가 제품 기능이나 고객 범위를 확정하지는 않는다. [scope] [Q8]

사용자가 확인한 제품 경계는 B2B 타겟과 하드웨어·소프트웨어 두 상품 타입이다. 현재 작업 범위는 이 경계 안에서 신규 OMS의 도메인을 조사하고 첫 제품의 방향을 정의하는 것이며, 구체적인 MVP 기능은 조사 결과를 근거로 결정한다. [Q1] [Q8] [Q9]

## Evidence and Decision Principles

- 확인되지 않은 내용은 사실로 가정하지 않고 assumption으로 명시한다. [Q1]
- 일반적인 OMS 기능 목록을 이 제품의 요구사항으로 바로 채택하지 않는다. [Q1] [Q8]
- 기술 스택과 아키텍처를 먼저 결정하지 않는다. [Q1]
- Ideation에서 충분한 근거를 확보한 뒤 사용자의 승인을 받아 Inception의 Requirements와 Architecture로 넘어간다. [Q1] [Q3] [Q6]
- 조사 결과와 결정 사항은 이 대화에서 사용자가 검토한다. [Q7]
