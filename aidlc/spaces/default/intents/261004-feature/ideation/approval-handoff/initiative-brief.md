# B2B OMS 이니셔티브 인계 요약

## 목적과 현재 판단

자사 업무용 하드웨어·소프트웨어를 구매하는 기업과 판매 측 내부 직원이 주문 요청부터 수락·상품 제공·청구/지급·후속 처리까지 상태와 근거를 연결해 확인하는 서비스를 만든다. 현재 자료는 공개 도메인 조사와 사용자의 제품 결정이다. 실제 고객의 불편 빈도·구매 의사·운영 효과는 미검증이다.

**권고: 미검증 사항을 유지하며 Inception에서 요구사항 구체화와 검증을 병행하는 조건부 진행.** 이는 [이번 Q1의 선택](approval-handoff-questions.md)에 따른 권고이며 최종 단계 전환 승인은 아직 대기 중이다. 관련 연동의 구현 약속, 실제 고객 데이터·실거래 도입 전에는 아래 근거와 조건을 확보해야 한다. 구현·출시·상용 운영의 승인을 포함하지 않는다.

## 승인된 제품 방향

| 영역 | 인계할 결정 |
|---|---|
| 고객·상품 | 자사 업무용 구매 기업. 판매 상품 등록은 내부 직원만, 고객은 직접 주문 요청. 하드웨어·소프트웨어 주문 분리 |
| 주문·하드웨어 | 조건별 자동 확정/직원 확인. 재고 출고/주문 후 확보 모두 지원하고 품목별 진행·부분 이행·배송 결과 연결 |
| 소프트웨어 | 우리 측의 영구·기간제 권한 발급·기간 관리. 요청 갱신/사전 합의된 자동 갱신 모두 지원 |
| 대금·예외 | 선결제/후불, 청구·지급 상태 구분. 변경·취소·반품과 필요한 회수·환불 결과, 실패 확인·재처리 |
| 접근·화면 | 고객 PC 우선·PC/모바일 웹. 직원 사내망 PC 전용·직원 모바일 제외. 기업별 접근·행위 권한·중요 처리 이력 |
| 인력·기술 | 개발자 1명이 필요한 개발·운영을 수행할 수 있는 구조가 목표. 인원 수로 기능 축소 금지. AWS·CDK 사용 |

첫 제품은 [범위 문서](../scope-definition/scope-document.md)의 SC-01–SC-10과 [백로그](../scope-definition/intent-backlog.md)의 Must 10개 업무를 포함한다. 외부 상품 등록·혼합 주문, 전사 PIM/CRM/구매 승인/인사·창고·구매 원장·회계/세금 시스템 전체, 실제 운송·결제망, 소프트웨어 실행 시 권한 검증 기능 자체 등 OUT-01–OUT-09는 직접 구축/지원에서 제외한다. 필요한 요청·결과 연결 책임은 남으며 모든 인접 제품 커넥터를 필수로 만들지 않는다.

## 조사·화면·실행 가능성의 근거

[패턴 조사](../market-research/competitive-analysis.md)는 Enterprise OMS, Commerce Platform, Open Source, ERP/WMS의 업무·사용자·도메인·책임 차이를 비교했다. 공급사 자료·공개 소스의 존재가 우리 고객 수요와 투자 수익을 증명하지는 않는다. [시장 신호](../market-research/market-trends.md)와 [개발·활용·연동 비교](../market-research/build-vs-buy.md)는 이 한계와 검증할 가설을 명시한다.

[화면 초안](../rough-mockups/wireframes.md) 13개와 [사용자 흐름](../rough-mockups/user-flow.md) 9개는 고객의 주문·갱신 현황, 직원의 처리 업무를 시작점으로 한다. 청구/지급 구분과 직원 일반·완료 주문 조회를 보완했고 [최신 검토](../rough-mockups/reviews/review-03.md)의 두 의견은 해소됐다. 이는 실제 사용자·보안·접근성 시험 통과를 의미하지 않는다.

[실행 가능성 평가](../feasibility/feasibility-assessment.md)는 개발 불가능을 입증하지도, 기간·비용·상용 운영 가능성을 보장하지도 않는다. [제약 등록부](../feasibility/constraint-register.md)의 자료·연동·운영 불확실성을 그대로 인계한다. Team Formation은 확인된 1인 프로젝트에 대한 단계 조건으로 생략됐다. 별도 인력·예산·일정이 배정되었다고 기록하지 않는다.

## 조건과 다음 단계의 과제

| 먼저 확인할 것 | 해소해야 할 시점·판단 |
|---|---|
| 실제 고객 수요·정상/예외 주문·구매 가치 | 요구사항 구체화와 병행 검증. 자료 미확보 시 가설을 유지하고 투자·구현 범위 약속 전에 남은 불확실성을 사용자에게 제시 |
| 수락·청구/지급·제공·갱신·변경 정책 | 관련 요구사항을 확정하기 전 OQ-01–OQ-06·OQ-10을 구체화. 접수와 완료, 자동 갱신과 자동 결제를 구별 |
| 공급·출고·수금·권한 적용의 실제 주체와 접근권 | 관련 연동의 구현 약속 전 필요한 동작·증거·시험 접근 확인. 없으면 해당 약속을 보류하고 대안 검토 |
| 직원 사내망·세부 권한·데이터·계약 조건 | 접근 통제 요구사항·설계에서 정의하고 실제 데이터·실거래 도입 전 검증. 사내망 접속만으로 모든 권한을 주지 않음 |
| 1인 수행·운영 규모·지원·비용 | 후속 설계·운영 검증에서 작업 부담과 목표를 측정. 충족하지 못하면 구조·자동화·운영 방식 개선 |

확인된 승인자는 사용자이며, 실제 고객·추가 이해관계자 전체의 합의는 미확인이다. [이해관계자 기록](../intent-capture/stakeholder-map.md)과 [개발 의도](../intent-capture/intent-statement.md)를 기준으로 한다. 상세 인계 조건·담당 제안은 [결정 기록](decision-log.md), 문서 연결과 실증 한계는 [단계 연결 검증](../../verification/phase-check-ideation.md)에 둔다. 조건을 충족하지 못했다고 임의로 완료 표시하거나 미정 정책을 구현 기본값으로 채우지 않는다.

## 최종 승인에서 결정할 것

이 문서와 남은 검증 조건을 근거로 **Inception 진입 여부**를 결정한다. 승인 시 다음 단계는 Practices Discovery이며 이후 Requirements·Architecture를 구체화한다. 사용자 승인 전에는 진입하지 않는다. 지금은 추가 기술 스택·아키텍처·개발 일정·투자 금액을 정하지 않는다.
