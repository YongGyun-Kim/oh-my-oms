# Ideation 결정과 인계 조건

## 기록 기준

이 문서는 사용자 결정의 읽기용 정리다. 단계 상태와 실제 승인 이력의 원본은 [aidlc-state](../../aidlc-state.md)와 기록의 audit 폴더다. 초기 문서는 당시의 미정 상태를 보존하며 최신 사용자 결정이 해당 항목을 구체화하거나 대체한다. 문서 승인, 사업 검증 완료, 구현·출시 허가는 구별한다.

근거 약어: IC는 [Intent Capture 답변](../intent-capture/intent-capture-questions.md), MR은 [Market Research 답변](../market-research/market-research-questions.md), FQ는 [Feasibility 답변](../feasibility/feasibility-questions.md), SQ는 [Scope 답변](../scope-definition/scope-definition-questions.md), RQ는 [Rough Mockups 답변](../rough-mockups/rough-mockups-questions.md), HQ는 [이번 인계 답변](approval-handoff-questions.md)이다.

## 경계·보완의 반영 상태

- [scope-document](../scope-definition/scope-document.md)의 고객·업무 결정은 초기 [stakeholder-map](../intent-capture/stakeholder-map.md)의 미정 항목을 제품 방향 수준에서 구체화했다. 실제 인물·조직 전체의 참여나 합의를 새로 확인한 것은 아니다.
- [constraint-register](../feasibility/constraint-register.md)의 C09·C12·C13은 고객·범위·제공 방식에 대한 선택으로 일부 구체화됐다. 실제 실행 원본·계약·접근권·운영 효과는 계속 미확인이다.
- 직원 사내망 접근은 Rough Mockups에서 추가된 사용자 제약으로 SC-01·OQ-07과 함께 인계한다. 상위 문서에 없다는 이유로 이 조건을 누락하지 않는다. 사내망의 판별·원격 예외·접속 중 변경 처리는 미정이다.
- [wireframes](../rough-mockups/wireframes.md)의 C04·S03은 청구·지급 구분을, S07은 사내망 PC에서 일반·완료 주문 조회와 복귀를 표현한다. [최신 화면 검토](../rough-mockups/reviews/review-03.md)는 두 의견 모두 Resolved다. 과거 Accepted risk를 현재 처리 방침으로 승계하지 않는다.
- [Intent Capture 최신 검토](../intent-capture/reviews/review-02.md)의 세 의견도 Resolved다. 기록된 미해결 문서 검토 의견이 없다는 것과 미정 정책·사업 위험이 없다는 것은 별개다.
- Team Formation은 1인 프로젝트의 조건부 생략이며 team-assessment는 생성하지 않았다. 이를 누락된 필수 팀 문서나 추가 인력 배정 완료로 해석하지 않는다.

## Inception에 전달할 검증 조건

HB는 인계 조건 ID다. 담당은 역할별 **제안**이며 별도 인원을 확보했다는 뜻이 아니다. 기한은 달력 날짜가 아니라 의사결정 시점이다. 모든 조건은 현재 Open이다.

| ID | 확인할 근거·결정 | 담당 제안 | 해소 시점·미충족 시 처리 | 연결 |
|---|---|---|---|---|
| HB-01 | 실제 고객의 정상·예외 주문, 문제 반복성, 기존 도구 대비 가치·지불 의사 | 사용자·제품 담당 역할 | 요구사항 구체화와 병행. 자료가 없으면 가설 유지, 투자·구현 약속 전 사용자에게 미확인 영향 제시 | OQ-08; Feasibility C05·R01 |
| HB-02 | 수락·거절·보류 조건, 주문/품목 구성, 완료·부분 이행·변경/취소/반품 정책 | 사용자·업무 담당 역할 | 해당 요구사항 확정 전. 없으면 모호한 자동 처리 규칙을 구현하지 않음 | OQ-01·OQ-05·OQ-10; R04 |
| HB-03 | 청구·지급 기한·근거·미수금, 제공·갱신과 지급의 관계 | 사용자·대금 업무 역할 | 해당 정책 확정 전, 실거래 도입 전 실행 근거 검증. 자동 결제·정기 청구는 별도 범위 결정 | OQ-02; SC-05·SC-08 |
| HB-04 | 공급·재고·출고·배송·수금의 실제 주체, 원본·참조·권한·시험 접근·계약 | 사용자·개발자 | 해당 연동 구현 약속 전. 미확보 연동을 구현 가능으로 약속하지 않고 대안/범위 판단 제시 | OQ-03; C11·C12·C17; R03·R06·R10 |
| HB-05 | 권한 대상·수량·기간 시작·전달/적용 환경, 갱신 합의·해제·가격·실패·중복·회수 | 사용자·개발자 | 관련 요구사항 확정 전, 실제 제공·갱신 전 검증. 실행 통제 기능 자체의 구축 제외는 유지 | OQ-04·OQ-06; R03·R05·R08 |
| HB-06 | 기업·직원 신원/행위 권한, 사내망 범위·판별·원격 예외·접속 중 조건 변경, 결과 비밀 취급 | 사용자·개발자·보안 역할 | 접근 요구사항·설계에서 정의, 실데이터 도입 전 검증. UI 숨김을 접근 통제로 간주하지 않음 | OQ-07, RQ Q4; C15; R07·R08 |
| HB-07 | 국가·실제 데이터·보관/삭제·계약·지원 및 적용 의무 | 사용자, 필요 시 해당 전문가 | 실데이터·실거래 도입 전. 미확인 규정이나 인증 충족을 주장하지 않음 | OQ-08; C16; R09 |
| HB-08 | 거래 규모·지원 시간·복구 기대·비용 입력·AWS 환경 준비·1인 수행 측정 기준 | 사용자·개발자 | 설계 검증 기준·상용 약속 전. 미달하면 구조·자동화·운영 방식 개선하고 재검증 | OQ-09; C03·C04·C08·C10·C14; R02·R11 |

판단 기준은 증거의 존재와 정책의 일관성이다. 실제 확인 없이 HB를 종료하지 않는다. 합성 시나리오는 모순 발견에 활용하되 실제 고객·연동 검증으로 표시하지 않는다. 연락·자료 전송 등 외부 행동은 별도 사용자 지시를 따른다.

## 남은 승인과 위험의 의미

[feasibility-assessment](../feasibility/feasibility-assessment.md)의 판정은 조건부이며, [RAID](../feasibility/raid-log.md)의 위험은 이번 기록만으로 종료되지 않는다. 제품 역할·업무 경계가 정해졌어도 실제 실행 주체와 제공 조건을 확보해야 한다. 시장 조사만으로 투자 타당성이나 출시 기한을 확정할 근거는 없다.

확인된 사용자에게 인계 문서의 최종 승인을 받으면 Inception의 Practices Discovery부터 이어간다. Requirements·Architecture에서는 D 결정과 HB 조건을 입력으로 사용한다. 승인 전에는 다음 단계 진입을 완료로 표시하지 않는다. 최종 결정은 도구가 기록하는 단계 승인 이력으로 확인한다.

## Assumptions & Open Questions

- [assumption] 선택한 고객의 문제와 제품 가치가 실제 사례에서 확인될 것이다. HB-01로 검증한다.
- [assumption] 필요한 실행 주체·연동·권한 적용 환경을 확보할 수 있다. HB-04·HB-05로 검증한다.
- [assumption] 후속 설계가 합의할 업무량에서 1인 개발·운영 목표를 충족할 것이다. HB-08로 검증한다.
- D-25는 검증을 병행하는 계획 선택이며 위 가설의 사실 확인이 아니다. OQ-01–OQ-10과 HB-01–HB-08은 미해결 상태로 전달한다.
