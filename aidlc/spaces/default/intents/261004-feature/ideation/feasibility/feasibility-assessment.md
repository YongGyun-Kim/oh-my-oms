# B2B OMS 실행 가능성 평가

작성일: 2026-10-05. 상태: 사용자 검토용. 기술 실증·고객 검증·출시 승인 문서가 아니다.

## 평가 결론

**분석: 고객과 업무 범위를 좁히는 Ideation은 계속할 수 있다. 특정 MVP를 정해진 비용·기간 안에 구현하고 상용 운영할 수 있는지는 아직 판단할 근거가 부족하다.** 알려진 조건만으로 개발 불가능이라고 판단할 근거도 없다. 따라서 이번 결론은 개발 착수나 운영 약속에 대한 Go 판정이 아니다.

현재 가장 큰 불확실성은 기술의 존재보다 **누구의 어떤 주문 문제를 해결하는지**, 그리고 **필요한 기능의 개발과 운영을 1명이 충분히 수행할 수 있는 구조를 어떻게 실현하고 검증할지**다. 사용자는 1인 개발을 기능 범위의 제약으로 두지 말라고 명시했다. 기능의 필요성과 우선순위는 고객 문제와 제품 가치로 판단하고, 1인 수행 가능성은 달성해야 할 설계 목표로 다룬다. 실제 업무를 검증할 사람·자료가 없다는 점은 확인된 제약이다. 공개 OMS 사례는 가능한 패턴을 설명하지만 우리 고객의 필요성과 구현 적합성을 증명하지 않는다.

| 판단 대상 | 현재 판정 | 근거와 한계 |
|---|---|---|
| 도메인 조사와 고객군·use case 후보 비교 | 진행 가능 | 승인된 네 범주 패턴 조사 존재. 고객 선택은 아직 미정 |
| 특정 주문 시나리오의 업무 타당성 | 미검증 | 실제 주문 담당자·주문 자료 미확보 |
| AWS·CDK 사용 | 사용자 확정 제약 | 서비스·리전·계정·언어·운영 환경 확보 여부는 미확인 |
| MVP의 기술 구현·외부 연동 가능성 | 조건부 검토 대상 | MVP, 연동 대상, 계약·API 접근권 및 실패 처리 정책 미정 |
| 개발 기간·총비용·처리량 | 산정 보류 | 범위, 투입 시간, 트래픽, 지원 수준 입력 없음 |
| 상용 운영과 보안·규정 충족 | 미검증 | 1인 개발·운영을 뒷받침할 구조의 효과, 데이터·국가·계약 조건 미검증 |

## 확인된 사실과 증거 수준

- **사용자 결정:** 신규 B2B OMS이며 하드웨어·소프트웨어 두 상품 타입을 다룬다. 고객군·주문 정책·MVP는 후속 정의한다. [개발 의도](../intent-capture/intent-statement.md)
- **사용자 답변 Q1 및 후속 정정:** 개발·운영 참여 인력은 개발자 1명이다. 이 인원 수를 기능 범위를 제한하는 제약으로 두지 않으며, 필요한 기능 개발과 운영을 1명이 충분히 수행할 수 있는 구조를 만드는 것이 확정된 설계 목표다. 전담 시간·경험·운영 조건과 목표 달성 여부는 아직 확인되지 않았다.
- **사용자 답변 Q2:** 실제 업무 검증을 위한 사람·자료는 현재 없다. 공개 제품 조사 자료와 고객의 실제 업무 자료는 구별한다.
- **사용자 답변 Q3:** AWS와 CDK를 사용한다. AWS 계정이 이미 구성되어 있다거나 특정 AWS 서비스가 적합하다는 뜻은 아니다.
- **기존 답변:** 확정된 예산·기한·대상 국가·필수 연동 조건은 없다. 무제한 예산·무기한 일정이나 규제 의무 부재로 해석하지 않는다.
- **조사 한계:** 이번 평가는 문헌과 사용자 답변에 근거한다. 인터뷰, AWS 계정 점검, 배포, 연동 시험, 부하 시험은 수행하지 않았다.

| 돈과 이행의 관계 | 선결제·후불·부분 청구 가능성 | 일회 판매·기간제·사용량 과금 가능성 | 실제 판매 형태부터 확인; 모든 모델을 지원하지 않음 |

두 상품 타입을 다룬다는 결정만으로 같은 주문에 혼합 판매하거나, 하드웨어 배송 후에만 소프트웨어를 제공한다고 가정하지 않는다. 설치·검수·갱신·반품도 사업별 적용 여부를 먼저 확인한다.

외부 이벤트 위험의 구체적 사례로 Stripe는 이벤트의 도착 순서를 보장하지 않으며 중복 전달이 가능하다고 설명한다. 이는 선택된 모든 제공자의 동일한 동작을 증명하지 않는다. 연동 대상이 정해지면 해당 제공자의 약속과 실제 동작을 따로 확인해야 한다. [Stripe Webhooks](https://docs.stripe.com/webhooks)

## 1인 개발·운영을 가능하게 하는 설계 목표

**사용자 결정:** 인력 1명을 이유로 필요한 기능을 제외하거나 개발·운영 범위를 자동 축소하지 않는다. 필요한 기능을 개발하고 운영하는 일을 1명이 충분히 수행할 수 있는 구조를 지향한다. 이 목표는 확정이며 달성 여부는 후속 설계·구현 검증 대상이다.

**분석:** 반복 작업, 복잡한 변경, 잦은 수동 개입은 설계로 해결할 과제로 다룬다. 기능 범위는 고객 가치와 실제 업무 근거로 결정한다. 현재 단계에서는 구체적인 자동화 도구나 서비스 구성을 선택하지 않는다.

후속 설계가 줄여야 할 개발·운영 부담을 식별하는 관점은 다음과 같다.

- 업무 종류의 수: 주문 조회와 실제 취소·환불·권한 회수는 책임이 다르다.
- 외부 연동의 수와 다양성: 공급자별 인증·상태·오류·정책 차이가 지원 범위를 늘릴 수 있다.
- 고객별 차이: 계약 조건과 예외 정책의 개별화가 반복되면 제품 개발 외의 운영 일이 생긴다.
- 시간 제약: 고객이 요구하는 응답 시간과 개발자의 대응 가능 시간이 맞는지 확인해야 한다. 24시간 대응을 약속하지 않는다.
- 수동 처리: 초기 수동 보완이 가능하다는 가설은 처리량과 복구 난도를 확인해야 성립한다. 수동 처리를 무비용 대안으로 계산하지 않는다.

**검증 제안:** 후속 단계에서 기능 변경·검증·배포에 필요한 작업 시간, 정상 주문당 수동 개입, 예외당 처리 시간, 장애 진단·복구 작업, 문의 대응 부담을 관찰한다. 반복 작업의 자동화, 일관된 변경 절차, 운영 상태 파악과 복구의 용이성을 평가할 기준으로 사용한다. 목표값과 검증할 거래 규모·서비스 수준은 실제 업무를 확인한 뒤 정한다. 기준을 충족하지 못하면 구조와 자동화·운영 방식을 개선한다. 인원 수만을 이유로 기능을 제외하지 않으며, 목표 달성이 검증되었다고 미리 주장하지 않는다.

## AWS·CDK 및 보안·준수 검토

**확인한 사실:** AWS CDK는 코드로 인프라를 정의하고 AWS CloudFormation을 통해 프로비저닝하는 도구다. 도구 선택 자체가 OMS 업무 정책이나 운영 적합성을 검증하지는 않는다. [AWS CDK 공식 개요](https://docs.aws.amazon.com/cdk/v2/guide/home.html)

**확인한 사실:** AWS 책임 공유 모델에서 고객 측 책임은 선택한 서비스에 따라 달라지며, 데이터와 접근 권한 등 제품 운영 측에 남는 책임이 있다. 따라서 AWS 사용만으로 우리 제품의 보안·준수가 충족됐다고 판단하지 않는다. [AWS 책임 공유 모델](https://aws.amazon.com/compliance/shared-responsibility-model/)

**검토 제안:** 구현 설계 전에는 필요한 운영 책임을 먼저 식별한다. 현재 서비스 구성·계정·리전·배포 방식·CDK 언어는 선택하지 않는다.

| 확인할 영역 | 필요한 정보 | 현재 다루는 수준 |
|---|---|---|
| 사용자와 기업 간 접근 | 실제 역할, 고객사 관계, 민감한 주문·가격 정보 | 타사 정보 노출·오조작 위험 검토. 멀티테넌트 구조는 미정 |
| 외부 인증과 비밀 정보 | 연동 계정·API 키·소프트웨어 키의 취급 범위 | 위조 결과·키 노출·잘못된 대상에 제공되는 위험 검토 |
| 변경과 복구 | 누가 취소·환불·권한 회수를 결정하며 근거를 보관하는가 | 변경 이력과 복구 판단의 필요성 확인. 구현 방식 미정 |
| 데이터·계약·규정 | 판매 국가, 실제 데이터 항목, 보관·삭제·위탁 조건 | 특정 법률·인증의 적용 여부나 보관 기간을 단정하지 않음 |
| 비용과 운영 | 예산, 고객·주문 규모, 지원 시간, 복구 기대 | 산정 입력과 책임자 확인. AWS 요금 견적·가용성 수치 없음 |

아래는 **후속 검증 제안**이며 아직 실행한 결과가 아니다. 합성 시나리오는 정책 모순을 찾는 데 사용하고 고객 수요의 증거로 표시하지 않는다.

| ID | 확인 시점 | 할 일과 확보할 증거 | 판단 기준과 미확보 시 대응 |

| V2 | Ideation 최종 검토 전 | 상품별 판매·제공·취소 의미와 OMS/외부 시스템 책임 표 작성 | 각 단계의 판단자·원본·완료 증거가 설명됨. 미정 정책은 범위를 좁히거나 후속 검증으로 명시 |

| V4 | 외부 연동 구현 약속 전 | 선택한 대상의 공식 문서·접근권·시험 환경·이용 조건 확인 | 필요한 동작과 실패 후 확인 가능성을 입증. 접근 불가면 해당 연동의 구현 약속 보류 |
| V5 | 후속 설계 및 상용 운영 검증 전 | 필요한 기능 개발·배포·운영의 수동 개입, 변경/복구 작업, 예상 규모와 서비스 수준에 따른 수행 기준 정의 | 1명이 수행 가능한지 검증. 미달하면 구조·자동화·운영 방식을 개선하며 인원 수만으로 기능을 축소하지 않음 |
| V6 | 실제 고객 데이터·실거래 도입 전 | 데이터·권한·운영 책임과 적용 계약/규정 확인, 복구·오조작 대응 검증 | 출시 판단에 필요한 근거 확보. 누락된 범위의 실거래 운영은 승인 대상으로 올리지 않음 |

업무 검증에서 사용할 예시는 하드웨어 잔량 지연, 소프트웨어 제공 실패, 결과 미확인 중 재요청, 취소 요청 후 뒤늦은 완료 통보다. 혼합 주문·반품·권한 회수는 실제 대상 업무에 해당할 때만 추가한다. 각 사례는 예상 판단, 담당자, 고객 안내, 완료 증거를 비교한다. 합성 사례 통과는 API·수요·운영 검증을 대체하지 않는다.

## 다음 단계로 넘길 내용

[market-trends](../market-research/market-trends.md)의 고객군 후보와 [build-vs-buy](../market-research/build-vs-buy.md)의 가치 가설을 고객 문제와 제품 가치로 비교한다. **1인 개발·운영을 가능하게 하는 구조**는 설계 목표로, **실무 자료 없음과 AWS·CDK**는 각각 검증 제약과 기술 제약으로 전달한다. 특정 고객군·OSS·상용 제품·개발 구조를 이번 평가로 선정하지 않는다.

검토할 핵심은 고객에게 가치 있는 최소 업무, 시스템별 책임, 포함·제외 후보, 소프트웨어 제공 형태, 운영 약속의 범위다. 이번 단계 승인과 Inception 진입 승인은 별개이며, Requirements·Architecture를 시작하지 않는다.

## Assumptions & Open Questions

- A1 [assumption]: 후속 단계에서 제안할 구조·자동화·운영 방식이 합의된 업무량과 서비스 수준에서 1인 개발·운영 목표를 충족할 수 있다는 가설. 아직 구조가 제안되거나 검증되지 않았다. 1인 수행 가능성을 목표로 삼는 것 자체는 사용자 결정이며 assumption이 아니다.
- A2 [assumption]: 합성 주문 사례로 초기 정책 모순 일부를 찾을 수 있다는 가설. 고객 수요·실거래 검증으로 사용하지 않는다.
- A3 [assumption]: 고객 업무 근거와 연동 접근권을 이후 확보할 수 있다는 가설. 확보 불가 시 범위나 제품 가설을 재검토한다.
- 미확인: 개발 경험·투입 시간·운영 지원, 예산·처리량, 고객·상품 세부 형태, 계정·데이터·계약 조건. 상세 해소 항목은 [제약 등록부](constraint-register.md)와 [RAID](raid-log.md)에 기록한다.
