# OMS 고객·직원 사용자 흐름

상태: 검토용 업무 흐름. 실제 상태 전이 모델·API·구현 구조가 아니다. 화면 ID는 [wireframes](wireframes.md)의 C01–C06, S01–S07을 가리킨다.

## 적용 전제

[intent-statement](../intent-capture/intent-statement.md), [scope-document](../scope-definition/scope-document.md), [intent-backlog](../scope-definition/intent-backlog.md)와 [이번 답변](rough-mockups-questions.md)을 근거로 한다. PC 웹을 우선한다. 고객은 PC·모바일 웹에서 같은 업무를 지원하고, 내부 직원은 Q4에 따라 사내 내부망의 PC 웹으로만 접근하며 직원 모바일 화면은 제공하지 않는다.

고객의 시작은 자기 기업의 주문·갱신 현황 C01, 직원의 시작은 처리 업무 S01이다. 역할·기업 문맥은 접근이 허용된 상태를 전제로 하며 실제 가입·로그인·역할 부여 절차는 OQ-07에서 정의한다. 한 사용자가 역할을 자유롭게 전환하거나 타 기업을 조회한다고 가정하지 않는다. 직원 흐름 F02–F07의 직원 업무 및 F08의 직원 조회에는 F09의 사내망·직원 권한 조건이 공통으로 적용된다.

상품 등록은 내부 직원만 가능하다. 하드웨어와 소프트웨어는 **서로 다른 주문**이다. 소프트웨어는 우리 측이 권한을 발급한다. 선결제·후불 및 요청·자동 갱신을 모두 유지하되 미정 조건을 확정하지 않는다.

## 전체 흐름 지도

기호는 연결 관계만 표현한다. 화면 ID의 뜻은 아래 텍스트 설명과 개별 흐름에 명시한다.

```text
C01 --> C02 --> C03 --> C04 --> C06
 |                      |
 +----------> C05 <-----+

S01 --> S07 --> S03
S01 --> S03 --> S04 --> S06
S03 --> S05 --> S06
S01 --> S06
S01 --> S02
```

텍스트 설명: 고객은 주문·갱신 현황에서 상품을 골라 타입별 주문 요청을 제출하고, 주문 상세에서 지급과 제공 결과 또는 변경 요청으로 이동한다. 소프트웨어 권한·갱신은 현황이나 해당 주문에서 연다. 직원은 처리 업무에서 주문 근거를 확인하고 상품 타입에 따라 하드웨어 이행 또는 소프트웨어 제공으로 이동한다. 직원 탐색의 주문 메뉴에서는 S07의 권한 내 일반·완료 주문 목록으로 이동하여 S03 상세를 열 수 있으며, 이 경로는 처리할 업무가 없어도 이용 가능하다. 필요한 예외는 변경·예외 상세에서 처리하며, 상품 등록은 직원 상품 화면에서 별도로 수행한다. S04와 S05는 서로 다른 주문의 경로이며 같은 주문의 순차 단계가 아니다. 각 상세에는 원래 목록·연결 주문으로 돌아가는 경로가 있다.

## F01 — 고객이 상품을 확인하고 주문 요청

대상: 자사 업무용 구매 기업의 담당자. 시작: C01의 상품 메뉴. 범위: SC-02·SC-03·SC-04, IB-02–IB-04.

| 단계 | 화면·고객 행동 | 화면에 나타날 결과 |
|---|---|---|
| 상품 확인 | C02에서 하드웨어 또는 소프트웨어 상품 확인 | 판매 정보와 확인 가능한 조건 |
| 요청 준비 | C03에서 해당 타입의 주문 내용 입력 | 기업·상품·요청 내용, 거래 조건과 확인 필요 항목 |
| 내용 검토 | C03에서 제출 전 대상·내용 확인 | 수정하거나 요청 제출 가능 |
| 요청 제출 | C03에서 ‘주문 요청 제출’ | 접수 여부와 확인 가능한 주문 참조 |
| 판매 판단 결과 확인 | C04로 이동 | 자동 확정 결과 또는 직원 확인 필요 상태 등 정책에 따른 결과 |

정상 결과는 고객이 접수와 판매 확정 여부를 구분해 확인하는 것이다. 직원 확인이 필요하면 F02로 연결되고, 자동 확정이면 같은 조건·권한 확인 아래 F03 또는 F04로 이어진다. 직원이 모든 주문을 다시 승인하는 흐름으로 만들지 않는다.

오류·복구: 입력 오류는 값을 유지하고 해당 입력으로 이동한다. 제출 응답이 없으면 이미 접수되었을 가능성을 남겨 ‘결과 확인 필요’와 기존 요청 확인 경로를 제공한다. 접수 여부 확인 없이 동일 주문을 새로 만들도록 유도하지 않는다. 혼합 타입 요청은 허용하지 않으며 분리하여 요청하도록 안내한다. 서버 보장 방식·요청 식별 규칙은 후속 설계에서 정의한다.

## F02 — 직원이 주문 확인과 거래 조건 판단

대상: 해당 주문 판단 권한을 가진 직원. 시작: S01의 확인 업무 또는 S07 주문 목록에서 연 S03 상세. 일반·완료 주문 조회만 필요한 경우 새 판단을 제출하지 않는다. 범위: SC-01·SC-04·SC-05.

1. S01에서 확인이 필요한 이유와 연결 주문을 식별한다.
2. S03에서 고객 요청, 판매 판단 근거, 거래 조건과 주문에 연결된 청구 내용·청구 상태 및 별도의 지급 결과를 읽는다. 청구 참조·대상·금액·기한은 확인된 정보만 표시하고 미확인은 그대로 남긴다. 고객은 C04의 대금 영역에서 자기 기업에 공개 가능한 같은 구분의 청구·지급 정보를 확인한다.
3. 정책에 따라 가능한 판단과 영향을 검토한다. 수락·보류·거절 등의 최종 명칭과 조건은 OQ-01에 따른다.
4. 판단을 제출하고 기록된 결과를 확인한다. 고객 C04에는 공개 가능한 수락 상태·진행 결과를 연결한다.
5. 이행 가능한 조건이면 해당 타입의 F03 또는 F04로 이어진다. 직원의 판단 제출 자체가 실제 상품 제공 완료를 뜻하지 않는다.

지급 관계: **선결제는 지급 확인 후 제공**, 후불은 **합의된 거래 조건에 따라 제공하고 기한 내 지급**이다. 요청 접수·수락·청구의 세부 순서와 미수금 조치는 OQ-01·OQ-02에서 결정한다. 모든 후불 주문을 미지급이라는 이유로 차단하거나, 모든 수락 주문을 무조건 즉시 제공하지 않는다. 청구 전(확인됨), 청구 후 지급 미완료, 청구 정보 확인 불가를 화면에서 구별하며 청구 조회 실패를 미청구로 표시하지 않는다. 지급 결과는 청구 상태와 별도 영역에 유지한다.

오류·복구: 근거 부족·상태 변경·권한 부족은 원인과 확인 경로를 제시한다. 판단 결과 응답이 불명확하면 현재 주문·처리 이력을 조회한 뒤 가능한 다음 행동을 안내한다. 중복 판단으로 재출고·재발급을 유도하지 않는다.

## F03 — 하드웨어 확보·출고·배송 결과

대상: 해당 이행 권한을 가진 직원과 주문을 조회하는 고객. 시작: 이행 조건을 확인한 하드웨어 주문 S03/S04. 범위: SC-05·SC-06·SC-09.

| 분기 | 직원의 업무 | 확인할 실제 결과 |
|---|---|---|
| 보유 재고 출고 | S04에서 재고·제공 조건 근거 확인 후 출고 요청 | 출고 요청 접수, 실제 출고와 배송 결과 |
| 주문 후 확보 | S04에서 상품 확보 요청·진행 확인 후 가능한 출고 요청 | 확보 결과와 잔량, 출고·배송 결과 |

실제 공급·창고·운송 주체가 제공한 확인 근거를 주문에 연결한다. 결과 입력·연동 수단, 직송, 예약/할당 원본은 OQ-03으로 남긴다. 고객 C04에서 품목별 진행·잔량·지연과 확인 가능한 결과를 본다. 상품 제공과 후불 지급은 별개로 표시한다.

오류·복구: 재고 확인 실패·확보 지연·부분 출고·늦은 배송 통보는 해당 단계의 미확인/남은 업무로 보여 준다. 결과 미확인을 출고 실패로 단정하지 않는다. 중복·상충 결과는 기존 요청과 대조하고 S06에서 판단한다. 이 화면에서 창고 위치·피킹·운송 실행 전체를 구현하지 않는다.

## F04 — 우리 측 소프트웨어 권한 발급

대상: 발급 조건을 충족한 소프트웨어 주문의 처리 주체와 고객. 시작: S03/S05. 범위: SC-05·SC-07·SC-09.

1. S05에서 대상 기업·주문·상품·영구/기간제와 제공 조건을 확인한다.
2. 허용된 발급 처리를 요청한다. 우리 측이 권한 생성과 이용 기간 적용을 책임진다. 자동 처리와 직원 조작의 구체적 분담은 후속 정책·설계에서 정한다.
3. 발급 결과, 고객에게 제공한 결과, 기간 반영 여부를 확인한다. 전달 방식은 키·계정 등 어느 하나로 미리 정하지 않는다.
4. 고객은 C04에서 소프트웨어 제공 결과를, C05에서 자신에게 허용된 권한 정보와 기간을 확인한다.

영구형에 임의 만료를 붙이지 않으며 기간제의 시작 기준은 OQ-04로 남긴다. 권한 발급 성공은 소프트웨어 실행 환경에서의 적용·사용 성공까지 증명하지 않는다. 실행 시 권한 검증 기능 자체는 범위 밖이지만 적용 주체와 연결 근거를 확보해야 한다.

오류·복구: 발급·전달·기간 반영 중 어느 결과가 확인됐는지 구분한다. 응답이 불명확하면 S06에서 기존 발급 결과와 대조한 뒤 허용된 재처리를 한다. 고객에게는 중복 갱신/재구매 대신 현재 결과 확인 경로를 제공한다.

## F05 — 기간제 요청 갱신과 자동 갱신

대상: 기간제 권한을 가진 기업 고객과 갱신 처리 주체. 범위: SC-07·SC-08·SC-09.

| 방식 | 시작과 고객 행동 | 처리·확인 경로 |
|---|---|---|
| 고객 요청 갱신 | C01 또는 C05에서 기간·현재 조건 확인, 갱신 내용 검토 후 요청 제출 | 요청 접수 → 갱신 조건 확인 → 기간 반영/결과 확인 → C05에 결과 표시; 직원 확인이 필요하면 S05 |
| 사전 합의된 자동 갱신 | 합의된 조건·시점 충족; 매번 고객이 새 요청을 제출하는 흐름은 아님 | 합의·지급 관계 등 적용 조건 확인 → 갱신 처리 → C05 결과 표시; 확인이 필요한 실패/미확인은 S01/S05/S06 |

자동 갱신은 자동 출금·정기 청구와 같은 의미가 아니다. 사전 동의·해제, 갱신 가격·주기·시점, 지급과 갱신의 관계는 OQ-02·OQ-06에서 결정한다. 첫 주문으로 자동 갱신 동의가 생긴다고 가정하지 않는다. 동의·변경을 직접 수행할 화면 세부는 이 정책 이후 확장한다.

오류·복구: 접수만으로 이용 기간을 연장 완료로 표시하지 않는다. 실패·중복·미확인·기간 반영 오류를 구분하여 S05/S06에서 기존 결과와 대조한다. 미수금이나 갱신 실패 때문에 소프트웨어를 즉시 중지하는 정책을 임의로 넣지 않는다.

## F06 — 고객 변경·취소·반품과 직원의 후속 처리

대상: 자기 기업의 주문에 요청하는 고객, 판단·회수·환불 권한을 가진 직원. 범위: SC-10 및 SC-01·SC-05–SC-09.

1. 고객은 C04에서 적용 가능한 요청을 확인하고 C06에서 대상·내용을 검토하여 제출한다.
2. C06에는 요청 접수 결과를 표시한다. 실제 주문 변경·출고 중단·권한 회수·환불 완료라고 표시하지 않는다.
3. 직원은 S01/S06에서 이미 제공·지급된 부분과 최신 실행 근거를 대조하여 허용 여부를 판단한다.
4. 필요한 변경·회수·환불을 요청하고 각각의 실제 결과를 확인한다. 외부 실행 결과가 필요한 경우 미확인 상태를 유지한다.
5. C06과 관련 C04/C05에는 공개 가능한 판단·실행 결과와 아직 남은 조치를 구분한다.

오류·복구: 반품·회수 불가, 부분 환불, 늦은 출고 통보와 취소 충돌 등은 정책과 실행 가능성을 확인한 후 처리한다. 결과가 불명확하면 기존 요청 확인을 먼저 제공한다. 모든 상품·상태에서 환불·회수가 가능하다는 가정은 두지 않는다. OQ-05가 결정되기 전 이 흐름은 처리 구조 제안이다.

## F07 — 직원의 상품 등록·수정

대상: 상품 관리 권한을 가진 내부 직원. 시작: S01의 상품 메뉴 → S02. 범위: SC-01·SC-02.

직원이 하드웨어/소프트웨어와 판매 정보를 입력 → 저장 내용 검토 → 저장 결과 확인 → 고객 C02에 제시할 상품 정보로 연결한다. 실제 공개·판매 가능 조건과 필수 입력은 후속 정의한다. 등록과 동시에 무조건 판매 개시되는 정책은 확정하지 않는다.

오류·복구: 권한 부족·필수 정보 오류는 위치와 사유를 설명한다. 저장 충돌·응답 미확인은 입력 내용을 보존하고 현재 저장 결과를 확인하도록 한다. 고객은 이 흐름에 진입할 권한이 없다. 상품 변경이 기존 주문 내용을 자동 변경하는지는 별도 정책이다.

## F08 — 목록·상세 조회와 접근·공통 복구

대상: 고객·직원 각각의 허용된 문맥. 범위: SC-01·SC-09 및 전체.

- 고객은 C01에서 자기 기업의 주문·갱신·요청 상세로 이동한다.
- 직원의 처리 업무 경로는 S01 → 관련 S03/S04/S05/S06이다. 일반 주문 조회 경로는 직원 탐색 ‘주문’ → S07 주문 목록 → S03 상세다. S01의 ‘현재 확인할 업무 없음’ 상태에서도 주문 메뉴는 이용 가능하다.
- S07에서는 권한 내 정상 진행·완료 주문을 찾아 상세로 이동한다. 상세에 조치할 업무가 없어도 주문·품목·청구·지급·이행·이력을 조회할 수 있다. 조회만을 위해 신규 처리 업무를 생성하지 않는다.
- S03에서 돌아갈 때 진입한 S01 또는 S07을 구별하고 당시 조회 조건·선택 주문·목록 위치를 유지하도록 제안한다. 직원 경로는 사내망 PC 웹에만 제공하며 목록·상세에 동일한 접근 조건을 적용한다.
- 데이터 없음·선택 조건에 맞는 결과 없음·권한 없음·조회 실패·일부 결과 미확인을 구별한다. 금전·발급·출고의 실행 결과를 추측하여 채우지 않는다.
- 조회 실패는 조회를 재시도할 수 있다. 제출·실행 결과 미확인은 기존 결과 확인을 먼저 안내한다. 재실행은 안전성과 허용 조건 확인 후 제공한다.
- 읽거나 처리할 권한이 없으면 대상 기업·비밀 정보·내부 판단 근거를 노출하지 않으면서 접근 불가와 가능한 복귀 경로를 안내한다.
- 고객 모바일도 동일한 대상·권한·확인·제출·결과 흐름을 제공한다. 고객 PC의 분할 영역은 순차 상세로 바뀔 수 있다. 직원 업무는 사내망 PC 웹에서만 제공하며 직원 모바일 흐름은 제외한다.

## F09 — 내부 직원의 사내망 접근 조건

대상: 직원용 화면과 정보를 이용하려는 내부 사용자. 근거: 이번 Q4의 추가 사용자 결정, SC-01/IB-01의 접근 통제 범위. 목적은 민감 데이터 유출 가능성 감소이며, 실제 보안 효과는 구현과 검증 전이다.

1. 직원용 PC 웹에 접근할 때 사내 내부망 조건과 직원 신원·해당 업무 권한을 확인하는 경계를 둔다. 확인 수단은 설계에서 정한다.
2. 조건을 충족한 경우 S01 또는 허용된 상세로 이동한다. 사내망 접속만으로 모든 주문·금전·발급 업무 권한이 생기지 않는다.
3. 사내망 외부이거나 필요한 조건을 확인할 수 없으면 내부 정보·업무를 제공하지 않고 접근 불가 또는 확인 불가를 안내한다. 메뉴를 거치지 않은 상세 접근·조회·처리 요청에도 같은 제한이 적용된다.
4. 이미 접속한 뒤 네트워크 조건이 바뀌는 경우에도 새 조회·처리가 제한을 우회하지 않아야 한다. 이미 표시된 정보·진행 중 작업·재접속 처리의 상세 정책은 OQ-07과 연결하여 후속 정의한다. 화면에 이미 표시된 정보를 소급 회수할 수 있다고 가정하지 않는다.
5. 직원 모바일 화면·업무 흐름은 제공하지 않는다. 고객 PC·모바일 흐름은 유지한다.

복구 안내는 승인된 사내망 환경과 필요한 권한을 확인하는 방향으로 제시한다. 외부 접근을 허용하는 임시 우회나 특정 원격 접속 방식을 제안하지 않는다. 원격 예외·사내망 범위·단말 판별·직원/고객 접점의 구체적 기술 구조는 확정하지 않는다. 접근 불가 안내 자체는 제목·읽기 순서·키보드 이동을 갖추며 내부 민감 정보를 포함하지 않는다.

## 검토 시나리오와 확인할 질문

아직 수행하지 않은 사용자 검토 계획이다. 가상 자료로 정책 모순을 찾되 실제 고객 수요나 실행 통합이 검증됐다고 기록하지 않는다.

| Scope 시나리오 | 화면·흐름 | 검토할 질문 |
|---|---|---|
| VS-01 재고 하드웨어 선결제 | C01–C04, S01·S03·S04 / F01–F03 | 접수·수락·지급 확인·출고/배송이 서로 구별되는가 |
| VS-02 후불·확보·부분 출고 | C04·S03·S04·S06 / F02·F03·F06 | 후불 지급과 잔량·지연을 분리해 이해하고 조치하는가 |
| VS-03 영구/기간제 발급 | C04·C05·S05 / F04 | 발급 결과와 전달·기간·실제 사용을 혼동하지 않는가 |
| VS-04 요청/자동 갱신 | C01·C05·S01·S05·S06 / F05 | 합의된 자동 갱신과 고객 요청, 지급과 기간 반영이 구분되는가 |
| VS-05 부분 제공 후 변경·외부 결과 지연 | C04·C06·S03·S06 / F06·F08 | 요청 접수가 회수·환불 완료로 오인되지 않는가 |
| VS-06 고객 등록 시도·타 기업 조회 | C02·S02 및 관련 상세 / F07·F08 | 금지된 접근이 차단되고 불필요한 정보가 노출되지 않는가 |
| UX-01 직원 사내망 외부·조건 미확인 접근 | 직원 화면 전체 / F09 | 내부 정보 없이 접근이 거절되고 상세 직접 접근·조회·처리에서도 동일한가 |
| UX-02 사내망 직원의 허용·금지 업무 | S01–S07 / F09 및 해당 업무 흐름 | 사내망 안에서도 업무 권한이 적용되며, 허용된 PC 업무는 수행 가능한가 |
| UX-03 이용 환경 범위 확인 | 고객 C01–C06·직원 S01–S07 | 고객 모바일은 유지하고 직원 모바일 화면은 제외했는가. 네트워크 변경 중 후속 요청이 제한을 우회하지 않는가 |
| UX-04 청구·지급 구분 | C04·S03 / F02·F08 | 청구 전·청구 후 미지급·청구 조회 실패를 구별하고 확인된 지급 결과를 독립적으로 읽을 수 있는가. 고객 PC·모바일 및 직원 사내망 PC에서 확인 |
| UX-05 처리 업무 없는 일반·완료 주문 조회 | S01·S07·S03 / F08·F09 | 처리 업무가 없어도 주문 메뉴로 정상·완료 주문을 찾아 상세를 보고 같은 목록 위치로 복귀할 수 있는가. 사내망·행위 권한 경계가 유지되는가 |

각 시나리오의 고객 조작은 PC와 모바일에서 비교하고, 직원 조작은 사내망 PC 웹에서 검토한다. 직원 모바일 화면을 검토·구현 대상으로 삼지 않는다. 긴 기업·상품명, 여러 품목, 빈 목록, 오류, 제출 결과 미확인 상황과 키보드 이동·읽기 순서를 함께 확인한다. 실제 테스트 결과·완료 시간·성공률은 아직 없다.

## Assumptions & Open Questions

- [assumption] 제안한 시작점과 화면 연결이 고객·직원의 판단 부담을 줄인다. 시작점은 사용자 선택이며 사용성 효과는 미검증이다.
- [assumption] 필요한 실제 결과와 안전한 재처리 판단 근거를 확보할 수 있다. 외부 실행 주체·연동 접근권은 아직 미확인이다.
- Q4에서 직원 사내망 전용 접근과 모바일 화면 제외는 사용자 결정으로 확정했다. 사내망 정의·검증 수단·원격 예외·접속 중 네트워크 변경 처리의 세부 사항은 OQ-07과 연결해 후속 정의한다.
- OQ-01–OQ-10의 업무 정책은 Scope 문서에서 계속 추적한다. 특히 가입·기업/역할 확인, 자동 갱신 동의·변경·해제, 결제 경로, 실제 권한 전달·적용, 취소/환불 조건은 후속 정의한다.
- 오류 복구는 흐름 제안이며 무조건 되돌릴 수 있다는 보장이 아니다. 실제 재시도·복구 계약과 정량 목표는 후속 설계·검증에서 정한다.
