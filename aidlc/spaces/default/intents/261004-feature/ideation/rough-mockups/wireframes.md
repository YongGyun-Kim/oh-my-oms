# OMS 초기 화면 구조

상태: 검토용 저충실도 초안. 근거: [확인된 답변](rough-mockups-questions.md), [개발 의도](../intent-capture/intent-statement.md), [승인된 범위](../scope-definition/scope-document.md), [업무 백로그](../scope-definition/intent-backlog.md).

## 목적과 표현 원칙

고객이 자기 기업의 주문·갱신 현황에서 필요한 조치로 이동하고, 내부 직원이 처리할 업무에서 주문·이행·예외의 근거를 확인하는 흐름을 제안한다. 고객은 PC·모바일 웹을 지원하며 **PC를 우선**한다. 내부 직원은 **사내 내부망의 PC 웹에서만 접근**하는 시나리오로 구성하며 직원용 모바일 화면은 제공하지 않는다. 고객 모바일에서는 같은 권한 아래 승인된 업무를 수행한다. 기존 브랜드 기준은 없으며 최종 시각 디자인·구현 기술·배포 구조는 결정하지 않는다.

이 문서는 화면의 영역·정보·조작을 표로 그린 구조형 와이어프레임이다. 표의 위에서 아래 순서는 PC에서 읽는 순서이며 좌측 탐색과 우측 상세는 별도로 표시한다. 실제 페이지 수·주소·팝업 여부는 확정하지 않는다. 수치·기업명·상태 예시는 실제 데이터가 아니다. 사용자에게 보일 문구와 설계 주석을 구분한다. OQ 번호·백로그 번호·기술 설명은 실제 제품 화면에 표시하지 않는다.

상태 문구는 이해를 돕는 후보이며 최종 상태 모델이 아니다. ‘요청 접수’, ‘직원 확인 필요’, ‘처리 중’, ‘결과 확인 필요’, ‘일부 완료’ 등은 처리 근거에 따라 표시한다. 응답이 없다는 이유만으로 실패나 완료를 단정하지 않는다. 하나의 ‘완료’ 표시로 판매 확정·대금 지급·상품 제공·라이선스 만료를 합치지 않는다.

## 정보 구조와 화면 목록

역할별 탐색 제안이다. 고객·직원을 별도 앱으로 배포한다는 뜻은 아니며, 한 사람이 두 역할을 가진다는 가정도 하지 않는다. 로그인·가입·기업 확인·역할 부여 정책은 Scope OQ-07에서 결정한다. 본 초안의 업무 시작점은 허용된 기업/역할 문맥이 확인된 이후다. 직원용 화면에는 아래 사내망 접근 조건을 추가로 적용한다.

## 내부 직원의 접근 조건

사용자의 Q4에 따라 민감 데이터 유출 가능성을 줄이기 위해 직원용 접근을 사내 내부망으로 제한한다. 이 조건은 S01–S07의 진입과 주문·상품·권한·지급 등 내부 정보 조회/처리 요청에 적용한다. 직원 신원·행위 권한과 기업별 데이터 접근 범위도 함께 확인하는 것으로 표현한다. 사내망 접속만으로 모든 업무 권한을 얻지는 않는다.

| 접근 상황 | 화면·행동의 표현 | 검증할 경계 |
|---|---|---|
| 사내망에서 허용된 직원이 PC 웹 이용 | S01 또는 권한 있는 해당 상세로 진입 | 연결된 직원 화면·업무에도 같은 조건 적용 |
| 사내망 외부에서 직원 화면·상세로 접근 | 주문·기업·상품·금액·권한 정보를 표시하지 않고 ‘접근할 수 없습니다. 사내망에서 접속해 주세요.’ 안내 | 목록뿐 아니라 상세 직접 접근과 내부 정보 조회·처리도 허용되지 않음 |
| 사내망 여부 또는 직원 권한 확인 불가 | 내부 업무 내용을 불러오지 않고 확인 불가·다음 확인 경로 안내 | 확인 실패를 허용으로 바꾸지 않음 |
| 사내망이지만 해당 업무 권한 없음 | 업무 내용 노출 없이 접근 불가·허용된 복귀 경로 안내 | 네트워크 조건과 행위 권한을 구분 |
| 직원의 모바일 이용 | 직원용 모바일 화면·모바일 업무 흐름을 제공하지 않음 | 모바일 화면 제외를 사내망 접근 통제의 구현으로 간주하지 않음 |

접근 불가 안내에도 읽을 수 있는 제목·본문과 키보드로 이동할 수 있는 안내 링크를 제공한다. 고객 화면에 사내망 조건을 확대 적용하지 않는다. 고객·직원 화면의 접점에서 직원용 정보가 노출되지 않는지 후속 검증한다.

사내망의 구체적 범위, 허용 접속의 판별·검증 수단, 원격 접속 예외 유무, 네트워크 변경 시 이미 열린 화면·진행 중 작업의 처리는 후속 요구사항·설계에서 정의한다. 모바일 단말 자체를 기술적으로 차단하는 방식까지 이번 ‘모바일 화면 제외’로 확정하지 않는다. 특정 VPN·주소·클라우드 서비스·앱 배치 구조를 고르지 않는다. 화면 안내와 숨김만으로 제한이 구현되거나 민감 정보 유출이 방지됐다고 주장하지 않는다.

## 고객 화면

### C01 — 주문·갱신 현황

**사용자 목표:** 자기 기업에서 무엇이 진행 중이고 어떤 확인이 필요한지 파악한다. 첫 화면에 매출 분석·예측을 추가하지 않는다.

| PC 위치 | 표시할 정보 | 가능한 이동·조작 |
|---|---|---|
| 상단 | 현재 기업 문맥, ‘주문·갱신 현황’ 제목 | 본문으로 이동, 고객 탐색 |
| 본문 상단 | 확인이 필요한 주문·갱신 안내와 근거 | 해당 C04 또는 C05로 이동 |
| 본문 중앙 | 주문 목록: 주문 식별 정보, 하드웨어/소프트웨어, 판매 확인·지급·이행 요약 | 주문 상세 C04 |
| 본문 하단 | 기간제 권한의 기간·갱신 결과 요약 | 권한·갱신 상세 C05 |
| 탐색 | 상품, 주문, 사용 권한·갱신, 요청 내역 | 새 주문은 C02에서 시작; 기존 요청은 C06 |

**모바일:** 확인할 업무를 먼저 두고 주문 행은 요약 목록으로 바꾼다. 주문의 세 상태를 문구로 구분하고 상세로 연결한다. 숨긴 열의 내용은 상세에서 확인할 수 있다.

**특이 상태:** 갱신 대상이 없으면 임의 추천·신규 갱신을 만들지 않는다. 일부 결과가 오래되었거나 미확인이면 그 항목에 확인 필요를 표시한다. 접근 가능한 기업이 정해지지 않았다면 다른 기업 목록을 대신 보여 주지 않는다.

**접근성:** h1 현황, h2 확인할 업무/주문/갱신; header·nav·main 영역; 키보드 진입은 본문 바로가기 후 첫 업무 링크. 상태는 색상 외에 문구로 표시한다.

### C02 — 상품 목록·상세

| PC 위치 | 표시할 정보 | 가능한 이동·조작 |
|---|---|---|
| 상단 | ‘상품’, 하드웨어/소프트웨어 구분 | 상품 타입 선택 |
| 본문 좌측/중앙 | 선택한 타입의 판매 상품 목록 | 상품 상세 열기 |
| 상세 영역 | 상품명·설명·판매 조건; 소프트웨어는 영구/기간제 구분 | ‘이 상품 주문 요청’으로 C03 |
| 보조 정보 | 확인된 가격·제공 조건 또는 확인이 필요한 항목 | 조건 안내 확인; 없는 가격을 임의로 표시하지 않음 |

**모바일:** 목록 후 상세의 단일 열 흐름. 다른 상품 타입으로 이동할 때 요청 중인 타입과의 혼합을 유도하지 않는다. 혼합 장바구니는 제공하지 않는다.

**특이 상태:** 상품이 없으면 빈 목록 안내. 판매 조건이 미확인인 경우 무엇을 확인해야 하는지 표시하되 무조건 주문 가능/불가능 정책은 OQ-01·OQ-02에서 정한다. 상품 등록 버튼은 고객에게 제공하지 않는다.

**접근성:** h1 상품, h2 상품 목록/상세; header·nav·main; 키보드 진입은 타입 선택 후 상품 링크. 타입과 선택 여부를 텍스트로 전달한다.

### C03 — 주문 요청·제출 결과

| PC 위치 | 표시할 정보 | 가능한 이동·조작 |
|---|---|---|
| 상단 | ‘하드웨어 주문 요청’ 또는 ‘소프트웨어 주문 요청’ | C02로 돌아가기 |
| 본문 | 현재 기업, 선택 상품·요청 수량, 요청에 필요한 제공 정보 | 입력·검토; 실제 필수 항목은 후속 정책에 따름 |
| 검토 영역 | 상품 타입·내용·확인된 거래 조건·확인 필요 항목 | 제출 전 내용 수정 |
| 하단 | 주요 행동 ‘주문 요청 제출’ | 한 번 제출 후 처리 결과 확인 |
| 결과 영역 | 요청 접수와 판매 확정 여부를 별개로 표시 | 접수 확인 시 C04로 이동 |

**모바일:** 입력과 검토를 세로로 배치한다. 고정 행동 영역을 쓰더라도 입력·오류를 가리지 않는다. PC와 동일한 요청 제출을 제공한다.

**특이 상태:** 입력 오류는 입력값을 유지하며 해당 위치에서 수정 안내. 제출 후 응답 미확인은 ‘접수 결과 확인 필요’로 보여 주고 기존 요청 확인 경로를 제공한다. 곧바로 새 주문 제출을 권하지 않는다. 자동/직원 확인 분기는 결과로 표시하며 금액 기준 등을 예시로 확정하지 않는다.

**접근성:** h1 타입별 주문 요청, h2 입력/검토/결과; header·nav·main 및 form; 키보드 진입은 첫 입력 라벨, 오류 시 오류 요약에서 해당 입력으로 이동. 제출 후 결과 제목으로 안내한다.

### C04 — 주문 상세

| PC 위치 | 표시할 정보 | 가능한 이동·조작 |
|---|---|---|
| 상단 | 주문 식별 정보·상품 타입·현재 기업 | 목록 C01로 돌아가기 |
| 본문 상단 | 판매 확인 결과 / 선결제·후불 조건 / 청구 상태 / 지급 상태 / 이행 진행 | 각 영역의 확인 근거와 필요한 조치 보기 |
| 대금 영역 | 주문에 연결된 청구 정보·상태와 지급 결과를 별도 표시. 확인된 청구 식별 정보·대상·금액·기한 및 지급 근거 | 해당 청구의 확인된 내용과 연결된 지급 결과 확인; 미확인 항목은 미확인으로 표시 |
| 본문 중앙 | 품목별 주문량·제공 결과·남은 수량/업무 | 하드웨어 배송 결과 또는 소프트웨어 C05 |

| 결과/이력 | 판단 결과와 실제 변경·회수·환불·재처리 결과를 구분 | 미해결 항목 확인, 고객에게 공개할 진행 결과 연결 |

**접근 환경:** 사내 내부망의 PC 웹에서만 제공한다. 직원용 모바일 화면은 제공하지 않는다. 공통 사내망 접근 조건과 해당 업무 권한을 함께 적용하며, PC의 키보드·확대 이용을 유지한다.

**특이 상태:** 요청 접수·판단·실제 실행 결과는 각각 추적한다. 재처리 전 기존 작업의 상태와 중복 영향 확인이 필요하다. 안전한 반복 가능 여부·되돌리기 가능 여부는 OQ 정책에 따라 결정하며 모든 조작의 취소·복구를 보장하지 않는다.

**접근성:** h1 변경·예외 상세, h2 근거/처리 판단/결과·이력; header·nav·main; 키보드 진입은 연결 대상 후 근거. 중요한 조작은 대상·영향 확인 후 제출하고 결과 안내로 연결한다.

### S07 — 직원 주문 목록

**사용자 목표:** 확인 대기 업무가 없는 정상 진행·완료 주문도 찾아서 상세를 확인한다. S01과 목록 표현을 공유할 수 있지만 조회 대상은 처리 업무가 아닌 권한 내 주문이다. 같은 업무의 목록 보기 방식 제안이며 구현 화면·컴포넌트를 새로 분리한다는 뜻은 아니다.

| PC 위치 | 표시할 정보 | 가능한 이동·조작 |
|---|---|---|
| 직원 탐색 | 처리 업무와 별도로 항상 접근 가능한 ‘주문’ 메뉴 | S01에 처리 업무가 없어도 S07 진입 |
| 상단 | ‘주문’ 제목, 현재 허용된 조회 문맥 | 조회 조건 확인·초기화 |
| 조회 영역 | 주문 식별 정보와 상품 타입·진행 구분 등 주문을 찾을 조건 | 정상 진행·완료를 포함한 허용 범위에서 탐색; 실제 조건 세트는 후속 구체화 |
| 본문 목록 | 주문 식별 정보·기업·상품 타입·판매 확인·청구/지급·이행 요약 | 해당 주문을 선택해 S03 상세 조회 |
| 결과/복귀 | 조건에 맞는 주문 수와 현재 목록 위치 | 상세에서 돌아오면 진입 당시 조건·목록 위치를 유지 |

**접근 환경:** 사내 내부망의 PC 웹에서만 제공한다. 직원용 모바일 화면은 제공하지 않는다. 모든 주문이라는 표시는 해당 직원에게 허용된 조회 범위 안의 주문을 뜻한다.

**특이 상태:** ‘처리할 업무 없음’이어도 주문 목록은 이용 가능하다. ‘현재 조회할 주문 없음’, ‘조회 조건에 맞는 주문 없음’, ‘조회 실패’, ‘권한 없음’을 구별한다. 완료 주문에는 새로운 확인 업무를 만들지 않고 상세 조회를 제공한다. 목록·상세 모두 사내망·직원 신원·행위 권한 조건을 적용한다.

**접근성:** h1 주문, h2 조회 조건/주문 목록; header·nav·main; 키보드 진입은 주문 메뉴 이후 조회 조건과 주문 링크 순서. 상세 복귀 시 원래 주문 링크·목록 위치를 찾을 수 있게 한다. 목록 상태 문구와 표의 열 제목을 읽을 수 있게 한다.

### 청구·지급 표시 예시 — C04·S03 공통

가상 상태를 구분하기 위한 예시다. 고객에게는 공개 가능한 자기 기업의 청구·지급 정보만, 직원에게는 업무 권한 내 정보만 표시한다. 금액·기한·청구 생성 주체와 정책을 예시로 확정하지 않는다. 한 주문에 여러 청구가 필요한지는 별도 정책이며 확인된 연결 단위로 보여 준다.

| 확인된 업무 상황 | 청구 정보·상태 영역 | 지급 결과 영역 |
|---|---|---|
| 아직 청구하지 않았음이 확인됨 | ‘청구 전’, 확인된 주문·청구 대상 참조 | 확인된 지급 기록이 없으면 그 사실을 표시; ‘연체’로 추론하지 않음 |
| 청구가 확인됐으나 지급이 완료되지 않음 | ‘청구됨’, 확인된 청구 참조·대상·금액·기한 | ‘지급 미완료’ 또는 실제 확인 결과와 근거. 기한 경과 판단은 정책에 따름 |
| 청구와 지급 결과가 모두 확인됨 | 청구 내용과 상태 유지 | 연결된 지급 결과·확인 근거 표시. 이행 완료와 구분 |
| 청구 조회만 실패하거나 결과가 불명확함 | ‘청구 정보 확인 필요’. 미청구라고 표시하지 않음 | 확인된 지급 결과가 있으면 별도 유지하고 확인 시점·한계 표시 |

## 공통 상태와 모바일·접근성 기준

다음 다섯 상태는 C01–C06·S01–S07 전체에 적용한다. 각 화면의 특이 상태가 이를 보완한다.

| 상태 | 목록·상세 화면 | 입력·처리 화면 | 사용자의 다음 행동 |
|---|---|---|---|
| 비어 있음 | 데이터 없음과 필터 결과 없음, 관련 대상 없음 구분 | 필수 입력·권한을 안내; 기본값으로 미정 정책을 채우지 않음 | 조건 조정 또는 권한 내 시작점으로 이동 |
| 조회/처리 중 | 어느 영역을 확인 중인지 표시 | 제출 중임을 표시하고 중복 제출 방지; 즉시 성공 문구 금지 | 결과를 기다리거나 기존 요청 확인 |
| 정상 결과 | 최신 확인 근거와 대상 표시 | 저장/접수/실제 완료 중 무엇이 확인됐는지 명시 | 관련 상세·목록으로 이동 |
| 오류 | 조회 실패·권한 부족 등을 구별; 다른 기업 데이터로 대체하지 않음 | 입력은 보존하고 수정 가능 위치 안내 | 안전한 조회 재시도 또는 입력 수정 |
| 부분/미확인 | 확인된 내용과 미확인·지연 항목을 구별 | 서버 응답 미확인과 실제 업무 실패를 구별 | 기존 처리 결과를 먼저 확인; 무조건 재실행하지 않음 |

고객 모바일에서는 승인된 기능을 축소하지 않는다. 고객 PC의 나란한 영역은 모바일에서 순서대로 배치하고 중요한 대상·상태·행동을 유지한다. 내부 직원은 사내망 PC 웹만 제공하며 모바일 적응 화면을 만들지 않는다. 직원 PC 웹에서도 키보드·확대·창 크기 변화에 따른 접근성 검토는 유지한다. 상세를 열고 돌아왔을 때 목록 문맥을 잃지 않도록 제안한다. 메뉴 접힘, 긴 이름·많은 품목, 확대 화면에서도 정보와 조작을 이용할 수 있는지 후속 실물 검증한다.

모든 입력에는 보이는 라벨을 두고, 오류·부분 상태는 색상 외에 문구로 표현한다. 키보드 이동·초점·결과 안내와 스크린리더가 읽을 제목·영역을 주석으로 정리했다. 이는 접근성 검토 계획이며 실제 구현의 WCAG 적합성 인증이나 테스트 통과 주장이 아니다. 별도 접근성·보조기기 요구는 미확인이다.

## Assumptions & Open Questions

- [assumption] 제안한 메뉴·영역·화면 묶음이 고객과 직원의 업무 이해에 적합하다. 실제 사용자 검증은 아직 없다.
- [assumption] 고객 모바일에서 영역을 순서대로 재배치해 동일 업무를 수행할 수 있다. 긴 품목·오류·중요 조작을 포함해 후속 시안에서 검증한다.
- [assumption] 후속 실행 주체에서 확인 가능한 주문·지급·이행 근거를 제공할 수 있다. 연결 가능성을 이번 화면이 입증하지는 않는다.
- 로그인·가입·상세 권한·업무 정책은 위 OQ로 전달한다. 그림을 승인해도 미정 정책이 자동 확정되지 않는다.
