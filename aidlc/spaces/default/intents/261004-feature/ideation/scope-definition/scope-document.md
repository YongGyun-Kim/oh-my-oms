# B2B OMS 첫 제품 범위

작성일: 2026-10-05. 상태: 사용자 검토용. 질문별 결정과 작성 전 요약 확인에 근거한 범위안이며, 단계 최종 승인·Inception 진입·출시 승인은 별도다.

## 목적과 핵심 가치

**자사 업무용 하드웨어·소프트웨어를 구매하는 기업과 판매 측 내부 직원이 주문 요청, 판매 확정, 상품 제공, 대금 지급, 후속 요청의 상태와 처리 결과를 연결해 확인하고 필요한 조치를 수행하는 제품**을 만든다.

고객에게 제공하려는 가치는 주문한 상품이 수락되었는지, 무엇이 제공되었는지, 어떤 조치가 남았는지 이해할 수 있게 하는 것이다. 내부 직원에게 제공하려는 가치는 주문과 실제 처리 결과를 연결하여 지연·부분 이행·변경·실패를 다루는 것이다. 이는 사용자와 함께 선택한 제품 방향이다. 현재 고객이 실제로 이 문제를 얼마나 겪는지, 지불 의사가 있는지는 **검증 전 가설**이다.

일반적인 OMS 기능 목록을 그대로 요구사항으로 채택하지 않는다. 아래 포함 범위는 [이번 단계 답변](scope-definition-questions.md)의 결정에서 도출했다. [intent-statement](../intent-capture/intent-statement.md), [feasibility-assessment](../feasibility/feasibility-assessment.md), [constraint-register](../feasibility/constraint-register.md)를 상위 근거로 유지한다.

## 고객과 사용자

| 구분 | 범위에서의 의미 | 근거·확실성 |
|---|---|---|
| 첫 타깃 고객 | 자기 회사의 업무에 사용할 하드웨어·소프트웨어를 구매하는 기업 | Q2의 사용자 결정. 업종·기업 규모·국가는 미정 |
| 고객 측 직접 사용자 | 상품을 확인하고 주문 요청을 제출하며 자기 기업의 주문을 확인하는 담당자 | Q3·Q10. 구매·총무·IT라는 직함은 후보이며 실제 역할 미검증 |
| 판매 측 내부 직원 | 판매 상품 등록, 조건에 따른 주문 확인과 주문 운영 업무 | Q1·Q5·Q10. 내부 직원 모두에게 모든 권한을 주는 결정은 아님 |
| 소프트웨어 제공 책임 | 우리 측이 사용 권한을 발급하고 기간·갱신 업무를 책임짐 | Q6·Q10. 전담 인원 또는 별도 시스템이 존재한다고 가정하지 않음 |
| 운영·개발 책임 | 필요한 개발과 운영을 1명이 충분히 수행할 수 있도록 구조를 설계 | Feasibility의 사용자 정정과 프로젝트 원칙. 기능 축소 조건이 아님 |
| 인접 업무 담당자 | 재고·공급·출고·운송·수금 등의 실제 결과를 제공하는 주체 | 연결할 책임은 필요하나 실제 조직·제공자·접근권은 미확인 |

이번 고객 선택은 **상품 구매 기업**에 관한 것이다. OMS 소프트웨어 자체의 판매·과금 모델, 운영 법인 수, 여러 판매 조직의 사용 여부는 정하지 않았다. 재판매·고객 프로젝트용 구매는 초기 타깃으로 선택하지 않았으며, 해당 사업을 하는 기업의 자사 업무용 구매까지 일괄 차단하는 정책을 뜻하지 않는다.

## MVP에 반드시 포함할 업무

이 문서의 MVP는 **사용자가 선택한 첫 제품 전체의 업무 범위**다. 검증·개발을 여러 단계로 나눠도 뒤에 배치한 포함 업무가 MVP에서 빠지지는 않는다. 필요성은 고객 검증으로 계속 확인하되 범위 변경은 사용자 결정으로 다룬다.

| 범위 ID | 포함할 업무와 고객 결과 | 왜 필요한가 | 백로그 |
|---|---|---|---|
| SC-01 | 기업·담당자 정보, 내부 직원/고객의 행위 권한, 기업별 주문 접근 통제, 주요 변경·처리 이력 | 주문 주체를 연결하고 승인된 권한 경계를 지킴. Q1·Q10 | IB-01 |
| SC-02 | 내부 직원 상품 등록과 기업 고객의 판매 상품 확인 | 고객이 주문할 하드웨어·소프트웨어를 제시. Q1·Q3·Q10 | IB-02 |
| SC-03 | 고객 직접 주문 요청과 상품 타입별 주문 분리 | 하드웨어와 소프트웨어의 서로 다른 이행을 별도 주문으로 접수. Q3·Q11 | IB-03 |
| SC-04 | 조건별 자동 확정과 내부 직원 확인, 수락 여부·판단 결과 확인 | 요청 접수와 판매 이행 약속을 구분. Q5·Q10 | IB-04 |
| SC-05 | 선결제/후불 조건, 주문과 청구·지급 상태 연결, 상품 제공 판단에 필요한 지급 확인 | 거래 조건에 맞게 주문과 대금을 연결. Q9·Q10 | IB-05 |
| SC-06 | 하드웨어의 재고 확인, 상품 확보 요청·진행, 출고 요청·배송 결과 연결 | 두 공급 방식의 주문을 이행 결과까지 추적. Q7·Q10 | IB-06 |
| SC-07 | 우리 측 소프트웨어 사용 권한 발급, 고객·주문 연결, 영구/기간제 및 이용 기간 관리, 결과 제공 | 소프트웨어 판매를 실제 제공 결과로 연결. Q4·Q6·Q10 | IB-07 |
| SC-08 | 고객 요청 갱신과 사전 합의된 자동 갱신, 기간·처리 결과 연결 | 기간제의 후속 이용을 주문·권한 맥락에서 관리. Q8·Q10 | IB-08 |
| SC-09 | 고객·직원의 주문 조회, 품목별 진행·지연·부분 이행과 남은 조치 확인 | 주문 전체 상태만으로 미완료 부분을 숨기지 않음. Q10 | IB-09 |
| SC-10 | 변경·취소·반품 요청, 허용 여부 판단, 필요한 회수·환불 요청 및 결과, 이행 실패 확인·재처리 | 정상 주문 외의 후속 업무도 끝까지 추적. Q10 | IB-10 |

SC-07의 발급 책임은 제품 범위에 포함한다. 이를 OMS 내부 기능 또는 별도 권한 관리 기능 중 어디에 배치할지는 아키텍처 결정으로 남긴다. 소프트웨어 자체가 권한을 검사하는 기능의 개발은 아래 제외 범위와 구별한다.

## 제외 범위와 미선택 항목

### 첫 제품에서 제외한 업무

| ID | 제외 범위 | 제품에 남는 연결 책임 | 근거 |
|---|---|---|---|
| OUT-01 | 외부 판매자·고객의 판매 상품 등록 | 내부 직원이 상품 등록 | Q1·Q10 |
| OUT-02 | 한 주문에 하드웨어와 소프트웨어를 함께 담는 혼합 주문 | 타입별로 별도 주문 접수·처리 | Q11 |
| OUT-03 | 전사 PIM·CRM·구매 승인·인사 시스템 전체의 구축 | 주문에 필요한 상품·기업·담당자·행위 권한 관리 | Q10 |
| OUT-04 | 창고 입출고 작업·피킹·패킹·창고 위치 관리 전체 | 재고 확인과 주문별 확보·출고 요청·결과 연결 | Q10 |
| OUT-05 | 공급사 선정과 구매 원장 전체 | 주문 후 상품 확보 요청과 진행 확인 | Q10 |
| OUT-06 | 실제 운송 수행 | 출고 요청·배송 결과 연결 | Q10 |
| OUT-07 | 회계 원장·세금 신고 시스템 전체 | 주문에 연결된 거래 조건·청구·지급·환불 상태 | Q10 |
| OUT-08 | 카드 결제망·은행 수금·자동 출금·정기 결제 실행 기능 자체 구축 | 필요한 지급 확인·환불 요청과 결과 연결. 결제 연동의 포함 범위는 후속 결정 | Q10 |
| OUT-09 | 소프트웨어 자체 기능, 실행 시 권한 검증·장치 제어 기능의 개발 | 권한 발급·기간 관리·갱신과 필요한 결과 연결 | Q10 |

제외는 인원 수에 따른 축소가 아니라 Q10·Q11에서 선택한 책임 경계다. 실제 재고·조달·수금·소프트웨어 실행은 누군가 수행해야 한다. 제외한 업무의 실행 담당자나 수단이 이미 확보되었다고 가정하지 않는다. 대체 경로가 없으면 해당 주문 흐름의 상용 운영 가능성은 미검증으로 남는다.

### 자동으로 포함하지 않은 업무

직원 대리 주문 입력은 Q3에서 선택하지 않았다. 자동 결제 연동·정기 청구, 범용 업무 규칙 편집기, 모든 ERP/WMS/PIM/CRM 커넥터, 설치·유지보수·업그레이드·고객 자산 관리도 필수 범위에 자동 추가하지 않는다. 이는 영구 금지나 모든 연동의 배제를 의미하지 않는다. 필요성이 확인되면 별도 범위 결정으로 다룬다.

## 인접 시스템과 업무 책임 경계

아래는 구현 구성도가 아니라 업무 책임 표다. 특정 외부 제품의 존재·도입·연동을 확정하지 않는다. 여기서 ‘결과 원본’은 어떤 업무의 실제 발생을 확인할 근거를 누가 제공하는지이며 DB 소유권 설계가 아니다.

| 인접 영역 | 첫 제품이 맡는 책임 | 인접 주체가 맡는 실행·원본 | 아직 확인할 접점 |
|---|---|---|---|
| ERP·조달 | 고객 주문, 상품 확보 요청·진행, 청구·지급 결과 연결 | 공급사 거래·구매 원장·회계/세금 업무 | 고객 주문과 공급 확보·금전 결과의 참조 관계, ERP 유무와 대체 수단 |
| WMS·창고 | 주문에 필요한 재고 확인·출고 요청·결과 추적 | 실물 재고·창고 작업·실제 출고 결과 | 재고 최신성·확보 판단·할당 책임과 부분 출고 증거 |
| PIM | 내부 직원의 판매 상품 등록·고객에게 제시할 정보 | 전사 상품정보 관리 전체가 필요하면 별도 책임 | 외부 상품 원본이 있는지, 판매 정보와의 수정 권한 |
| CRM | 주문에 필요한 기업·담당자 연결 | 잠재고객·캠페인·영업 관계 관리 전체 | 기업 정보의 원본·변경자, CRM 유무 |
| 결제·수금 | 선후불 조건과 상태 연결, 지급 확인·환불 요청/결과 | 실제 자금 이동·결제 처리 | 결제 경로, 증빙, 실패·중복·지연 결과 확인 방법 |
| 배송 | 출고 요청과 배송 결과의 주문 연결 | 실제 운송·배송 결과 | 제공되는 상태의 의미, 지연·반품 결과의 확인 주체 |
| 소프트웨어 실행 환경 | 우리 측 권한 발급·기간·갱신과 고객/주문 연결 | 실행 시 권한 적용·검증, 소프트웨어 기능 | 발급 결과를 어디서 어떻게 적용·검증하는지, 만료·회수 결과 확인 |

내부 상품 등록만 허용한다는 조건은 내부 직원이 공급사 상품 정보를 참고하거나 외부 공급자에게 상품을 조달하는 것을 금지하지 않는다. 다만 상품 등록 권한을 외부에 열어 주는 요구로 확대하지 않는다.

## 가치 흐름 지도

아래 표와 텍스트는 업무 흐름을 설명하기 위한 지도다. 최종 상태 목록이나 상태 전이 규칙은 아니다. 지급 조건은 이행과 나란히 평가하며, 선결제와 후불을 하나의 고정 순서로 합치지 않는다.

| 단계 | 고객 행동·관심 | 내부/제품의 업무 | 남겨야 할 업무 결과 | 관련 범위 |
|---|---|---|---|---|
| 상품 제시 | 자사 업무에 필요한 상품 확인 | 내부 직원 상품 등록·판매 정보 제시 | 주문 가능한 상품 정보 | SC-01·SC-02 |
| 주문 요청 | 하드웨어 또는 소프트웨어 주문 제출 | 기업·상품 타입·주문 요청 연결 | 요청 접수 결과 | SC-03 |
| 판매 확정 판단 | 수락 여부와 다음 단계 확인 | 조건별 자동 판단 또는 직원 확인 | 수락·확인 필요 등 판단 결과와 근거 | SC-04 |
| 거래 조건 확인 | 선결제 또는 후불 조건에 따른 지급 | 청구·지급 상태와 제공 조건 확인 | 이행 판단에 필요한 지급 결과 | SC-05 |
| 하드웨어 이행 | 언제 무엇을 받을 수 있는지 확인 | 재고 출고 또는 주문 후 확보, 출고 요청·배송 결과 연결 | 품목별 제공·잔량·지연 결과 | SC-06·SC-09 |
| 소프트웨어 이행 | 발급된 권한과 기간 확인 | 우리 측 권한 발급·고객/주문/기간 연결 | 영구 또는 기간제 권한의 발급 결과 | SC-07·SC-09 |
| 후속 이용 | 기간제 갱신 요청 또는 사전 합의한 갱신 결과 확인 | 요청/자동 갱신과 결과·기간 연결 | 갱신 결과, 실패 시 남은 조치 | SC-08·SC-09 |
| 변경·예외 | 변경·취소·반품 요청과 결과 확인 | 허용 여부 확인, 회수·환불 요청과 결과, 실패 대조·재처리 | 처리 근거, 부분 결과와 미해결 업무 | SC-10 |

텍스트 흐름:

```text
내부 직원 상품 등록 → 고객 상품 확인 → 상품 타입별 주문 요청 → 판매 확정 판단
  하드웨어 주문: 재고 확인/주문 후 확보 → 출고 요청 → 배송 결과 확인
  소프트웨어 주문: 권한 발급 → 고객에게 결과 제공 → 기간제는 요청/자동 갱신
거래 조건: 선결제는 지급 확인 후 제공 / 후불은 합의된 조건으로 제공·기한 내 지급
각 흐름에서: 진행 조회, 지연·부분 이행, 변경·취소·반품·회수·환불·실패 처리
```

하드웨어와 소프트웨어는 서로 다른 주문이다. 이전 시장 조사에서 예시로 든 혼합 주문은 이번 제품의 지원 시나리오로 승계하지 않는다. 주문 이행 완료와 지급 완료, 기간제의 유효 기간 종료는 같은 사건으로 취급하지 않는다. 각 완료 의미는 OQ-04·OQ-05에서 확인한다.

## 업무 시나리오와 범위 검증 제안

아래는 실제 고객 사례가 아닌 **설명·검증용 합성 시나리오**다. 구체적인 허용 결과는 관련 정책을 결정한 뒤 검증한다.

| ID | 시나리오 | 검증할 업무 결과 | 관련 미정 정책 |
|---|---|---|---|
| VS-01 | 고객이 보유 재고 하드웨어를 선결제 조건으로 주문 | 요청·판매 확정·지급 확인·출고/배송 결과가 같은 주문에 연결됨 | OQ-01·OQ-02·OQ-03 |
| VS-02 | 후불 하드웨어 주문에 상품 확보와 부분 출고가 필요 | 확보 진행·납품 잔량·지급 기한과 상태를 구별하여 설명 가능 | OQ-02·OQ-03·OQ-05 |
| VS-03 | 영구 또는 기간제 소프트웨어 주문에 우리 측 권한 발급 | 올바른 고객·주문·이용 조건과 발급 결과 연결 | OQ-02·OQ-04 |
| VS-04 | 고객 요청 갱신과 사전 합의된 자동 갱신 각각 수행 | 기간·갱신 결과·지급 조건을 구분하며 실패나 중복 요청의 처리 근거 확인 | OQ-02·OQ-04·OQ-06 |
| VS-05 | 일부 제공 후 변경·취소·반품 요청, 외부 완료 결과 지연 | 요청 접수와 실제 회수·환불 완료를 혼동하지 않고 남은 조치 확인 | OQ-03·OQ-05·OQ-06 |
| VS-06 | 고객의 상품 등록 시도 또는 다른 기업 주문 조회 | 승인된 행위·기업별 접근 경계가 유지됨 | OQ-07 |

영구·기간제 소프트웨어는 모두 지원하지만 한 소프트웨어 주문에서 두 이용형을 함께 담을지까지 확정한 것은 아니다. VS-03은 각 유형을 검증하며 두 유형을 한 주문에 강제로 묶지 않는다.

## 성공 판단과 증거 확보

**범위 완결성의 검증 제안:** SC-01–SC-10과 OUT-01–OUT-09가 모두 추적되고, VS-01–VS-06을 관련 정책 결정 후 끝까지 설명·검증할 수 있어야 한다. 합성 시나리오 검증은 고객 수요 검증이나 외부 시스템 실증과 구별한다.

| 측정 후보 | 관찰 방법 | 현재 상태 |
|---|---|---|
| 주문 상태 확인 부담 | 주문별 조회·문의·수동 대조 횟수와 소요 시간 수집 | 기준값·목표값 없음 |
| 이행·갱신 예외 해결 시간 | 문제 인지부터 결과 확정까지 걸린 시간과 수동 개입 기록 | 기준값·목표값 없음 |
| 주문과 제공 결과의 불일치 | 대조한 주문에서 미확인·잘못 연결된 결과 건수 확인 | 실제 주문 표본 없음 |
| 1인 개발·운영 가능성 | 기능 변경·검증·배포·진단·복구 작업 시간과 반복 수동 개입 측정 | 거래 규모·서비스 수준·목표값 미정 |
| 고객 가치·구매 의사 | 실제 담당자에게 정상·예외 주문과 기존 방식의 차이를 확인 | 담당자·실제 업무 자료 미확보 |

수치 목표·처리량·가용성·출시일·비용을 임의로 정하지 않는다. 1인 수행 기준을 충족하지 못하면 구조·자동화·운영 방식을 개선하고 재검증한다. 인원 수를 이유로 포함 기능을 자동 제외하지 않는다.

## 상위 검토와의 연결 및 다음 판단

Feasibility의 C09는 이번 단계에서 고객의 구매 목적과 첫 업무 범위를 구체화했다. C12는 업무 경계를 정했으나 각 결과의 실제 원본·접근권은 남아 있다. C13은 소프트웨어 유형·발급 책임·하드웨어 공급 방식을 선택했으며 세부 제공 정책은 남아 있다. 실제 업무 자료 부재 C05, 플랫폼 준비 C08, 준수·운영 검증 C14–C16은 해결 완료로 표시하지 않는다. 상위 문서는 당시 기록으로 보존한다.

[RAID](../feasibility/raid-log.md)의 고객 수요·외부 결과 불일치·변경 충돌·권한·운영 위험을 [intent-backlog](intent-backlog.md)의 검증 묶음으로 전달한다. ‘모든 위험 해결’이나 ‘Inception 준비 완료’를 이번 범위 선택에서 추론하지 않는다.

이번 산출물은 업무 수준의 범위와 우선순위다. AWS·CDK는 기존 사용자 제약으로 유지하고, 언어·DB·서비스 구성·배포 구조·API·상태 모델을 정하지 않는다. Ideation 최종 검토와 사용자 승인 뒤에 Requirements·Architecture로 넘어간다.

## Assumptions & Open Questions

- A-S1 [assumption]: 선택한 고객군이 주문·제공·지급 결과의 연결에서 가치를 얻는다. 실제 고객 사례·지불 의사로 검증해야 한다.
- A-S2 [assumption]: 필요한 공급·출고·수금·소프트웨어 실행 주체와 연결 근거를 확보할 수 있다. 현재 접근권·계약·실행 환경은 미확인이다.
- A-S3 [assumption]: 후속 구조·자동화·운영 방식이 합의할 업무량에서 1인 개발·운영 목표를 달성한다. 목표는 확정이며 달성 가능성은 미검증이다.
- A-S4 [assumption]: 위 합성 시나리오가 정책 모순을 발견하는 데 도움이 된다. 실제 고객·연동 검증을 대신하지 않는다.
- 상세 미정은 OQ-01–OQ-10으로 추적한다. SD-01–SD-10은 사용자 결정이며 assumption으로 격하하지 않는다.
