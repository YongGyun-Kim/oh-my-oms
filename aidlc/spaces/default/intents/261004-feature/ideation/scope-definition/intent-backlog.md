# OMS 첫 제품 업무 백로그

작성일: 2026-10-05. 상태: 사용자 검토용. 업무 묶음(proto-Units)을 정리한 문서이며 실제 개발 단위·서비스·담당 조직·일정은 아니다.

## 우선순위 원칙

범위는 [scope-document](scope-document.md)의 SC-01–SC-10, 근거는 [질문 답변](scope-definition-questions.md) Q1–Q12다. [intent-statement](../intent-capture/intent-statement.md)의 조사 우선 원칙과 [feasibility-assessment](../feasibility/feasibility-assessment.md), [constraint-register](../feasibility/constraint-register.md)의 검증 한계를 유지한다.

- **범위 분류:** MoSCoW를 사용한다. Must는 사용자가 선택한 첫 제품에 포함할 업무, Won't는 이번 직접 구축·지원 제외다. 아직 선택하지 않은 항목은 미정으로 구분한다.
- **진행 순서:** Q12에 따라 불확실성 우선. 미정 정책과 실패 사례를 먼저 확인하고, 검증한 업무를 필요한 선행 관계에 맞춰 연결한다. 위험 검증을 앞에 둔다고 의존 기능 없이 구현하거나 요구사항 승인 전에 개발하지 않는다.
- **임의 점수 없음:** 고객 수·효과·공수 근거가 없어 RICE·WSJF 점수, 인일·기간·금액을 만들지 않는다.
- **1인 수행 목표:** 인원 수를 범위 축소 근거로 사용하지 않는다. 자동화와 변경·운영 용이성의 효과를 후속 검증한다.

## 첫 제품의 Must 업무 묶음

모든 IB 항목은 Must다. 사용자가 선택한 범위를 인위적으로 Should/Could로 낮추지 않는다. 표의 확인 증거는 **검증 제안**이며 세부 정책을 정한 뒤 후속 요구사항·테스트로 구체화한다.

| ID | 업무 묶음·사용자 결과 | 범위·결정 근거 | 검증할 핵심 증거 | 미정 정책 |
|---|---|---|---|---|
| IB-01 | 주문 주체와 권한·기록: 직원과 고객이 허용된 기업·업무 범위에서 처리 | SC-01; Q1·Q10 | 고객 상품 등록·타 기업 주문 접근이 허용되지 않으며 중요한 처리의 주체와 결과를 설명 | OQ-07·OQ-08 |
| IB-02 | 상품 등록·확인: 직원이 판매 상품을 등록하고 기업 고객이 확인 | SC-02; Q1·Q3·Q4·Q10 | 등록 주체와 상품 타입·이용형이 주문할 정보로 연결됨 | OQ-04·OQ-07·OQ-10 |
| IB-03 | 타입별 주문 요청: 고객이 하드웨어/소프트웨어 주문을 각각 제출 | SC-03; Q3·Q11 | 혼합 주문은 접수 대상이 아니며 각 주문의 기업·품목·요청 결과 확인 | OQ-07·OQ-10 |
| IB-04 | 주문 수락: 조건별 자동 확정/직원 확인으로 판매 여부 결정 | SC-04; Q5·Q10 | 같은 조건에 대한 판단 근거와 확인 필요 상태를 설명; 접수와 확정을 구분 | OQ-01·OQ-02 |
| IB-05 | 거래 조건과 대금: 선결제/후불 주문의 청구·지급과 제공 판단 연결 | SC-05; Q9·Q10 | 지급 확인·미확인·지연 결과가 실제 제공 조건과 일치하는지 검증 | OQ-02·OQ-05 |
| IB-06 | 하드웨어 이행: 재고 출고/주문 후 확보에서 배송 결과까지 연결 | SC-06; Q7·Q10 | 두 공급 경로의 확보·출고·배송·잔량과 지연 근거 확인 | OQ-03·OQ-05 |
| IB-07 | 소프트웨어 권한 제공: 우리 측이 영구/기간제 권한을 발급하고 결과 제공 | SC-07; Q4·Q6·Q10 | 고객·주문·발급 결과·기간이 일치하고 실패·불명확 결과를 완료로 오인하지 않음 | OQ-04·OQ-05·OQ-10 |
| IB-08 | 기간제 갱신: 고객 요청/합의된 자동 갱신으로 기간과 결과 연결 | SC-08; Q8·Q10 | 두 갱신 경로와 실패·중복·지급 조건의 처리 결과를 설명 | OQ-02·OQ-04·OQ-06 |
| IB-09 | 진행 조회: 고객·직원이 주문·품목 진행과 남은 조치를 확인 | SC-09; Q10 | 부분 이행·지연·제공 완료와 지급 상태가 구분되어 원인·남은 조치를 확인 | OQ-03·OQ-04·OQ-05 |
| IB-10 | 변경·예외 처리: 변경/취소/반품과 필요한 회수·환불·실패 대응 추적 | SC-10; Q10 | 요청 수락과 실제 완료를 구분하고 결과 미확인 상태에서 잘못된 중복 실행을 방지할 정책 검증 | OQ-01–OQ-06 |

IB-01의 접근 통제·기록과 IB-09·IB-10의 상태·예외 처리는 모든 관련 업무에서 함께 확인한다. 표의 순서 때문에 마지막까지 미루는 독립 작업으로 해석하지 않는다.

## 의존성: 판단에 필요한 업무 정보

이 표는 업무 정보·정책의 의존성이다. 런타임 호출 방향, 배포 단위, DB 경계 또는 전부 구현해야 다음 업무를 시작할 수 있는 고정 개발 DAG가 아니다. 각 기능의 의미를 먼저 합의하고 좁은 시나리오로 함께 검증할 수 있다.

| 업무 묶음 | 필요한 선행 정보·정책 | 이유 |
|---|---|---|
| IB-01 | 기업·직원·고객 역할, 허용 행위 | 기업별 접근과 처리 주체를 구분 |
| IB-02 | IB-01의 등록 주체·조회 범위 | 상품 등록 권한을 내부 직원으로 제한 |
| IB-03 | IB-01의 기업 식별, IB-02의 상품·타입 정보 | 고객 요청의 주체와 주문 분리를 판단 |
| IB-04 | IB-03의 요청 정보, OQ-01 및 IB-05의 거래 조건 정의 | 조건에 맞는 판매 수락과 확인 필요 판단 |
| IB-05 | IB-03의 주문 참조와 거래 조건, 외부 수금 결과의 의미 | 청구·지급을 주문과 연결. 최초 상태 생성 시점은 OQ-02에서 결정 |
| IB-06 | IB-04의 수락 결과, IB-05의 제공 조건, 실제 공급·출고 결과 | 허용된 하드웨어 이행을 진행하고 결과 확인 |
| IB-07 | IB-04의 수락 결과, IB-05의 제공 조건, 이용형·대상·기간 정책 | 올바른 소프트웨어 권한 제공 |
| IB-08 | IB-07의 권한·기간, 갱신 합의·요청과 IB-05의 지급 관계 | 갱신의 대상과 허용 조건 판단 |
| IB-09 | IB-03–IB-08의 적용 가능한 진행 결과, IB-01의 접근 범위 | 고객과 직원에게 근거 있는 진행 상태 제공 |
| IB-10 | IB-03–IB-08의 현재 결과와 변경·회수·환불 정책, IB-01의 권한 | 이미 실행된 일과 남은 일을 구분하여 후속 처리 |

IB-04와 IB-05의 정책은 함께 검증한다. 후불은 지급 완료가 상품 제공의 보편적 선행 조건이 아니며, 선결제는 지급 확인과 제공 허용의 관계를 명확히 해야 한다. 한 개의 고정 단계 순서로 두 거래 형태를 덮지 않는다.

## 불확실성 우선의 검증 순서 제안

아래 EV 항목은 포함 기능을 추가하는 백로그가 아니라 **근거를 확보하는 검증 묶음**이다. 아직 실행하지 않았다. 결과에 따라 순서는 조정할 수 있으나 Must를 자동 제외하지 않는다.

| 순서·ID | 먼저 확인할 불확실성 | 필요한 증거와 판단 결과 | 연결 업무·상위 위험 |
|---|---|---|---|
| 1 / EV-01 | 타깃 고객의 주문 문제와 실제 업무 근거 | 선택한 고객·정상/예외 사례·대체 수단 비교. 없으면 가설과 확보 계획을 유지 | 전체; Feasibility R01·I01 |
| 2 / EV-02 | 수락·선후불·변경과 제공의 관계 | 조건별 수락·지급·이행·변경 판단을 합성 사례로 검토하고 미정 정책 명시 | IB-04·IB-05·IB-10; R04 |
| 2 / EV-03 | 우리 측 발급·기간·자동 갱신의 책임과 적용 | 권한 발급 결과를 적용할 대상, 기간·갱신·실패·회수 규칙과 외부 경계 확인 | IB-07·IB-08·IB-10; R03·R05·R08 |
| 2 / EV-04 | 재고·주문 후 확보·출고·배송 결과의 신뢰성 | 실제 수행 주체·참조·결과 확인 경로와 시험 접근 가능성 확인 | IB-06·IB-09·IB-10; R03·R06 |
| 전 과정 / EV-05 | 기업·사용자 권한과 데이터·계약 조건 | 허용/금지 업무와 기업별 접근 경계, 실제 데이터·국가·계약 확인 | IB-01 및 전체; R07·R09 |
| 흐름 검증 후 / EV-06 | 1인 개발·운영 구조의 효과 | 필요한 업무량에서 변경·배포·진단·복구·수동 개입을 측정할 기준과 증거 | 전체; R02·R10·R11 |

EV-02–EV-04 사이의 실제 착수 순서는 근거 접근성과 업무 의존에 따라 조정한다. 숫자는 기간·우선순위 점수가 아니다. 자료 미확보로 진행한 합성 검증을 실증으로 바꾸어 기록하지 않는다.

## 업무를 연결하는 순서 제안

정책 검증 후 고객 가치가 끝까지 보이는 흐름으로 구성한다. 다음은 실제 구현 계획 이전의 전달 관점 제안이다.

| 묶음 | 보여 줄 결과 | 연결 업무 |
|---|---|---|
| 주문 접점과 판매 판단 | 내부 상품 등록에서 고객의 타입별 주문 요청·판매 확정 판단·상태 확인까지 | IB-01–IB-05·IB-09, 관련 IB-10 |
| 하드웨어 이행 | 재고 출고와 주문 후 확보 경로 각각에서 고객이 실제 진행·결과를 확인 | IB-06·IB-09·IB-10, 선행 주문/대금 업무 |
| 소프트웨어 제공·갱신 | 영구/기간제 발급과 요청/자동 갱신에서 권한·기간·지급·처리 결과 확인 | IB-07·IB-08·IB-09·IB-10, 선행 주문/대금 업무 |
| 전체 범위 확인 | 예외·접근·운영 부담을 포함한 VS-01–VS-06 검증 | IB-01–IB-10 |

하드웨어와 소프트웨어 흐름 중 무엇을 먼저 구현할지는 EV-03·EV-04의 결과와 후속 의존성 분석으로 정한다. 실제 Bolt·개발 단위·일정·기술 선택은 여기서 확정하지 않는다. 어느 흐름을 먼저 보여 주더라도 나머지 Must를 제외한 상태를 전체 MVP 완료라고 부르지 않는다.

## MoSCoW의 나머지 범주

| 분류 | 항목 | 처리 원칙 |
|---|---|---|
| Should | 별도로 선택한 항목 없음 | 추가 가치를 실제 근거로 확인하면 사용자와 우선순위 결정 |
| Could | 별도로 선택한 항목 없음 | 장식적·부가적 기능을 임의로 추가하지 않음 |
| Won't: 이번 제외 | scope-document의 OUT-01–OUT-09 | 외부 상품 등록·혼합 주문·인접 시스템 전체/실행 기능 직접 구축 제외 |
| 미선택·미정 | 직원 대리 입력, 자동 결제 연동·정기 청구, 범용 규칙 편집, 모든 커넥터, 설치·유지보수·업그레이드·고객 자산 관리 | Won't와 구별. 실제 필요 확인 및 별도 범위 결정 없이 필수로 승격하지 않음 |

이번 포함 범위가 모두 Must인 이유는 Q10에서 업무 경계 전체를 첫 제품 범위로 선택했기 때문이다. 프레임워크상의 비율을 맞추기 위해 사용자가 포함한 갱신·후불·예외 업무 등을 임의로 낮추지 않는다. 경제성·수요·기간이 입증되었다는 의미도 아니다.

## 완료 판단과 추적

범위 정의 산출물의 점검 기준:

- SC-01–SC-10 각각에 IB 항목과 사용자 결정 근거가 있다.
- 각 IB에 고객 결과·검증할 증거·미정 정책·업무 의존을 기록했다.
- OUT-01–OUT-09와 미선택 항목을 포함 범위와 구별했다.
- 혼합 주문·외부 상품 등록이 흐름에 재등장하지 않는다.
- 1인 수행 목표를 기능 축소의 근거로 전환하지 않는다.
- 실제 고객·외부 연동·운영 효과가 검증되지 않았음을 유지한다.

제품 완성 기준과 정량 목표는 정책·데이터 확보 후 구체화한다. 현재 백로그 작성 완료는 제품 구현·시장 검증·운영 준비 완료가 아니다. 상위 Feasibility의 위험은 문서화만으로 종결하지 않는다.

## Assumptions & Open Questions

[scope-document](scope-document.md)의 A-S1–A-S4와 OQ-01–OQ-10을 동일하게 적용한다. 제안한 업무 묶음과 검증 순서의 세부 구성은 분석자의 정리이며, 실제 구현 단위는 후속 분해에서 바뀔 수 있다. 국가·기한·예산·처리량·연동 대상·계약·지원 시간의 수치나 대상을 임의로 채우지 않았다.
