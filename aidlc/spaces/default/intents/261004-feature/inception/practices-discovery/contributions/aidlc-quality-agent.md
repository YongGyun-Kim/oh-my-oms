### 테스트 방법과 범위

- 초안의 `Methodology: test-after`와 계층별 구현 후 테스트 순서는 조직 기본 제안으로 타당하며, 아직 팀 확정으로 기록하면 안 된다.
- 인터뷰에서 구현 전/후/혼합 순서를 확인한다. 혼합이면 `custom`과 계층별 순서를 명시하고, 시나리오의 Given/When/Then 형식만으로 BDD 개발 순서를 선택했다고 해석하지 않는다.
- 현재 `Standard`는 단위·통합 테스트를 포함한다. 초안의 “테스트 종류 미정”은 이 최소 범위와 추가할 테스트 종류를 구별하도록 보완한다.
- `feature`의 라인 커버리지 80%와 병합 전 CI 실행은 현재 조직 기본 하한이다. 테스트 방법 변경이나 1인 인력 현황으로 하한을 낮추지 않는다.
- 커버리지는 업무 검증의 대체 지표가 아니다. 각 수락 기준의 정상·실패·경계 검증과 연결을 별도로 남기는 방식을 제안한다.
- 커버리지 산정 단위(전체/모듈), 제품 코드 포함 범위, 생성 코드 등 제외 사유를 정해야 한다. 미실행 제품 파일을 분모에서 빼거나 프레임워크 내부 코드를 섞어 수치를 부풀리지 않는 안을 제시한다.
- 언어·테스트 러너·리포터는 후속 기술 결정 뒤 선정한다. 지금은 측정 대상과 실패 시 처리 원칙을 합의하며 특정 제품을 선택하지 않는다.

### CI와 배포 검증의 보완안

- 병합 전에는 해당 단위·통합 테스트의 성공, 커버리지 하한, 린트/포맷 검사를 확인하고 실패 시 병합을 막는 기본안을 명시한다.
- 실패·미실행·건너뛴 검사와 성공을 구분하고, 커버리지 보고서가 생성되지 않았을 때 통과로 간주하지 않는 안을 제시한다.
- 불안정 테스트의 반복 재실행만으로 통과 처리하지 않는 원칙과 수정 담당·기한·긴급 수정 절차를 인터뷰에서 확인한다. 별도 QA 인력을 가정하지 않는다.
- 전체 사용자 흐름 검증을 모든 PR에 추가할지, 검증 환경이나 운영 배포 전에 실행할지는 별도 합의 사항이다. Standard를 이유로 필요한 핵심 경로 검증을 누락하지 않는다.
- 최소 동작 확인은 사용자 승인 검증 명령으로 실제 연결 결과를 보여야 한다. 문서 검토·단위 테스트 커버리지만으로 최초 동작 승인을 대체할 수 없다.
- 보안 검사 세부 차단 기준은 보안 검토와 통합한다. 본 검토는 스캐너·CI 서비스·배포 구조를 고정하지 않는다.

### 업무 위험과 테스트 패턴

- 요구사항 확정 후 우선 검증할 후보: 주문 수락 분기, 중복 요청·재처리, 권한 발급·갱신의 기간 경계, 청구/지급 구분, 부분 이행·취소 처리의 상태 일관성이다. 미정 정책의 기대 결과는 지금 만들지 않는다.
- 기업 간 접근 차단과 직원 행위 권한, 직원 사내망 조건을 서버 측 결과로 검증하는 후보를 포함한다. 직원 모바일 제외를 고객 모바일 제외로 확대하지 않는다.
- 테스트는 각자 데이터를 준비·정리하고 시간·순서·외부 응답에 의존하지 않게 만드는 안을 제안한다. 정상·실패·중복·시간 경계 데이터는 재현 가능하게 관리한다.
- 단위 테스트의 대역과 실제 경계의 통합 검증을 구분한다. 모든 외부 응답을 모사한 결과만으로 실제 연동을 검증했다고 쓰지 않는다.
- 실제 시험 접근·원본·계약이 없는 연동은 HB-04·HB-05에 미검증으로 남긴다. 합성 자료는 HB-01의 고객 검증이나 HB-07의 실데이터 도입 조건을 해소하지 않는다.
- 부하·복구·운영 부담의 수치는 HB-08에서 입력과 목표를 정한 뒤 검증한다. 현재 임의의 지연·처리량·복구 수치나 자동 확장 구조를 의무화하지 않는다.
