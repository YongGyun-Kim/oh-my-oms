- 실제 비밀이 노출되면 폐기·교체와 영향 확인을 우선하는 대응 절차를 제안한다. 파일 삭제나 탐지 예외만으로 해소됐다고 처리하지 않는다.
- 검사 실패와 검사 미실행을 구분하는 정책을 제안한다. 필수 검사가 실패·중단·누락되면 통과로 표시하지 않으며 예외는 별도 승인 기록을 남긴다.
- 취약점 심각도·악용 가능성에 따른 차단선, 오탐 검토, 예외 승인자·사유·만료·재검토를 인터뷰에서 확인한다. 구체적인 수치와 도구는 아직 확정하지 않는다.
- 인증·기업별 데이터 접근·직원 행위 권한·사내망 제한의 실패 경로를 별도 검증 대상으로 제안한다. 커버리지 80%나 린트 통과만으로 이 경계의 검증을 대체하지 않는다.
- 운영 배포 사람 승인이라는 기본안을 유지하되 실제 승인자와 긴급 수정·복구 권한을 확인한다. 별도 보안팀이나 다인 승인 체계가 확보됐다고 가정하지 않는다.

### 인터뷰에서 해소할 공백

1. **Code Style**: 병합 전 포맷·린트와 비밀·코드·의존성 보안 검사를 필수 검사로 둘지, 기존 강제 규칙이나 사용할 수 있는 조직 도구가 있는지 확인한다.
2. **Testing Posture**: 접근 거부와 기업 간 데이터 격리 검증을 필수 결과로 관리할지 확인한다. 상세 접근 정책은 HB-06을 따라 후속 요구사항에서 결정한다.
3. **Way of Working**: 보안 발견 항목을 누가 확인하고, 어떤 위험에서 병합을 차단하며, 오탐·기한부 예외를 누가 승인할지 확인한다.
4. **Deployment**: 운영 승인·긴급 수정·복구 책임, 필수 검사 장애 시 처리, 검증 환경의 실행 보안 검사와 운영 승격의 관계를 확인한다.
5. **공급망·비밀 관리**: 허용할 외부 의존성·빌드 도구 검토 방식, 업데이트·재검사 주기, 비밀 접근·회수 담당과 사고 대응 절차의 선호를 확인한다.

위 질문은 다섯 관행 영역 인터뷰에 필요한 항목만 합쳐 제시할 권고다. 이 검토에서는 사용자 질문이나 결정을 기록하지 않았다.

### 후속 단계로 넘길 경계

- HB-06: 사내망의 의미와 판별·원격 예외·세션 중 조건 변경, 기업·직원별 신원·행위 권한, 발급 결과 비밀 취급을 요구사항·설계에서 구체화한다. UI 숨김이나 PC 화면만으로 접근 통제를 충족했다고 보지 않는다.
- HB-07: 실제 데이터·국가·계약·보관/삭제와 적용 의무를 실데이터·실거래 도입 전 확인한다. 특정 인증·법규 준수를 새 의무나 완료 사실로 만들지 않는다.
- HB-08: 정기 검사·업데이트·예외 재검토·알림 대응의 부담도 1인 개발·운영 가능성 검증에 포함한다. 인원 수를 이유로 승인 기능을 축소하지 않는다.
- 제안은 인터뷰 답변에 따라 팀 관행에 반영한다. `discovered-rules.md`의 `ALWAYS`/`NEVER`에는 사용자가 명시한 강제 조건만 기록한다.
