### 인터뷰 보완 항목

1. 기존에 반드시 따라야 하는 코드 표준·설정 파일·도메인 용어집이 있는지 확인한다. 없다면 언어 관례와 저장소 설정을 기본으로 삼는 초안을 제시한다.
2. 오류 처리에 이미 정한 강제 규칙이 있는지 확인한다. 예상 가능한 업무 거절과 시스템 실패를 구분하고, 실패를 성공으로 처리하지 않는 원칙은 추가 제안으로만 제시한다.
3. 고객에게 보여줄 오류 설명과 개발자가 원인을 찾는 진단 기록의 구분, 민감정보를 기록하지 않는 기존 규칙이 있는지 확인한다. 보안 검토와 질문 중복을 조정한다.
4. 파일 배치·모듈 의존 방향·테스트 위치에 기존 표준이 있는지 확인한다. 선호가 없다면 후속 설계에서 결정한다고 명시하고 이번 인터뷰에서 구조 선택을 요구하지 않는다.
5. 자동 검사 실패를 병합 차단으로 삼는 제안에 대한 의사와, 기존 예외 처리 규칙의 유무를 확인한다. 도구 이름과 언어 선택을 묶어서 묻지 않는다.

위 항목은 Code Style 영역의 한 묶음으로 통합할 수 있다. 초안이 이미 제안한 다섯 영역 인터뷰를 늘리는 별도 제품 요구사항 질문이 아니다.

### 후속 설계로 넘길 사항

- AWS·CDK 채택은 구현 언어·DB·API 방식·폴더 구조를 결정하지 않는다. D-07의 해석 범위를 유지한다.
- D-19의 하드웨어·소프트웨어 주문 분리는 업무 결정이다. 별도 서비스나 저장소가 필요하다는 아키텍처 결론으로 옮기지 않는다.
- HB-02·HB-05의 실패·중복·재처리 정책이 구체화되면 계약 설계에서 오류 분류와 재시도 가능성을 연결한다. 지금 자동 재시도나 멱등성 수단을 선택하지 않는다.
- HB-06의 기업·직원 접근 경계는 API와 업무 처리의 검증 책임으로 이어져야 한다. UI 숨김이나 직원 사내망 접속만으로 접근 통제를 완료했다고 간주하지 않는다.
- 공통 코드·외부 연동·업무 로직의 책임 경계와 테스트 배치는 후속 설계 근거를 따른다. 기능별 파일 배치는 후보이며 이미 채택된 팀 표준으로 기록하지 않는다.
- 함수 길이·매개변수 개수·파일 줄 수·Result 사용처럼 지식에 든 구체적 권고를 사용자 발언 없이 `ALWAYS`/`NEVER` 규칙으로 승격하지 않는다.

### 기록 정합성

- `discovered-rules.md`의 AWS·CDK와 1인 수행 목표는 승인 인계 근거가 있다. 개발자 수로 기능을 축소하지 않는 원칙을 그대로 유지한다.
- 최종 통합 시 기존 `project.md` Corrections의 인력 원칙과 중복 영구 기록 필요성을 점검한다는 초안 설명을 유지한다.
- 실제 구현·운영 검증과 HB 해소는 이번 개발 관례 인터뷰로 완료되지 않는다. 새 관례는 사용자 답변과 근거를 연결한 뒤 반영한다.
