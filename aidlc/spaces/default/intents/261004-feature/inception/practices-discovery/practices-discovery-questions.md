# 개발·테스트·배포 관행 확인

## Prior Context

- Greenfield이며 기존 팀 관행은 아직 확정되지 않았다. [초안](team-practices.md)은 조직 기본값의 제안이다.
- AWS·CDK 사용, 개발자 1명으로 필요한 기능의 개발·운영이 가능한 구조를 목표로 하는 점, 인원 수로 기능을 축소하지 않는 점은 이미 확정됐다. 다시 선택하지 않는다.
- 제품 범위와 직원 사내망 PC 전용·고객 PC 우선 및 모바일 지원은 [승인된 인계 결정](../../ideation/approval-handoff/decision-log.md)을 따른다.
- 이번 확인은 개발 관행이다. 언어·DB·서비스 구성·구체적 CI/CD 제품·세부 업무 정책은 여기서 확정하지 않는다.
- [품질 검토](contributions/aidlc-quality-agent.md), [개발 검토](contributions/aidlc-developer-agent.md), [보안 검토](contributions/aidlc-devsecops-agent.md)의 공백을 Q1–Q8에 반영했다. 검토자의 제안은 사용자 답변 전까지 의무나 구현 완료가 아니다.
- 현재 조직 기준의 단위·통합 테스트, 라인 커버리지 80% 하한, 병합 전 CI 실행은 유지한다. 방법론·도구·측정 범위는 구분해서 확인한다.

## Q1. 변경 사항은 짧은 작업 브랜치에서 검증한 뒤 main으로 합치고, 병합 판단은 누가 맡도록 할까요?

작업별 브랜치를 만들고 변경 이력을 하나로 묶어 합치는 squash 병합을 기본안으로 삼는다. 현재 인력이 1명이므로 별도 리뷰 인원을 있다고 가정하지 않는다. 이 답변은 지금 코드를 자동으로 병합하라는 실행 지시가 아니다.

A. 짧은 작업 브랜치·squash 병합을 사용하고, 개발자 본인이 검사 결과와 변경 내용을 검토해 병합한다.
B. 짧은 작업 브랜치·squash 병합을 사용하되, 별도 검토자의 확인도 받는다. 검토자는 추가로 지정한다.
C. 기존 조직의 리뷰·병합 절차가 있다. 해당 절차를 설명한다.
X. Other (please specify)

[Answer]: A. 짧은 작업 브랜치·squash 병합을 사용하고, 개발자 본인이 검사 결과와 변경 내용을 검토해 병합한다. 사용자 선택: "1" (개발자 본인이 검토·병합).

## Q2. 전체 경로가 연결되는 최소 동작 버전을 먼저 만들까요? Walking skeleton은 화면부터 필요한 처리까지 끝까지 실행되는 작은 버전을 먼저 만들어 구성 요소의 연결을 확인하는 방식입니다.

기능 범위를 줄이는 결정이 아니라 구현 순서의 결정이다. 첫 업무 흐름과 실제 검증 명령은 요구사항·설계를 구체화한 뒤 정한다. 현재 feature 기본안은 먼저 만드는 방식이다.

A. 예. 최소 동작 버전을 먼저 실행·검증한 뒤 나머지 기능을 확장한다.
B. 아니요. 다른 구현 순서를 원한다. 현재 절차와의 영향은 별도로 확인한다.
X. Other (please specify)

[Answer]: A. 예. 최소 동작 버전을 먼저 실행·검증한 뒤 나머지 기능을 확장한다. 사용자 선택: "1" (예 — 최소 동작 버전부터 검증). 승인된 전체 기능 범위를 유지하며 첫 검증 흐름과 명령은 후속 요구사항·설계에서 정한다.

## Q3. 테스트는 기능 구현 전후 중 언제 작성할까요?

테스트 작성 순서와 테스트 종류·커버리지 기준은 별개다. 사용자 시나리오를 Given/When/Then으로 적는다는 사실만으로 테스트 우선 개발을 선택한 것으로 간주하지 않는다.

A. 각 테스트 가능한 계층을 구현한 뒤 해당 계층의 테스트를 작성·실행한다. 조직 기본안인 test-after다.
B. 실패하는 테스트를 먼저 작성하고 기능을 구현한 뒤 코드를 정리한다. TDD 방식이다.
C. 업무 동작의 예시와 수락 테스트를 먼저 작성하고 그 동작을 구현한다. BDD 또는 ATDD의 구체적 순서는 추가로 확인한다.
D. 업무·계층에 따라 순서를 섞는다. 어느 부분을 먼저/나중에 테스트할지 설명한다.
X. Other (please specify)

[Answer]: A. 각 테스트 가능한 계층을 구현한 뒤 해당 계층의 테스트를 작성·실행한다. 조직 기본안인 test-after다. 사용자 선택: "1" (구현 후 테스트). Methodology는 test-after로 기록하고 단위·통합 테스트 및 커버리지 하한은 별도로 유지한다.

## Q4. 라인 커버리지 80%는 어떤 코드 범위에 적용하고, 중요한 업무 검증은 어떻게 관리할까요?

커버리지는 테스트가 실행한 코드의 비율이며 업무가 올바르다는 보증은 아니다. 아직 제품 코드·측정 도구는 없다. 아래 선택은 앞으로 적용할 기준이다.

A. 직접 작성한 테스트 가능한 제품 코드 전체에 80% 하한을 적용한다. 생성물·외부 코드 등의 제외 사유를 기록하고 미실행 제품 파일도 분모에 포함한다. 수락 기준별 정상·실패·경계 검증은 따로 추적한다.
B. 전체 80%에 더해 주요 모듈별 하한도 둔다. 대상 모듈과 추가 하한은 설계 후 확정한다.
C. 기존 측정·제외 기준이 있다. 현재 하한을 유지하는 기준을 제공한다.
X. Other (please specify)

[Answer]: A. 직접 작성한 테스트 가능한 제품 코드 전체에 80% 하한을 적용한다. 생성물·외부 코드 등의 제외 사유를 기록하고 미실행 제품 파일도 분모에 포함한다. 수락 기준별 정상·실패·경계 검증은 따로 추적한다. 사용자 선택: "1" (제품 코드 전체에 80%).

## Q5. 병합 후 검증 환경에 자동 배포하고 운영 배포에는 사람 승인을 두는 기본안에서, 승인과 복구 책임은 어떻게 둘까요?

검증 환경은 staging, 실제 서비스를 제공하는 환경은 production이다. 환경이 이미 마련됐다는 뜻은 아니다. 운영 배포 전후에는 핵심 동작을 확인하고, 구체적인 검증·복구 방법은 후속 설계에서 정한다.

A. 기본안을 사용한다. 개발자 본인이 검사·핵심 동작 결과를 확인해 운영 배포를 승인하고, 긴급 수정·복구 판단과 실행 이력을 남긴다.
B. 기본안을 사용하되 운영 승인과 긴급 수정·복구 권한을 별도 담당자에게 둔다. 실제 담당자는 추가 지정한다.
C. 기존 배포·승인·복구 절차가 있다. 해당 절차를 제공한다.
X. Other (please specify)

[Answer]: A. 기본안을 사용한다. 개발자 본인이 검사·핵심 동작 결과를 확인해 운영 배포를 승인하고, 긴급 수정·복구 판단과 실행 이력을 남긴다. 사용자 선택: "1" (개발자 본인이 승인·복구 책임). main 병합 후 검증 환경에 자동 배포하고 운영 환경에는 사람 승인 후 배포한다. 실제 환경 구성·검증·복구 방법은 후속 설계에서 정한다.

## Q6. 코드의 이름·오류 처리·파일 배치에 이미 반드시 따라야 할 표준이 있나요?

기본안은 선정할 언어의 관례와 버전 관리되는 포매터·린터 설정을 로컬과 CI에서 동일하게 사용하는 것이다. 구체적인 폴더·계층·오류 표현 방식은 후속 설계에서 정한다.

A. 기존 표준은 없다. 기본안을 사용하고 오류 처리·파일 배치·모듈 의존 규칙은 후속 설계에서 정한다.
B. 기존 표준이나 설정이 있다. 명명·오류 처리·파일 배치·의존 경계 중 적용할 내용을 제공한다.
C. 기존 문서는 없지만 반드시 지킬 선호나 금지 규칙이 있다. 내용을 설명한다.
X. Other (please specify)

[Answer]: A. 기존 표준은 없다. 기본안을 사용하고 오류 처리·파일 배치·모듈 의존 규칙은 후속 설계에서 정한다. 사용자 선택: "1" (기존 표준 없음 — 언어 관례와 자동 검사 적용). 선정할 언어의 관례를 따르고 포매터·린터 설정을 저장소에서 관리해 로컬과 CI에서 동일하게 검사한다.

## Q7. 개발 과정에 어떤 보안 검사를 필수로 포함할까요?

제안은 키·토큰 유입 검사, 코드의 취약 패턴 검사, 의존성 취약점 검사, CDK와 생성 인프라의 보안 설정 검사다. 실행 중 서비스 검사는 격리된 검증 환경과 합성 데이터로 수행할 계획을 세운다. 직원 사내망·기업별 권한의 실제 검증 기준은 이미 인계한 접근 요구사항에서 구체화한다.

A. 제안한 검사들을 필수 계획에 포함한다. 언어·구조가 정해지면 대상·도구·실행 시점·차단 기준을 구체화하고, 실제 적용 전 확인한다.
B. 이미 사용할 보안 검사 정책·도구가 있다. 해당 정책을 제공한다.
C. 추가 검사의 필수 범위는 후속 보안 요구사항에서 결정한다. 지금 구현·검사 완료로 표시하지 않는다.
X. Other (please specify)

[Answer]: A. 제안한 검사들을 필수 계획에 포함한다. 언어·구조가 정해지면 대상·도구·실행 시점·차단 기준을 구체화하고, 실제 적용 전 확인한다. 사용자 선택: "1" (제안한 검사를 필수 계획에 포함). 키·토큰 유입, 코드 취약 패턴·의존성 취약점, CDK·생성 인프라 보안 설정, 격리된 검증 환경에서 실행 중 서비스의 보안 검사를 포함한다. 현재 검사가 구현되거나 통과한 것으로 표시하지 않는다.

## Q8. 필수 검사 실패·누락과 보안 발견 사항은 누가 어떤 원칙으로 처리할까요?

제안은 필수 검사 실패·미실행·보고서 누락 시 병합 또는 해당 배포를 보류하는 것이다. 불안정 테스트를 반복 실행해 우연히 통과한 결과로 대신하지 않는다. 보안 오탐·예외는 사유·담당·만료·재검토를 기록하며, 테스트 하한을 낮춰 통과시키지 않는다. 실제 비밀 노출은 폐기·교체와 영향 확인으로 처리한다.

A. 이 원칙을 사용하고 개발자 본인이 처리·검토 책임을 맡는다. 의존성·외부 빌드 도구의 변경 검토와 정기 재검사·예외 재검토 주기는 운영 설계에서 확정한다.
B. 이 원칙을 사용하되 보안 예외 승인·비밀 대응 책임은 별도 담당자에게 둔다. 담당자를 추가 지정한다.
C. 기존 검사 실패·보안 대응·예외 정책이 있다. 해당 정책을 제공한다.
X. Other (please specify)

[Answer]: A. 이 원칙을 사용하고 개발자 본인이 처리·검토 책임을 맡는다. 의존성·외부 빌드 도구의 변경 검토와 정기 재검사·예외 재검토 주기는 운영 설계에서 확정한다. 사용자 선택: "1" (제안한 원칙 적용 — 개발자 본인이 책임). 필수 검사 실패·미실행·보고서 누락 시 병합 또는 해당 배포를 보류하고, 불안정 테스트의 우연한 통과나 테스트 하한 완화로 대체하지 않는다. 보안 오탐·예외의 사유·담당·만료·재검토를 기록하고 실제 비밀 노출은 폐기·교체와 영향 확인으로 대응한다.

## Follow-up Boundaries

- Q2의 다른 순서 선택은 기존 절차를 임의 변경하는 승인으로 처리하지 않고 영향과 필요한 변경 절차를 확인한다.
- 별도 담당자·기존 정책을 선택하면 실제 이름 또는 역할·자료를 추가로 확인한다. 인원·권한을 가정하지 않는다.
- 혼합 테스트 순서는 Methodology를 custom으로 기록하고 Ordering에 각 순서를 명시한다.
- 검사 종류·필수 시점·차단선·예외 권한·정기 검사 주기의 미정 값은 구현·운영 전 해당 후속 단계에서 확정한다. 현재 그 값이나 검사 통과를 만들어 기록하지 않는다.
- 모든 답변 후 별도 요약 확인을 받고 리드가 최종 문서에 통합한다. 현재 네 산출물은 Step 2 초안이다.
