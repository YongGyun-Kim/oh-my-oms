# OMS PC 화면 시안

## 작성 범위와 사용 방법

확인한 답변으로 작성한 화면 설계와 합성 데이터 미리보기다. [미리보기](preview/index.html)를 로컬 브라우저에서 열고 상단 검토 도구에서 고객/직원·접근 화면과 상태를 선택한다. 미리보기 도구는 제품 UI 밖에 있으며 역할 선택은 실제 인증이나 접근 통제가 아니다. 새로고침 시 예시 처리 상태가 초기화되고 외부 전송·실제 지급·권한 발급을 수행하지 않는다.

[상호작용 명세](interaction-spec.md)는 업무와 AC별 조작·결과를, [시각 기준](design-system-mapping.md)은 토큰·밀도·PC 확대 배치를, [접근성 체크리스트](accessibility-checklist.md)는 검증 범위·실제 실행 근거·미검증 항목을 담는다. [기계 판독 연결](screen-traceability.json)은 69 US/227 AC의 화면·증거 접점을 담는다. UI가 없는 운영 목표는 O01에 연결하고 실제 운영 시험으로 확인한다.

[미리보기 안내](preview/README.md)는 열기·검토 도구·대표 흐름과 표현 범위를 설명한다. [고객 PC 화면](preview/customer-1280.png), [직원 PC 화면](preview/staff-1280.png)을 정적으로 확인할 수 있다. HTML은 23개 화면과 주요 입력·검토·상태 전환을 제공한다. 전체 227 AC의 실제 실행을 구현한 서비스는 아니며 나머지 업무의 상세 결과는 상호작용 명세와 실제 구현 검증으로 연결한다.

## 최신 기기 범위와 상위 변경 영향

고객·직원 모두 1280 CSS px 이상 PC를 기본 지원·설계 범위로 한다. 대표 너비는 1280·1440. 고객 모바일 지원 여부는 추후 결정하며 모바일 제품 배치·모바일 브라우저 지원·지원 일정은 확정하지 않는다. 직원 모바일은 제공하지 않는다. PC 창 축소·200% 확대·접근성 리플로우는 유지하며 1280 강제 최소 너비나 작은 뷰포트 일괄 차단으로 해석하지 않는다.

이 결정의 근거는 Q5의 사용자 변경이다. NFR12, stories 공통 고객 환경·AC1.3.4·AC3.1.4, wireframes/user-flow의 고객 모바일 배치를 이번 범위로 대체한다. 과거 승인 문서는 승인 시점의 기록으로 보존한다. 해당 AC의 업무·타 기업/미부여 행위 경계는 PC에서 검증하며 모바일 검증 의무는 지원 여부 결정 때 다시 정의한다. 나머지 업무 기능과 227개 AC의 원래 업무 목적은 유지한다. 이 변경을 새로운 상위 승인 또는 상위 검토 해결로 표시하지 않는다.

고객 PC Chrome·Edge·Safari·Firefox, 직원 PC Chrome·Edge: 출시 시점 최신·직전 안정 버전. 실제 모든 브라우저 검증은 구현 단계에서 필요하며 지금의 브라우저 실행 결과와 구별한다. 직원은 사내망/회사 승인 원격 PC·MFA·각 행위 권한을 모두 충족해야 한다. 화면 감춤·너비·사용자 에이전트만으로 접속 경계를 구현했다고 주장하지 않는다.

## 화면의 공통 골격

- 1280 기준: 폭 216의 좌측 탐색, 상단 기업/직원 문맥, 우측 1fr 본문. 본문 바깥 여백 32, 영역 간 24. 고객은 제목 30·본문 16, 직원은 제목 26·표/본문 14–16. 고정된 업무 행동 막대는 사용하지 않아 확대 시 초점을 가리지 않는다.
- 목록은 표 제목·열 제목·행 단위 상세 이동을 제공한다. 상세는 대상 → 독립 상태 → 필요한 조치 → 품목/금액/기간 근거 → 이력 순서로 읽힌다. 기업·상품·수량·금액·기간·단위가 필요한 곳에서 생략되지 않는다.
- 화면 첫 주요 행동은 한 개를 우선한다. 고객 C01은 필요한 조치 확인, C02는 주문 작성, 직원 S01은 확인 업무 진입이다. 정상 진행/완료 주문도 S07에서 조회한다.
- 고객 상품 등록·직원 모바일·매출 예측·자동 결제창·전용 기술 운영 대시보드는 추가하지 않는다. 문서 ID·OQ·API·AWS 구성 설명은 제품 UI에 표시하지 않는다.

## 상태의 공통 의미

| 상태 | 표시와 행동 | 보호할 경계 |
|---|---|---|
| 정상 | 확인된 사실과 다음 행동 표시 | 판매 확정·지급 확인·제공 완료를 별도 상태로 표시 |
| 비어 있음 | 해당 범위의 확인된 0건, 가능한 시작 행동 | 미조회/권한 없음/실패를 0건으로 치환하지 않음 |
| 조회/처리 중 | 진행 문구·업무 영역 busy·중복 실행 방지 | 접수 또는 대기를 업무 완료로 표시하지 않음 |
| 입력 오류 | 입력 유지·오류 요약·문제 항목 연결 | 기본 유효성 오류를 직원 수락 경로로 우회하지 않음 |
| 조회 오류 | 조회 실패와 재조회 경로 | 지급 0원/미지급·발급 실패 등 업무 사실로 표시하지 않음 |
| 부분 완료 | 확인 수량·금액·미완료 잔량·각 결과 | 전체 완료로 확대하지 않음 |
| 결과 미확인 | 기존 요청·마지막 확인 사실·결과 재확인 | 새 요청 생성·실패로 치환·위험한 재실행을 권하지 않음 |
| 전체 접근 불가 | 민감 본문 없이 이유와 허용 복귀 경로 | 직접 상세 접근도 같은 원칙 |
| 일부 권한 없음 | 허용 정보만 표시, 보호 정보는 권한 안내 | 숨긴 금액을 0원 또는 실패로 대체하지 않음 |

문구는 화면 표현 제안이며 영구 저장 상태 enum이나 최종 상태 전이 규칙은 아니다. 계약/정책 미확정은 OQ의 해소를 전제로 표시하고 유효한 합성 시나리오만 전환한다.

## 화면별 배치·조작·상태

### C01 주문·갱신 현황

- **읽는 순서:** 확인할 업무 → 판매·지급·제공 요약 → 최근 주문 표 → 기간제 갱신 목록.
- **조작과 규칙:** 다음 조치·관련 주문·권한 상세로 이동. 요청 대기와 실제 완료를 분리한다.
- **진입/복귀:** 허용 기업 문맥과 조회·실행 권한을 확인하고 고객 탐색/연결 상세로 진입한다. 목록 또는 이전 상세로 복귀하며 허용된 목록 문맥을 유지한다.
- **상태:** 정상·0건·조회 중·조회 오류·부분 결과·결과 미확인·권한 차이를 공통 상태 규칙과 아래 AC 연결대로 표현한다. 비어 있거나 접근 불가이면 예시 데이터를 표시하지 않는다.
- **검토할 목표:** US8.8 주문 진행과 남은 조치 확인; US8.9 업무 알림 수신.

### C02 상품

- **읽는 순서:** HW/SW 타입 선택 → 목록·상세 → 공개/가격·이용형·공급 확인 근거.
- **조작과 규칙:** 같은 타입 주문 작성으로 이동. 고객에게 상품 등록 행동을 제공하지 않는다.
- **진입/복귀:** 허용 기업 문맥과 조회·실행 권한을 확인하고 고객 탐색/연결 상세로 진입한다. 목록 또는 이전 상세로 복귀하며 허용된 목록 문맥을 유지한다.
- **상태:** 정상·0건·조회 중·조회 오류·부분 결과·결과 미확인·권한 차이를 공통 상태 규칙과 아래 AC 연결대로 표현한다. 비어 있거나 접근 불가이면 예시 데이터를 표시하지 않는다.
- **검토할 목표:** US2.2 기업에 허용된 상품 확인.

### C03 주문 작성

- **읽는 순서:** 상품·수량 → 품목별 이용·지급 조건 및 일괄/부분 제공 → 전체 검토 → 접수 결과.
- **조작과 규칙:** 일괄 제공 기본값. HW/SW 혼합은 거절. SW 영구/기간제와 선후불 혼합은 품목별로 유지한다.
- **진입/복귀:** 허용 기업 문맥과 조회·실행 권한을 확인하고 고객 탐색/연결 상세로 진입한다. 목록 또는 이전 상세로 복귀하며 허용된 목록 문맥을 유지한다.
- **상태:** 정상·0건·조회 중·조회 오류·부분 결과·결과 미확인·권한 차이를 공통 상태 규칙과 아래 AC 연결대로 표현한다. 비어 있거나 접근 불가이면 예시 데이터를 표시하지 않는다.
- **검토할 목표:** US1.5 조직 범위에 맞는 업무 접근; US3.1 같은 타입 다품목 주문 제출; US3.6 일괄·부분 제공 선택.

### C04 주문 상세

- **읽는 순서:** 주문 제목·타입 → 세 상태 요약 → 청구/지급 별도 영역 → 수량별 진행 → 공개 이력.
- **조작과 규칙:** 가격 변경 동의·전체 주문 후속 요청·권한 상세 연결. 주문 조회만 있으면 대금·발급 결과를 노출하지 않는다.
- **진입/복귀:** 허용 기업 문맥과 조회·실행 권한을 확인하고 고객 탐색/연결 상세로 진입한다. 목록 또는 이전 상세로 복귀하며 허용된 목록 문맥을 유지한다.

## 스토리·AC 연결과 범위 보존

각 스토리와 모든 AC의 화면·표시 결과·실제 검증 경계는 [interaction-spec](interaction-spec.md#스토리별-화면행동-연결) 및 [screen-traceability](screen-traceability.json)에 연결한다. 69개 목표에 69개 별도 페이지를 요구하지 않는다. UI가 없는 6개 운영 스토리는 O01의 증거 접점에 연결하고, 이력 조회 US9.4는 S01/S11 및 해당 상세의 이력에 연결한다.

중복/응답 미확인: US3.1/AC3.1.3(C03), US4.1/AC4.1.2·US4.2/AC4.2.2(S09), US6.1/AC6.1.3·US6.4/AC6.4.2(S05), US7.4/AC7.4.3(S05), US8.6/AC8.6.2·AC8.6.4(S09/S06), US5.7·US6.6의 잔량 재처리로 직접 연결한다. UI의 이중 클릭 방지는 저장·외부 실행의 정확성을 입증하지 않으며 FR15.1의 실제 통합 시험이 필요하다. 이는 이전 사용자 스토리 검토 R-02의 후속 화면 구체화이며 상위 traceability.json을 소급 수정하지 않는다.

고객 수동 갱신 완료 화면 구체화는 FR11.1에 근거한 이전 검토 R-01의 후속 반영이다. 세부 계산·회차 경계·합의·지급·권한 적용의 OQ1–OQ3을 해소하기 전 실행 준비 완료라고 판단하지 않는다.

### C04 주문·C05 갱신 가격 변경 동의

C04의 품목/청구 이후, C05의 계약/실제 기간 이후에 ‘가격 변경 제안’을 둔다. 제안 식별·내용 버전·주문 또는 기업 권한 대상·수량·적용 회차 → 원래/변경 비교 표 → 현재 제안 상태 → 동의/거절 → 같은 내용을 재확인하는 대화상자 → 접수 결과/기존 요청 재확인 순서다.

| 항목 | 주문 제안 합성 예시 | 갱신 제안 합성 예시 |
|---|---|---|
| 식별/내용 | P-ORDER-DEMO-01 / v3 | P-RENEW-DEMO-01 / v2 |
| 대상 | OM-26-HW-0181 전체 8개 | ENT-DEMO-03, 기간제 기업 권한10개 |
| 원래 → 제안 금액 | 6,000,000 → 6,300,000원 | 1,800,000 → 1,980,000원 |
| 단가/조건 | 서버A1,200,000×4 →1,275,000×4, 장비B300,000×4 유지. 부분 제공/품목별 지급 조건 유지 | 180,000×10 →198,000×10. 선결제·기업 계약 우선. 유효 합의 범위 밖 제안이라는 합성 전제 |
| 회차/기간 | 해당 주문 | 2027-12-01 시작 회차, 제안 기간2027-12-01~2028-11-30 |

값은 확인된 합성 제안이며 가격 산식·허용 인상률·날짜 포함 규칙이 아니다. 계약 산식 범위 안 자동 갱신에 매회 새로운 동의를 요구하지 않는다. 여기서는 새 동의가 필요한 범위 밖 제안을 예시로 다룬다.

동의·거절은 제안ID/내용 버전/대상/회차에 연결한다. 제출 당시 가격·기존 계약·현재 실제 기간은 보존한다. 동의 접수·의사 확인을 실제 조건/기간 적용·지급 완료로 표시하지 않는다. 거절하면 새 제안을 적용하지 않고 기존 사실을 보존하며 이후 계약상 처리 방법은 OQ2 해소 후 연결한다. 현재 제안이 미조회·변경되면 해당 버튼을 비활성화하고 현재 내용 재확인·새 검토를 제공한다. 검토 대화상자 이후 내용이 달라져도 이전 확인으로 제출을 확정하지 않는다. 응답 미확인은 동일 요청 참조로 재확인하며 같은 제안에 별도 중복 효과를 만들지 않는다.

### C07 초대·소속/활성·관리자 변경

담당자 목록의 자기 기업 문맥을 유지한다. 업무 선택(초대/기존 변경) → 대상 담당자 → 이름/이메일 → 부서·사업장 → 활성/관리자 권한 → 사유 → 원래/변경 내용 검토 → 요청/확인 결과·이력 순서다. 초대는 활성 확인 대기와 구별한다. 소속/활성 변경은 다른 담당자의 역할·상태를 자동 바꾸지 않는다.

마지막 활성 관리자 회수·비활성화는 검토 대화상자에 ‘관리자0명’ 결과와 직원 근거 확인 후 재지정 경로를 경고하고, 그 경고를 확인한 후 허용·기록한다. 완료 화면에도 부재 안내와 다른 사용자 권한 유지 사실을 표시한다. 대상·소속·활성 상태·관리자 지정의 실제 신원/효력·진행 작업 영향은 OQ4를 확정하고 검증한다. 시안의 관리자 표식과 합성 조직은 실제 도메인/권한 계산 방식의 결정이 아니다.

### C08 역할 정의·부여/회수·최종 범위

역할 선택/새 역할 → 이름 → 전체 고객 행위 각각 허용/미부여 → 허용 행위별 범위 추가·삭제 → 행위별 최종 범위 검토 → 정의 결과/이력 순서다. 이후 대상 담당자 → 복수 역할 선택/선택 해제 → 원래/변경 역할과 행위별 유효 범위 검토 → 부여/회수 결과·이력을 표시한다. 새 역할을 저장했다고 자동으로 모든 사용자에게 부여하지 않는다.

| 고객 행위(15개) | 각 행위에서 사용할 범위 |
|---|---|
| 상품 조회; 주문 조회; 주문 제출; 청구·지급 조회; 발급 결과 조회 | 부서·사업장 조합 / 사업장 전체 / 부서 전체 / 자기 기업 전체 |
| 갱신 요청; 자동 갱신 신청; 자동 갱신 해제 | 위 네 가지 범위를 독립 선택, 같은 행위에 복수 범위 가능 |
| 변경 요청; 취소 요청; 반품 요청; 계약 조건 변경 요청 | 다른 조회/실행 행위 범위를 자동 상속하지 않음 |
| 조직 관리; 사용자 관리; 역할 관리 | 관리 권한을 거래 조회/실행으로 자동 확대하지 않음 |

합성 검토 예: 김담당에게 ‘서울 구매’(주문 조회 기업 전체, 제출 서울·IT)와 ‘부산 구매’(제출 부산·IT)를 부여하면 조회는 기업 전체, 제출은 서울·IT 및 부산·IT 두 조합만 허용한다. 서울·총무로 제출 범위를 교차 확대하지 않는다. 사용자 부여/회수 대화상자는 이 최종 결과를 행위마다 표시한다. 내부 직원 전용 권한이나 타 기업 선택은 생성하지 않는다. 실제 권한 효력·관리자 지정과 역할의 연계·범위 중복 정규화·조직 변경 시점은 OQ4에서 확정한다.

## Assumptions & Open Questions

- [assumption] 여유 있는 고객/촘촘한 직원 화면과 이번 화면 묶음이 실제 업무에 적합하다. 사용자 선택은 사용성 시험의 증거가 아니다.
- 모든 기업명·상품·수량·가격·날짜·근거 참조는 합성 예시다. 화면의 값은 계약 기본값·상한·계산 규칙으로 채택하지 않는다. 날짜 끝점 포함 여부와 회차 중첩 계산은 OQ1.
- OQ1–OQ3: 필수 판매/신청 항목, 계약 계산·가격 중첩·기간/후불 달력·예약·전이·외부 결과 형식은 관련 설계/실행 전에 해소. 화면의 입력 제안으로 규칙을 확정하지 않음.
- OQ4: MFA 수단·세션/효력·신원 확인·비상 복구·망/단말 검증·동일인 식별은 미정. 미리보기는 합성 조건만 표현.
- OQ5–OQ7: 보관/법적 근거·DR 실패 범위·국내 저장·알림 제공자·재알림/수신 확인은 실제 선정·검증 필요.
- OQ8은 브라우저·PC 기본 너비·WCAG 버전·주문 입력 표현만 이번 답변으로 구체화. 입력 상한·화면 성능·비동기 완료시간·부하 상세는 계속 미정. 고객 모바일은 지원 여부 자체가 유보됨.
- OQ9–OQ10: 기술 구성·CI/보안 도구·운영 절차·실제 판매 승인 인력 미정. 1인 개발은 기능 범위 제약이 아니며 계약의 다른 승인자 조건도 자동 면제하지 않음.
- 실제 브라우저 실행 근거와 미검증 범위는 accessibility-checklist에 기록한다. 시안은 인증·권한·정확성·성능·가용성·국내 저장의 실제 통과 증거가 아니다.
