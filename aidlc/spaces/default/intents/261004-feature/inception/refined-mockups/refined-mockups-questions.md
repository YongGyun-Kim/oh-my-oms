# OMS 화면·상호작용 구체화 질문

## Prior Context

- [초기 화면](../../ideation/rough-mockups/wireframes.md), [초기 흐름](../../ideation/rough-mockups/user-flow.md), [승인된 스토리](../user-stories/stories.md), [요구사항](../requirements-analysis/requirements.md), [팀 개발 원칙](../practices-discovery/team-practices.md)을 기준으로 한다.
- 상위 승인 문서는 고객 PC 우선·모바일 웹 지원을 기준으로 했다. 이번 Q5에서 사용자가 고객 화면도 1280 CSS px 이상부터 대응하고 모바일 지원 여부는 추후 결정하도록 변경했다. 현재 화면 설계에는 Q5의 최신 결정을 적용하며, 과거 모바일 지원 결정을 현재 확정 범위로 취급하지 않는다. 직원은 사내망 또는 회사가 승인한 원격 접속을 통한 PC만 허용하고 직원 모바일 화면은 제공하지 않는다. 창 너비·확대·반응형 CSS만으로 망·단말·업무 권한 통제를 구현했다고 주장하지 않는다.
- 고객 첫 화면은 자기 기업의 주문·갱신 현황, 직원 첫 화면은 처리할 업무 목록이다. 직원의 일반·완료 주문 조회 경로도 유지한다. 상품 등록은 내부 직원만 가능하다.
- 기존 브랜드·디자인 시스템·참고 서비스는 없다. 선택할 시각 기준은 이 제품의 화면 작성 기준이며 React·UI 라이브러리·DB·인증 제품 등의 기술 선정이 아니다.
- 한 사용자의 한 업무 목표를 중심으로 정리한 8개 업무 관점·69개 스토리·227개 AC를 화면·조작·상태에 연결한다. 하나의 화면이 여러 스토리를 표현할 수 있고, 모든 목표를 위해 69개의 별도 페이지를 만든다는 뜻은 아니다.
- 이전 단계처럼 질문을 하나씩 안내한다. 원하면 파일 직접 작성 또는 자유 대화로 변경할 수 있다.
- 사용자 스토리 검토 R-01·R-02는 승인 시 미해결 상태로 수용했다. 고객 요청 갱신도 실제 적용 기간·금액·처리 결과까지 표현하고, 중복/응답 미확인 방지의 해당 US/AC를 직접 연결한다. 승인된 상위 문서와 검토 상태를 수정하거나 해당 이슈가 소급 해결됐다고 표시하지 않는다.

## 작성·검증 원칙

- 기존 C01–C06·S01–S07의 의미를 유지하면서 가입·MFA·복구, 고객사 조직/역할, 내부 권한, 계약 등록/승인, 지급 배분 등 새로 구체화된 업무의 화면·상태를 연결한다.
- 고객/직원·행위/데이터 범위·요청/판단/실제 완료를 구별한다. 계약 등록자는 자기 등록을 승인할 수 없고 실제 SW 기간 조정의 동일인 별도 승인 허용은 유지한다.
- 각 화면에 정상·비어 있음·조회/처리 중·입력/조회 오류·부분/결과 미확인·권한 차이를 명시한다. 미조회·권한 없음·미지급·업무 실패를 같은 상태로 치환하지 않는다.
- 표·상태 요약·입력·확인·결과 안내의 재사용 원칙과 시각 토큰을 정의한다. 미정 상태 전이·계약 값·금액/기간 계산을 버튼이나 예시로 확정하지 않는다.
- 문서의 설계 주석과 제품 사용자에게 보이는 문구를 구별한다. FR/US/AC/OQ 번호, API/인프라 설명, 검토 메모를 실제 제품 화면에 노출하지 않는다.
- 화면·미리보기는 합성 데이터로 검토한다. 인증·권한·결제·발급·외부 연동의 실제 실행이나 접근성 인증을 미리보기 동작만으로 증명하지 않는다.

## Q1. 화면 시안은 어떤 형태로 확인하고 싶나요?

필수 산출물은 mockups.md, interaction-spec.md, design-system-mapping.md, accessibility-checklist.md와 이 질문 파일이다. 아래 선택은 화면을 함께 검토할 표현 형식이며 실제 OMS 구현·배포를 시작하는 선택이 아니다.

A. 문서와 함께 로컬에서 열 수 있는 클릭 가능한 HTML 미리보기를 제공한다. 고객/직원 화면 이동, 주요 입력·확인·결과 및 상태 전환을 합성 데이터로 확인한다.
B. 문서와 주석이 있는 정적 화면 시안으로 확인한다. 클릭 가능한 미리보기는 만들지 않는다.

## Q2. 화면의 시각 방향과 정보 밀도는 어떻게 잡을까요?

기존 브랜드 기준은 없다는 결정을 유지한다. 역할·권한과 업무 범위는 동일하며 한 화면에 얼마나 많은 정보를 보여 줄지와 읽기 편한 배치를 정하는 질문이다.

A. 밝은 중립색과 절제된 강조색을 사용한다. 고객 화면은 주요 상태·다음 행동을 여유 있게, 직원 화면은 목록·근거·판단 정보를 더 촘촘하게 배치한다.
B. 고객과 직원 화면 모두 같은 정보 밀도로 통일한다. 목록·표 중심의 간결한 업무 화면을 사용한다.
X. Other (please specify)

[Answer]: A. 고객은 여유 있게, 직원은 촘촘하게. 밝은 중립색과 절제된 강조색을 공통으로 사용한다.

## Q3. 고객의 주문 작성은 단계별로 나눌까요, 한 화면에서 작성할까요?

다품목, 같은 타입 주문, SW 영구/기간제 조합, 선후불 혼합, 일괄/부분 제공 선택을 유지한다. 아래는 입력·검토의 표현 방식이다. 신규 자동 저장·장바구니 보관·오프라인 제출 기능을 이 선택으로 추가하지 않는다.

A. 단계별 작성: 상품·수량 → 이용·거래/제공 조건 → 전체 내용 검토·제출. 제출 전 앞 단계로 돌아가 수정하고 작성 중인 화면 세션 내 입력을 유지한다.
B. 한 화면 작성: 상품·수량·조건을 한 화면에서 입력하고, 제출 직전에 전체 내용 검토 영역을 확인한다. 긴 내용은 구역별로 정리한다.
X. Other (please specify)

[Answer]: A. 단계별 작성. 상품·수량 → 이용·거래/제공 조건 → 전체 검토·제출. 제출 전 수정과 작성 중인 화면 세션 내 입력 유지를 제공한다.

## Q4. 접근성 목표는 어떤 기준으로 둘까요?

기존 키보드·입력 라벨·초점·색상 외 상태/오류 안내·복구 경로는 유지한다. 아래는 제품의 설계·검증 목표이며 특정 법령 적용이나 인증 완료를 주장하는 질문이 아니다. AA 목표는 해당 버전의 적용 가능한 A·AA 성공 기준을 전체 업무 흐름에 검증하는 범위다.

A. WCAG 2.2 AA를 설계·검증 목표로 둔다. 화면·상호작용 명세와 체크리스트에 연결하고 실제 구현에서 자동·수동 검증한다.
B. WCAG 2.1 AA를 첫 제품 목표로 두고 2.2의 추가 기준은 후속 검토 대상으로 남긴다.
X. Other (please specify)

[Answer]: A. WCAG 2.2 AA를 설계·검증 목표로 둔다. 적용 가능한 A·AA 기준을 전체 업무 흐름에 연결하고 실제 구현에서 자동·수동 검증한다.

기준 근거: [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)의 버전·성공 기준·적합성 정의를 참고한다. 목표의 버전 선택은 사용자 결정으로 확정하며, 참고 가이드의 수치나 법적 의무를 무조건 제품 요구로 옮기지 않는다.

## Q5. 지원 브라우저와 화면 검증 범위는 다음 제안을 적용할까요?

실제 고객의 기기 비율은 미확인이다. 아래 표는 질문 당시의 최초 제안이며, 실제 확정 범위는 이 질문의 답변과 변경 내용을 따른다. 특정 현재 브라우저 버전을 임의로 고정하지 않는다.

| 대상 | 제안 범위 |
|---|---|
| 고객 PC | 출시 시점의 최신·직전 안정 버전 Chrome·Edge·Safari·Firefox |
| 고객 모바일 웹 | 출시 시점의 최신·직전 안정 버전 iOS Safari·Android Chrome. 조회·입력·제출·관리의 허용 업무 유지 |
| 내부 직원 PC | 출시 시점의 최신·직전 안정 버전 Chrome·Edge. 사내망/승인 원격 PC·MFA·행위 권한 조건 유지 |
| 반응형 구성 | 고객은 768 CSS px 미만 단일 열, 768–1023은 좁은 화면 구성, 1024 이상 PC 구성으로 검토. 내용이 깨지는 지점은 실물 검증 후 조정 |
| 대표 검증 너비 | 고객 360·768·1280·1440 CSS px. 직원 1280·1440을 기본으로 하되 PC 창 축소·확대·키보드 이용도 검증 |
| 확대·리플로우 | 선택한 접근성 기준의 확대·리플로우 조건을 별도로 검사. 직원 창이 좁다는 이유로 모바일 단말이라고 판정하지 않음 |

A. 이 범위를 첫 지원·화면 검증 기준으로 사용한다.
B. 지원 브라우저·기기 또는 검증 너비를 변경한다. 필요한 범위를 설명한다.
X. Other (please specify)

[Answer]: B. 고객 화면도 1280 부터 대응으로 한다 모바일은 추후 지원 여부 결정

### Q5 확정 범위와 변경 영향

- 고객 화면도 1280 CSS px 이상 PC 환경을 기본 지원·설계 범위로 한다. 대표 검증 너비는 고객·직원 모두 1280·1440 CSS px이다.
- 고객 모바일은 첫 버전의 확정 지원 범위에 넣지 않고 추후 지원 여부를 결정한다. 모바일 구현 일정·조회 전용 지원·향후 지원 확약은 추가하지 않는다. 최초 제안의 360·768 검증 너비와 모바일 브라우저·모바일 전용 배치를 채택하지 않는다.
- 고객 PC Chrome·Edge·Safari·Firefox, 직원 PC Chrome·Edge의 출시 시점 최신·직전 안정 버전 제안은 유지한다. 특정 버전 번호는 미정이다.
- 1280은 기본 지원·화면 설계 기준이다. PC 창 축소·확대와 WCAG 2.2 AA의 적용 가능한 확대·리플로우 검증을 유지하고, CSS min-width로 모든 화면을 1280에 고정하거나 작은 뷰포트 접근을 일괄 차단하는 결정으로 확대하지 않는다. 확대된 PC 화면의 재배치를 모바일 제품 지원으로 간주하지 않는다.
- 변경 영향: 요구사항 NFR12, 사용자 스토리의 공통 고객 환경 설명·AC1.3.4·AC3.1.4, 초기 wireframes/user-flow의 고객 모바일 배치 설명에 있던 첫 버전 모바일 지원 기준을 이번 결정이 대체한다. 업무 목표·행위/데이터 권한·처리 결과는 유지하며 모바일에서의 동일 업무 검증 의무는 지원 여부 결정 시 다시 정의한다.
- 상위 문서는 이전 승인 시점의 기록으로 보존한다. 이번 단계 산출물에 최신 결정과 영향 대상 ID를 명시하여 후속 설계·검증이 이전 모바일 기준을 그대로 적용하지 않도록 연결한다. 이전 단계 승인이나 검토 판정을 소급 변경하지 않는다.

## Consolidated Summary Confirmation
