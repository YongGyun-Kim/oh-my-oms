# OMS 구현·배포 단위 구성 질문

## Prior Context

- **Interaction mode:** Guide me. 질문을 하나씩 설명하고 답변을 기록한다. 질문 파일 직접 작성 또는 자유 대화로 변경할 수 있다.

- 승인된 [components](../domain-design/components.md)와 [decisions](../domain-design/decisions.md)는14개 논리 컴포넌트·75개 엔티티를 정의한다. [requirements](../requirements-analysis/requirements.md)·[stories](../user-stories/stories.md)의69 US·227 AC와 전체 기능 범위를 유지한다.
- 논리 책임 분리와 실제 배포 분리는 다르다. 각 데이터의 쓰기 소유자는 하나이며 UI/조회/연동/운영이라는 이름으로 중앙 업무 흐름 조정 책임을 새로 추가하지 않는다. 각 업무가 확인된 결과를 바탕으로 다음 업무를 연결하는 기존 선택을 유지한다.
- 전체 컴포넌트 그래프의 두 의도적 사실 왕복 묶음은 대금/HW/SW와 신원/접근/통지다. 동기 호출 부분은 무순환이다. 이를 작업 단위 DAG와 같은 그래프로 취급하지 않으며, 소유권·공급 계약·구현 선행 조건을 분명히 연결한다.
- Domain Design의 보완 의견 두 건은 사용자가 미해결로 수용한 상태다: 주문 보호 대상의 부서·사업장 문맥 누락(Major), 명명된 교차 참조5건 누락(Minor). 이 단계에서 이전 산출물을 바꾸거나 해결됐다고 표시하지 않는다. 해당 단위/후속 Contract·Functional Design에서 원본·문맥·참조를 구체화할 책임과 구현 전 확인 조건을 연결한다.
- 기존 결정: AWS·CDK, 1인 개발/기술 운영 가능한 구조 목표·인원 수에 따른 기능 자동 축소 금지, 최소 통합 동작 버전 우선, 현재 직렬 Construction, test-after/Standard/80%와 필수 보안/배포 확인을 유지한다. 새 팀·추가 운영 인력이 확보됐다고 가정하지 않는다.
- 고객·직원 UI 논리 분리는 이미 결정됐다. 고객/직원 PC1280 이상, 고객 모바일 지원 여부 미정·직원 모바일 제외, MFA·직원 사내망/승인 원격 PC·기업/행위별 권한도 유지한다. 아래 UI 질문은 실제 빌드/배포 묶음만 다룬다.
- 현재 단계는 단위 경계·kind·순환 없는 의존 DAG·스토리 할당을 정한다. 나머지 업무의 우선순위·Bolt 순서·critical path·시장 가치/위험에 따른 선택은 Delivery Planning에 둔다. 직렬 실행 결정 때문에 독립 단위 사이에 가짜 의존을 넣지 않는다.
- 언어/DB/AWS 서비스·인증/외부 제공자·실제 메시지/저장/동시 제어·상세 상태/산식·스키마·운영 증거는 관련 후속 단계에서 확인한다. 지금 배포 묶음을 선택하는 것이 그 기술이나 SLO 달성을 확정하지 않는다.

## Q1. 업무 핵심 코드는 어떤 배포 경계로 시작할까요?

독립 서비스가 늘면 개별 변경/장애를 분리할 수 있지만 연결·배포·장애 대조의 경계도 늘어난다. 지급과 제공처럼 확인된 결과가 왕복하는 현재 업무와 운영 목표를 함께 판단한다. 아래 선택은 UI·백그라운드 실행 역할의 배포를 Q2·Q3에서 따로 정할 수 있게 한다.

A. 업무 핵심은 하나의 모듈화된 애플리케이션으로 시작한다. 계약·주문·대금·HW·SW 등의 코드 책임/소유권은 구분하지만 업무별 독립 네트워크 서비스로 나누지 않는다. 같은 업무 코드의 실행 역할과 UI의 배포는 별도 검토한다.
B. 결합이 큰 업무를 묶은 소수의 업무 서비스로 시작한다. 각 묶음을 별도 실행·배포하고 묶음 사이의 계약·결과 대조를 명시한다. 실제 묶음 목록은 나머지 답변과 원본 의존으로 확인한다.
C. 업무 책임별로 독립 서비스를 나눈다. 개별 배포/확장/장애 경계를 확보하되 업무 간 왕복·부분 실패·관측/복구 부담을 각각 설계·검증한다.
X. Other (please specify)

[Answer]: A. 업무 핵심은 모듈화된 단일 애플리케이션으로 시작한다. 각 업무의 코드 책임과 데이터 소유권을 구분하며 업무별 독립 네트워크 서비스로 나누지 않는다. UI와 백그라운드 실행 역할의 배포는 Q2·Q3에서 별도로 정한다.

추천: A를 첫 후보로 제안한다. 현재의 원본/사실 왕복을 코드 모듈 경계로 유지하면서 서비스 간 대조·배포 경계를 제한하기 위한 설계 판단이다. 인원 수로 기능을 줄이는 결론이 아니며, 운영 부담과 장애 영향이 실제로 유리한지는 [assumption]이다. B/C의 독립성 이점과 비교하고 후속 검증으로 필요 경계를 재구성한다. AWS 문서는 분할의 이점과 운영 복잡성의 균형·초기 모듈화/향후 분해 가능성을 설명한다; 이 OMS에 A가 적합하다는 실증은 아니다. [W1–W2]

## Q2. 고객 UI와 직원 UI의 실제 빌드·배포 묶음은 어떻게 둘까요?

논리 UI 책임은 이미 분리했다. 여기서는 고객 공개 접점과 직원 사내망/승인 원격 PC 접점의 배포·변경 검증 경계를 정한다. 양쪽 모두 서버측 접근 조건과 업무 권한을 검증한다.

A. 고객 UI와 직원 UI를 별도 빌드·배포 대상으로 둔다. 공통 디자인/기초 조작 코드는 재사용하고 각 접점의 정책·변경/검증을 관리한다.
B. 하나의 UI 빌드·배포 묶음 안에 고객/직원 화면을 구별한다. 직원 접점의 망/PC 조건을 별도로 강제하고 해당 경로의 공개 노출·우회가 없음을 검증한다.
X. Other (please specify)

[Answer]: A. 고객 UI와 직원 UI를 별도 빌드·배포 대상으로 둔다. 각 접점의 접근 정책과 변경 검증을 구분하고 공통 디자인·기초 조작 코드는 재사용한다. 두 UI는 모듈화된 단일 업무 애플리케이션을 함께 사용한다.

추천: A. 서로 다른 접근 접점·화면 흐름·릴리스 검증을 명확히 분리하기 위한 제안이다. 빌드/배포 대상이 늘어나는 비용은 인정한다. 프론트엔드 프레임워크·도메인 주소·AWS 제공 서비스·리포지토리 수는 아직 선택하지 않는다.

## Q3. 갱신·결과 대조·재처리 같은 백그라운드 업무의 실행·배포는 어떻게 둘까요?

시간에 따른 갱신/만료·외부 결과 대조·실패 재처리는 화면 요청 이후에도 진행될 수 있다. 실행 역할을 분리해도 판단/원본 소유자는 기존 대금·HW·SW 등의 업무 책임이며 중앙 조정자로 바뀌지 않는다.

A. 웹 요청 처리와 같은 실행·배포 묶음에서 백그라운드 역할을 구분한다. 실행/변경 경계는 적지만 작업 부하·장애가 화면 요청에 미치는 영향을 검증한다.
B. 백그라운드 실행을 별도 worker 실행·배포 대상으로 둔다. 같은 업무 모듈/계약을 재사용하고 버전·중복 실행·접수 보존·실패 대조를 관리한다. 독립 실행 경계가 늘어나는 부담을 검증한다.
X. Other (please specify)

[Answer]: B. 백그라운드 업무는 별도 worker 실행·배포 대상으로 둔다. 같은 업무 모듈/계약을 재사용하며 판단과 데이터 소유권은 기존 업무 컴포넌트에 유지한다. 웹과 worker 사이의 버전 호환·중복 실행·접수 보존·실패 대조 조건을 후속 설계에서 검증한다.

추천: B. 작업 부하/실패의 실행 경계를 웹 요청 처리와 구분하는 제안이다. 모든 업무 컴포넌트를 독립 서비스로 나누는 뜻은 아니다. 실제 시간 실행·전달·저장·병렬 소비 방법은 후속 NFR/Infrastructure Design에서 정한다. 두 선택 모두 OMS 자체 장애 중 복구 시도/실패 알림을 보낼 경로를 별도 검증해야 한다.

## Q4. 구현·검증 작업 단위의 크기는 어느 쪽으로 잡을까요?

작업 단위 수는 실제 서비스 배포 수와 다를 수 있다. 같은 애플리케이션에 추가되는 기능도 shared/embedded 단위로 나눠 검증할 수 있다. 첫 최소 통합 동작 단위 이후의 구현 순서는 여기서 추천하지 않는다.

A. 최소 통합 동작 단위와 기능 확장 단위를 비교적 작게 나눈다. 전체 대략6–9개 단위를 후보로 삼아 책임·상대 복잡도·통합 검증을 확인한다. 같은 배포 대상을 확장하는 경우 기존 코드/계약과 변경 소유를 명시한다.
B. 관련 업무를 넓게 묶는다. 전체 대략3–5개 단위를 후보로 삼고 각 단위 안에서 작은 통합 검증을 둔다. 단위 수는 적지만 한 단위가 다루는 규칙/검증 범위가 커진다.
X. Other (please specify)

[Answer]: A. 최소 통합 동작 단위와 기능 확장 단위를 비교적 작게 나눈다. 전체6–9개는 후보 범위로 두며, 같은 배포 대상을 여러 작업 단위에서 확장할 경우 기존 코드/계약과 변경 소유를 명시한다. 실제 단위 수·책임·kind·의존 관계는 구성 계획에서 확인한다.

추천: A. 계약/금액·HW 수량·SW 기간·후속 판단·운영 검증의 변경을 확인 가능한 범위로 나누기 위한 제안이다. 숫자는 [assumption] 후보 범위이며 확정 단위 수/기간/서비스 수가 아니다. 실제 단위와 kind는 답변 후 구성 계획에서 확인한다.

## Q5. 첫 DAG 단위의 최소 통합 동작 범위는 어디까지로 둘까요?

최소 통합 동작 버전을 먼저 만든다는 기존 결정은 유지한다. 여기서는 후속 단위 없이 실행할 수 있게 포함할 책임의 범위를 정한다. 실제 데모 상세·HW/SW 사례·실행 명령은 Delivery Planning과 해당 구현 확인에서 정한다.

A. 필요한 인증/MFA·기업/직원 접근, 최소 상품 등록/조회, 고객 주문 접수·지속 기록·확인 대기/진행 조회까지 실제 연결한다. 미확인 공급/지급/발급을 완료로 표시하지 않는다. 이후 단위가 수락·대금·실제 제공·갱신 등의 전체 기능을 확장한다.
B. 위 기본 연결에 더해 한 구매 시나리오의 지급 확인과 실제 제공 결과까지 첫 단위에 포함한다. 더 넓은 거래 연결을 검증하지만 필요한 계약·제공자/증거와 구현 범위가 커진다.
X. Other (please specify)

[Answer]: A. 첫 단위는 필요한 인증·MFA·기업 승인·권한, 최소 상품 등록/조회, 고객 주문 접수·지속 기록·확인 대기/진행 조회까지 실제 연결한다. 미확인 공급·지급·발급은 확인 대기로 표현한다. 이후 단위에서 수락·대금·실제 제공·갱신 등의 전체 기능을 확장하며, 구체적인 데모 사례와 실행 검증 명령은 Delivery Planning 및 구현 확인에서 정한다.

추천: A. 실제 UI/API·권한·주문 기록/조회가 끝까지 실행되고 원본/미확인 표현을 검증하는 최소 통합 범위를 제안한다. 후속 단위가 없는데 성공 제공처럼 보이게 만들거나 실제 제품 구현을 문서/모형으로 대체하지 않는다. 첫 범위만 전체 제품 완료로 표시하지 않는다.

## Q6. 공통 운영·배포 검증 준비는 작업 단위로 어떻게 관리할까요?

AWS/CDK·검사/배포 승인·국내 저장·가용성/복구·알림·1인 작업 측정은 이미 요구됐다. 제품 안의 진단/대조 코드 원본은 기존 소유자에게 두고, 그 코드를 실행/배포/관측하는 준비의 변경 경계를 정한다.

A. 첫 단위에 실행에 필요한 최소 준비를 포함하고, 공통 CDK·검사/배포·관측/복구와 근거 수집의 완성을 별도 기술 준비 단위로 구분한다. 후속 기능별 필요한 연동은 각 기능 단위와 연결한다.
B. 공통 준비는 첫 단위에서 확장하고, 이후의 운영/배포 검증 개선을 각 업무 단위에 함께 포함한다. 별도 기술 준비 단위는 두지 않으며 공통 코드/실제 결과의 변경 소유를 명시한다.
X. Other (please specify)

[Answer]: A. 첫 단위에 실행에 필요한 최소 준비를 포함하고, 공통 CDK·검사/배포·관측/복구와 근거 수집의 완성은 별도 기술 준비 단위로 관리한다. 후속 기능별 필요한 연동은 각 기능 단위와 연결한다. 첫 단위는 나중 기술 준비 단위 없이도 실행 가능해야 하며 제품의 진단·대조 코드와 실제 운영 주체의 책임을 구분한다.
