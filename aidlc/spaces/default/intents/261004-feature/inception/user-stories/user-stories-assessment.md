# 사용자 스토리 적용성·작성 품질 평가

## 실행 판단

**Decision: Execute**

이 프로젝트는 Greenfield B2B OMS이며 고객과 내부 직원의 사용자 접점, 조직·행위 권한, 계약 등록자/승인자 분리, 선후불·부분 이행, HW/SW·기간·갱신·회수/환불의 복합 규칙이 있다. 요구사항만으로는 누가 어떤 상황에서 무엇을 확인하고 수행하는지 드러나기 어려워 사용자 스토리가 필요하다. [requirements](../requirements-analysis/requirements.md)의 기능 범위를 바꾸지 않고 사용자 목표와 관찰 가능한 결과를 구체화한다.

## 작성 결과와 범위

| 항목 | 내용 |
|---|---|
| 관점 | 8개 업무 관점; 실제 직함·인원·고정 권한 모델 아님 |
| 분해 | 업무 흐름별 69개 스토리, 총 227개 Given/When/Then 기준 |
| 우선순위 | 첫 제품의 포함 범위를 유지한 Must Have. 후속 고도화·제외 범위를 추가하지 않음 |
| 추적 | 상위 16개 FR 그룹·58개 세부 FR·14개 NFR, 총 88개 ID |
| 연결 상태 | 79개 OK, 9개 Deferred. OK는 문서 연결이지 구현/시험 통과가 아님 |
| 개발 준비 | 미정 OQ별 선행 조건을 명시. 현재 모든 스토리의 구현 준비 완료·기간 추정 확정을 주장하지 않음 |

작성 계획 Q1–Q3와 별도 요약 확인을 반영했다. 60–70개의 초기 예상 안에서 69개로 분해했다. 직원 후속 요청 판단, HW 회수와 환불, 직원 진행 조회, 개별 장애 복구와 30일 가용성, 반복 운영 부담의 관찰 결과를 구별했다. [팀 개발 원칙](../practices-discovery/team-practices.md)의 최소 통합 흐름 우선은 구현 순서이며 전체 범위 축소가 아니다.

## 가치 흐름과 관계

가입/접근/권한 → 상품/계약 → 주문/확정 → 청구/지급 → HW 또는 SW 제공 → 갱신/보상 → 변경/예외/조회, 그리고 기술 운영·추적을 연결했다. 갱신·후속 처리는 필요할 때 진입하며 모든 주문이 선형으로 모든 단계를 거쳐야 한다는 뜻은 아니다. 선결제·후불과 제공 흐름은 병행 조건으로 판단한다.

스토리의 선행 업무/입력은 데이터 의존성을 설명한다. 두 입력 경로나 HW/SW 흐름이 대안이면 시나리오에 적용되는 쪽만 사용한다. 실제 개발 순서·단위 분해·견적은 후속 Domain Design·Units Generation·Delivery Planning에서 정하며 의존성 수만으로 병렬 구현 가능성을 보장하지 않는다.

## INVEST 평가

| 항목 | 적용한 기준 | 남은 확인 |
|---|---|---|
| Independent | 관찰 가능한 한 업무 목표로 분리하고 필요한 선행 결과를 명시 | 실제 연동 없이 fixture로 독립 시험할 수 있으나 제품 연결·순서는 후속 검증 |
| Negotiable | UI·API·DB·서비스 구성을 지시하지 않고 업무 결과를 고정 | 이미 승인된 권한·금액·기간·책임 경계는 임의 협상/완화하지 않음 |
| Valuable | 각 스토리의 사용자 목표·가치와 페르소나를 명시 | 실고객 가치·지불 의사는 미검증 가설 |
| Estimable | 정책·근거가 필요한 OQ와 관련 선행 결과를 표시 | OQ 해소·실행 주체·구조 검토 전 견적 미확정 |
| Small | 한 업무 목표를 기본으로 필요한 정상·실패·권한·동시 처리 기준을 작성하고 서로 다른 완료 결과를 분리 | 코드/계약 구조와 통합 복잡성에 따라 추가 분할 필요; 1–3일 등의 수치 약속 없음 |
| Testable | 고유 AC ID와 Given/When/Then, 정상·실패·권한·중복/충돌 조건 | OQ가 확정돼야 결정적 시험 데이터를 구성할 수 있으며 현재 전부 테스트 실행 가능이라고 주장하지 않음 |

개발 준비 전에는 해당 OQ의 사용자 결정·실제 근거, 필요 UX 검토, 크기·견적과 의존성 해소를 확인한다. 정의되지 않은 값은 테스트 예시에 넣어 제품 정책으로 확정하지 않는다. 미정 항목이 있다고 기능을 삭제하거나 해당 스토리를 완료 처리하지 않는다.

## 이전 요구사항 보완 사항의 연결

| 상위 근거 | 이번 시나리오에 명시한 내용 | 남은 조건 |
|---|---|---|
| SC-10·FR9/FR10/FR15·요구사항 검토 R-01 | US5.7·US6.6의 실패 확정·원인 해소 후 재처리, 기존 주문/실패/새 결과 연결, 성공분 중복 방지 | 구체 상태 전이·재처리 허용 조건·실제 실행 근거 OQ2·OQ3 |
| Q9·FR9·요구사항 검토 R-02 | US5.1·US5.2의 직원 근거 등록과 외부 연동, 출처 보존·충돌 확인 | 업무별 적용 방식·제공자·참조·최신성 OQ3. 모든 업무의 두 방식 강제 아님 |

이는 승인된 범위의 후속 구체화다. 과거 requirements.md·검토 기록·승인 처분을 수정하거나 미해결 의견을 소급해 해결 완료로 표시하지 않는다.

## 비기능 요구의 후속 구체화

- NFR2 → `observability-setup`: US9.6이 관측 평가 결과를 정의한다. 업무별 측정 지점·주기·부분 장애 규칙과 연속 30일 실측 증거를 구체화하고 단기 장애 시험으로 대체하지 않는다.
- NFR3 → `nfr-requirements`: 장애 범위·재난 제외·야간 지원과 30분 복구 검증 프로필을 구체화한다. US9.2는 업무 목표이며 실증 완료가 아니다.
- NFR4 → `nfr-design`: 논리 오염·오삭제를 포함한 성공 접수 RPO 0과 RTO의 동시 달성 설계·증거를 확정한다.
- NFR5 → `build-and-test`: 8개 정확성 영역의 통합·중복·동시 처리·장애 시험을 수행한다. 스토리별 기준 연결은 전체 시험 통과를 뜻하지 않는다.
- NFR6 → `performance-validation`: 확정된 시험 위치·네트워크·요청 구성에서 p95와 기술 오류율을 검증한다.
- NFR7 → `performance-validation`: 합성 데이터·정상/집중 부하·5분 회복 및 10분 유지 프로필을 시험한다.
- NFR12 → `refined-mockups`: PC 우선 고객 모바일·직원 PC 전용과 한국어/KRW/한국 시간·접근성 및 미정 브라우저/해상도를 구체화한다.
- NFR13 → `build-and-test`: test-after·Standard·80% 커버리지와 필수 검증 실패/누락 차단을 구현 증거로 확인한다.
- NFR14 → `ci-pipeline`: 보안 검사 도구·대상·차단선·주기를 정해 필수 검사와 예외 기록을 파이프라인에 연결한다.

각 Deferred는 구체화/검증 책임의 후속 단계와 근거를 남긴 것이다. 기능 요구 삭제·상용 검증 면제·기한 연기를 승인한 것으로 해석하지 않는다. 요구사항 OQ에 명시된 관련 설계·구현 전 결정 기한도 그대로 유지한다. 운영 측정/성능 시험의 나중 실행을 이유로 그 전 설계에서 목표를 무시할 수 없다.

## Assumptions & Open Questions

- [assumption] 8개 관점과 업무 목표가 실제 사용을 대표한다. 실제 고객·직원 인터뷰로 확인한다.
- 요구사항 OQ1–OQ10의 값·제공자·연동 증거·권한 확인·보관·복구 범위는 아직 열려 있다. [요구사항](../requirements-analysis/requirements.md)의 책임·해소 시점·영향을 유지한다.
- 스토리의 성공 조건은 합성 검증 기준이며 실제 달성·연동·개인정보 취급·운영 인력 확보의 증거가 아니다.
