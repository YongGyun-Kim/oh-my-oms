# OMS 사용자 스토리

> **첫 배포 범위 변경 — 2026-10-11:** 아래69개 US·227개 AC는 전체 제품 백로그로 보존한다. 기존 ‘모든 스토리가 첫 제품 Must Have’라는 해석은 고객사10곳 이내 제한 파일럿의 [확정 범위](../../release-planning/first-release-scope-proposal.md)와 [첫 배포/후속 연결](../../release-planning/first-release-delivery-plan.md)로 대체한다. 고객/직원 PC1280 이상이며 고객 모바일 지원 여부는 후속 결정이다. 일부 경로만 구현한 스토리는 원래 모든 AC를 충족했다고 표시하지 않는다.

## 범위와 작성 기준

[승인된 요구사항](../requirements-analysis/requirements.md), [확인된 작성 계획](user-stories-questions.md), [팀 개발 원칙](../practices-discovery/team-practices.md)을 기준으로 8개 업무 관점·69개 스토리·227개 수락 기준을 작성했다. 문서 순서는 업무 흐름이며 개발 순서나 납기가 아니다. 각 스토리의 `USx.y`와 `ACx.y.z`는 영구 추적 키다. 페르소나는 [personas](personas.md), 요소별 연결은 [traceability.json](traceability.json)을 따른다.

모든 스토리는 첫 제품 포함 범위의 **Must Have**다. 단계적 구현은 기능 제외를 뜻하지 않는다. 무중단 배포·10분 복구·영어(미국) 등의 후속 목표는 별도 범위이며 이 스토리의 완료 기준으로 확대하지 않는다. 일반 이행 실패 재처리와 HW의 직원 근거 등록·외부 연동 병행은 승인된 SC-10·Q9 및 요구사항 검토 R-01·R-02를 구체화했다. 상위 문서나 과거 검토 상태를 수정했다는 뜻은 아니다.

## 읽는 방법과 공통 검증 조건

- 스토리의 **근거**는 requirements.md의 FR/NFR이며, `OQ`는 같은 문서의 미정 항목이다. 현재 스토리는 업무 결과를 정한 것이며 아래 OQ가 해소되지 않은 상태를 개발 준비 완료로 표시하지 않는다.
- **선행 업무/입력**은 필요한 데이터·결과의 연결이다. 모두를 순차 개발하라는 지시나 모든 대안 경로를 동시에 실행하라는 의미가 아니다. 예를 들어 직원 지급 입력과 외부 지급 연동은 시나리오별 대안이다. 각 스토리는 검증된 fixture/대체 시험 주체로 독립 시험하되 이것을 실제 연동 실증으로 주장하지 않는다.
- 인증이 필요한 업무는 MFA·행위 권한·고객사/조직 범위와 직원의 사내망/승인 원격 PC 조건을 만족해야 한다. 허용된 신청·복구 진입 경로는 OQ4에서 정하며 이 경로로 거래 권한을 우회하지 않는다.
- 조회·실행·승인을 자동 묶지 않는다. 모든 지원 화면/API·연결 조회에도 권한 경계를 적용한다. 고객은 PC 우선·모바일 웹, 내부 직원은 PC 전용 조건을 유지한다.
- 변경·외부 결과·재처리의 시험에는 같은 요청 반복, 늦은 결과, 동시 변경을 적용하고 유실·중복 효과·오래된 상태 덮어쓰기를 검사한다. 서로 다른 정당한 신규 요청을 같은 내용이라는 이유만으로 제거하지 않는다.
- 거래 금액·수량·기간의 합격 기준은 **확정한** 산식·상태 관계를 사용한다. OQ를 임의 기본값으로 채우지 않는다. 합성 예시가 실제 계약 정책이 되지 않는다.
- 일반 이행 실패는 실패 확정과 결과 미확인을 구별한다. 실제 완료 증거가 없으면 완료를 주장하지 않고, 이미 성공한 부분을 중복 처리하지 않는다.
- 주요 변경·승인·정정에는 행위자·시각·사유·전후 값·연관 근거/결과를 남긴다. 일반 권한으로 과거 이력을 덮어쓰지 않는다. 보관/삭제는 OQ5의 후속 결정 대상이다.
- Given/When/Then의 Given에 '확정된 규칙·검증된 연동'이 있으면 해당 근거의 확보가 실행 전제다. 근거가 없는 현재 상태에서 AC 통과·실거래 준비 완료로 기록하지 않는다.

### 공통 사용자 경험과 경계 시험

- 고객 P1·P2의 업무는 확정한 지원 환경에서 PC·모바일 웹 모두 동일한 권한·업무 결과를 제공한다. 모바일을 조회 전용으로 축소하지 않는다. 직원 OMS 업무는 PC 전용이며 고객 범위를 직원 모바일로 확대하지 않는다.
- AC8.8.4의 입력 라벨·초점·키보드·색상 외 상태/오류 전달 검증은 조회 화면뿐 아니라 지원하는 입력·승인·복구 화면에도 적용한다. 구체 지원 브라우저·해상도·보조기술·접근성 수치는 OQ8에서 정하며 인증 달성을 주장하지 않는다.
- 주문·계약 변경·갱신·자동 갱신 신청/해제·변경/취소/반품 요청에는 AC3.1.2–AC3.1.3의 입력 오류/접수 미확인 구분과 같은 요청 결과 재확인 원칙을 적용한다. 초안 자동 저장·오프라인 제출·고정 타임아웃을 새로 정하지 않는다.
- 고객이 본 제안의 내용·유효성이 응답 전에 바뀌면 이전 화면의 동의를 새 제안에 대한 동의로 사용하지 않고 재확인을 안내한다. 적용 시점·동의 방식·기한은 OQ1·OQ2·OQ4에서 구체화한다.
- 경계 시험은 동일 요청의 순차 중복, 서로 다른 유효 요청의 동시 잔액/수량 소비, 역순 외부 결과를 각각 구분한다. AC4.4.4·AC5.4.3·AC7.4.3·AC8.4.4·AC8.6.4를 연결하며 특정 경합 승자·잠금·메시징 기술을 선택하지 않는다.
- 직원 통합 조회는 US8.12로 분리한다. P3·P4·P5·P6 각각의 실제 부여 조회 권한으로 시험하고 직원 지위나 기술 운영자에게 포괄 권한을 가정하지 않는다.

## 사용자 스토리

### 가입·접근·권한

#### US1.1 기업 이용 신청

**스토리:** 나는 고객 구매 담당자로서, 승인 후 거래를 시작하기 위해 기업 이용을 신청하고 결과를 확인하고 싶다.

- 페르소나: P1 / 우선순위: Must Have
- 근거: FR1.1
- 선행 업무/입력(경로별 적용): 기존 계정·권한 또는 확정한 운영 시험 조건. 최초 준비 절차는 아래 OQ에서 정의.
- 준비 상태: 추가 구체화 필요 — OQ4. 해당 정책·증거 해소 전 구현 준비 완료로 판단하지 않는다.
- INVEST: 독립 관찰 결과는 ‘기업 이용 신청’이며 위 사용자 가치와 연결한다. 필요한 업무 사실은 선행 입력을 따르고 fixture 독립 시험과 실제 연결을 구별한다. 상세 표현은 협의 가능하나 추정·크기는 OQ4 해소와 구현 구조 검토 전 미확정이다.

| 수락 기준 | Given | When | Then |
|---|---|---|---|
| AC1.1.1 | 기업 이용 신청에 필요한 확인 항목이 정해져 있다 | 고객이 신청을 제출한다 | 신청 결과와 직원 확인 대기 여부를 확인할 수 있다 |
| AC1.1.2 | 기업이 아직 승인되지 않았다 | 신청자가 주문을 제출한다 | 주문은 접수되지 않고 미승인 사유를 안내한다 |
| AC1.1.3 | 다른 기업의 신청 식별자를 알고 있다 | 그 신청을 조회한다 | 해당 기업 정보와 신청 내용을 제공하지 않는다 |

#### US1.2 기업 확인과 최초 관리자 지정

**스토리:** 나는 내부 거래 운영 담당자로서, 확인된 기업만 거래하게 하기 위해 기업 신청과 첫 관리자를 확인·승인하고 싶다.

- 페르소나: P3 / 우선순위: Must Have
- 근거: FR1.1, FR1.2
- 선행 업무/입력(경로별 적용): US1.1
- 준비 상태: 추가 구체화 필요 — OQ4. 해당 정책·증거 해소 전 구현 준비 완료로 판단하지 않는다.
- INVEST: 독립 관찰 결과는 ‘기업 확인과 최초 관리자 지정’이며 위 사용자 가치와 연결한다. 필요한 업무 사실은 선행 입력을 따르고 fixture 독립 시험과 실제 연결을 구별한다. 상세 표현은 협의 가능하나 추정·크기는 OQ4 해소와 구현 구조 검토 전 미확정이다.

| 수락 기준 | Given | When | Then |
|---|---|---|---|
| AC1.2.1 | 직원에게 기업 확인·지정 권한과 필요한 근거가 있다 | 신청을 승인하고 첫 관리자를 지정한다 | 승인 기업과 확인된 관리자 연결 및 처리 이력이 남는다 |
| AC1.2.2 | 확인 근거가 부족하다 | 승인을 시도한다 | 이용 승인으로 확정하지 않고 부족한 근거를 확인 대상으로 남긴다 |
| AC1.2.3 | 기업 확인 권한만 있고 관리자 지정 권한은 없다 | 관리자를 지정한다 | 미부여 행동을 거절하고 권한을 자동 확대하지 않는다 |

#### US1.3 고객 담당자와 소속 관리

**스토리:** 나는 고객사 권한 관리자로서, 조직에 맞는 담당자가 업무하게 하기 위해 담당자를 초대하고 소속·활성 상태를 관리하고 싶다.

- 페르소나: P2 / 우선순위: Must Have
- 근거: FR1.2
- 선행 업무/입력(경로별 적용): US1.2
- 준비 상태: 추가 구체화 필요 — OQ4. 해당 정책·증거 해소 전 구현 준비 완료로 판단하지 않는다.
- INVEST: 독립 관찰 결과는 ‘고객 담당자와 소속 관리’이며 위 사용자 가치와 연결한다. 필요한 업무 사실은 선행 입력을 따르고 fixture 독립 시험과 실제 연결을 구별한다. 상세 표현은 협의 가능하나 추정·크기는 OQ4 해소와 구현 구조 검토 전 미확정이다.

| 수락 기준 | Given | When | Then |
|---|---|---|---|
| AC1.3.1 | 자기 기업의 사용자 관리 권한이 있다 | 담당자를 초대하고 허용된 소속을 지정한다 | 해당 기업의 담당자와 소속·처리 이력을 확인한다 |
| AC1.3.2 | 대상이 다른 기업의 담당자다 | 소속이나 활성 상태를 변경한다 | 변경을 거절하고 타 기업 정보를 노출하지 않는다 |
| AC1.3.3 | 진행 중 요청을 가진 담당자의 권한을 회수하려 한다 | 확정된 회수 시점 정책에 따라 변경한다 | 이후 접근과 진행 작업이 OQ4에서 확정한 규칙에 일치하고 과거 이력은 남는다 |
| AC1.3.4 | 자기 기업 사용자 관리 권한과 확정된 고객 PC·모바일 환경이 있다 | 초대·소속·활성 상태 관리를 수행한다 | 두 환경에서 허용된 관리를 완료하고 타 기업·미부여 행위 경계를 동일하게 유지한다 |

#### US1.4 고객 역할 정의

**스토리:** 나는 고객사 권한 관리자로서, 업무별로 필요한 권한만 주기 위해 허용된 행위 권한을 조합해 역할을 정의·부여하고 싶다.

- 페르소나: P2 / 우선순위: Must Have
- 근거: FR2.2, FR2.4
- 선행 업무/입력(경로별 적용): US1.2
- 준비 상태: 추가 구체화 필요 — OQ4. 해당 정책·증거 해소 전 구현 준비 완료로 판단하지 않는다.
- INVEST: 독립 관찰 결과는 ‘고객 역할 정의’이며 위 사용자 가치와 연결한다. 필요한 업무 사실은 선행 입력을 따르고 fixture 독립 시험과 실제 연결을 구별한다. 상세 표현은 협의 가능하나 추정·크기는 OQ4 해소와 구현 구조 검토 전 미확정이다.

| 수락 기준 | Given | When | Then |
|---|---|---|---|
| AC1.4.1 | 역할 관리 권한과 FR2.2의 확정 행위 목록이 있다 | 각 행위를 구별해 역할을 만들고 부여·회수한다 | 상품/주문/대금/발급 조회, 주문 제출, 갱신·자동 갱신 신청/해제, 변경·취소·반품·계약 변경 요청, 조직/사용자/역할 관리 각각의 부여 행위만 허용하고 회수 효력 이후 거절한다 |
| AC1.4.2 | 계정 관리 권한만 가진 사용자다 | 주문·지급·발급 결과에 접근한다 | 별도 권한이 없는 행동·정보는 허용하지 않는다 |
| AC1.4.3 | 고객사 관리자가 내부 직원 전용 권한을 지정한다 | 역할을 저장한다 | 해당 권한 생성을 거절하고 다른 기업 권한도 부여하지 않는다 |

#### US1.5 조직 범위에 맞는 업무 접근

**스토리:** 나는 고객 구매 담당자로서, 다른 조직 정보 노출 없이 담당 업무를 처리하기 위해 내 역할과 조직 범위 안에서 업무를 수행하고 싶다.

**스토리:** 나는 내부 거래 운영 담당자로서, 승인자가 정확한 내용을 판단하게 하기 위해 합의 근거와 대상·유효 시점을 담아 계약 조건을 등록하고 싶다.

| AC4.6.3 | 제한 해제 근거가 확인됐다 | 해제를 처리한다 | 해제 이력을 남기며 기존 권한 기간 변경·회수는 별도 승인 없이 실행하지 않는다 |

### HW 제공

#### US5.1 HW 결과의 직원 근거 등록

**스토리:** 나는 내부 거래 운영 담당자로서, 재고·확보·출고·배송의 상태를 주문과 연결하기 위해 실제 담당 주체에게 확인한 HW 결과를 등록하고 싶다.

- 페르소나: P3 / 우선순위: Must Have
- 근거: FR9.1, FR9.4 · 상위 Q9·이전 검토 R-02
- 선행 업무/입력(경로별 적용): 해당 HW 단계의 주문·품목 참조와 실제 근거. 판매 판단용 재고 근거와 확정 후 이행 결과를 구별하며 모든 결과에 직원 수락을 요구하지 않는다.
- 준비 상태: 추가 구체화 필요 — OQ3. 해당 정책·증거 해소 전 구현 준비 완료로 판단하지 않는다.
- INVEST: 독립 관찰 결과는 ‘HW 결과의 직원 근거 등록’이며 위 사용자 가치와 연결한다. 필요한 업무 사실은 선행 입력을 따르고 fixture 독립 시험과 실제 연결을 구별한다. 상세 표현은 협의 가능하나 추정·크기는 OQ3 해소와 구현 구조 검토 전 미확정이다.

| 수락 기준 | Given | When | Then |
|---|---|---|---|
| AC5.1.1 | 업무별 직원 등록 경로와 필요한 증거가 정해져 있다 | 확인된 HW 결과를 등록한다 | 주문·품목·수량·단계·출처·근거가 연결된다 |
| AC5.1.2 | 실제 확인 없이 확보·출고 요청만 있다 | 진행 상태를 등록한다 | 요청을 실제 확보·출고·배송 완료로 표시하지 않는다 |
| AC5.1.3 | 기존 결과와 다른 근거가 등록됐다 | 완료 상태를 판단한다 | 차이와 원래 근거를 보존하고 충돌 확인 대상으로 남긴다 |

- 선행 업무/입력(경로별 적용): 기존 계정·권한 또는 확정한 운영 시험 조건. 최초 준비 절차는 아래 OQ에서 정의.

#### US9.6 핵심 업무별 가용성 평가

**스토리:** 나는 기술 운영 담당자로서, 서비스 목표 달성 여부를 정확히 판단하기 위해 연속 30일 업무별 가용성을 평가하고 싶다.

- 페르소나: P8 / 우선순위: Must Have
- 근거: NFR2

- 준비 상태: 추가 구체화 필요 — OQ6. 해당 정책·증거 해소 전 구현 준비 완료로 판단하지 않는다.

## Assumptions & Open Questions

- 실제 사용자의 직함·사용 빈도·숙련도·불편 정도는 미확인이다. 8개 관점은 사용자 확인을 받은 작성 틀이며 실고객 연구의 증거가 아니다.
- 모든 OQ는 원래 requirements.md의 책임·기한을 유지한다. 상세 정책이 필요한 스토리에 추가 구체화 필요를 표시했으며 모든 스토리가 즉시 구현 가능한 상태라고 주장하지 않는다.
- 기술 운영 스토리는 담당자가 관찰할 결과를 표현한다. 전체 NFR의 상세 측정·시험은 traceability.json의 명시적 후속 단계에서 수행하며 인프라·보안·성능 요구를 생략하지 않는다.
- 스토리 수는 실제 분해 결과 69개이며 승인된 초기 예상 60–70개 안이다. 사람 수·작업일·출시일 또는 코드 완성도를 나타내지 않는다.
