### DEV-01 — 직원의 후속 요청 판단에서 실제 변경 적용까지 연결 보완

- 분류: 객관적 내용 누락. 대상: US8.1–US8.4, 특히 AC8.1.1·AC8.2.1·AC8.3.1·AC8.4.1. 근거: FR13.1–FR13.3, FR15.3–FR15.4.
- 현황: 고객 요청 스토리는 허용·거절·확인 필요를 추적하지만, 직원이 확인 필요 건을 판단하는 목표와 승인된 주문 변경을 실제 반영하는 결과는 명시되지 않는다. US8.4의 추가 이행 보류 판단은 취소·변경·반품 자체의 판단과 다르다. US8.5–US8.6의 Given에 있는 후속 처리 승인의 생성 경로도 불분명하다.
- 통합 제안: US8.1–US8.3은 고객 접수·결과 조회에 유지하고 새 US8.10을 추가한다. 제목은 ‘확인 필요한 후속 요청 판단’. 스토리는 ‘나는 내부 거래 운영 담당으로서, 고객에게 근거 있는 후속 처리 결과를 제공하기 위해 자동 판단할 수 없는 주문 전체 변경·취소·반품 요청을 검토하고 판단을 기록하고 싶다.’ 근거는 FR13.2, FR15.3–FR15.4, 준비 조건은 OQ1·OQ2다.
- 제안 AC8.10.1: Given 권한 있는 직원에게 확인 필요 요청과 확정된 계약·상태 정책 및 판단 근거가 있다 / When 요청의 허용 또는 거절을 판단한다 / Then 대상·사유·근거·판단 결과를 기록하고 고객의 요청 결과와 연결한다.
- 제안 AC8.10.2: Given 허용된 주문 변경이며 확정된 적용 조건이 충족됐다 / When 변경을 반영한다 / Then 원래 조건·변경 후 조건·적용 결과를 연결하고 요청 접수나 검토 중 보류만으로 적용 완료를 표시하지 않는다.
- 제안 AC8.10.3: Given 허용된 취소 또는 반품에 회수·환불 등 실제 후속 처리가 필요하다 / When 판단 결과를 반영한다 / Then 필요한 후속 처리에 연결하되 승인만으로 회수·환불 완료를 표시하지 않는다.
- 제안 AC8.10.4: Given 검토 이후 이행 상태나 승인 대상이 달라졌다 / When 과거 전제로 판단·적용을 시도한다 / Then 확정된 재검증 규칙을 만족하기 전 상충하는 결과를 완료로 처리하지 않는다.
- 자동 허용 경로는 기존 AC8.1.1·AC8.2.1·AC8.3.1에서 확정된 정책에 따른 결과로 명시한다. 모든 요청에 직원 승인을 새로 강제하지 않는다. 허용 시점·판단 권한 상세·변경 산식은 OQ1·OQ2에 유지한다.

### DEV-02 — 선행 스토리 나열을 필요한 업무 사실과 대안 경로로 교체

- 분류: 객관적 의존관계 표기 누락. 대상: US5.1–US5.5, US6.1, US7.1–US7.3·US7.7. 근거: FR6.1·FR6.3, FR8.2, FR9.1, FR11.1–FR11.2, FR2.2·FR2.4.
- 현황: 공통 설명은 경로별 대안을 허용하지만 US5.1–US5.4·US6.1은 직원 수락인 US3.4만, US5.3·US5.5·US6.1은 직원 배분인 US4.4만 가리킨다. 자동 확정·자동 배분 경로가 구현 순서와 입력 정의에서 빠질 수 있다. US7.2의 US7.1, US7.3의 US7.2는 요청 갱신이나 개별 신청을 거치지 않은 기업 계약 자동 갱신을 설명하지 못한다.
- 다음 문구로 선행 입력을 교체한다.

| 대상 | 제안 선행 업무/입력 문구 |
|---|---|
| US5.1·US5.2 | 해당 HW 업무 단계의 주문·품목 참조와 실제 결과 근거. 재고 확인 등 판매 판단용 근거와 확정 후 이행 결과를 구별하며 모든 결과 수신에 직원 수락을 필수로 요구하지 않는다. |
| US5.3·US5.4·US6.1 | 주문 전체 판매 확정 결과(US3.2 자동 확정 또는 US3.4 직원 수락). 해당 정책이 지급을 요구할 때 확인된 배분 결과(US4.3 자동 또는 US4.4 직원 결정). |
| US5.5 | 판매 확정·제공 방식(US3.6)·해당 품목 지급 조건·실제 공급 가능 수량. 보유 재고 경로와 주문 후 확보 경로(US5.3)를 구별하고 예약이 필요한 정책에만 US5.4를 적용한다. |
| US7.1 | 대상 기간제 권한·유효 계약과 갱신 요청 권한. US6.2의 민감한 발급 결과 조회 권한을 갱신 요청 권한의 필수 조건으로 추가하지 않는다. |
| US7.2 | 대상 기간제 권한·기업 계약과 자동 갱신 신청 권한. 선행 수동 갱신 요청(US7.1)은 필수가 아니다. |
| US7.3 | 유효한 자동 갱신 합의와 해제 권한. 합의는 기업 계약 또는 직원 확인된 개별 신청(US7.2)에서 올 수 있다. |
| US7.7 | 유효한 유예와 확인된 지급 배분(US4.3 또는 US4.4), 해당 회차·기간 근거. |

- 데이터 준비와 권한은 분리한다. fixture로 독립 시험할 수 있다는 설명은 유지하되, 실제 연결 시험에서 위 대안 경로 각각의 결과가 소비되는지 확인한다. 이 표는 개발 DAG나 시스템 구성 선택이 아니다.

### DEV-03 — HW 회수와 환불을 독립된 결과로 분리

- 분류: 객관적 담당·완료 결과 경계 부족. 대상: US8.6, AC8.6.1–AC8.6.3, personas P3·P4. 근거: FR13.4, FR3.1, 확인된 작성 계획 Q1·Q3.
- 현황: 내부 대금 담당 스토리 하나가 실물 회수 수량·회수 실패 재처리와 환불 금액·환불 실패 재처리를 함께 맡는다. P4라는 관점만으로 물류 회수 실행 권한을 부여할 수 없고 두 결과는 외부 실행 주체·단위·실패 복구가 다르다. SW 회수는 이미 US8.5로 분리돼 있다.
- US8.6은 ‘환불 요청·결과·잔액 추적’으로 좁혀 P4를 유지한다. 기존 AC8.6.1의 회수 수량은 환불 판단의 입력 근거로 참조하고, 직접 완료 결과는 합의된 환불 대상·금액·미완료 잔액·실패·정정 이력으로 명시한다. AC8.6.2의 중복·한도 검사와 AC8.6.3의 실패분 재처리는 환불에 적용한다.
- 새 US8.11 ‘HW 회수 요청·결과·잔량 추적’을 P3 관점으로 추가한다. ‘나는 내부 거래 운영 담당으로서, 승인된 반품·취소의 실물 처리 완료를 판단하기 위해 HW 회수 요청과 실제 결과·잔량을 추적하고 싶다.’ 준비 조건은 OQ2·OQ3다. 이는 실제 운송 수행을 OMS에 추가하지 않는다.
- 제안 AC8.11.1: Given 승인된 HW 후속 요청과 회수 대상·권한·실행 주체 근거가 있다 / When 회수를 요청하고 실제 결과를 연결한다 / Then 주문·품목·수량·승인·요청·실제 회수 결과를 연결한다.
- 제안 AC8.11.2: Given 일부만 회수됐거나 실제 결과가 미확인이다 / When 처리 상태를 조회한다 / Then 확인된 회수 수량과 잔량·미확인을 구별하고 전체 완료로 표시하지 않는다.
- 제안 AC8.11.3: Given 실패가 확인되고 원인이 해소됐으며 현재 조건이 유효하다 / When 실패분을 재처리한다 / Then 기존 실패와 새 결과를 연결하고 성공분 중복 회수·허용 수량 초과를 막는다. 성공 여부가 불명확한 경우 대조 전 위험한 재실행을 하지 않는다.
- 한 실제 사람이 P3·P4를 겸임할 수 있다. 다만 각 행위 권한은 별개이며 역할 인원 수를 늘리거나 기능을 제외하는 제안이 아니다.

### DEV-04 — 실제 SW 적용과 동시 수량 처리의 OQ 연결 보강

- 분류: 객관적 준비 조건 누락. 대상: US6.4/AC6.4.1, US7.7/AC7.7.1, US5.4/AC5.4.3. 근거: FR10.3, FR11.5, FR15.3 및 OQ2·OQ3.
- US6.4와 US7.7은 실제 기간 적용을 결과로 요구하므로 준비 상태에 OQ3(실제 적용 주체·증거)를 추가한다. 승인 또는 지급 확인만으로 외부 적용 완료를 단정하지 않는 별도 관찰 결과가 필요하다.
- 제안 AC6.4.4: Given 기간 변경은 승인됐지만 실제 적용 결과가 미확인이다 / When 처리 상태를 조회한다 / Then 승인 결과와 실제 적용 미확인을 구별하고 미확인을 적용 완료로 표시하지 않는다.
- 제안 AC7.7.4: Given 유예 중 지급은 확인됐으나 새 기간의 실제 적용이 미확인이다 / When 갱신 결과를 조회한다 / Then 지급 확인·계산된 기간·실제 적용 상태를 구별하고 원래 결과를 대조하기 전 중복 적용하지 않는다.
- US5.4의 준비 상태에는 OQ2를 추가한다. AC5.4.3은 동시 요청 수량 충돌을 다루지만 현재 OQ1·OQ3만 열거한다. 구체 잠금·메시징·재시도 기술은 정하지 않는다.
- 공통 규칙상 전부 미정임을 밝힌 것은 적절하다. 다만 해당 스토리만 추출해 구현할 때도 필요한 OQ를 놓치지 않도록 개별 연결이 필요하다. OQ10의 실제 사업 승인자 확보는 US2.6의 실거래 전제에도 명시하되 개발 fixture 조건과 구별한다.

### DEV-05 — 기업별 가격 예외가 계약 승인 경계를 우회하지 않게 명시

- 분류: 객관적 경계 명료화. 대상: US2.3/AC2.3.1, US2.4·US2.6. 근거: FR3.2, FR7.1·FR7.3, FR4.2.
- 현황: AC2.3.1은 확인된 예외 근거만으로 ‘반영’한다고 읽힐 수 있다. 고객사·상품별 가격이 계약 조건에 해당하는 경우에는 다른 등록자의 승인이 필요하다. 상품 공개 설정 전부에 새로운 승인 의무를 추가해서도 안 된다.
- AC2.3.1 대체 제안: Given 해당 관리 권한과 예외 근거·유효 범위가 확인됐고, 계약 조건에 해당하는 가격 예외는 US2.6의 승인을 거쳤다 / When 기업별 예외를 적용한다 / Then 승인된 대상·내용·유효 조건과 적용 결과를 추적한다.
- 추가 AC2.3.4 제안: Given 계약 조건에 해당하는 가격 예외가 미승인이다 / When 예외 관리 경로에서 적용하려 한다 / Then 계약 등록·승인 경로와 동일하게 적용을 막고 이 경로로 자기 승인을 우회하지 못한다.

### DEV-06 — 기술 운영 스토리의 크기·증거 창구 구체화

- 분류: 분해·표현 개선 제안. 대상: US9.2/AC9.2.3, US9.3/AC9.3.3, 모든 스토리의 동일 INVEST 문구. 근거: NFR2–NFR5·NFR9, 작성 계획 Q3.
- 장애 1건의 30분 복구와 업무별 연속 30일 가용성 측정은 관찰 기간·완료 증거가 다르다. US9.2는 장애별 복구·성공 접수 보존 결과에 집중하고 AC9.2.3의 가용성 부분은 별도 ‘핵심 업무별 가용성 평가’ 결과 또는 명시적 후속 NFR 검증 항목으로 연결하는 편이 낫다. 짧은 합성 장애 시험을 30일 운영 달성 근거로 사용할 수 없음을 명시한다.
- US9.3의 배포 1회와 정상일 반복 운영 시간도 별도 평가 결과다. AC9.3.3은 ‘반복 기술 운영 부담 평가’로 분리하거나 후속 측정 항목으로 명확히 연결한다. 시간 초과의 Then에는 NFR9의 ‘구조·자동화 개선 후 재검증’을 포함한다. 현재 문구는 기능 자동 삭제 금지만 명시한다.
- 각 INVEST 문구에 최소한 ‘독립 완료 결과 / 필요한 업무 사실 / 아직 추정할 수 없는 OQ’를 해당 스토리 기준으로 적는다. 예: US6.4는 ‘승인 판단과 적용 상태가 구별돼 추적됨 / 등록된 기간 조정 요청과 권한 / OQ1·OQ2·OQ3 해소 전 적용 구현 규모 미정’이다. 동일 문구 반복만으로 Small·Estimable을 충족했다고 평가하지 않는다.
- 별도 스토리로 둘지 후속 NFR 측정 항목으로 둘지는 문서 구성 선택이다. 어느 쪽이든 추적을 유지하면 수용 가능하다. 새 제품 정책이나 사용자 재선택을 요구할 사안은 아니다.

### 통합 시 유지할 조건

- 새 ID는 기존 US/AC를 재번호화하지 않고 추가한다. 위 US8.10·US8.11은 통합 시 미사용 여부를 확인할 제안 ID다. 분리된 기준의 출처를 남기고 실제 수·traceability·assessment를 갱신한다. 모든 추가 결과의 근거는 기존 FR/NFR이며 기능 축소나 범위 확장이 아니다.
- R-01·R-02의 후속 구체화는 적절하다. US5.7·US6.6의 실패 확정/미확인 구분과 성공분 중복 방지를 보존한다. 각 HW 업무마다 직원 입력·모든 커넥터를 둘 다 구현하도록 확대하지 않는다.
- 직원 판단·지급·이행·승인의 결과가 연결되더라도 특정 서비스·DB·이벤트·인증 제공자·잠금 방식을 이 단계에서 정하지 않는다.
- 기존 OQ1–OQ10은 유지하며 새 정책 선택이 필요한 항목은 추가로 발견하지 않았다. 상세 상태·값·권한·실행 근거는 기존 담당과 해소 시점에서 결정한다.

### Round 2 재확인 결과

기존 OBJECT 다섯 건은 모두 해결됐고 DEV-06의 개선 제안도 반영됐다. 유지하는 이견은 없다. 이는 사용자 스토리 문서의 보완 확인이며 기존 OQ의 해소·구현 준비 완료·제품 시험 통과·사용자 최종 승인을 뜻하지 않는다.

| 의견 | 처분 | 수정본에서 확인한 근거 |
|---|---|---|
| DEV-01 | 해결 | US8.10 및 AC8.10.1–AC8.10.4가 직원의 허용/거절 판단, 승인된 변경 적용, 취소/반품 후속 연결, 판단 전제 변경 재검증을 정의한다. AC8.1.1·AC8.2.1·AC8.3.1과 US8.10 선행 입력은 자동 판단을 유지하고 모든 건의 직원 승인을 강제하지 않는다. traceability의 FR13.2에 US8.10이 연결됐다. |
| DEV-02 | 해결 | US5.1–US5.5·US6.1의 선행 입력이 판매 판단용 근거와 확정 후 이행, US3.2/US3.4, US4.3/US4.4 및 보유/확보·조건부 예약 경로를 구별한다. US7.1은 민감 결과 조회 권한을 필수화하지 않고 US7.2–US7.3은 수동 갱신 선행 없이 기업 계약/개별 신청 합의를 허용하며 US7.7도 자동/직원 배분을 모두 참조한다. |
| DEV-03 | 해결 | US8.6·AC8.6.1–AC8.6.4는 P4의 환불 결과·잔액·한도로 한정됐다. US8.11·AC8.11.1–AC8.11.3은 P3의 HW 회수·수량·실패 재처리를 정의한다. 기존 US8.5 SW 회수와 구별되며 P3 설명도 수정됐다. FR13.4 추적은 US8.5·US8.6·US8.11을 모두 포함한다. |
| DEV-04 | 해결 | US6.4·US7.7 준비 상태에 OQ3가 추가됐고 AC6.4.4·AC7.7.4는 승인/지급 확인과 실제 적용 실패·미확인을 구별한다. US5.4에는 OQ2, US2.6에는 OQ10 및 별도 승인자 부재 경계 AC2.6.4가 추가됐다. |
| DEV-05 | 해결 | AC2.3.1은 계약 조건인 가격 예외에 US2.6 승인을 요구하고 AC2.3.4는 미승인 적용·자기 승인 우회를 막는다. 승인 조건을 모든 상품 공개 설정에 일률적으로 추가하지 않았다. |
| DEV-06 | 반영 확인 | AC9.2.3은 장애별 복구 증거를 다루고 US9.6·AC9.6.1–AC9.6.3은 별도 연속 30일 관측과 자료 부족을 다룬다. US9.3·AC9.3.3은 배포별 작업, US9.7은 정상일 반복 부담을 분리하며 각각 초과 후 개선·재검증을 명시한다. 개별 INVEST와 assessment는 OQ 해소 전 크기·견적 미확정을 유지한다. |

읽기 전용 확인으로 스토리 69개·AC 227개·상위/coverage 각 88개를 확인했고 모든 OK의 US 대상이 존재함을 대조했다. 9개 Deferred는 담당 후속 단계와 사유를 갖추며, assessment가 설계·구현 전 OQ 결정 기한과 시험 의무를 계속 유지한다. 다른 참여자의 모바일·접근성·동시 처리·배포 통제 보완은 위 개발 경계와 충돌하지 않는다.
