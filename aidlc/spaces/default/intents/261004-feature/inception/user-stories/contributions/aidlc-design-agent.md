### Round 1의 발견과 원래 제안

### D-01 — 고객 모바일의 실행 범위와 접근성을 검증할 AC 필요

- 대상: US1.3–US1.5, US3.1, US8.8, 공통 검증 조건. 근거: NFR1·NFR12, OQ4·OQ8.
- 관찰: 고객 PC·모바일과 직원 PC 조건은 공통 문장에 있지만 실제 AC는 고객 모바일에서 조회 외 제출·관리까지 완료하는지 검사하지 않는다. NFR12의 라벨·키보드·색상 외 상태 전달 역시 본문 AC에 없다. P2도 고객이므로 모바일 대상에서 빠지면 안 된다.
- 공통 조건 추가안: “고객 P1·P2의 각 업무는 확정한 지원 브라우저·화면 조건에서 PC와 모바일 웹 모두 동일한 권한·업무 결과를 제공한다. 모바일을 조회 전용으로 축소하지 않는다. 직원 P3–P7 및 P8의 직원 OMS 업무는 PC 전용이며 고객 모바일 범위를 직원 모바일 업무로 확대하지 않는다. 모바일 레이아웃·입력 방식이 달라도 검증·오류 복구·결과 확인 경계는 동일하다.”
- AC 추가안:

| ID | Given | When | Then |
|---|---|---|---|
| AC3.1.4 | OQ8에서 확정한 고객 PC·모바일 환경과 동일한 주문 제출 권한·유효 입력이 있다 | 각 환경에서 다품목 입력·제공 방식 확인·제출·결과 확인을 수행한다 | 두 환경 모두 업무를 완료하며 모바일에서 필수 입력·수정·제출을 누락하거나 PC 이용을 필수로 요구하지 않는다 |

AC8.8.4의 적용 범위를 고객 조회 화면 하나로 한정하지 않도록 공통 화면 검증 조건으로 참조한다. 접근성 수치·지원 해상도·브라우저는 OQ8에 남긴다. 디자인 검증에서는 WCAG 2.1 AA 가이드를 참조하되, 미확정 수치나 인증 달성을 이번에 승인된 제품 정책으로 쓰지 않는다.

### D-02 — 가격 변경 동의의 정상 결과가 빠짐

- 대상: US3.5/AC3.5.2–AC3.5.3, US7.5/AC7.5.2–AC7.5.3. 근거: FR4.3·FR11.3·FR15.3–FR15.4, OQ1·OQ2·OQ4.
- 관찰: 두 스토리 모두 고객이 의사를 전달하려는 목표인데 AC는 가격 보존·무동의 확정 금지·동의 미확인만 검증한다. 유효한 제안에 실제 동의했을 때 어떤 대상·가격에 대한 응답이 기록되고 어떤 결과를 보는지 없다.
- AC 추가안:

| ID | Given | When | Then |
|---|---|---|---|
| AC3.5.4 | 필요한 행위 권한이 있고 유효한 변경 제안의 원래 조건·제안 조건·대상을 확인했다 | 고객이 그 제안에 동의 의사를 제출한다 | 해당 제안·내용에 연결된 동의 근거와 제출 결과를 확인하고 원래 주문 조건·변경 이력을 보존하며 동의를 지급·제공 완료로 표시하지 않는다 |
| AC7.5.4 | 합의 범위 밖 갱신 제안과 대상 권한·회차·조건이 확인되고 필요한 행위 권한이 있다 | 고객이 그 제안에 동의 의사를 제출한다 | 해당 회차·제안에 연결된 동의 근거와 후속 처리 상태를 확인하고 동의를 실제 연장·지급 완료로 표시하지 않는다 |

두 추가 AC에 “표시 후 제안 내용이 바뀌거나 유효성이 상실되면 이전 화면의 응답을 새 제안의 동의로 간주하지 않으며 재확인 안내를 제공한다”는 공통 경계를 연결한다. 동의 방식·허용 기한·거절 후 상태·권한 명칭은 OQ2·OQ4에서 정하며 자동 확정을 추가로 강제하지 않는다.

### D-03 — 접수 결과 미확인 상태의 고객 행동 안내 필요

- 대상: US3.1/AC3.1.2–AC3.1.3; US2.5, US7.1–US7.3, US8.1–US8.3의 요청 공통 조건. 근거: FR5.2·FR15.1·NFR4·NFR12.
- 관찰: AC3.1.3의 중복 방지는 적절하지만 고객에게 응답이 끊긴 순간 무엇을 보여 주는지는 없다. 오류를 전부 “실패, 다시 주문”으로 안내하면 이미 접수된 건의 재확인 경로를 찾기 어렵다. 입력 검증 실패와 접수 결과 미확인을 구별해야 한다.
- AC3.1.2 Then 보완안: “사유와 함께 접수를 거절하고 직원 확인으로 우회하지 않는다. 수정 가능한 입력 오류는 해당 입력과 연결해 안내하고 권한·기업 상태 문제와 구별하며, 권한이 유지되는 범위에서 입력을 수정해 다시 제출할 수 있다.”
- AC3.1.3 Then 보완안: “추적 가능한 원래 접수 결과를 확인하고 주문 효과는 추가 생성하지 않는다. 결과를 아직 확인할 수 없으면 성공·실패로 단정하지 않고 미확인 및 결과 재확인 경로를 안내한다. 이미 확인된 접수는 실제 업무 완료와 구별한다.”
- 같은 요청 재확인 원칙을 계약 변경·갱신·자동 갱신 신청/해제·변경/취소/반품 요청에 공통 적용한다. 별도 초안 자동 저장·오프라인 제출·고정 타임아웃 기능을 추가하는 제안은 아니다.

### D-04 — 진행 화면의 빈 결과·조회 실패와 권한별 다음 조치 구체화

- 대상: US8.8/AC8.8.1–AC8.8.3, US6.2/AC6.2.1, US8.9. 근거: FR2.4·FR14.1–FR14.3·NFR12, OQ4·OQ7·OQ8.
- 관찰: 부분 완료와 민감 정보 차단은 명확하지만 “남은 조치”가 고객 실행인지 직원 확인 대기인지 불분명하다. 조회 실패를 데이터 없음 또는 미지급으로 표현하는 오류도 현재 AC로 직접 잡기 어렵다.
- AC8.8.1 Then 보완안: “전체·품목·수량별 확정/제공/지급/갱신/후속 상태와 남은 조치를 구별한다. 자기 권한으로 실행할 수 있는 고객 조치와 직원·외부 결과 확인 대기를 구별해 안내하고, 실행 경로를 제시할 때 해당 행위 권한도 확인한다.”
- AC8.8.3 Then 보완안: “미부여 정보가 다른 조회 경로로 노출되지 않는다. 숨겨진 금액·발급 내용 등을 0원·미지급·발급 실패처럼 사실 상태로 대체하지 않으며, 허용된 주문 정보는 계속 확인할 수 있다.”
- AC 추가안:

| ID | Given | When | Then |
|---|---|---|---|
| AC8.8.5 | 허용 범위의 조회가 정상 완료됐고 결과가 없다 | 고객이 목록을 확인한다 | 조회 범위에 결과가 없음을 알리고 권한이 있는 경우에만 주문 시작 또는 확정한 검색 조건 수정 경로를 제공한다 |
| AC8.8.6 | 전체 또는 일부 조회가 실패해 최신 결과를 확인할 수 없다 | 고객이 진행 화면을 확인한다 | 조회 불가 범위와 재확인 경로를 안내하며 실패한 영역을 데이터 없음·미지급·업무 실패·전체 완료로 치환하지 않는다 |
| AC8.9.4 | 고객이 이전에 수신한 로그인 후 확인 링크를 가지고 있으며 이후 관련 권한이 회수됐다 | 링크에서 대상 업무를 확인하려 한다 | 현재 권한을 검증해 미부여 내용을 제공하지 않고 접근 불가를 안내하며 안전하게 허용 화면으로 돌아갈 수 있다 |

구체 담당자 이름·지원 시간·처리 예상 시각은 미확정이다. 다음 조치는 역할 수준으로 표현하고 실제 연락 경로는 OQ4·OQ7·OQ10에 맞춰 구체화한다. 타 기업 존재나 비공개 거래 사실을 오류 안내로 드러내지 않는다.

### D-05 — 계약 승인자 부재 결과를 명시해야 함

- 관찰: 동일인 다른 계정 승인 금지는 잘 반영됐지만 요구사항에 명시된 “별도 승인자가 없으면 미승인 유지”의 사용자 결과는 빠졌다. 1인 개발자가 존재한다는 사실을 자동 승인 우회로 해석할 여지를 닫아야 한다.
- AC 추가안:

| ID | Given | When | Then |
|---|---|---|---|
| AC2.6.4 | 등록자 외에 해당 계약을 승인할 수 있는 사람이 없다 | 등록자가 적용 상태와 다음 조치를 확인한다 | 미승인 상태와 다른 승인자의 확인 필요를 안내하며 자동 승인·권한 확대·유효 조건 적용을 하지 않는다 |

특정 직급, 승인자 채용, 대리 승인 정책은 추가하지 않는다. personas.md의 서로 다른 사람 원칙과 OQ10은 유지한다.

### D-06 — 직원 업무 조회의 행위자 검증을 명시해야 함

- 대상: US8.8/AC8.8.1–AC8.8.3, P3–P5·P6. 근거: FR3.1·FR14.1·NFR1.
- 관찰: FR14.1은 고객·직원 모두의 진행·남은 조치 확인인데 US8.8은 P1만 명시한다. 여러 직원 처리 스토리에 개별 조회가 있지만 고객용 AC만으로 직원 통합 조회까지 검증했다고 보기 어렵다. 권한별 미완료 업무 인계 관찰을 분명히 한다.
- 최소 수정안: US8.8의 주 관점 P1은 유지하고 “관련 검증 관점: P3·P4·P5·P6의 각각 부여된 조회 권한”을 명시한다. 아래 AC를 추가한다. 별도 직원 대시보드 제품을 강제하지 않는다.

| ID | Given | When | Then |
|---|---|---|---|
| AC8.8.7 | 허용 접속 환경의 직원에게 해당 주문 및 관련 업무 조회 권한이 부여돼 있다 | 전체·품목·수량별 진행과 남은 조치를 조회한다 | 자기 권한 범위에서 확인 대기·미완료·부분 결과와 후속 조치를 확인하고 별도 권한 없는 대금·발급·계약 근거는 연결 화면에서도 노출하지 않는다 |

이 AC는 여러 직원 관점에 대한 권한 조합별 시험으로 검증한다. 직원 신분이나 기술 운영 역할에 포괄 조회 권한을 새로 부여하지 않는다.

### 추가 편집 제안 및 유지할 경계

- 여러 스토리의 “담당로서”를 “담당자로서”로 수정한다. 의미·ID 변경 없는 문장 교정이다.
- P1–P8을 인물·정원·고정 RBAC 묶음으로 만들지 않은 점을 유지한다. P2의 고객 관리와 P7의 직원 관리는 계속 구별한다.
- US5.7·US6.6의 일반 이행 실패 재처리, 성공분 중복 방지, 결과 미확인 시 대조 우선에 동의한다. US5.1·US5.2의 직원 근거·외부 연동 병행도 유지한다. 과거 R-01·R-02를 이 검토만으로 해결 상태로 바꾸지 않는다.
- 화면별 구체 배치, 고정 반응 시간, 필터 종류, 화면 너비, 실제 외부 제공자, 승인·만료 산식은 선택하지 않았다. OQ1–OQ10 및 각 해소 시점은 그대로 유지한다.
- 본 검토가 새로 요구하는 사용자 판단 질문은 없다. D-01–D-06의 기존 요구 해석에 이견이 남으면 객관적 내용/지식 쟁점으로 재검토하며, 범위·위험 선호의 선택 문제로 바뀌는 경우에만 리드가 사용자에게 구분해 제시한다.

## Positions

- AGREE: 8개 업무 관점을 사실 확인되지 않은 인물·인원·고정 권한 역할로 만들지 않은 페르소나 구성을 유지한다. 실제 고객 연구와 제품 정책 결정을 구분한다.
- AGREE: 고객 PC·모바일, 직원 PC 전용, 행위별·조직별 권한 합산, 계약 자기 승인 금지, 실제 SW 기간의 동일인 별도 승인 허용을 유지한다. 서로 다른 통제를 합치지 않았다.
- AGREE: 모든 포함 기능 Must Have, OQ 미해결 표시, R-01·R-02의 후속 구체화와 과거 상태 보존에 동의한다. 기능 축소나 실증 완료를 주장하지 않는다.
- AGREE: D-01 해소 — 공통 모바일·접근성 적용 조건과 AC1.3.4·AC3.1.4·AC8.8.4가 고객 실행·관리·복구의 관찰 결과를 검증하며 직원 PC 경계를 유지한다.
- AGREE: D-02 해소 — AC3.5.4·AC7.5.4와 제안 변경 시 재확인 조건이 유효 동의의 정상 결과와 대상 연결을 보완했다.
- AGREE: D-03 해소 — AC3.1.2–AC3.1.3 및 다른 요청으로의 공통 적용이 입력 거절·접수 미확인·안전한 재확인을 구별한다.
- AGREE: D-04 해소 — AC8.8.1·AC8.8.3·AC8.8.5·AC8.8.6·AC8.9.4가 권한별 다음 조치, 빈 결과/조회 실패, 알림 링크의 현재 권한 경계를 명시한다.
- AGREE: D-05 해소 — AC2.6.4와 OQ10이 별도 계약 승인자 부재의 미승인 유지와 다음 조치를 명시한다.
- AGREE: D-06 해소 — 별도 US8.12와 AC8.12.1–AC8.12.3, FR14.1·FR3.1·NFR1 추적이 직원의 권한별 진행 조회를 검증한다. 원안 대신 독립 스토리로 분리한 통합안을 수용한다.
