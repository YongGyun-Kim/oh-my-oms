# OMS 사용자 스토리 작성 계획과 질문

## Prior Context

- [승인된 요구사항](../requirements-analysis/requirements.md)과 [팀 개발 원칙](../practices-discovery/team-practices.md)을 기준으로 한다. FR1–FR16 및 하위 ID·NFR1–NFR14를 그대로 보존해 스토리와 연결한다.
- User Stories 실행 근거: 고객과 내부 직원의 서로 다른 목표·접근 환경, 역할별 권한, 계약·지급·이행·기간·갱신의 복합 정책이 있어 사용자별 목표와 정상/실패 결과를 분리해야 한다. 현재 단계는 시나리오·수락 기준 작성이며 기술 스택·아키텍처 선정이 아니다. 최종 assessment는 요약 확인 후 작성한다.
- 사용자는 Jump 선택을 취소하고 현재 User Stories의 시나리오 작업을 계속하도록 지시했다. 단계 이동은 실행하지 않았다.
- 이전 인터뷰처럼 질문을 하나씩 안내하는 방식을 유지한다. 사용자는 언제든 파일 직접 작성(self-guided) 또는 자유 대화(chat)로 바꿀 수 있다.
- 요구사항 검토 R-01·R-02는 승인 시 미해결 상태로 수용했다. 일반 이행 실패의 재처리와 HW 업무의 직원 근거 등록·외부 연동 병행을 스토리에서 명시적으로 다룰 계획이며, 승인된 requirements.md나 과거 검토의 상태를 수정하지 않는다. 근거는 SC-10, 기존 Q9, FR9·FR10·FR13·FR15와 [검토 기록](../requirements-analysis/reviews/review-01.md)이다. 모든 HW 업무마다 두 입력 방식 또는 모든 커넥터를 요구하는 범위로 확대하지 않는다.

## 작성 원칙과 계획

- 실제 직함·인원·사용 빈도·기술 숙련도·인터뷰 증거가 없는 인물상은 사실로 만들지 않는다. 페르소나는 합의된 업무를 수행하는 관점이며 고정 권한 묶음이나 인력 채용 계획이 아니다.
- 스토리는 사용자·목표·가치를 명시하고 안정적인 `US{group}.{seq}` ID를 부여한다. 수락 기준은 `AC{group}.{seq}.{criterion}` ID와 Given/When/Then으로 작성하며 정상·실패·권한·중복/충돌 경계를 포함한다.
- INVEST를 점검하되 미정 정책·외부 근거가 있는 스토리에 개발 준비 완료·기간 추정 확정을 주장하지 않는다. 의존성과 OQ 해소 전제, 검증 가능한 결과를 명시한다.
- 이미 첫 제품에 포함하기로 한 기능은 임의로 Should/Could로 낮춰 제외하지 않는다. 포함 범위는 Must Have로 추적하고 후속 고도화·미포함은 구분한다. 우선순위와 구현 순서는 다르며 실제 개발 순서·MVP 경계 변경은 Delivery Planning에서 기존 범위를 보존한 채 판단한다.
- 기능별 사용자 결과를 중심으로 스토리를 나누고 요구사항 전체의 추적 누락을 검사한다. 공통 NFR은 관련 스토리의 수락 기준과 연결하거나 구체화를 맡을 후속 단계를 지정한다. 이관은 첫 제품 요구 삭제나 검증 면제를 뜻하지 않는다.
- 질문 답변과 별도 요약 확인 뒤 personas·stories·assessment 초안을 작성하고 디자인·개발·품질 담당자가 독립적으로 검토에 참여한다. 합의한 OQ를 임의 정책으로 채우지 않는다.

## Q1. 시나리오의 사용자를 다음 8개 업무 관점으로 나눌까요?

| 업무 관점 후보 | 시나리오에서 다룰 목표 |
|---|---|
| 고객 구매 담당 | 허용된 상품·주문·지급/발급 결과 확인, 주문·갱신·변경·계약 조건 변경 요청 |
| 고객사 권한 관리자 | 자기 기업의 담당자·부서·사업장·역할 관리 |
| 내부 거래 운영 담당 | 기업 확인·상품 등록·주문 판단·HW 이행 추적·계약 조건 등록 |
| 내부 대금 담당 | 청구·지급 근거·배분·연체·환불 결과 확인 |
| 내부 SW 권한 담당 | 발급·실제 기간 조정 요청/승인·갱신·회수 결과 관리 |
| 내부 계약 승인 담당 | 등록자와 다른 사람으로서 합의 근거를 확인하고 계약 조건 승인 |
| 내부 권한 관리자 | 내부 직원 역할·권한 관리, 허용된 계정 복구 업무 |
| 기술 운영 담당 | 배포·관측·장애 복구·데이터 보존·운영 부담 검증 |

B. 업무 관점을 추가·분리·통합하고 싶다. 변경할 구성을 설명한다.

[Answer]: A. 이 8개 업무 관점으로 시나리오를 정리한다. 사용자 선택: "1" (이 8개 관점으로 진행). 고객 구매 담당·고객사 권한 관리자·내부 거래 운영 담당·내부 대금 담당·내부 SW 권한 담당·내부 계약 승인 담당·내부 권한 관리자·기술 운영 담당을 사용한다. 실제 인원·직함·고정 권한 묶음은 확정하지 않으며 각 스토리에서 필요한 권한을 명시한다. 동일인의 여러 업무 수행은 가능하되 계약 조건 등록자·승인자 분리와 실제 SW 기간 조정의 동일인 별도 승인 허용은 기존 결정을 유지한다.

## Q2. 시나리오를 어떤 순서와 묶음으로 읽고 검토할까요?

아래는 문서 구성 방식이며 개발 순서나 포함 범위 변경이 아니다. 어떤 선택에서도 고객/직원 관점과 HW/SW의 차이, 조건별 정상·실패 흐름을 모두 추적한다.

A. 업무 흐름 중심: 가입·권한 → 상품·계약 → 주문·확정 → 지급·HW/SW 제공 → 갱신·변경·예외 → 기술 운영 순으로 정리한다.
B. 사용자 중심: 각 업무 관점이 수행할 일을 모아 정리하고, 서로 주고받는 업무를 연결한다.
C. 요구사항 영역 중심: FR1–FR16의 순서로 스토리를 묶고 업무 흐름을 별도로 연결한다.
X. Other (please specify)

[Answer]: A. 업무 흐름 중심: 가입·권한 → 상품·계약 → 주문·확정 → 지급·HW/SW 제공 → 갱신·변경·예외 → 기술 운영 순으로 정리한다. 사용자 선택: "1" (업무 흐름 중심). 각 흐름에 고객/직원 관점, HW/SW 차이, 정상·실패 결과와 요구사항 ID를 연결한다. 이 문서 구성 선택으로 개발 순서·포함 기능·첫 제품 범위를 변경하지 않는다.

## Q3. 스토리 하나의 크기는 어떻게 잡을까요?

두 선택 모두 사용자에게 의미 있는 결과를 단위로 하고 정상·실패 수락 기준을 포함한다. 화면·API·DB를 따로 구현하는 작업 목록이나 검증 불가능한 큰 묶음으로 만들지 않는다. 실제 스토리 수는 선택한 분해 기준과 검토 후 산정하며 지금 임의로 확정하지 않는다.

A. 한 사용자의 한 업무 목표를 기본 단위로 한다. 정상·실패·권한 경계를 함께 쓰고, 독립된 결과·정책·의존성을 가진 경우만 분리한다.
B. 같은 업무 목표도 정책별로 더 잘게 나눈다. 예를 들어 일반 갱신·계약 유예 갱신·보상 중첩 갱신을 각각 독립 스토리로 정리하고 공통 기준을 연결한다.
X. Other (please specify)

[Answer]: A. 한 사용자의 한 업무 목표를 기본 단위로 한다. 정상·실패·권한 경계를 함께 쓰고, 독립된 결과·정책·의존성을 가진 경우만 분리한다. 사용자 선택: "1" (한 사용자의 한 업무 목표 중심). 공통 실패 조건을 이유 없이 별도 스토리로 복제하지 않으며, 사용자에게 독립된 가치가 있거나 업무 정책·의존성 때문에 필요한 경우 분리한다. 스토리 수·구현 기간·개발 준비 완료 여부는 이 답변만으로 확정하지 않는다.
