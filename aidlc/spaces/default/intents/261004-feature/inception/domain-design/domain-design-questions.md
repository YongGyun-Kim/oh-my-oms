## 설계·검증 범위

- components.md에 기계 판독 YAML과 동일한 컴포넌트/호출 관계의 Mermaid·텍스트 설명·요약·엔티티 소유권 표를 작성한다.
- 엔티티는 소유 컴포넌트·식별자·속성 이름·다른 소유자 엔티티 참조만 구체화한다. 타입·검증식·허용 값·관계 수 등 전체 스키마는 Functional Design에서 정의한다.
- 각 데이터의 쓰기 권위는 한 곳이다. 조회/이력/화면 복제는 원래 권위가 아니며 같은 데이터·행위 권한을 유지한다. DB·캐시·큐·외부 제품을 자체 도메인 컴포넌트로 분류하지 않는다.
- 의존/역의존의 대칭·선언된 참조·단일 엔티티 소유·호출 그래프의 순환 여부와69개 US→컴포넌트/엔티티 연결을 검사한다. 도메인 사실의 흐름과 코드 호출 의존을 구별한다.
- 결정은 대안·장단점·보안/운영 영향·가역성을 비교해 ADR에 남긴다. 아래 분해안은 선택 전 제안이며 새 기능이나 이미 선택된 배포 구성을 뜻하지 않는다.

## Q1. 주문 업무를 어떤 논리 책임 단위로 나눌까요?

A. 상품·판매 조건, 기업 계약·합의, 주문 접수·전체 수락, 대금, HW 이행, SW 권한·갱신, 후속 요청 판단을 각각 구별한다. 각자의 사실·규칙·이력을 소유하고 명시적 연결로 협력한다. 변경 이유가 다른 업무를 독립적으로 검토하기 쉽지만 연결 계약과 흐름 관리가 더 필요하다.
B. 상품·계약은 구별하되 주문 접수·전체 수락·후속 요청 판단을 하나의 주문 업무 컴포넌트로 묶고, HW/SW 이행도 하나의 제공 컴포넌트 안에서 구분한다. 연결 수는 적지만 서로 다른 업무 규칙과 변경이 한 컴포넌트에 모인다.
X. Other (please specify)

[Answer]: [assumption] A. 업무별 책임 구분을 확인 전 설계 제안으로 둔다. 선택 도구에서 답변이 반환되지 않아 사용자 선택으로 기록하지 않으며, 작성 전 요약 확인에 포함한다.

추천: A. 계약·대금·HW/SW·후속 요청의 이미 확인된 서로 다른 규칙/실제 결과를 명시적으로 구별한다. 코드 모듈을 나눈다는 결정이며 별도 서비스 배포를 선택하지 않는다. 정확한 컴포넌트 목록은 다른 답변과 엔티티 소유권 분석으로 정리한다.

## Q2. 인증·복구와 기업 조직·업무 권한 관리는 어떤 책임으로 나눌까요?

A. 인증·MFA·계정 복구/확인된 신원 연결을 담당하는 논리 책임과, 기업 가입·부서/사업장·소속·고객/직원 역할·행위 범위를 담당하는 논리 책임을 구별한다. 신원 확인 결과를 이용하되 업무 권한이나 기업 이용 승인을 자동 획득하지 않는다.
B. 인증·복구·기업 가입·조직·고객/직원 업무 권한을 하나의 접근 관리 컴포넌트로 묶는다. 한곳에서 관리할 수 있지만 인증 수단 변경과 조직/권한 변경이 함께 영향을 받는다.
X. Other (please specify)

[Answer]: A. 인증·복구와 기업 조직·업무 권한의 논리 책임을 구분한다.

추천: A. MFA/복구의 수단·신원 확인과 기업/행위 권한은 서로 다른 검증 책임이다. 두 선택 모두 기존 접근·권한 요구를 유지한다. 인증 제공자·실제 동일인 식별·세션/권한 효력은 OQ4에서 확정한다.

## Q3. 환불의 금액·실제 지급 결과는 어느 논리 책임이 소유할까요?

A. 청구·지급·배분을 맡는 대금 컴포넌트가 환불 대상 금액·잔액·실제 환불 결과/정정도 소유한다. 후속 요청 판단 컴포넌트는 환불 허용 판단·합의 근거를 전달하고 실제 결과를 직접 덮어쓰지 않는다. 금액 한도와 정정을 같은 책임에서 대조하기 쉽다.
B. 환불 실행·결과를 별도 논리 컴포넌트가 소유하고 대금 컴포넌트의 확인 금액·이미 사용한 금액/환불 가능 한도와 명시적으로 협력한다. 환불 실행의 변경은 분리되지만 금액 보존과 연계 실패의 대조 경계가 더 늘어난다.
X. Other (please specify)

[Answer]: A. 환불의 대상 금액·잔액·실제 처리 결과와 정정은 대금 책임에 포함한다. 후속 요청 판단은 환불 허용 판단과 합의 근거를 전달한다.

추천: A. 지급·배분·환불의 중복/초과와 정정 근거를 일관되게 연결하기 위한 제안이다. 실제 자금 이동 수단·승인 절차·금액 계산 규칙은 새로 확정하지 않는다.

## Q4. SW 발급·실제 기간·갱신의 논리 소유권은 어떻게 둘까요?

A. 기업 SW 권한의 발급 결과·실제 기간·기간 조정·갱신 회차/적용 결과를 같은 SW 생애주기 컴포넌트가 소유한다. 계약 조건은 계약 소유자, 청구/지급/요금 조정 결과는 대금 소유자와 연결한다. 동일 권한의 이중 연장·역순 만료·기존 보상 기간을 함께 대조한다.
B. SW 발급·실제 기간 소유자와 갱신 업무 소유자를 구별한다. 갱신은 해당 권한 소유자에게 기간 적용을 요청하며 실제 기간을 직접 수정하지 않는다. 갱신 규칙을 독립 변경하기 쉽지만 회차·기간·발급 결과의 대조 연결이 늘어난다.
X. Other (please specify)

[Answer]: A. SW 발급 결과·실제 이용 기간·기간 조정·갱신 회차와 적용 결과는 같은 SW 생애주기 책임으로 묶는다. 계약 조건과 대금 기록은 각 소유자에 두고 연결한다.

추천: A. 첫 제품에서 실제 기간과 갱신/보상/유예의 상호작용이 이미 중요하다. 양쪽 선택 모두 영구/기간제, 고객 요청·합의된 자동 갱신, 기업 계약 우선·실제 결과 검증을 유지한다.

## Q5. 여러 업무에 걸친 진행·남은 조치의 연결은 어떻게 관리할까요?

A. 연결된 업무 흐름을 조정하는 논리 책임을 둔다. 주문·대금·이행·회수 등의 소유자에게 판단/실행을 요청하고 진행·대기·남은 조치·요청 참조를 연결한다. 각 소유자의 업무 규칙과 실제 금액·수량·기간을 대신 수정하지 않는다. 직원이 전체 진행을 추적하기 쉽지만 조정 책임이 너무 커지지 않도록 경계를 관리해야 한다.
B. 각 업무 컴포넌트가 확인된 사실에 반응해 다음 업무를 연결하고 진행 조회를 조합한다. 중앙 조정 책임은 줄지만 누락·실패·미확인·경합의 전체 진행을 추적할 책임을 여러 곳에서 맞춰야 한다.
X. Other (please specify)

[Answer]: B. 각 업무 컴포넌트가 확인된 결과를 바탕으로 다음 업무를 연결하고, 전체 진행 조회를 조합한다. 별도 중앙 조정 책임은 두지 않는다. 실패·미확인·누락·남은 조치를 추적할 책임과 연결 기준은 컴포넌트 사이에 명시한다.

추천: A. 1인 기술 운영과 직원의 미확인/부분 진행 추적 목표에 맞춘 제안이다. 기능 범위를 축소하거나 모든 도메인 규칙을 하나의 처리기로 옮기지 않는다. 요청/실제 결과의 구별은 기존 결정이다. 정확한 API·메시지·저장/트랜잭션·재시도 수단은 후속 단계에서 정한다. 사용자 선택은 B이며, 분산된 업무 책임에서도 전체 진행과 오류를 추적하는 요구를 유지한다.

## Q6. 외부 연동의 전송·수신 기록과 업무 사실은 어떻게 소유할까요?

여기서 외부 연동은 OMS 밖에서 수행되는 업무의 요청·결과를 연결하는 것이다. 별도 사내 시스템도 포함한다. 대금의 청구·지급·환불, HW의 재고·확보·출고·배송·회수, 별도 SW 발급/적용 주체가 있는 경우의 발급·기간 변경·회수 등이 예시이며 실제 연결 대상·제품·API·실행 주체는 OQ3에서 확인한다. 전송 성공과 실제 업무 완료를 구별한다.

A. HW·SW·대금 등 각 업무 소유자가 자기 외부 연동의 요청/수신 대조 기록과 정규화된 업무 사실을 소유한다. 공통 통신/검증 코드는 재사용할 수 있다. 의미가 다른 결과를 업무별로 판단하기 쉽지만 공통 전송·수신 기록 형식을 일관되게 유지해야 한다.
B. 공통 연동 관리 컴포넌트가 외부 교환의 전송·수신·재전송·출처/참조 기록을 소유하고, 정규화된 지급·배송·발급 등의 업무 사실은 해당 도메인 소유자가 소유한다. 공통 교환 이력은 모으기 쉽지만 교환 기록과 실제 업무 결과의 구별·연결이 추가로 필요하다.
X. Other (please specify)

[Answer]: A. 각 업무 책임이 자기 외부 연동의 요청·수신 대조 기록과 확인된 업무 결과를 소유한다. 공통 통신/검증 코드는 재사용할 수 있으며 실제 연동 대상과 방식은 미정으로 유지한다.

추천: A. 아직 실제 연동 주체/형식이 없고 HW·대금·발급의 의미와 대조 규칙이 서로 다르다. ERP/WMS/결제/배송의 외부 권위와 직원 근거 등록 경로는 두 선택 모두 유지한다. 확인된 기록을 최신 도착이라는 이유로 무조건 덮어쓰지 않는다. 공급자·제품·프로토콜은 OQ3 등에서 검증한다.

## Q7. 고객 화면과 내부 직원 화면의 논리 UI 책임은 어떻게 구분할까요?

A. 고객 업무 UI와 내부 직원 업무 UI를 별도 논리 컴포넌트로 구분하고 공통 시각 토큰·기초 조작 코드를 재사용한다. 각 UI는 허용된 조회/행동을 업무 소유자에게 연결하며 데이터·계약/금액/기간 규칙의 최종 권위는 갖지 않는다.
B. 하나의 UI 논리 컴포넌트 안에서 고객/직원 탐색·화면·접속 조건을 명시적으로 구분한다. 재사용이 쉽지만 고객/직원 전용 흐름이 섞이지 않게 경계를 검사해야 한다.
