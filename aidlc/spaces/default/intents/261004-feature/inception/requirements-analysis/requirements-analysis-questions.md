- 아래 선택지는 제안이며 선택 전에는 확정 요구사항이 아니다. 특정 구현 언어·DB·인증 제품·클라우드 서비스 구성을 선택하지 않는다.

## Q1. 이 OMS를 판매 측에서 사용하는 조직은 첫 제품에서 어떤 형태인가요?

이전 고객군 선택은 상품을 구매하는 기업에 관한 것이었다. OMS 자체를 한 판매 회사가 운영하는지, 여러 판매 회사에 제공하는지는 아직 정하지 않았다. 어느 경우든 판매 상품 등록은 해당 OMS를 관리하는 내부 직원만 가능하다는 조건을 유지한다.

A. 우리 판매 회사 한 곳의 직원이 운영하고, 여러 구매 기업 고객에게 상품을 판매한다.
B. 서로 독립된 여러 판매 회사가 사용한다. 각 회사의 내부 직원과 고객·주문 데이터를 구분해야 한다.
C. 아직 결정하지 못했다. 두 형태의 업무 차이를 먼저 설명받고 결정한다.
X. Other (please specify)

[Answer]: A. 우리 판매 회사 한 곳의 직원이 운영하고, 여러 구매 기업 고객에게 상품을 판매한다. 사용자 선택: "1" (우리 판매 회사 한 곳이 운영). 독립된 여러 판매 회사가 사용하는 형태는 첫 제품의 운영 모델로 선택하지 않았다. 판매 상품 등록은 OMS를 관리하는 내부 직원만 가능하다는 조건을 유지한다.

## Q2. 기업 고객과 첫 담당자는 어떻게 이용을 시작하나요?

고객이 직접 주문한다는 선택은 유지한다. 이 질문은 주문 전 고객 기업의 등록·확인과 계정 이용 시작 방식이다.

A. 내부 직원이 거래 기업을 등록하고 첫 담당자를 초대한다.
B. 고객이 기업 이용을 신청하고 내부 직원이 확인·승인한 뒤 사용한다.
C. 고객이 직접 등록한 뒤 사용할 수 있다. 거래 권한을 주기 전 확인 조건은 추가로 정한다.
X. Other (please specify)

[Answer]: B. 고객이 기업 이용을 신청하고 내부 직원이 확인·승인한 뒤 사용한다. 사용자 선택: "2" (고객 신청 후 내부 직원 승인). 기업·첫 담당자의 확인 근거와 승인 전 허용 행동, 추가 담당자 등록 방식은 후속 질문에서 구체화한다.

## Q3. 같은 고객 기업의 담당자들은 어떤 주문까지 볼 수 있나요?

다른 기업의 주문 접근은 허용하지 않는다는 기존 경계는 유지한다. 기업 내부 담당자 간 조회 범위와 주문·갱신·계정 관리 권한은 구분해 정의한다.

A. 같은 기업의 주문은 함께 조회한다. 주문·갱신·계정 관리 등 실행 권한은 역할별로 나눈다.
B. 일반 담당자는 본인 주문만 조회하고 지정된 기업 관리자는 기업 전체 주문을 조회한다.
C. 부서·사업장 등 기업 내부 조직별로 조회 범위를 나눈다. 필요한 조직 단위를 추가로 정한다.
X. Other (please specify)

[Answer]: C. 부서·사업장 등 기업 내부 조직별로 조회 범위를 나눈다. 필요한 조직 단위를 추가로 정한다. 사용자 선택: "3" (부서·사업장별 조회). 구체적인 조직 단위, 상위 조직·기업 전체 조회 권한과 복수 조직 소속은 이 답변만으로 확정하지 않는다. Q17에서 조직 단위를 확인한다.

## Q4. 고객에게 보여 주는 상품과 가격은 기업마다 달라지나요?

내부 직원 상품 등록과 고객 상품 확인은 이미 포함됐다. 상품 공개 범위와 거래 가격의 차이가 주문 시 확인할 조건에 영향을 준다.

A. 이용 가능한 고객 기업에는 같은 판매 상품과 공통 가격을 보여 준다.
B. 기업별로 허용된 상품과 합의된 가격을 보여 준다.
C. 공통 상품·가격을 기본으로 두고 기업별로 상품 공개·가격을 달리 정할 수 있다.
X. Other (please specify)

[Answer]: C. 공통 상품·가격을 기본으로 두고 기업별로 상품 공개·가격을 달리 정할 수 있다. 사용자 선택: "3" (공통 기준에 기업별 예외 적용). 예외의 적용 우선순위·유효 기간·가격 변경 시 기존 주문 처리와 수정 권한은 후속 확인 대상으로 유지한다.

## Q5. 같은 상품 타입의 여러 품목을 한 주문에 담을 수 있나요?

하드웨어와 소프트웨어 혼합 주문은 계속 제외한다. 영구·기간제는 모두 소프트웨어 타입이지만 한 주문에 함께 담을지는 아직 미정이다.

A. 같은 타입의 여러 품목을 담을 수 있다. 소프트웨어는 영구·기간제 품목도 함께 담을 수 있다.
B. 같은 타입의 여러 품목을 담되 소프트웨어의 영구·기간제 주문도 서로 분리한다.
C. 주문 하나는 상품 한 품목으로 제한하고 수량만 지정한다.
X. Other (please specify)

[Answer]: A. 같은 타입의 여러 품목을 담을 수 있다. 소프트웨어는 영구·기간제 품목도 함께 담을 수 있다. 사용자 선택: "1" (같은 타입 여러 품목 — 영구·기간제 함께 가능). 하드웨어와 소프트웨어 혼합 주문 제외는 유지한다. 품목별 수량·제공·기간·부분 처리의 상세 정책은 후속 확인한다.

## Q6. 주문을 자동 확정할지 직원이 확인할지는 무엇을 기준으로 나눌까요?

자동 확정과 직원 확인을 모두 지원한다는 결정은 유지한다. 아래는 분기 정책의 출발점이며 선택 후 구체적인 조건과 조건 미충족·판단 불가 결과를 확인한다.

A. 기업·상품·가격·지급 조건 등 사전에 합의한 판매 조건이 모두 맞으면 자동 확정하고, 그 외는 직원이 확인한다.
B. 상품별로 자동 확정 가능 여부를 정한다. 가능한 상품의 기본 검증을 통과하면 자동 확정하고 나머지는 직원이 확인한다.
C. 기업별로 자동 확정 가능 여부를 정한다. 해당 기업 주문의 기본 검증을 통과하면 자동 확정하고 나머지는 직원이 확인한다.
D. 별도 판매 확정 규칙이 있다. 구체적인 분기 기준을 설명한다.
X. Other (please specify)

[Answer]: A. 기업·상품·가격·지급 조건 등 사전에 합의한 판매 조건이 모두 맞으면 자동 확정하고, 그 외는 직원이 확인한다. 사용자 선택: "1" (사전 합의한 판매 조건 기준). 평가할 조건의 구체적 목록·합의 근거·유효성·복수 품목 판정과 판단 불가 시 처리는 후속 확인한다. 특정 금액 한도나 범용 규칙 편집기를 이 답변만으로 추가하지 않는다.

## Q7. 선결제 주문에서 지급 확인 전에는 어떤 업무까지 진행할 수 있나요?

선결제는 지급 확인 후 상품 제공, 후불은 합의 조건으로 제공한다는 기존 방향을 구체화한다. 주문 수락·상품 확보와 실제 출고·권한 발급은 서로 다른 행동이다. 부분 지급·후불 기한·미수금은 선택 후 추가 확인한다.

A. 주문 확정까지 진행하고, 상품 확보 요청·출고·권한 발급은 지급 확인 후 시작한다.
B. 주문 확정과 상품 확보까지 진행할 수 있지만, 출고·권한 발급은 지급 확인 후 진행한다.
C. 상품별 합의 조건으로 정한다. 지급 전 허용할 업무를 구체적으로 설명한다.
X. Other (please specify)

[Answer]: C. 상품별 합의 조건으로 정한다. 지급 전 허용할 업무를 구체적으로 설명한다. 사용자 선택: "3" (상품별 합의 조건으로 결정). 지급 전 진행 범위를 일률적으로 확정하지 않는다. Q19에서 허용할 정책을 확인하며 선결제의 출고·권한 발급은 지급 확인 후 진행한다는 상위 방향을 유지한다.

## Q8. 첫 제품에서 청구 정보와 지급 확인 결과는 어떻게 확보할까요?

OMS는 청구·지급 상태를 연결하지만 실제 자금 이동·회계 시스템 전체를 구축하지 않는다. 이 질문은 확인 결과의 입력·연동 방식이며 실제 제공자나 API가 이미 확보됐다고 가정하지 않는다.

A. 내부 직원이 청구 정보와 지급 확인 근거를 등록·정정하고 처리 이력을 남긴다.
B. 외부 청구·수금 시스템의 결과를 연동해 받는다. 대상과 확인 가능한 근거를 추가로 정한다.
C. 직원 등록과 외부 연동을 모두 지원한다. 두 결과가 충돌할 때의 기준을 추가로 정한다.
X. Other (please specify)

[Answer]: C. 직원 등록과 외부 연동을 모두 지원한다. 두 결과가 충돌할 때의 기준을 추가로 정한다. 사용자 선택: "3" (직원 등록과 외부 연동 모두 지원). 청구 정보·지급 확인 근거의 등록·정정 권한, 외부 연동 대상, 결과 충돌·중복·지연·취소 및 확인 근거의 우선순위는 후속 확인한다. 실제 연동 제공자·접근권이 확보됐다고 가정하지 않는다.

## Q9. 하드웨어의 재고·상품 확보·출고·배송 결과는 어디에서 확인하나요?

재고 출고와 주문 후 확보를 모두 지원하며 창고 작업·실제 운송 자체는 제외한다. 주문에 연결할 결과의 제공 방식과 책임을 확인한다. 재고 할당·부분 출고·완료 판단은 후속 질문에서 구체화한다.

A. 내부 직원이 실제 담당 주체에게 확인한 결과와 근거를 OMS에 등록한다.
B. 재고·공급·배송을 담당하는 외부 시스템 결과를 연동한다. 대상과 제공할 상태를 추가로 정한다.
C. 업무별로 직원 등록과 외부 연동을 함께 사용한다. 어떤 업무에 어떤 방식을 쓸지 추가로 정한다.
X. Other (please specify)

[Answer]: C. 업무별로 직원 등록과 외부 연동을 함께 사용한다. 어떤 업무에 어떤 방식을 쓸지 추가로 정한다. 사용자 선택: "3" (업무별 직원 등록·외부 연동 병행). 재고·예약·확보·출고·배송 각각의 적용 방식, 실제 제공 주체와 원본·확인 근거, 결과 충돌·중복·지연·정정 기준은 후속 확인한다. 모든 외부 시스템의 도입이나 연동 접근권 확보를 가정하지 않는다. 창고 작업·실제 운송 자체의 제외 범위는 유지한다.

## Q10. 발급하는 소프트웨어 사용 권한은 누구 또는 무엇에 부여하나요?

우리 측 권한 발급 책임과 영구·기간제 지원은 유지한다. 발급 대상과 수량의 의미를 정하며 소프트웨어 실행 시 권한 검증 기능 자체를 새로 개발하는 범위는 추가하지 않는다.

A. 구매 기업에 부여하고 사용할 수 있는 수량을 관리한다. 개별 사용자·장치 배정은 OMS 범위로 자동 추가하지 않는다.
B. 지정된 최종 사용자에게 부여한다. 대상 사용자와 수량의 관계를 추가로 정한다.

[Answer]: C. 역할에 따라 조합 범위·사업장 전체·부서 전체·기업 전체 조회 권한을 부여한다. 기본 범위와 확대 권한의 부여 주체·중복 적용 규칙을 추가로 정한다. 사용자 선택: "3" (역할별로 조회 범위를 다르게 부여). 역할별 실제 허용 범위, 기본 역할, 권한 부여·회수 주체, 복수 역할의 결합 방식과 조직 변경 시 처리는 후속 확인 대상으로 유지한다. 조회 권한을 주문·갱신·계정 관리 실행 권한으로 자동 확대하지 않는다.

## Q19. 상품별 선결제 정책은 다음 두 가지로 구분하면 될까요?

Q7에서 상품별 합의 조건을 선택했다. 정책 1은 지급 확인 전 주문 확정까지만 진행하고 상품 확보 요청도 기다리는 방식이다. 정책 2는 하드웨어 상품 확보 요청·진행까지 허용하되 실제 출고는 지급 확인 후 진행하는 방식이다. 소프트웨어 권한 발급은 지급 확인 후 진행한다. 상품 확보는 우리 측 재고·조달 비용이 먼저 발생할 수 있는 업무이며 실제 공급 수단을 확보했다는 뜻은 아니다.

A. 위 두 정책 중 상품별로 지정한다. 소프트웨어 권한 발급은 지급 확인 후 진행한다.
B. 다른 상품별 정책도 필요하다. 지급 전에 허용할 구체적인 업무와 적용 상품을 설명한다.
C. 두 정책의 주문 처리 예시를 먼저 설명받고 결정한다.
X. Other (please specify)

[Answer]: B. 다른 상품별 정책도 필요하다. 지급 전에 허용할 구체적인 업무와 적용 상품을 설명한다. 사용자의 마지막 선택: "2" (다른 상품별 정책도 필요). 직전 "1" 이후 중단하고 변경한 최종 답변을 적용한다. 제안한 두 정책만으로 충분하다고 확정하지 않으며 추가 정책의 내용은 아직 미정이다.

## Q20. 추가로 필요한 상품별 선결제 정책은 무엇인가요?

Q19에서 다른 정책도 필요하다고 답했다. 적용 상품, 지급 확인 전 허용할 업무, 적용 조건을 구체적으로 확인한다. 실제 지급 전 출고·권한 발급 예외를 원하는지는 아직 알 수 없으므로 기존 경계를 임의로 변경하지 않는다.

[Answer]: B. 아직 구체적인 정책은 없다. 가능한 정책 예시를 먼저 제안받는다. 사용자 선택: "2" (가능한 정책 예시부터 제안). Q21의 예시는 제안이며 선택 전에는 확정 요구사항이 아니다.

## Q21. 제안한 두 선결제 정책에 어떤 추가 정책이 필요한가요?

현재 비교하는 기본안은 지급 확인 전 주문 확정까지만 진행하거나 하드웨어 확보까지 진행하는 두 정책이다. 다음은 추가로 선택할 수 있는 제품 정책 예시이며 업계의 보편적 기준이나 이미 검증한 운영 방식이라는 주장이 아니다.

| 추가 정책 후보 | 예시 행동 | 추가로 결정할 내용 |

| 보유 재고 예약 | 미지급 주문에도 이미 보유한 재고를 예약하되 새 조달 요청은 하지 않는다. 지급이 확인되면 출고로 진행한다. | 예약 주체·확인 근거, 예약 기간·해제, 부족·동시 주문 처리. 실제 재고 예약을 OMS가 수행할지 외부 주체에 요청할지는 후속 경계·설계에서 확인 |

출고·소프트웨어 권한 발급 전에 선결제 지급 조건을 충족한다는 기존 방향은 유지한다. 아래 선택은 상품별로 사용할 수 있는 정책 유형을 정하는 것이며 모든 상품에 일괄 적용하거나 재고·수금 연동이 준비됐다는 뜻이 아니다. 선택 후 기존 두 정책과의 구분·필수 조건을 확인한다.

A. 기존 두 정책에 보유 재고 예약 정책을 추가한다.
B. 기존 두 정책에 일부 지급 후 확보 정책을 추가한다.
C. 기존 두 정책에 위 두 추가 정책을 모두 포함한다.
D. 추가 정책 없이 기존 두 정책만 사용한다.
X. Other (please specify)

[Answer]: C. 기존 두 정책에 위 두 추가 정책을 모두 포함한다. 사용자 선택: "3" (두 추가 정책 모두 포함). 상품별 선택 가능한 정책 유형은 지급 확인 전 주문 확정까지만 진행, 지급 전 하드웨어 확보까지 허용, 지급 전 보유 재고 예약, 일부 지급 확인 후 하드웨어 확보의 네 가지다. 보유 재고 예약의 기한·미지급 시 해제, 계약금 금액·비율·잔액 조건, 취소·환불·조달 실패 처리와 정책 우선순위는 후속 확인한다. 출고·소프트웨어 권한 발급은 합의된 선결제 지급 조건 충족 후 진행한다는 방향을 유지한다. 실제 재고 예약·수금의 실행 주체와 접근 근거는 미확인으로 남긴다.

## Q22. 조기 시작·보상 연장 등 실제 이용 기간의 조정은 어떤 방식으로 결정하나요?

## Q24. 첫 성능 검증의 합성 업무량을 다음 규모로 잡을까요?

Q16의 요청에 따라 제시하는 초기 시험 가설이다. 실제 고객 수요 예측·상용 용량 보장·사용량 제한 또는 인프라 선정이 아니다. 선택 후 응답 시간·오류율·가용성·복구·1인 운영 목표를 별도로 정한다. 실제 운영 관측을 확보하면 차이를 검토하고 시험 기준을 갱신한다.

| 항목 | 제안하는 합성 시험 기준 |
|---|---|
| 구매 기업·계정 | 구매 기업 100곳, 고객 계정 총 1,000개, 내부 직원 계정 10개. 직원 계정은 권한 검증용 합성 데이터이며 실제 인력 수를 가정하지 않음 |
| 상품 | 판매 상품 10,000개. 하드웨어·영구 소프트웨어·기간제 소프트웨어와 기업별 판매 조건 포함 |
| 누적 주문 | 주문 100,000건, 주문당 평균 5개 품목·시험 최대 50개 품목. 50개는 시험 데이터 경계이며 제품의 주문 한도를 확정하지 않음 |
| 정상 부하 | 로그인한 활동 세션 100개로 총 초당 요청 20건을 30분 유지. 조회 요청 80%, 변경 요청 20% |
| 순간 집중 부하 | 같은 요청 비율로 총 초당 요청 100건을 5분 부여해 지연·오류·회복을 관찰. 정상 부하와 동일한 응답 시간 보장을 아직 정하지 않음 |

요청은 시험 대상 서비스의 요청 단위이며 주문 수와 같지 않다. 주문 접수·승인·지급 결과·권한 발급·갱신 등 실제 기능별 요청과 백그라운드 처리 부하는 설계 후 시험 계획에서 구분한다. 기업·부서·사업장 권한, 변경 이력, 부분 처리·기간 조정 사례가 있는 데이터를 사용한다. 기간제 권한 수·동시 갱신 집중 등 별도 대량 작업은 시험 프로필을 추가로 확인한다.

방법 근거: [AWS 부하 시험 유형 안내](https://docs.aws.amazon.com/prescriptive-guidance/latest/load-testing/test-types.html)는 동시 사용자·초당 요청 등 부하와 지연·실패를 구분해 측정하도록 설명한다. 위 구체적인 숫자는 AWS의 권장값이 아니라 이 제품에 제안한 미확인 시험 가설이다.

A. 이 규모를 첫 합성 시험 기준으로 사용한다. 실제 수요와 성능 달성 여부는 별도 검증한다.
B. 일부 수치를 바꾼다. 변경할 항목과 값을 알려준다.
C. 수치의 의미와 시험 사례를 더 설명받고 결정한다.
X. Other (please specify)

[Answer]: A. 이 규모를 첫 합성 시험 기준으로 사용한다. 실제 수요와 성능 달성 여부는 별도 검증한다. 사용자 선택: "1" (제안한 시험 규모 사용). Q24 표의 합성 데이터 규모와 정상·순간 부하를 시험 기준으로 채택한다. 실제 수요·상용 용량 보장·제품 사용 한도·인프라 구성을 확정한 것은 아니다. 응답·오류·회복 목표는 Q25에서 별도로 확인한다.

## Q25. 합의한 시험 규모에서 응답 시간·오류율·부하 회복 목표를 다음과 같이 잡을까요?

아래 숫자는 제품 검증을 위한 제안이며 외부 표준이나 현재 달성 실적이 아니다. Q24의 정상 부하(초당 20건, 조회 80%·변경 20%, 30분)와 합성 데이터를 기준으로 한다. p95는 측정한 요청 중 95%가 해당 시간 이내에 응답해야 한다는 뜻이다.

| 항목 | 제안 목표 |
|---|---|
| 조회 응답 | 상품·주문 목록/상세 등 시험 대상 조회 요청 p95 1초 이내 |
| 변경 응답 | 주문 제출·승인·정보 변경 등 요청 p95 2초 이내. 처리 결과 또는 추적 가능한 접수 결과를 응답하며 접수를 업무 완료로 표시하지 않음 |
| 기술 오류율 | 정상 부하에서 유효한 요청의 0.1% 이하. 서버 오류·시간 초과·예상하지 않은 누락 응답을 포함하며 재시도 성공으로 최초 실패를 지우지 않음 |
| 순간 부하 후 회복 | 초당 100건의 5분 부하 후 초당 20건으로 낮추면 5분 안에 정상 목표로 회복하고 이후 10분 동안 조회·변경 p95와 기술 오류율 목표를 충족 |

시험 요청 송신부터 응답 본문 수신까지 측정한다. 서비스가 동기적으로 기다리는 연동 시간은 포함한다. 테스트 실행 위치·네트워크 조건·목록 크기·조회 필터·정확한 요청 구성은 성능 시험 계획에서 고정하고 결과와 함께 남긴다. 웹 화면의 렌더링·사용 가능 시점과 비동기 발급·갱신 등의 업무 완료 시간은 별도 검증 기준을 정한다.

## Q26. 가용성과 장애 복구 시간의 초기 목표를 다음과 같이 잡을까요?

사용자 검토 질문(아직 선택 답변 아님):

> 점검 포함 중단 시간 43분12초는 어떻게 나온 수치이지?
> B2B용 OMS에서 무중단까지 지향할 필요는 없는가?
> 없다면 왜 그렇게 생각하는지 얘기해봐

설명·검토 이력: 30일 × 24시간 × 60분 × (1 − 0.999) = 43.2분 = 43분 12초다. 이는 99.9%를 선택했을 때의 계산 결과이며 해당 수치가 이 OMS의 업무 중단 영향에 충분하다는 근거는 아니다. 정기 배포·통상 유지보수의 사용자 관점 무중단 목표, 예기치 않은 장애를 포함한 전체 가용성, 장애 유형별 복구 시간은 구분해 결정해야 한다. 1인 개발·운영 현황을 무중단 지향을 제외하는 근거로 사용하지 않는다. 당시 99.9%·30분 복구는 미승인 제안이었으며 최종 사용자 선택은 아래 Answer를 따른다.

추가 설명 근거: [AWS 가용성 정의](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)는 예정·비예정 중단을 포함하는 사용자 관점의 가용성을 설명한다. [AWS 변경 배포 안내](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_tracking_change_management_immutable_infrastructure.html)와 [데이터 변경 호환성 안내](https://docs.aws.amazon.com/whitepapers/latest/blue-green-deployments/best-practices-for-managing-data-synchronization-and-schema-changes.html)는 새 버전 검증·점진적 전환·이전 버전과의 데이터 호환성 유지 같은 방법을 설명한다. 방법의 존재가 이 OMS의 무중단 달성 증거는 아니며 현재 특정 배포·DB 구성을 선택하지 않는다. 제안: 통상 변경은 핵심 업무의 계획 중단 없이 수행하도록 지향하고, 전체 가용성 수치는 업무별 중단 영향·허용 시간·실제 검증 근거로 별도 결정한다. 아직 사용자 확정 요구사항으로 기록하지 않는다.

아래는 제품의 설계·검증 목표 제안이며 상용 SLA 약속이나 현재 실적이 아니다. 장애 복구 시간(RTO)은 장애 발생부터 업무를 다시 수행할 수 있을 때까지의 시간이다. 정의는 [AWS 복구 목표 안내](https://docs.aws.amazon.com/wellarchitected/2025-02-25/framework/rel_planning_for_recovery_objective_defined_recovery.html)를 참고했다. 구체적인 목표 수치는 이 제품에 대한 제안이며 AWS 권장 수치가 아니다.

| 항목 | 제안 목표 |
|---|---|
| 핵심 업무 가용성 | 연속 30일 기준 99.9% 이상. 30일의 0.1%는 43분 12초이며 계획된 점검 중단도 포함 |
| 장애 복구 시간 | 초기 검증 대상 장애에서 발생 후 30분 이내 핵심 업무 재개. 감지·판단·조치·복원·검증 시간을 포함 |

핵심 업무는 승인된 고객의 로그인·자기 권한 내 주문 조회·주문 접수와, 허용된 내부 접속에서의 직원 주문 조회·판단 처리다. 단순 서버 응답이나 접수 응답만으로 실제 업무 기능 정상 여부를 대체하지 않는다. 정상 업무 거절·권한 없는 접근 거부는 장애로 세지 않으며 정상적으로 허용돼야 할 업무의 실패는 장애로 기록한다. 업무별 가용성을 분리해 기록하고 한 업무의 중단을 다른 업무의 성공으로 상쇄하지 않는다. 측정 지점·표본 주기·경계 판정은 관측 설계에서 고정한다.

초기 복구 시험은 배포 실패, 일부 구성요소 고장, 잘못된 변경·삭제로 복원이 필요한 사례를 포함한다. 전체 리전 장애·외부 실행 주체의 장기 중단에 대한 복구 범위와 별도 목표는 후속 확인한다. 데이터 복구 시 허용할 손실(RPO)은 별도 질문에서 정하며 이 답변이 데이터 손실을 허용하는 것은 아니다. 장애 건별 복구 목표를 지켜도 누적 중단이 43분 12초를 넘으면 30일 가용성 목표는 미달로 기록한다. 운영자 응답 가능 시간과 자동 복구 필요성은 운영 부담·지원 시간 질문에서 확인한다.

A. 가용성 99.9%와 초기 검증 대상 장애의 30분 이내 복구를 목표로 삼는다. 실제 달성 여부와 미정 범위를 후속 검증한다.

### 데이터 손실에 대한 사용자 추가 조건과 가능성 검토

사용자 원문:

> 재해 복구시 성공 접수한 데이터는 잃으면 안되는데 이게 이룰 수 있는 목표인가
> 예를들어 AWS 데이터센터가 날아가는 정도의 재난은 제외하고

사용자는 성공 접수한 데이터의 손실 금지를 요구 목표로 제시하고 달성 가능성을 질문했다. 데이터센터 소실 수준의 물리적 대재난은 제외하려는 조건이다. 이를 모든 AWS 장애나 단일 구성요소 장애의 제외로 확대하지 않는다. 단일 AZ·리전·복구 사본의 동시 상실 등 구체적 제외 범위는 장애 시나리오 정의에서 확인한다.

검토 판단: 장애 범위를 명시한 성공 접수 데이터의 RPO 0은 설계·시험 목표로 삼을 수 있다. 성공 접수는 요청 수신이나 메모리 적재가 아니라 해당 장애 범위에서 보존 가능한 영속화가 완료된 후 반환하는 결과로 정의할 필요가 있다. 접수 증거와 업무 완료를 구별하고, 저장 후 응답이 끊긴 경우에는 동일 요청의 처리 결과를 재확인하며 중복 효과 없이 재시도해야 한다. 이는 현재 구현이나 보장 실적이 아니다.

AWS 근거 예시: [RDS Multi-AZ DB 인스턴스](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html)는 다른 AZ의 동기식 대기 복제본을 설명한다. 이런 저장 보장은 목표 달성을 위한 후보 근거이며 특정 DB 채택 결정은 아니다. [RDS 시점 복구](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_PIT.html)는 복구 가능한 최신 시각이 별도로 존재함을 설명하므로 정기 백업·시점 복구만으로 모든 최신 성공 접수 데이터의 RPO 0을 입증할 수는 없다.

운영자 오삭제·버그에 의한 논리적 오염은 복제본에도 전파될 수 있어 인프라 고장과 구별해 복원·변경 근거·재처리 검증이 필요하다. 사용자는 이를 제외한다고 말하지 않았으며 임의 제외하지 않는다. 정상 인프라 장애에서의 전환과 대규모 논리 복원 각각에 대해 손실 금지와 10분 복구의 동시 달성 여부를 검증한다. 안전한 저장·정합성을 확인할 수 없을 때 성공으로 응답하지 않는 처리 원칙을 제안하며, 이런 제한도 가용성에 반영해야 한다. 데이터 보존 목표를 달성했다고 주장하려면 장애 주입 후 성공 접수 목록과 복구된 업무·이력의 대조 증거가 필요하다.

### 처리 정확성 검토안 — 위 데이터 손실 조건 외에는 아직 미확정

- 성공 접수한 주문·승인·지급 확인·권한 변경의 유실 방지. 정상 재시작·배포 전환·장애 복구의 검증 범위와 재해 시 허용 손실(RPO)은 명시적으로 구분하고 후속 결정한다.
- 동일 업무 요청의 재시도·중복 알림은 주문·청구 반영·환불·발급·기간 연장 효과를 중복 발생시키지 않는다. 내용이 같아도 별개의 정당한 신규 요청과 구별한다.
- 허용된 상태 전이와 동시 변경 충돌 처리. 늦게 도착한 결과로 최신 확정 상태를 덮어쓰거나 출고와 취소 등 상충한 결과를 모두 완료로 표시하지 않는다.
- 거래 당시 가격·조건, 청구·지급·환불 금액과 품목별 제공·취소·회수 수량의 일관성. 정확한 산식·반올림·한도·부분 처리 정책은 별도로 확정해야 한다.
- 고객사·상품·주문에 맞는 권한 수량과 계약 기준 기간·실제 적용 기간을 유지한다. 기간 변경은 승인된 내용만 적용하고 같은 승인으로 두 번 연장하지 않으며 과거 만료 작업과 갱신·보상 변경의 충돌을 처리한다. 갱신 기준일은 별도 정책 결정 대상이다.
- 기업·사업장·부서·행위 권한을 지킨다. 본인 기간 변경 요청을 승인할 때도 요청·승인 권한과 별도 승인 이력을 확인한다.
- 직원 입력과 외부 연동 결과의 출처·근거·충돌·미확인 상태를 관리한다. 외부에서 실제 완료됐는지 모르면 임의로 완료·실패로 단정하거나 중복 효과가 가능한 재실행을 하지 않는다. 확인·대조 후 정정 또는 재처리한다.

## Q31. 야간·휴일에 자동 복구가 실패하면 누가 언제 대응하나요?

X. Other (please specify)

[Answer]: A를 기본으로 하되 자동 복구 시도 시에도 개발자에게 알림을 전송한다. 사용자 원문: "1번을 토대로하지만 자동 복구 시도시에도 개발자에게 알림 전송". 야간·휴일을 포함해 시간대와 관계없이 장애 발생 후 30분 이내 복구를 목표로 하며 자동 감지·복구를 우선한다. 자동 복구 실패를 기다리지 않고 시도 시점부터 개발자에게 알리고, 실패하거나 수동 판단이 필요한 경우에도 즉시 긴급 알림을 보낸다. 알림 채널·반복 알림·수신 확인·복구 결과 안내와 실제 대응 가능성은 후속 구체화한다. 자동 복구마다 사전 사람 승인이 필요하다는 의미로 해석하지 않는다.

## Q32. 장애·자동 복구 알림은 어떤 수단으로 개발자에게 전달할까요?

D. 이미 사용하는 알림 수단이 있다. 사용할 채널을 설명한다.
X. Other (please specify)

[Answer]: B. 업무 메신저와 이메일로 받는다. 야간 수신·미확인 대응 방식은 추가로 정한다. 사용자 선택: "2" (업무 메신저·이메일). 자동 복구 시도 시점과 실패·수동 개입 필요 시의 알림에 적용한다. 특정 메신저 제품·연동 계정·수신 확인 기능이 준비됐다고 가정하지 않는다. 발송 실패·미확인 재알림·중복 묶음·복구 결과 안내와 야간 실제 수신·대응 가능성은 관측·운영 설계에서 검증한다. 문자·전화·직원 모바일 화면을 추가하기로 한 결정은 아니다.

## Q33. 승인된 고객 기업의 추가 담당자와 조직별 권한은 누가 관리하나요?

X. Other (please specify)

## Q35. 마지막 기업관리자의 권한 회수나 계정 비활성화는 어떻게 처리할까요?

B. 관리자 부재도 허용하되 명시적으로 경고하고 기록한다. 이후 우리 내부 직원이 확인 후 새 관리자를 지정한다.

## Q36. 고객 담당자의 기본 역할은 어떻게 구성할까요?

계정 관리 권한과 주문 업무 권한을 구분하고, 부서·사업장·기업 전체 등의 조회 범위는 별도로 부여한다는 기존 방향을 구체화한다. 아래 역할은 제안이며 실제 직함·인원 수를 가정하지 않는다.

A. 기업관리자·구매담당자·조회담당자의 기본 역할을 제공한다. 기업관리자는 계정·소속·허용 역할 관리, 구매담당자는 허용 범위의 조회·주문·갱신·변경/취소/반품 요청, 조회담당자는 허용 범위 조회를 맡는다. 여러 역할을 함께 부여할 수 있으며 기업관리자 역할만으로 주문 실행·전체 주문 조회를 자동 허용하지 않는다.
B. 고객사가 행위 권한을 조합해 자기 기업의 역할을 직접 정의한다. 허용할 권한 목록과 관리자 위임 한계는 추가로 정한다.
C. 원하는 역할 구성이 별도로 있다. 역할과 각 역할의 업무를 설명한다.
X. Other (please specify)

[Answer]: B. 고객사가 행위 권한을 조합해 자기 기업의 역할을 직접 정의한다. 허용할 권한 목록과 관리자 위임 한계는 추가로 정한다. 사용자 선택: "2" (고객사가 권한을 조합해 역할 직접 정의). 기업관리자·구매담당자·조회담당자 세 가지 고정 역할안을 필수 역할 구성으로 채택하지 않는다. 고객사에서 정의한 역할은 해당 기업에만 적용되며 내부 직원 전용 권한이나 다른 기업 접근 권한을 새로 생성할 수 있다는 뜻은 아니다. OMS가 제공할 고객 권한 목록은 Q37에서 확인한다.

## Q37. 고객사가 역할에 조합할 권한을 다음 목록으로 시작할까요?

| 권한 영역 | 별도로 선택할 행위 권한 제안 |
|---|---|
| 상품·주문 | 상품 조회, 주문 조회, 주문 요청 제출 |
| 대금 | 청구·지급 정보 조회 |
| 소프트웨어 | 발급된 사용 권한 결과 조회, 갱신 요청, 자동 갱신 신청·해제 요청 |

## Q47. 선결제·후불 혼합 주문에서 ‘전체 금액 지급 후 제공’ 품목은 어떤 금액을 기다리나요?

## Q48. 후불 품목의 지급 기한은 어떤 기준으로 정하나요?

X. Other (please specify)

[Answer]: C. 상품 제공 완료일을 기준으로 합의한 일수를 더해 정한다. 부분 제공의 기준 단위와 완료 의미는 추가로 정한다. 사용자 선택: "3" (제공 완료일 기준·합의 일수 적용). 합의한 일수의 값·달력 계산 규칙·제공 완료의 근거와 정정 처리는 후속 구체화한다. 부분 제공 시 기한 산정 단위는 Q49에서 확인하며 청구일이나 계약 당시 고정일로 자동 대체하지 않는다.

## Q49. 후불 품목을 일부 수량씩 제공하면 지급 기한을 어떤 단위로 계산하나요?

Q48에서 제공 완료일을 기산 기준으로 정했다. 고객이 부분 제공을 허용한 주문에서 같은 후불 품목 10개 중 5개를 먼저 제공하고 나머지 5개를 나중에 제공하는 예시로 기준을 확인한다. 상품 타입별 제공 완료의 의미와 확인 근거는 별도로 정한다.

B. 해당 품목 전체 수량의 제공이 끝나면 계산한다. 예시의 10개가 모두 제공된 날부터 해당 품목 전체 금액의 기한을 정한다.

## Q50. 하드웨어의 제공 완료는 어떤 근거로 판단하나요?

Q48–Q49에 따라 제공 완료일이 제공 수량별 후불 지급 기한의 기준이 된다. 실제 출고와 고객에게 제공 완료된 상태를 구분한다. 직원 등록 또는 외부 연동으로 근거를 받을 수 있다는 Q9의 결정은 유지한다.

A. 배송 완료 근거가 확인되면 해당 수량의 제공 완료로 본다. 고객의 별도 인수 승인을 기다리지는 않는다.
B. 고객이 인수 확인한 수량을 제공 완료로 본다. 배송 완료만으로 후불 지급 기한을 시작하지 않는다.
C. 기업·상품의 합의 조건에 따라 배송 완료 또는 고객 인수 확인을 기준으로 삼는다. 주문에서 적용 기준을 명시한다.
X. Other (please specify)

[Answer]: C. 기업·상품의 합의 조건에 따라 배송 완료 또는 고객 인수 확인을 기준으로 삼는다. 주문에서 적용 기준을 명시한다. 사용자 선택: "3" (기업·상품별 합의 기준 적용). 해당 기준으로 확인한 제공 수량과 완료일을 후불 지급 기한 계산에 연결한다. 직원 등록·외부 연동의 근거를 보존하고, 배송 완료 기준인 품목에 고객 인수 조건을 자동 추가하거나 인수 기준인 품목을 배송 정보만으로 완료 처리하지 않는다. 기준 미설정·상충은 미확인 조건으로 처리하며 실제 근거 형식·확인 권한·정정 절차는 후속 구체화한다.

## Q51. 소프트웨어의 제공 완료는 어떤 시점으로 판단하나요?

권한 발급 성공, 고객에게 결과 전달, 실제 이용 기간 시작, 정상 사용 확인은 서로 다른 사건이다. Q11·Q22–Q23에서 계약 기준 기간과 실제 적용 기간의 조정·승인을 다루기로 했지만 제공 완료 기준은 아직 정하지 않았다. 이번 선택은 제공 수량별 후불 지급 기한의 기산점에도 영향을 준다. 실제 소프트웨어 실행 시 권한 검증 기능 자체의 개발은 기존 제외 범위를 유지한다.

## Q56. 기업 계약과 개별 사용 권한의 자동 갱신 합의가 충돌하면 어떤 기준을 적용하나요?

사용자 설명 요청(아직 선택 답변 아님):

> 기업 계약과 개별 사용 권한의 자동 갱신이 어떻게 충돌할 수 있지?
> 시나리오로 알려줘

설명용 가정이며 확정 요구사항이 아닌 시나리오:

- 갱신 여부: 기업 계약에는 특정 소프트웨어 권한의 자동 갱신이 명시돼 있는데, 동일 대상·동일 갱신 회차에 대해 고객의 개별 해제 요청을 직원이 승인했다고 기록한 경우다. 계약 내 해제가 허용된 정상 절차인지, 별도 예외 합의인지, 허용되지 않은 승인인지에 따라 판단이 달라진다. 해제 요청만 접수된 상태는 확인된 두 합의의 충돌로 취급하지 않는다.
- 갱신 기간: 기업 계약은 해당 상품을 매회 1년 갱신하도록 정했는데 같은 권한의 다음 회차만 6개월로 갱신하는 개별 신청을 직원이 승인했다고 기록한 경우다. 이 제품에 1년·6개월을 필수 판매 기간으로 추가하는 예시가 아니며, 개별 예외 합의를 허용할 때 필요한 우선순위의 설명이다.
- 최신 정보 불일치: 계약 변경으로 갱신 중단이 확정됐지만 개별 권한 화면에 옛 자동 갱신 설정이 남아 있는 경우다. 이는 두 유효한 합의의 우선순위 문제와 구분해야 하며 최신 변경의 반영·일관성 문제다.

Q12의 두 방식 지원만으로 개별 신청이 기업 계약을 독립적으로 덮어쓸 수 있다는 모델을 확정한 것은 아니다. 기업 계약이 허용한 범위 안에서만 개별 신청을 처리하도록 정하면, 허용된 신청은 정상 적용하고 범위를 벗어난 신청은 계약 변경·예외 합의 확인 전 적용하지 않는 모델도 가능하다. 따라서 Q56의 충돌은 가능한 정책·기록 상태를 설명하기 위한 가정이며 반드시 발생하거나 별도 범용 충돌 엔진이 필요하다는 뜻은 아니다. 실제 예외 허용 여부는 사용자와 구체화한다.

Q12에서 기업 계약에 따른 자동 갱신과 고객의 권한별 신청·직원 확인을 모두 지원하기로 했다. 예를 들어 기업 계약의 갱신 조건과 내부 직원이 확인한 개별 권한의 갱신 조건이 서로 다른 경우다. 단순 신청 접수와 확인된 합의를 구분하며, 실제 계약의 효력이나 법적 우선순위를 임의로 판단하는 것이 아니라 OMS의 업무 처리 기준을 정한다.

A. 내부 직원이 확인한 유효한 개별 권한 합의를 기업 계약의 기본 조건보다 우선한다. 적용 대상·유효 기간·확인 근거를 명시한다.

X. Other (please specify)

[Answer]: B. 기업 계약 조건을 우선한다. 개별 권한의 예외를 적용하려면 계약 조건의 변경·예외 합의를 먼저 확인한다. 사용자 원문: "기업 계약 조건 우선으로 한다". 개별 신청 접수나 직원의 처리 기록만으로 기업 계약을 덮어쓰지 않는다. 계약이 허용한 범위의 개별 신청은 해당 조건에 따라 처리하고, 범위를 벗어난 예외는 계약 변경·예외 합의 근거를 확인한 뒤 적용한다. 최신 계약 변경이 반영되지 않은 데이터 불일치는 합의 우선순위 문제와 구분해 정정한다.

## Q57. 자동 갱신 가격은 어떤 경우에 고객의 추가 동의를 받아야 하나요?

B. 계약에 자동 갱신이 있어도 갱신할 때마다 산정 가격을 고객에게 제시하고 동의를 받은 뒤 확정한다.
X. Other (please specify)

[Answer]: A. 계약에 합의된 가격 또는 산정 규칙으로 정해지는 경우 추가 동의 없이 자동 갱신할 수 있다. 합의 범위를 벗어난 가격·조건 변경은 직원 확인과 고객의 새 합의를 거친다. 사용자 선택: "1" (합의 범위 안은 자동·범위 밖은 새 동의). 적용할 유효 계약·가격·산식과 자동 갱신 합의 근거가 확인돼야 하며 미확인·상충 조건을 임의로 채워 자동 확정하지 않는다. 지급 확인·권한 연장·실제 완료와 자동 갱신 조건 판단은 구별한다.

## Q58. 선결제 자동 갱신의 지급이 확인되지 않은 채 현재 이용 기간이 끝나면 어떻게 처리하나요?

자동 갱신 합의는 자동 결제나 미지급 상태의 권한 연장을 뜻하지 않는다. 기본 선결제 정책은 지급 확인 후 실제 권한 제공이다. 이번 질문은 자동 갱신에 별도 유예 조건을 둘지 확인한다. 현재 이용 기간에는 이미 승인된 보상 연장도 포함하며 미지급을 이유로 그 기간을 임의로 단축하지 않는다.

A. 미지급 상태에서는 권한 기간을 연장하지 않는다. 갱신은 지급 확인 대기로 관리하고 기존 실제 이용 기간이 끝나면 만료로 표시한다. 고객·직원에게 미완료와 필요한 조치를 안내한다.
B. 기업 계약에서 명시적으로 합의한 유예 기간이 있으면 그 범위에서 임시 이용을 허용한다. 유예가 없으면 지급 확인 전 연장하지 않는다. 유예 기간·승인 근거·종료·지급 후 정산 정책은 추가로 정한다.
X. Other (please specify)

[Answer]: B. 기업 계약에서 명시적으로 합의한 유예 기간이 있으면 그 범위에서 임시 이용을 허용한다. 유예가 없으면 지급 확인 전 연장하지 않는다. 유예 기간·승인 근거·종료·지급 후 정산 정책은 추가로 정한다. 사용자 선택: "2" (계약에 명시된 유예 기간만 허용). 선결제 자동 갱신의 사전 합의된 예외로 다루며, 모든 고객·상품에 임의의 유예를 부여하지 않는다. 유예의 계약 근거·적용 대상·유효 조건·기한을 추적하고 지급 완료나 갱신 전체 완료와 구분한다. 기존 보상 연장 기간을 임의로 줄이지 않는다. 유예 중 지급이 확인된 경우의 갱신 이용 기간 기준은 Q59에서 확인한다.

실제 소프트웨어의 접근 차단·실행 제어 기능 자체는 기존 제외 범위를 유지한다. OMS의 권한 상태·기간과 실제 적용 결과를 구분해 추적하며 외부 실행 환경이 자동으로 차단된다고 가정하지 않는다. 기한 뒤 지급 확인 시 다음 기간의 시작·종료 계산은 별도 구체화한다.

## Q59. 유예 기간 중 지급이 확인되면 갱신 이용 기간은 언제부터 계산하나요?

예: 계약상 다음 이용 기간은 12월 1일 시작이고, 합의된 유예로 이용을 이어가다가 12월 5일에 지급이 확인된 경우다. 날짜는 설명용 예시다. Q53의 보상 연장에 대한 계약상 갱신 일정 유지와 별개로, 선결제 지급 유예의 처리 기준을 확인한다. 이번 선택이 이미 승인된 보상 기간이나 중첩 기간 요금 조정을 지우는 것으로 해석하지 않는다.

A. 계약상 예정된 갱신 시작일을 유지한다. 예시에서는 12월 1일부터 새 이용 기간을 계산하며 유예 중 이용한 날도 그 기간에 포함한다.
B. 지급 확인일을 새 이용 기간의 시작일로 삼는다. 예시에서는 12월 5일부터 계산하고 그 전 유예 이용은 별도 추가 기간으로 취급한다. 이후 갱신 일정에 미치는 영향은 추가로 정한다.
X. Other (please specify)

[Answer]: A. 계약상 예정된 갱신 시작일을 유지한다. 예시에서는 12월 1일부터 새 이용 기간을 계산하며 유예 중 이용한 날도 그 기간에 포함한다. 사용자 선택: "1" (예정된 갱신 시작일 유지·유예 이용 포함). 지급 확인일만큼 새 유료 이용 기간을 뒤로 이동하거나 유예 기간을 별도의 추가 보상으로 중복 부여하지 않는다. 이미 승인된 보상 기간과 중첩 기간 요금 조정은 별도 근거로 유지한다.

## Q60. 직원 입력과 외부 연동 결과의 근거가 충돌하면 어떤 방식으로 판단하나요?

Q8–Q9에서 청구·지급 및 하드웨어 업무의 직원 등록과 외부 연동을 함께 지원하기로 했다. 동일 거래·품목·수량에 대한 지급 또는 제공 결과가 서로 달라 근거 대조가 필요한 상황을 다룬다. 단순한 도착 순서나 가장 최근 입력만으로 참이라고 판단하지 않으며, 과거 결과의 늦은 도착과 실제 근거 충돌을 구별한다.

A. 충돌을 표시하고 권한 있는 내부 직원이 근거를 확인해 판단한다. 해결 전에는 충돌한 사실에 의존하는 추가 출고·발급·환불 등 처리를 보류한다. 기존 완료 이력을 지우거나 무관한 업무 전체를 자동 중단하지 않는다.
B. 업무별로 신뢰할 원본과 검증 규칙을 사전에 지정한다. 그 규칙으로 명확히 해소되는 경우만 자동 반영하고, 원본도 불명확하거나 근거가 상충하면 직원이 판단한다. 원래 결과·차이·판단 이력은 보존한다.
X. Other (please specify)

[Answer]: A. 충돌을 표시하고 권한 있는 내부 직원이 근거를 확인해 판단한다. 해결 전에는 충돌한 사실에 의존하는 추가 출고·발급·환불 등 처리를 보류한다. 기존 완료 이력을 지우거나 무관한 업무 전체를 자동 중단하지 않는다. 사용자 선택: "1" (충돌 표시·내부 직원이 근거 확인). 직원 입력이나 외부 결과 어느 쪽도 도착 순서만으로 우선하지 않는다. 원래 값·출처·근거·차이·판단자·판단 사유와 적용 결과를 보존하고, 늦게 도착한 과거 결과와 실제 근거 충돌을 구별한다.

## Q61. 고객의 변경·취소·반품 요청은 어떤 단위까지 허용하나요?

Q13에서 허용 여부와 자동 처리·직원 판단은 상품별 계약 정책을 따르기로 했다. 이번 질문은 요청할 수 있는 대상 단위다. 같은 타입의 여러 품목을 담은 주문과 일부 수량의 제공을 지원하며, 요청 접수는 실제 취소·반품·회수·환불 완료와 구별한다.

A. 고객은 주문 전체 단위로 요청한다. 품목·수량별 세부 처리 결과는 내부에서 추적하되 고객의 부분 요청은 제공하지 않는다.
B. 주문 전체 또는 특정 품목·수량을 지정해 요청할 수 있다. 허용 가능한 잔량·이행 상태·계약 조건을 검증하고 관련 금액·회수·환불 결과를 연결한다.
X. Other (please specify)

[Answer]: A. 고객은 주문 전체 단위로 요청한다. 품목·수량별 세부 처리 결과는 내부에서 추적하되 고객의 부분 요청은 제공하지 않는다. 사용자 선택: "1" (고객 요청은 주문 전체 단위). 고객이 특정 품목이나 수량만 지정하는 변경·취소·반품 요청 기능은 첫 버전에 포함하지 않는다. 전체 요청의 허용 여부는 상품별 계약·실제 이행 상태로 판단하며 내부 처리의 일부 완료·잔량·회수·환불 결과 추적과 고객이 선택한 부분 제공 기능은 유지한다.

## Q62. 변경·취소·반품 요청이 직원 검토 중이면 기존 주문의 추가 이행을 멈추나요?

Q13의 계약 조건에 따라 자동으로 결론이 나지 않고 직원 확인이 필요한 요청을 다룬다. Q61에 따라 고객 요청은 주문 전체 단위다. 검토 중 보류는 실제 취소·회수·환불 승인이나 이미 제공한 권한의 즉시 회수를 뜻하지 않는다. 이미 진행 중인 외부 작업은 정지 가능 여부와 확인 결과를 구분해야 한다.

A. 검토가 끝날 때까지 해당 주문의 아직 시작하지 않은 추가 확보·출고·발급을 보류한다. 이미 시작된 외부 작업은 정지 요청 가능 여부와 결과를 확인하고 실제 멈췄다고 가정하지 않는다.
B. 검토 중에는 기존 조건에 따라 이행을 계속하고, 변경·취소 등이 승인된 시점에 가능한 범위에서 중단·후속 처리한다. 검토 중 진행된 결과도 판단에 반영한다.
C. 계약 정책에 검토 중 보류 여부를 명시하고 그 기준을 적용한다. 미정·충돌 시에는 직원이 판단한다.
X. Other (please specify)

[Answer]: C. 계약 정책에 검토 중 보류 여부를 명시하고 그 기준을 적용한다. 미정·충돌 시에는 직원이 판단한다. 사용자 선택: "3" (계약 정책의 보류 기준 적용). 검토 중 일률적으로 모든 이행을 중단하거나 계속한다고 가정하지 않는다. 적용 계약·보류 대상·판단 사유·진행 중 외부 작업의 실제 정지 가능 여부와 결과를 기록한다. 보류와 취소·환불·권한 회수 승인은 구분한다.

## Q63. 후불 지급 기한이 지나도 미지급이면 OMS는 어디까지 자동으로 처리하나요?

후불 기한은 제공 수량별 완료일에 합의 일수를 적용한다. 지급 결과의 지연·충돌 때문에 미확인인 상태와 근거가 확인된 실제 연체는 구분한다. 연체 판정·제한의 계약 조건과 확인 근거 없이 고객의 유효 권한을 임의로 회수하지 않는다.

A. 연체 표시와 고객·직원 알림까지만 자동 처리한다. 신규 주문·추가 이행의 제한 여부는 내부 직원이 계약 조건을 확인해 판단한다.
B. 계약에 명시한 연체 제한 정책을 적용한다. 예를 들어 신규 주문 자동 확정이나 추가 출고·발급을 보류할 수 있으며 적용 조건·범위·해제 근거를 기록한다. 정책이 없거나 불명확하면 직원이 판단한다. 이미 발급한 이용 기간의 변경·회수는 별도 승인과 실제 적용 결과를 추적한다.
X. Other (please specify)

[Answer]: B. 계약에 명시한 연체 제한 정책을 적용한다. 사용자 선택: "2" (계약에 명시한 연체 제한 정책 적용). 확인된 실제 연체에 대해 계약상 조건·범위에 따라 신규 주문 자동 확정이나 추가 출고·발급을 보류할 수 있다. 제한 근거·대상·적용·해제 이력을 보존한다. 정책이 없거나 불명확하면 직원이 판단하며 지급 결과 미확인·충돌을 연체로 단정하지 않는다. 이미 발급한 이용 기간 변경·회수는 별도 승인과 실제 적용 결과를 추적한다.

## Q64. 다중 요소 인증(MFA)을 누구에게 필수로 적용하나요?

MFA는 비밀번호와 인증 앱·보안 키처럼 서로 다른 종류의 인증 요소를 조합해 본인을 확인하는 방식이다. 사내망 접근 제한은 이 인증을 대체하지 않는다. 내부 직원의 사내망·승인된 원격 접속 PC 전용 조건은 유지하며, 이번 선택으로 내부 모바일 화면이나 특정 인증 제공자를 도입하지 않는다. 고객사 역할은 직접 정의할 수 있으므로 관리 권한의 보유 여부를 기준으로 적용한다.

A. 내부 직원과 모든 고객 사용자에게 MFA를 필수로 적용한다.
B. 내부 직원과 고객사의 계정·조직·역할 관리 권한을 가진 사용자에게 MFA를 필수로 적용한다. 그 밖의 고객 사용자는 선택할 수 있다.
X. Other (please specify)

[Answer]: A. 내부 직원과 모든 고객 사용자에게 MFA를 필수로 적용한다. 사용자 선택: "1". 고객사의 역할·업무 권한과 관계없이 모든 고객 사용자에 적용한다. 내부 직원의 사내망·승인된 원격 접속 PC 전용 조건도 함께 유지한다. 인증 수단·세션·계정 복구 절차와 특정 제공자는 이번 답변으로 확정하지 않는다.

근거: OWASP Multifactor Authentication Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html . MFA의 정의에 대한 참고 자료이며 적용 대상은 사용자 결정으로 확정한다. 구체적인 인증 수단·세션·복구 절차는 후속 구체화 대상이다.

## Q65. MFA 인증 수단을 모두 잃었을 때의 계정 복구는 어떻게 제공하나요?

Q64에서 모든 사용자에게 MFA를 필수로 적용했다. 이번 질문은 기존 인증 수단을 사용할 수 없는 경우의 복구 경로다. 두 선택 모두 복구를 이유로 MFA를 영구 해제하지 않으며, 본인 확인 후 새 인증 수단 등록과 기존 수단 무효화, 복구 이력 및 당사자 알림을 요구하는 안이다. 구체적인 확인 증거·복구 코드 보호·세션 처리·내부 담당자도 접속할 수 없는 상황의 비상 복구 절차는 보안 설계에서 검증한다. 이메일 접근만으로 MFA를 해제할 수 있다고 가정하지 않는다.

A. 사전에 발급한 복구 코드나 등록한 별도 인증 수단으로 사용자가 직접 복구할 수 있게 한다. 그것도 없으면 내부의 권한 있는 담당자가 본인 확인 후 복구를 처리한다.
B. 사전 복구 코드를 통한 직접 복구는 제공하지 않는다. 사용 가능한 인증 수단이 없으면 내부의 권한 있는 담당자가 본인 확인 후 복구를 처리한다.
X. Other (please specify)

[Answer]: A. 사전에 발급한 복구 코드나 등록한 별도 인증 수단으로 사용자가 직접 복구할 수 있게 한다. 그것도 없으면 내부의 권한 있는 담당자가 본인 확인 후 복구를 처리한다. 사용자 선택: "1" (직접 복구 + 담당자 지원). 복구 후 MFA를 다시 설정하고 기존 수단의 무효화, 복구 이력 및 당사자 알림을 요구한다. 구체적 본인 확인 근거·복구 수단 보호·세션 처리와 내부 담당자의 접속 불가 상황에 대한 비상 복구 절차는 보안 설계에서 검증한다.

## Q66. 고객의 주문·이행·갱신 등 업무 알림은 어떤 채널로 제공하나요?

A. 주요 업무 알림을 OMS 화면과 이메일로 모두 제공한다.
B. 주요 업무 알림은 OMS 화면에서 제공하고, 이메일은 지급·동의 요청이나 갱신·만료 기한처럼 고객 조치 또는 기한이 있는 경우에 보낸다. 일반 진행·완료 알림은 화면에서 확인한다.
X. Other (please specify)

[Answer]: A. 주요 업무 알림을 OMS 화면과 이메일로 모두 제공한다. 사용자 선택: "1" (화면 + 이메일). 해당 고객사·업무의 조회 권한이 있는 수신자에게 제공하며, 이메일에는 최소한의 안내와 로그인 후 확인할 링크만 담는다. 라이선스 키·계약 상세 등 민감 내용은 이메일 본문·첨부에 담지 않는다. 기존 계획 점검·개발자 운영 장애·MFA 복구 알림 정책을 유지한다. 수신자 지정·발송 시점·전달 실패·재시도 기준은 후속 설계에서 구체화하며, 알림 발송·열람은 고객 동의나 실제 업무 완료를 대체하지 않는다.

두 안 모두 해당 고객사·업무의 조회 권한이 있는 수신자에게만 보내며, 이메일에는 최소한의 안내와 로그인 후 확인할 링크를 제공한다. 라이선스 키·계약 상세 등 민감 내용은 이메일 본문·첨부로 전달하지 않는 안이다. 수신자 지정·발송 시점·전달 실패·재시도 기준은 후속 설계에서 구체화하고, 알림 발송이나 열람을 고객 동의·지급·실제 이행 완료의 증거로 대신하지 않는다.

## Q67. 고객사별 계약 조건의 등록·변경 요청은 누가 할 수 있나요?

기업 계약 우선 원칙(Q56)을 적용하려면 고객사·상품별 가격, 지급 조건, 갱신 조건, 유예·연체 제한 등 합의 내용을 OMS가 판단 가능한 정보로 관리해야 한다. 이번 질문은 그 조건을 등록·변경하는 업무의 사용자 범위다. 계약서 작성·전자서명·법적 계약 체결 전체 기능을 포함하는 질문은 아니다. 어느 안이든 권한 있는 내부 직원이 합의 근거·적용 대상·유효 시점과 변경 이력을 확인해 반영하며, 조건 데이터 입력 자체를 고객의 계약 동의로 간주하지 않는다. 기존 주문·이용 기간을 새 조건으로 일괄 덮어쓰지 않는다.

A. 내부 직원만 계약 조건을 등록·변경한다. 고객과의 협의는 OMS 밖에서 진행하고, 직원이 합의 근거를 연결해 반영한다.
B. 내부 직원의 등록·변경에 더해, 권한 있는 고객 사용자도 OMS에서 계약 조건 변경 요청을 제출할 수 있다. 내부 직원이 합의 근거를 확인한 뒤 반영하며, 고객 요청만으로 유효 조건을 바꾸지 않는다.
X. Other (please specify)

[Answer]: B. 내부 직원의 등록·변경에 더해, 권한 있는 고객 사용자도 OMS에서 계약 조건 변경 요청을 제출할 수 있다. 사용자 선택: "2" (고객도 변경 요청 가능). 내부 직원이 합의 근거를 확인한 뒤 반영하며, 고객 요청만으로 유효 조건을 바꾸지 않는다. 고객사의 계약 조건 변경 요청 권한을 기존 개별 주문 변경·취소·반품 및 갱신 신청 권한과 구별해 관리한다. 합의 근거·적용 대상·유효 시점·변경 이력을 보존하고 기존 주문·이용 기간을 일괄 덮어쓰지 않는다.

이미 포함된 개별 주문 변경·취소·반품 요청과 자동 갱신 신청·해제 요청은 어느 안을 선택해도 유지한다. B의 기업 계약 조건 변경 요청은 해당 개별 업무 요청과 구별한다. 내부 등록과 승인 권한의 분리 여부·조건별 필수 값·적용 버전 검증은 후속 구체화 대상으로 남긴다.

## Q68. 내부 직원이 등록한 계약 조건을 적용할 때 별도 승인이 필요한가요?

Q67의 고객 변경 요청 또는 내부 등록을 통해 준비한 계약 조건을 유효한 조건으로 반영하는 시점의 통제다. 가격·지급·갱신 조건에 대한 고객과의 합의 근거 확인은 모든 선택에서 필요하다. 내부 승인은 고객 동의를 대신하지 않으며, 고객 요청 접수나 조건 초안 저장만으로 조건이 적용됐다고 표시하지 않는다. 소프트웨어 실제 이용 기간 변경의 별도 승인(Q22–Q23)은 유지한다.

A. 등록과 승인 권한을 구분하고 별도 승인 후 적용한다. 두 권한을 가진 동일 직원이 등록과 승인을 각각 수행하는 것은 허용한다.
B. 등록과 승인 권한을 구분하고 반드시 다른 내부 직원이 승인한 뒤 적용한다.
C. 계약 조건 적용 권한이 있는 내부 직원이 근거 확인 후 바로 적용할 수 있다. 별도 승인 단계 없이 변경 이력을 남긴다.
X. Other (please specify)

[Answer]: B. 등록과 승인 권한을 구분하고 반드시 다른 내부 직원이 승인한 뒤 적용한다. 사용자 원문: "2 등록자와 승인자를 분리하고 합의 근거를 확인 변경 이력을 남겨야한다". 계약 조건의 등록자와 승인자는 서로 다른 사람이어야 하며 두 권한을 보유한 사람도 자신이 등록한 조건을 스스로 승인할 수 없다. 승인자는 고객과의 합의 근거를 확인하고, 등록·변경 내용과 적용 대상·유효 시점·근거·등록자·승인자·처리 시점·결과를 이력으로 보존한다. 승인할 수 있는 별도 담당자가 없으면 미승인 상태를 유지하며 자동 승인으로 대체하지 않는다. 이 결정은 계약 조건 적용에 관한 것으로, Q22–Q23의 소프트웨어 실제 이용 기간 조정 승인 정책을 자동으로 변경하지 않는다.

어느 안이든 적용할 조건의 대상·내용·유효 시점을 식별하고 결과를 기록한다. 별도 승인을 선택한 경우 승인 대상 내용이 바뀌면 이전 승인을 재사용하지 않는 검증 기준을 구체화한다. 실제 계약 조건 값이나 승인 담당자의 인원 수를 이번 질문에서 임의로 정하지 않는다.

## Q69. 확인된 지급 금액을 어느 주문·품목에 반영할지 어떻게 결정하나요?

선결제·후불 혼합과 품목별 지급 조건(Q44–Q49)을 지원하므로, 일부 금액이 입금되었을 때 지급 대상이 정해져야 해당 출고·발급 조건 충족 여부를 판단할 수 있다. 예를 들어 선결제 품목 A와 B가 각각 100만 원인데 100만 원만 입금된 경우, 근거 없이 A 또는 B가 지급 완료라고 결정하지 않는다. 금액은 설명용 예시다. 이번 질문은 실제 입금·지급 확인(Q8) 이후 어느 지급 의무에 얼마를 연결할지에 관한 것이며, 지급 사실이 충돌하면 Q60의 직원 확인 절차를 먼저 따른다.

A. 권한 있는 내부 직원이 지급 근거를 확인하고 대상 주문·품목과 반영 금액을 지정한다. 외부 결과에 대상이 명시돼도 직원 확인 후 반영한다.
B. 지급 근거의 주문·청구 참조와 사전에 정한 배분 규칙으로 대상·금액이 명확한 경우 자동 반영한다. 대상이 없거나 여러 후보가 있거나 금액·근거가 맞지 않으면 미배분으로 두고 직원이 확인한다.
X. Other (please specify)

[Answer]: B. 지급 근거의 주문·청구 참조와 사전에 정한 배분 규칙으로 대상·금액이 명확한 경우 자동 반영한다. 사용자 선택: "2" (명확하면 자동, 불명확하면 직원 확인). 대상이 없거나 여러 후보가 있거나 금액·근거가 맞지 않으면 미배분 상태로 두고 권한 있는 직원이 확인한다. 동일 지급 금액의 중복 사용·초과 배분을 막고 배분·정정 이력을 보존한다. 회사명·금액의 일치만으로 자동 연결하지 않으며, 미배분 금액을 특정 품목의 지급 완료로 취급하지 않는다. 기존 지급 조건과 충돌 근거 확인 절차는 유지한다.

두 안 모두 동일 지급 금액의 중복 사용·초과 배분을 막고 배분·정정 이력을 보존한다. 단순히 회사명이나 금액이 같다는 이유만으로 자동 연결하지 않는다. 배분되지 않은 금액은 특정 품목의 지급 완료로 취급하지 않으며, 배분만으로 출고·발급 완료를 표시하지 않는다. 주문 전체 선결제 조건과 품목·제공 수량별 선결제 조건은 기존 합의를 유지한다. 구체적 지급 식별자·청구 구조·연동 제공자는 후속 설계와 실제 연동 확인에서 정한다.

## Q70. 고객·주문·계약 데이터와 백업의 저장 위치에 제약이 있나요?
