# B2B OMS 요구사항

> **첫 배포 범위 변경 — 2026-10-11:** 사용자가 고객사10곳 이내 제한 파일럿의 [범위](../../release-planning/first-release-scope-proposal.md)를 확정했다. 아래 FR/NFR과 과거 결정은 전체 제품 목표로 보존하며 첫 배포 적용/후속 연결은 [실행 계획](../../release-planning/first-release-delivery-plan.md)을 따른다. 고객/직원은 PC1280 이상, 고객 모바일 지원 여부는 후속 결정이다. 범위 승인은 원본 요구의 구현·검증 완료나 실제 배포 승인이 아니다.

## 의도와 근거

자사 업무용 하드웨어·소프트웨어를 구매하는 기업과 판매 회사의 내부 직원이 주문 요청, 판매 확정, 상품 제공, 대금, 갱신과 후속 처리의 상태·근거·남은 조치를 함께 확인하는 OMS를 만든다. 일반적인 OMS 기능 목록을 가져오는 대신 승인된 SC-01–SC-10 범위와 이번 단계 Q1–Q71의 선택을 요구사항으로 구체화한다. 고객의 실제 불편 정도·구매 의사·사업 성과는 아직 검증 전이다. [S1][S2][S3]

판매 회사는 한 곳이고 구매 기업은 여러 곳이다. 판매 상품 등록은 내부 직원만 가능하다. 첫 제품은 한국어·원화·한국 시간대이며 향후 영어(미국)를 지원한다. 고객은 PC 우선·모바일 웹, 내부 직원은 사내망 또는 회사가 승인한 원격 접속을 통한 PC만 지원한다. AWS·CDK 외 기술 구성은 이 문서에서 선택하지 않는다. [Q1][Q14][Q15][S2][S4]

모든 Q 표기는 [요구사항 질문과 사용자 확인](requirements-analysis-questions.md)의 번호다. 해당 파일의 `Consolidated Summary Confirmation`에 대한 `Looks correct`를 근거로 작성했다. S 표기는 마지막 Sources와 연결한다. FR/NFR ID는 후속 User Stories·설계·시험에서 유지하는 영구 추적 키다. 그룹 FR의 합격은 해당 하위 요구사항의 수락 기준을 모두 만족하는 것이다. [S3]

## 적용 범위와 해석

| 용어 | 이 문서에서의 의미 |
|---|---|
| 성공 접수 | 추적 가능한 접수 결과. 정의한 장애 범위에서 보존 가능한 저장을 확인한 뒤 응답하며 실제 업무 완료와 구별 |
| 판매 확정 | 주문 전체의 조건·공급 가능성·납기를 확인해 판매를 수락한 결과. 지급·실물 확보·출고·발급 완료와 구별 |
| 지급 확인·배분 | 실제 지급 근거의 확인과 그 금액을 어느 지급 의무에 반영할지의 결정. 실제 자금 이동 실행과 구별 |
| 제공 완료 | HW는 계약상 배송/인수 근거, SW는 발급·결과 제공과 합의 시작일 도달에 따른 완료. 품목·수량별로 추적 |
| 계약 기준 기간 / 실제 기간 | 계약·구매 시 명시한 기간 / 승인된 조기 이용·보상 연장 등을 반영한 실제 이용 기간 |
| 미확인 | 결과 또는 근거가 불충분한 상태. 실패·완료·미지급·연체 중 어느 하나로 임의 치환하지 않음 |
| 계약 정책 | 고객사·상품·거래에 적용할 확인된 조건. 범용 스크립트/규칙 편집기 도입을 뜻하지 않음 |

후속 세부 설계가 필요한 기준은 OQ ID로 연결한다. 미정 값은 테스트 fixture에 임의로 넣었다는 이유로 제품 정책이 되지 않는다. 관련 설계·구현 전에 사용자 결정이나 검증 근거를 확보해야 하며, 미정 항목을 포함한 요구 전체가 이미 구현 가능·검증 완료라고 주장하지 않는다. [S3]

## 기능 요구사항

### FR1. 기업 이용 신청과 관리자 수명주기

상위 범위 SC-01. 근거 Q1–Q2·Q33–Q35.

| ID | 요구사항 | 수락 기준: 정상 / 실패·경계 |
|---|---|---|
| FR1.1 | 고객이 기업 이용을 신청하고 내부 직원의 확인·승인 후 업무를 이용한다. | 승인된 기업·허용 사용자만 주문 업무를 수행한다. 미승인 기업의 주문 제출은 접수 거절 사유를 반환한다. 확인 증거·승인 전 신청 화면의 범위는 OQ4에서 확정한다. |
| FR1.2 | 최초 기업관리자는 내부 직원이 확인·지정하고 이후에는 권한 있는 고객사 관리자가 자기 기업의 추가 담당자·소속·활성 상태 및 관리자 권한을 관리한다. | 허용된 관리자는 자기 기업에서 초대·변경·회수를 수행하고 이력이 남는다. 다른 기업의 사용자·관리자를 변경할 수 없다. |
| FR1.3 | 마지막 관리자의 권한 회수·비활성화도 경고·기록 후 허용하며, 내부 직원이 확인해 새 관리자를 지정한다. | 관리자 0명 상태를 표현하고 복구 이력을 남긴다. 이 상태만으로 기업 전체 또는 다른 담당자의 업무 권한을 자동 중지하지 않는다. |

### FR2. 고객사 조직과 행위별 접근 권한

상위 범위 SC-01·SC-09. 근거 Q3·Q17–Q18·Q33–Q38·Q67.

| ID | 요구사항 | 수락 기준: 정상 / 실패·경계 |
|---|---|---|
| FR2.1 | 부서·사업장을 모두 사용하고 역할에 조합 범위·사업장 전체·부서 전체·기업 전체 범위를 부여한다. | 서울·IT만 허용된 행위는 부산·IT나 서울·총무에 수행할 수 없다. 기업 전체 범위도 타 기업으로 확장하지 않는다. 조직 식별·변경 시점 규칙은 OQ4. |
| FR2.2 | 고객사는 OMS가 제공한 행위 권한을 조합해 자기 기업의 역할을 정의·부여·회수한다. | 상품 조회, 주문 조회/제출, 청구·지급 조회, 발급 결과 조회, 갱신 요청, 자동 갱신 신청/해제, 변경/취소/반품 요청, 조직/사용자/역할 관리, 계약 조건 변경 요청을 각각 구별할 수 있다. 고객은 내부 직원 전용 권한을 생성·부여할 수 없다. |
| FR2.3 | 복수 역할은 행위별로 해당 행위를 허용한 범위만 합친다. | 기업 전체 조회와 서울·IT 주문 제출 역할을 함께 가지면 전체 조회와 서울·IT 제출만 가능하다. 서울·IT 제출과 부산·IT 제출은 두 범위에서만 허용한다. |
| FR2.4 | 계정·조직·역할 관리 권한을 주문 조회·실행·발급 결과 조회 권한으로 자동 확대하지 않는다. | 관리 권한만 가진 사용자의 미부여 업무 접근을 거절한다. 화면·API 등 지원하는 모든 경로에 같은 경계를 적용한다. |

### FR3. 내부 직원 역할과 승인 권한

상위 범위 SC-01. 근거 Q22–Q23·Q68·Q71.

| ID | 요구사항 | 수락 기준: 정상 / 실패·경계 |
|---|---|---|
| FR3.1 | 내부 권한 관리자가 업무 권한을 조합해 역할을 만들고 직원에게 복수 역할을 부여·회수한다. | 권한을 부여받은 직원만 해당 작업을 수행하고 변경 이력이 남는다. 직원 신분만으로 상품·주문·지급·계약·발급·권한 관리 전체를 허용하지 않는다. 상세 권한 목록·최초 관리자 준비는 OQ4. |
| FR3.2 | 계약 조건의 등록자와 승인자는 다른 사람이어야 한다. | 등록·승인 권한을 모두 가진 동일인도 자신의 계약 조건을 승인할 수 없다. 별도 승인자가 없으면 미승인 상태를 유지한다. 계정만 바꾼 동일인을 다른 사람으로 취급하지 않는 식별 방식은 OQ4. |
| FR3.3 | 실제 SW 이용 기간 조정은 요청·승인을 분리하되 두 권한을 가진 동일 직원의 별도 승인을 허용한다. | 요청만으로 기간이 적용되지 않는다. 동일인의 요청·승인도 각각 기록한다. 이 허용을 계약 조건 자기 승인으로 확대하지 않는다. |

### FR4. 상품과 판매 조건 제시

상위 범위 SC-02. 근거 Q4–Q5·Q10–Q11·Q39 및 S2.

| ID | 요구사항 | 수락 기준: 정상 / 실패·경계 |
|---|---|---|
| FR4.1 | 권한 있는 내부 직원만 HW·SW 판매 상품을 등록하고 고객은 허용된 상품을 조회한다. | 고객·외부 판매자의 상품 등록 시도를 차단한다. HW, 영구 SW, 기간제 SW의 주문 판단에 필요한 판매 정보가 구분된다. 상세 필드는 OQ1·OQ3. |
| FR4.2 | 공통 상품 공개·가격 기준에 고객사별 예외를 적용한다. | 해당 기업의 유효한 조건으로 상품·가격을 제시하고 다른 기업의 비공개 조건을 노출하지 않는다. 예외의 상세 유효성·중첩 검증은 OQ1에서 확정한다. |
| FR4.3 | 주문 제출 시점의 가격·조건을 보존한다. 이후 상품 가격 변경으로 기존 주문을 자동 변경하지 않는다. | 미확정·확정 주문 모두 원래 조건을 확인할 수 있다. 다른 가격으로 진행하려면 변경 제안과 고객 동의 근거가 필요하다. 거절·만료·정정 세부 흐름은 OQ2. |

### FR5. 고객 직접 주문과 제공 방식 선택

상위 범위 SC-03·SC-09. 근거 Q5·Q40–Q43·Q46.

| ID | 요구사항 | 수락 기준: 정상 / 실패·경계 |
|---|---|---|
| FR5.1 | 고객이 같은 타입의 여러 품목·수량을 주문한다. SW 주문에는 영구·기간제를 함께 담을 수 있다. | HW만 또는 SW만인 다품목 주문을 접수하고 HW·SW 혼합은 거절한다. 시험 최대 50품목을 제품 제한으로 구현하지 않는다. 실제 입력 상한은 OQ8. |
| FR5.2 | 주문 접수 시 기업 이용 상태·행위/조직 권한·상품 타입·필수 입력·수량을 검증한다. | 비승인/중지 기업, 권한 없음, 잘못된 입력·수량·타입의 요청은 사유와 함께 거절한다. 직원 확인 경로로 접근 검증을 우회하지 않는다. |
| FR5.3 | 고객이 일괄 제공 또는 부분 제공 허용을 선택하며 기본은 일괄 제공이다. | 부분 제공을 명시하지 않은 주문을 준비된 일부 품목만으로 제공하지 않는다. 부분 허용도 지급·수량·기간·승인 조건을 면제하지 않는다. 주문 후 변경은 변경 절차로 추적한다. |
| FR5.4 | 같은 타입 주문 안에 선결제·후불 품목을 함께 담고 각 품목의 지급 조건을 구별한다. | 혼합 주문에서도 품목별 지급 금액·기한·제공 가능 여부를 판단한다. 후불 금액을 선결제 필요액으로 잘못 합산하지 않는다. |

### FR6. 주문 전체 판매 확정과 확인 대기

상위 범위 SC-04. 근거 Q6·Q39–Q42.

| ID | 요구사항 | 수락 기준: 정상 / 실패·경계 |
|---|---|---|
| FR6.1 | 기업·상품·공개·가격·수량·지급/이용 조건과 전체 품목의 공급 가능성·납기 근거가 유효하면 주문 전체를 자동 확정한다. | 모든 조건이 확인된 시험 주문만 자동 확정된다. 지급 완료나 실제 재고 확보·발급 완료를 확정과 동일시하지 않는다. 상세 증거 검증은 OQ1·OQ3. |

### FR7. 고객사 계약 조건과 변경 합의

| ID | 요구사항 | 수락 기준: 정상 / 실패·경계 |

## 제약과 후속 고도화

- AWS·CDK를 사용하되 언어·DB·AWS 서비스·인증/메신저/결제 제공자·아키텍처는 미선정이다. 국내 저장 요구와 복구 목표를 모두 만족할 후보를 후속 설계에서 검증한다. [Q70][S5]
- 개발자 1명은 기능 범위 제한이 아니다. 1인 개발·기술 운영 부담을 측정하고 개선한다. 계약 조건 등록자/승인자 분리는 제품의 업무 통제이며 실제 두 업무 담당자가 확보됐다는 뜻은 아니다. 부족하면 미승인 상태를 유지한다. [Q30][Q68][S5]
- 짧은 브랜치에서 main으로 squash 병합, 최소 통합 동작 경로 우선 구현, main 병합 후 staging 자동 배포, production은 개발자 본인의 별도 확인·승인이라는 팀 관행을 유지한다. 단계를 나눠도 포함 기능을 자동 제외하지 않는다. [S5]
- 후속 목표는 무중단 배포·10분 복구·더 넓은 자동 대조/복구와 영어(미국)다. 첫 버전 정확성·기존 자동 확정/갱신·필요 연동을 후속으로 미룬다는 뜻은 아니다. [Q15][Q27][Q28]
- 기한·예산·사업 규모·법적 의무·상용 SLA를 임의 확정하지 않는다. 합성 목표와 실제 달성 증거를 구분한다. [S1][S2][S3]
