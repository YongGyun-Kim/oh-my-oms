## Q2. 별도 worker에 전달할 작업과 확정 업무 사실은 어떤 방식으로 남길까요?

A. 업무 변경과 전달할 작업/확정 사실을 같은 원자적 커밋 경계에 지속 기록하고, worker가 미전달 기록을 읽어 전달/처리한다. 기록별 식별자·원본 버전·중복 처리/재확인 계약을 둔다. 같은 메시지의 반복 전달 가능성을 인정하고 효과의 중복을 차단한다.
B. 별도의 전달 목록 대신 지속된 업무 원본/이력의 처리 필요 상태와 버전을 worker가 주기적으로 대조해 필요한 작업을 재구성한다. 빠진 작업·동시 조회·역순/중복과 재구성 기준을 소유자별로 명세하고 검증한다.

[Answer]: A. 원래 접수/업무 식별자로 결과를 조회한다. 화면이 열려 있는 동안 서버의 재조회 안내와 제한된 간격/횟수로 갱신하고 다시 방문하면 지속 기록된 결과를 확인한다.

## Q5. 일시적인 실패의 자동 재시도는 어디까지 허용할까요?

타임아웃은 요청이 도달하지 않았다는 증거가 아니다. 기존 중복 효과 금지·실제 결과 확인·자동 복구 시도 알림 요구는 유지한다. 여기서는 개별 경계 호출/작업의 반복 정책을 정한다.

A. 일시적 기술 실패이며 반복해도 효과가 중복되지 않는 경계만 제한된 자동 재시도를 허용한다. 변경 요청은 같은 업무 식별자/중복 방지 키와 원래 결과를 대조하고, 외부 결과 불명·충돌/입력/권한 실패는 무조건 재전송하지 않는다. 대조 또는 직원 판단으로 연결한다.
B. 첫 버전의 경계 호출 실패는 자동 재시도하지 않고 결과 대조 후 권한 있는 사용자의 명시적 재시도로 처리한다. 원래 식별자/중복 방지 키를 유지하고 새 업무로 생성하지 않는다. 별도로 정한 시스템 자동 복구/알림 정책은 유지한다.
X. Other (please specify)

## Q6. HTTP 오류의 공통 응답 형식은 어떻게 둘까요?

입력 오류·인증/권한 거절·버전 충돌·일시 장애를 UI와 기술 관측이 같은 의미로 구별해야 한다. 정상적인 확인 대기/미확인 업무 결과는 기술 오류와 구별한다.

A. HTTP 실패 상태와 RFC9457 Problem Details를 사용하고 OMS 오류 코드·추적 식별자·허용된 입력 오류 정보 등을 확장 필드로 정의한다.
B. HTTP 실패 상태와 자체 공통 JSON 오류 형식을 사용한다. 오류 코드·사용자 안내·추적 식별자·허용된 입력 오류 정보를 명세한다.
X. Other (please specify)

[Answer]: A. HTTP 실패 상태와 RFC9457 Problem Details를 사용하고 OMS 오류 코드·추적 식별자·허용된 입력 오류 정보 등을 확장 필드로 정의한다.

추천: A. 표준 형식에 OMS가 필요한 분류를 추가하는 제안이다. RFC9457은 HTTP 오류의 기계 판독 가능한 상세 형식을 정의한다. B도 동일한 오류 의미/검증을 충족하도록 명시할 수 있다. 어느 선택이든 민감한 계약/키·다른 기업의 존재·내부 스택/원본을 오류에 노출하지 않으며 권한별 안전한 안내를 반환한다. [W4]
