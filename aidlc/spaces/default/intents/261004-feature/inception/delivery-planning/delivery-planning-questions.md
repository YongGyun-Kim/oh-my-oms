# OMS Delivery Planning 질문

**Mode:** Guide me

## Prior Context

- 첫 제품의 승인된 69개 사용자 스토리·227개 수락 기준, 10개 구현 단위와 43개 개발 선행 관계를 유지한다. 단계적으로 개발하되 포함 기능을 자동 제외하지 않는다. [S1–S7]
- Scope Definition Q12의 답변은 불확실성이 큰 업무를 먼저 검증하는 것이다. Practices Discovery Q2와 Units Generation Q5에 따라 첫 단위인 최소 통합 실행 기반(U1)은 필요한 신원·MFA·기업 승인·권한, 상품 등록/조회, 고객 주문 접수·지속 기록·확인 대기/진행 조회를 실제로 연결한다. 이 우선순위와 첫 단위 범위를 다시 질문하지 않는다. [S5·S8]
- Bolt는 하나 이상의 구현 단위를 설계·구현해 실행되는 결과로 확인하는 개발 묶음이다. 이 단계에서 묶음별 완료 기준·시연·담당·위험 해소 근거를 정한다. 문서의 묶음이나 순서를 바꾸는 것만으로 실제 개발 선행 관계나 실행 순서가 바뀌지는 않는다. [S5–S6]
- 현재 설정은 한 단위의 해당 설계와 코드 구현을 마친 뒤 다음 단위로 가는 순차 진행이다. 첫 통합 동작은 실제 검증과 별도 사용자 확인이 필요하다. 병렬 개발이나 이후 완료 확인의 자동 진행을 선택한 것으로 해석하지 않는다. [S9]
- 개발자 1명은 현재 인력이며 기능 범위를 제한하는 조건이 아니다. 1명이 필요한 개발·기술 운영을 수행할 수 있는 구조를 검증한다. 계약 조건 등록자와 다른 승인자를 확보해야 하는 업무 통제는 별개다. [S1·S9]
- 실제 고객·업무 자료·제공자/API 접근권과 외부 업무 담당자·확보 소요 시간은 미확인이다. 관련 구현 약속·실데이터·실거래·상용 목표 전에 요구되는 근거 확보 조건을 유지한다. 외부 의존성 표에는 모르는 담당자·날짜를 임의로 넣지 않는다. 합성 계약 시험과 실제 제공자 검증은 구별한다. [S1·S4·S7·S8]
- AWS·CDK, 원본 업무 소유자의 연동 책임, test-after·Standard·80% 커버리지 하한과 필수 검사, main으로 squash 병합·staging 자동 배포·production 별도 승인을 유지한다. 언어·DB·AWS 서비스·제공자를 이번 계획에서 미리 선정하지 않는다. [S7·S9]
- 고객·직원 화면은 PC 1280 CSS px 이상이며 고객 모바일 지원은 미정, 직원 모바일은 제외한다. 직원 사내망/승인 원격 PC·MFA·서버 권한 통제와 접근성 요구를 유지한다. [S3]
- OMS 제품 코드와 실제 통합 검증 명령은 아직 없다. AI-DLC 자체 검사 명령을 OMS의 동작 검증 명령으로 사용하지 않는다. 실제 명령은 준비된 후 전체 내용을 별도로 제시하고 사용자 승인을 받는다. [S5·S9; 현재 작업공간 확인]

## Q1. 첫 통합 동작 버전을 어떤 시연으로 확인할까요?

첫 구현 단위인 최소 통합 실행 기반(U1)의 업무 범위는 이미 결정됐다. 여기서는 그 결과를 사용자가 확인할 대표 시연의 구성을 정한다. 모든 선택에서 해당 수락 기준·정확성·권한·보존 시험은 별도로 충족해야 한다. 합성 고객·상품은 실제 고객 검증이나 제품의 입력 상한을 뜻하지 않는다.

A. 합성 고객사 2개와 HW/SW 상품으로 각각 별도 주문을 접수하고, 확인 대기·원래 접수 ID 재조회·프로세스 재시작 후 기록 보존·다른 고객사 접근 거절을 함께 시연한다. 미구현 공급·대금·발급은 미확인으로 표시한다.
B. 한 합성 고객사의 대표 주문으로 가입/승인·상품 조회·접수/확인 대기를 먼저 시연하고, 다른 타입·권한 거절·재시작/보존은 실행 시험 결과로 별도 제시한다.

## Q2. 이미 정한 불확실성 우선 기준을 어떤 방식으로 비교하고 기록할까요?

가치·긴급성·위험 감소를 작업 규모와 비교하는 점수 방식은 WSJF라고 부른다. 현재 실제 고객 가치 수치·확정 일정·작업 기간은 없다. 점수를 사용하더라도 추정과 확인된 사실을 구별하며, 선행 관계와 첫 통합 단위 우선 원칙은 지킨다.

A. 정성적인 위험 우선 근거를 사용한다. 각 묶음의 불확실성·영향·먼저 검증할 결과를 설명하고, 근거 없는 가치 점수나 작업 일수를 만들지 않는다.
B. WSJF 비교표를 사용한다. 사용자와 평가 기준·가중치·상대 추정을 추가로 정한 뒤 순서를 비교한다. 미확인 수치와 실제 납기는 구별한다.
X. Other (please specify)

[Answer]: A. 정성적인 위험 우선 근거를 사용한다. 각 묶음의 불확실성·영향·먼저 검증할 결과를 설명하고, 근거 없는 가치 점수나 작업 일수를 만들지 않는다. 사용자 선택: "1" (정성적인 위험 우선 근거).

## Q3. 첫 통합 단위 이후의 개발 묶음(Bolt)은 어느 크기로 계획할까요?

이미 승인된 구현 단위는 10개다. 예를 들어 HW 공급·이행·회수와 SW 권한·기간·갱신은 공통 거래·대금 기반 뒤에 구현할 수 있는 별도 단위다. 묶음 크기와 무관하게 현재 단위별 순차 진행·각 단위의 검증 및 원본 소유 경계는 유지한다.

A. 구현 단위 하나를 개발 묶음 하나로 계획한다. 각 단위의 실행 결과·완료 기준·시연을 명시하고 다른 단위와의 실제 통합 확인을 연결한다.
B. 관련된 여러 구현 단위를 한 개발 묶음으로 계획한다. 첫 통합 단위는 별도로 두고, 이후 묶음에는 개별 단위 완료 조건과 묶음 전체의 통합 완료 조건을 함께 둔다. 병렬 개발로 바꾸는 선택은 아니다.
X. Other (please specify)

[Answer]: A. 구현 단위 하나를 개발 묶음 하나로 계획한다. 각 단위의 실행 결과·완료 기준·시연을 명시하고 다른 단위와의 실제 통합 확인을 연결한다. 사용자 선택: "1" (구현 단위 하나당 개발 묶음 하나).

## Q4. 불확실성 우선 검증에서 어떤 위험을 가장 먼저 깊게 확인할까요?

이전 결정은 미정 정책과 위험을 먼저 확인하는 것이다. 이번 질문은 그 안에서 초기 검증의 초점을 정한다. 모든 보안·정확성·복구·운영 요구는 유지하며, 선행 접근/권한 조건을 건너뛰거나 마지막 운영 단위까지 기본 보존·복구 준비를 미루지 않는다.

A. 대금·제공 수량·SW 기간의 연결을 우선 확인한다. 중복 지급/환불, 제공 건별 후불 기산, 실제 기간 조정·보상·갱신의 충돌을 관련 단위의 구현 전부터 시험 가능한 사례로 구체화한다.
B. 기업·조직·행위별 권한과 승인 경계를 우선 확인한다. 다른 기업 데이터 노출, 조직 변경 후 접근, 계약의 같은 사람 승인 금지와 기간 조정의 별도 승인 차이를 먼저 구체화한다.
C. 성공 접수 보존·장애 복구와 1인 기술 운영 부담을 우선 확인한다. 실제 장애 범위·지속 기록·재처리·독립 복구 알림과 사람 작업 측정 방법을 앞선 설계부터 구체화한다.
X. Other (please specify)

[Answer]: A. 대금·제공 수량·SW 기간의 연결을 우선 확인한다. 중복 지급/환불, 제공 건별 후불 기산, 실제 기간 조정·보상·갱신의 충돌을 관련 단위의 구현 전부터 시험 가능한 사례로 구체화한다. 사용자 선택: "1" (대금·제공 수량·SW 기간의 연결).

## Q5. Construction의 작업 소유와 확인은 어떤 방식으로 진행할까요?

현재 개발자는 1명이며 단위별 순차 진행으로 설정돼 있다. 이 질문은 실제 개발 인원을 다시 묻는 것이 아니라, 이번 세션에서 작업을 이어갈지 또는 여러 팀이 단위를 소유하고 별도로 승인하는 방식으로 바꿀지를 정한다. 기술 작업의 소유 선택으로 실제 판매·계약 승인 인력이 확보되지는 않는다.

A. 이번 세션에서 개발자와 AI가 전체 작업을 이어간다. 현재 단위별 순차 진행을 유지하고, 이후 자동 진행 여부는 첫 통합 동작 검증·승인 뒤 별도로 선택한다.
B. 여러 팀이 구현 단위를 각각 소유하고 독립적으로 승인한다. 실제 팀·단위 배정을 추가로 확인하고, 팀별 확인 주기를 별도로 정한다.
X. Other (please specify)

[Answer]: A. 이번 세션에서 개발자와 AI가 전체 작업을 이어간다. 현재 단위별 순차 진행을 유지하고, 이후 자동 진행 여부는 첫 통합 동작 검증·승인 뒤 별도로 선택한다. 사용자 선택: "1" (이번 세션에서 개발자와 AI가 전체 작업 진행).
