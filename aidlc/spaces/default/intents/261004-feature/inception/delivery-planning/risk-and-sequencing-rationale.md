# OMS 개발 순서와 위험 검증 근거

## Decision and Heuristic

Bolt는 하나의 구현 단위를 설계·구현하여 실행 결과로 확인하는 개발 묶음이다. Q2는 수치 점수 대신 정성적 위험 근거, Q3은 단위마다 한 묶음, Q4는 대금·제공 수량·SW 기간의 연결을 초기 깊은 검증 초점으로 선택했다. 이전 불확실성 우선 결정과 첫 통합 버전 우선 원칙을 유지한다. [S1–S10]

선택 기준은 최소 통합 실행으로 연결/보존 위험을 먼저 확인한 뒤, 선행이 허용하는 범위에서 금액·제공 건·기간/승인 위험을 먼저 구체화하는 것이다. 실제 고객 가치·긴급 납기·노력의 수치가 없으므로 WSJF(가치·긴급성·위험 감소를 작업 규모와 비교하는 점수 방식) 점수나 가중치를 만들지 않는다. 범위의 Must Have와 구현 순서를 구별한다.

## Economic Sequence and Alternatives

| 순서/구간 | 선택 이유·검증할 결과 | 다른 유효한 선택과 이번 계획의 경계 |
|---|---|---|
| B01 U1 최소 통합 실행 | 실제 신원/MFA·권한·접수/기록·대기/재조회·최소 UI/API/worker를 먼저 연결해 앞선 설계 가정을 시험 | 수평 공통 계층만 먼저 만드는 방식은 승인된 첫 Unit의 실제 연결 범위를 충족하지 않음 |

| B08 U8 → B09 U9 | 최소 두 UI는 B01부터 있다. 전체 고객 표면을 실제 owner 결과에 연결하고 직원 전체 조작·왕복/승인을 이어 확인하는 선언 순서 | U9→U8도 가능. 실제 업무 피드백에 따라 변경할 수 있으나 직원 기능의 가치가 낮다는 판단이 아님. 상용/전체 시나리오에는 두 UI 증거 필요 |
| B10 U10 | 모든 실행/업무/표면을 대상으로 복구·검사/배포·국내 저장·관측·사람 작업의 전체 증거를 연결 | 기본 신원/보존·알림 준비를 마지막까지 미루는 방식은 첫 접수/동작 목표와 충돌. B01부터 해당 설계/최소 실행 준비를 적용 |

각 구간의 선행 계약/코드가 미완료면 다음 관련 구현이 그 결과를 추정하지 않는다. 실제 실행은 S6의 DAG와 현재 단위별 순차 설정을 사용한다. bolt-plan만 재정렬하는 변경으로 실행 순서를 보장하지 않는다.

다른 접근인 고객 가치 우선은 실제 수요·시급성 근거 확보 뒤 비교할 수 있다. 수치 비교 모델은 실제/상대 평가 기준을 사용자와 추가로 정해야 한다. 관련 단위를 큰 Bolt로 묶는 방식은 전체 시연을 묶기 쉽지만 개별 완료/검증의 경계가 덜 보이므로 Q3의 단위별 묶음을 따른다. 이 대안 검토는 기능 제외·새 아키텍처/배포 서비스 선택이 아니다.

## DAG and Critical Path

10개 Unit·직접 의존43개·순환0개를 원본 YAML에서 확인했다. 현재 계획 B01→B10은 모든 직접 선행을 충족하며 첫 의존 없는 Unit은 U1 하나다.

- 구조상 최장 선행 경로는 **8개 Unit**이다. 작업 시간 가중치가 없어 기간상 critical path나 완료 예정일을 산정하지 않는다.
- 최장 경로는 HW/SW의 선택과 고객/직원 UI의 선택에 따라 다음4개다.
- U1 → U2 → U3 → U4 → U5 → U7 → U8 → U10
- U1 → U2 → U3 → U4 → U6 → U7 → U8 → U10
- U1 → U2 → U3 → U4 → U5 → U7 → U9 → U10
- U1 → U2 → U3 → U4 → U6 → U7 → U9 → U10
- 현재 직렬 진행의 자원 경로는 **10개 Unit 전체**다. 독립 집합 U5/U6와 U8/U9가 있어도 병렬 실행 설정/팀 확보로 해석하지 않는다.
- U1–U4는 모든 업무 확장의 공통 선행, U7은 두 제공 분기의 합류, U10은 두 UI까지 포함한 전체 증거의 합류다. 각 외부 준비 조건은 관련 경로를 추가로 지연시킬 수 있으며 소요 시간은 미정이다.
- L/XL은 S5의 상대 복잡도 추정이다. SW의 XL을 날짜/생산성·비용 수치로 변환하지 않는다.

## Inherited Design Conditions and Phase Evidence

Domain Design에서 수용된 미해결 R-01(주문 보호 부서/사업장 문맥)은 U1 Functional Design과 주문 코드 전에 해결할 설계 조건이다. U2–U9 연결에서도 같은 원본 문맥/권한을 검사한다. R-02의 교차 참조5건은 U3/U4/U5/U6 소유자의 관련 설계·인터페이스/스키마 코드 전에 확인한다. Contract의 선언/이번 담당 연결을 이전 검토의 해결 판정으로 쓰지 않는다. [S4–S8]

## Execution and Release Criteria

현재 단위별 순차 진행·한 세션 기술 작업 소유를 유지한다. 첫 통합 버전(walking skeleton)은 B01의 전체 작은 실제 연결을 실행 검증하고 사용자가 승인해야 다음 단위로 간다. 실제 OMS 검증 명령은 선정 유보이며 최초 검증 전에 전체 명령을 별도로 승인받는다. 이후 자동 진행 여부는 첫 통합 승인 뒤 선택한다.

적용되는 설계·Code Generation·단위 실행 검증, 종합 Build and Test/CI, 실제 운영 환경 구성·배포·관측/성능·복구/사람 작업 검증은 각 담당 단계에서 증거를 남긴다. 이 단계는 실행할 단계/깊이/테스트 전략을 변경하지 않는다. 필수 검사 실패/누락은 병합/배포를 보류한다.

전체 가용성99.9%(계획 점검 포함 연속30일), 복구30분, 정의한 성공 접수RPO0·8개 정확성 기본선과1인 기술 운영 목표를 유지한다. 논리 손상/오삭제를 재난 제외로 임의 처리하지 않는다. 무중단 배포·10분 복구·영어(미국)는 후속 목표다. 단기 시험·합성 부하·계획 문서 통과와 실제 관측/상용 약속을 구별한다.
